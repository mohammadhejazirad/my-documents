# نقشهٔ CI/CD

## مقدمه

این فصل یک خط لولهٔ ثابت را با سه ابزار جدا نشان می‌دهد: GitHub Actions، GitLab Runner، و Jenkins. خط لوله یکی است. ابزار اجرا عوض می‌شود. سرویس نمونه `app` است. کامیت روی شاخهٔ `main` می‌سازد، تست می‌کند، ایمیج Docker را با برچسب برابر شناسهٔ git می‌سازد، به `registry.example.internal` پوش می‌کند، و بعد فقط یک اسکریپت ازپیش‌موجود را صدا می‌زند.

هر سه صفحهٔ بعدی طوری نوشته شده‌اند که اگر فقط همان ابزار را دارید، همان صفحه برای نصب و اجرای شب حادثه کافی باشد. این صفحه کمک می‌کند ابزار اضافه نصب نکنید. سه کنترلر CI روی یک شبکهٔ کوچک یعنی سه صفحهٔ ورود، سه مدل راز، و سه جا برای فراموش کردن به‌روزرسانی.

آزمایشگاه همان جدول بقیهٔ دانشنامه است. برنامه روی `10.10.1.10` با نام `app-1.example.internal` است. موتور کانتینر روی `10.10.1.30` با نام `docker-1.example.internal` است. GitLab خودمیزبان روی `10.10.1.50` با نام `gitlab.example.internal` است. پروکسی `10.10.1.5` جلوی ترافیک عمومی است و کنترلر CI را به اینترنت منتشر نمی‌کند.

## مفهوم اصلی

یکپارچه‌سازی پیوسته (CI) یعنی هر کامیت روی شاخهٔ مورد توافق، ساخت و تست را بی‌دخالت دست اجرا کند. تحویل پیوسته (CD) در این آزمایشگاه تا استقرار روی `docker-1` ادامه دارد، ولی استقرار دکمهٔ آزاد «هر دستوری که نویسندهٔ workflow دوست دارد» نیست. job آخر فقط مسیر `/opt/apps/app/bin/deploy.sh` را با یک شناسهٔ git اجرا می‌کند. منطق عوض کردن برچسب و `docker compose up -d` داخل همان اسکریپت است و در [سناریوی خط لوله](/docs/09-cicd/pipeline-scenario) آمده است.

سه ابزار این کار را می‌کنند:

| ابزار | کجا منطقی است | صفحه |
| --- | --- | --- |
| GitHub Actions | کد روی GitHub است و یک runner خودمیزبان داخل آزمایشگاه به رجیستری و `10.10.1.10` راه دارد | [GitHub Actions](/docs/09-cicd/github-actions) |
| GitLab Runner | مخزن روی `gitlab.example.internal` است | [GitLab Runner](/docs/09-cicd/gitlab-runner) |
| Jenkins | تیم از قبل Jenkins دارد یا پلاگین و عامل SSH برایش آشناست | [Jenkins](/docs/09-cicd/jenkins) |

انتخاب، انتخاب تیم است نه انتخاب هر مخزن. دو سرویس با دو کنترلر فقط وقتی قابل دفاع است که تیم دومی واقعاً جدا باشد و رازها مشترک نباشند. در این آزمایشگاه سرویس `app` یک ابزار دارد.

اصطلاح‌هایی که در لاگ تکرار می‌شوند همان انگلیسی می‌مانند: workflow، pipeline، job، stage، runner، secret، environment. بار اول کنار معادل فارسی می‌آیند و بعد همان واژهٔ لاگ استفاده می‌شود.

## چرا استفاده می‌شود؟

استقرار دستی با SSH در فصل استقرار هست و برای روزی که خط لوله خوابیده حق دارید به آن برگردید. خط لوله برای روز عادی است، چون این‌ها را ثابت می‌کند:

- تست قبل از پوش ایمیج اجرا شده و خروجی غیرصفر جلوی پوش را گرفته است.
- ایمیجی که بالا می‌آید همان شناسهٔ git است، نه برچسب شناور `latest` که معلوم نیست مال کدام کامیت است.
- کلید خصوصی استقرار داخل مخزن و داخل لاگ نیست.
- برگشت به نسخهٔ قبل یعنی برگرداندن همان شناسه، نه حدس زدن اینکه روی سرور چه ساخته شده است.

بدون خط لوله هم می‌شود این نظم را با دست رعایت کرد. در عمل شب‌ها برچسب `latest` پوش می‌شود و کسی یادش نمی‌ماند شناسهٔ قبلی چه بود. اسکریپت استقرار و برچسب تغییرناپذیر این فراموشی را گران می‌کنند.

## Architecture

اگر ابزار را انتخاب کرده‌اید، بقیهٔ این فصل را از همان شاخه بخوانید. سناریو را همه می‌خوانند چون معنای استقرار آنجاست، نه داخل ابزار.

```text
کامیت روی main
        │
        ├─ GitHub Actions ── runner خودمیزبان روی docker-1
        ├─ GitLab Runner ─── executor جدا برای تست و برای تولید
        └─ Jenkins ───────── کنترلر داخلی، UI فقط روی localhost
                │
                ▼
        test  →  build image  →  push
        tag = git sha
        registry.example.internal/app:<sha>
                │
                ▼
        SSH یا اجرای محلی، فقط این مسیر:
        /opt/apps/app/bin/deploy.sh <sha>
                │
                ▼
        docker-1 : عوض شدن APP_TAG و docker compose up -d
```

جریان شبکه که هر سه ابزار باید داشته باشند:

```text
نویسنده
   │ git push
   ▼
مخزن (GitHub یا gitlab.example.internal یا مخزن Jenkins)
   │ job
   ▼
میزبان ساخت، معمولاً docker-1  (10.10.1.30)
   │ docker push
   ▼
registry.example.internal
   │ pull هنگام استقرار
   ▼
docker-1 دوباره، به‌عنوان موتور کانتینر
   ▲
   │ اسکریپت، از app-1 (10.10.1.10)
کنترل استقرار
```

`registry.example.internal` نام رجیستری نمونه است. آن را با `mirror.example.internal` (`10.10.1.60`) یکی نگیرید مگر خود سازمان عمداً رجیستری را روی همان آینه گذاشته باشد. نام رجیستری باید در DNS داخلی حل شود. این فصل به آن آدرس IP جدا نمی‌دهد.

## Installation

روی یک سرویس هر سه ابزار را نصب نکنید. ترتیب عملی این است:

1. صفحهٔ ابزار انتخاب‌شده را تا آخر نصب و یک job آزمایشی خالی جلو ببرید.
2. [سناریو](/docs/09-cicd/pipeline-scenario) را بخوانید و اسکریپت‌های `deploy.sh` را روی `app-1` و `docker-1` بگذارید، قبل از اینکه خط لوله اجازهٔ استقرار بگیرد.
3. یک کامیت کوچک روی `main` بدهید و در لاگ ابزار ببینید تست، پوش، و اجرای اسکریپت به همین ترتیب رخ داده‌اند.
4. یک بار برگشت به شناسهٔ قبلی را در ساعت اداری تمرین کنید. اولین برگشت نباید شب قطعی باشد.

بستهٔ مشترکی که میزبان ساخت لازم دارد Docker Engine از مخزن رسمی است، با دستور `docker compose` (با فاصله). باینری پایتونی `docker-compose` در این دانشنامه استفاده نمی‌شود. نصب خود Docker در فصل Docker است. اینجا فرض می‌شود روی `docker-1` دستور `docker version` و `docker compose version` جواب می‌دهند.

GitLabِ خودِ سازمان از قبل روی `10.10.1.50` است. Runner را روی همان ماشین GitLab نصب نکنید. صفحهٔ Runner دلیلش را می‌گوید. Jenkins را روی پروکسی، روی `db-1`، و روی خود GitLab نگذارید.

## Configuration

قبل از انتخاب، این سه سؤال را روی کاغذ جواب دهید. اگر جواب‌ها با هم نمی‌خوانند، ابزار را عوض کنید نه اسکریپت را.

| سؤال | اگر بله | اگر نه |
| --- | --- | --- |
| مخزن روی GitHub است؟ | Actions، با runner داخل آزمایشگاه | Actions را کنار بگذارید |
| مخزن روی `gitlab.example.internal` است؟ | Runner | Runner را روی سرور GitLab نصب نکنید تا «نزدیک مخزن» باشد |
| تیم از قبل Jenkins را اداره می‌کند؟ | Jenkins روی `docker-1` با UI روی loopback | Jenkins را برای یک سرویس تازه یاد نگیرید |

چهار قرار که در کانفیگ هر سه ابزار تکرار می‌شود:

- راه‌انداز، `push` به `main` است. اجرای دستی هم هست تا بدون کامیت خالی بتوانید همان خط لوله را دوباره بگیرید. درخواست ادغام و شاخهٔ ویژگی تا مرحلهٔ تست می‌توانند بروند و تا استقرار تولید نه.
- job تست اگر غیرصفر خارج شود، ساخت ایمیج و پوش و استقرار اجرا نمی‌شوند.
- برچسب ایمیج دقیقاً شناسهٔ کامل کامیت است. برچسب `latest` برای این سرویس پوش نمی‌شود.
- job استقرار دستور آزاد روی سرور اجرا نمی‌کند. مسیر اسکریپت ثابت است و تنها آرگومان، شناسه است.

رازها (secret) این‌ها هستند و در مخزن نیستند:

| نام عملی | مصرف | کجا دیده شود |
| --- | --- | --- |
| کلید خصوصی SSH کاربر `deploy` | وصل شدن به `10.10.1.10` | secret ابزار، فایل با مجوز `600` روی runner، بعد حذف |
| توکن یا گذرواژهٔ رجیستری | `docker login` و `docker push` | secret ابزار یا فایل `600` روی `docker-1` |
| توکن ثبت runner | فقط هنگام `gitlab-runner register` | متغیر محیط همان پوسته، نه تاریخچه اگر می‌شود جلوگیری کرد |

کاربر انسانی مدیر `ops` است. کاربر `deploy` اسکریپت را اجرا می‌کند و عضو `sudo` نیست. روی `app-1` برای اینکه CI بتواند با کلید وارد شود، استثنای `AllowUsers` در [سخت‌سازی SSH](/docs/10-security/ssh-hardening) آمده است. روی بقیهٔ میزبان‌ها همان `AllowUsers ops` می‌ماند.

## Production Example

تیم سرویس `app` GitLab داخلی دارد و کدش روی `gitlab.example.internal` است. انتخاب این تیم Runner است، نه Actions و نه Jenkins. Actions وقتی وارد آزمایشگاه می‌شود که مخزن واقعاً روی GitHub باشد و runner خودمیزبان بتواند هم GitHub را برای گرفتن action ببیند و هم `10.10.1.10` را. runner میزبانی‌شدهٔ GitHub به آدرس‌های `10.10.0.0/16` راه ندارد. اگر کسی workflow را با `ubuntu-latest` کپی کند، مرحلهٔ استقرار از نظر شبکه مرده است.

مثال مخالف: تیمی که مخزن را روی GitHub نگه می‌دارد و فقط شنیده GitLab «داخلی‌تر» است، Runner نصب نمی‌کند. ابزار را با محل مخزن یکی کنید، بعد سخت‌سازی کنید.

تغییر نمونه در سناریو یک اصلاح کوچک داخل خود سرویس `app` است. خط لوله محتوای برنامه را تفسیر نمی‌کند. اگر `scripts/test.sh` غیرصفر شود، ایمیج جدید به تولید نمی‌رسد و کانتینر قبلی با شناسهٔ قبلی بالا می‌ماند.

## Security Notes

کنترلر CI اگر لو برود، حکم کلید استقرار را دارد. این‌ها غیرقابل مذاکره است:

- UI جنکینز و GitLab را روی `proxy.example.internal` با پورت عمومی منتشر نکنید. GitLab از قبل داخلی است. Jenkins در صفحهٔ خودش به `127.0.0.1` و پورت `8080` محدود می‌شود.
- کاربر runner عضو گروه `sudo` بی‌محدودیت نیست. تنها اجازهٔ sudo، اجرای همان اسکریپت استقرار با کاربر `deploy` است و فقط روی runnerی که واقعاً استقرار می‌کند.
- گروه `docker` معادل root است. عضویت در آن فقط روی میزبان ساخت است، نه روی `db-1` و نه روی پروکسی.
- لاگ خط لوله کلید خصوصی، توکن رجیستری، و محتوای `.env` را چاپ نمی‌کند. دستور `set -x` دور و بر کلید ممنوع است.
- action و پلاگین را از منبع رسمی می‌گیریم. پین کردن SHA کامل بهتر از برچسب متحرک است. جزئیات در صفحهٔ GitHub Actions است.

اسکریپت استقرار آرگومان را فقط به‌شکل شناسهٔ هگز چهل یا شصت‌وچهار نویسه‌ای می‌پذیرد. رشتهٔ آزاد، نقطه-ویرگول، و مسیر دیگر رد می‌شوند. این بررسی داخل اسکریپت است تا حتی اگر job غلط نوشته شود، سرور دستور اضافه اجرا نکند.

## Troubleshooting

نشانه‌ها را با ابزار قاطی نکنید. اول بگویید کدام یک از سه ابزار را نصب کرده‌اید.

| نشانه | محل احتمالی | کار بعدی |
| --- | --- | --- |
| job سبز است ولی کانتینر عوض نشده | اسکریپت روی میزبان اشتباه، یا `APP_TAG` در فایل اشتباه | سناریو، بخش برگشت و مسیر فایل روی `docker-1` |
| پوش رجیستری رد می‌شود | login نشده، یا نام `registry.example.internal` حل نمی‌شود | `docker login` روی میزبان ساخت، بعد `getent hosts registry.example.internal` |
| استقرار از runner میزبانی‌شدهٔ GitHub تایم‌اوت می‌شود | مسیر شبکه به `10.10.1.10` وجود ندارد | صفحهٔ Actions، runner خودمیزبان |
| job استقرار اصلاً برداشته نمی‌شود | برچسب runner با `tags` فایل خط لوله یکی نیست | صفحهٔ Runner، `run_untagged` باید خاموش باشد |
| UI ابزار از اینترنت باز است | فایروال یا پروکسی اشتباه | فصل امنیت، UFW، و هشدار پورت `8080` در صفحهٔ Jenkins |

خروجی سالم یک استقرار، در لاگ ابزار فقط مسیر اسکریپت و شناسه است، نه یک زنجیرهٔ `cd` و `rm` و `bash -c`. اگر چنین زنجیره‌ای دیدید، خط لوله از قرار این فصل خارج شده و قبل از هر چیز آن job را متوقف کنید.

نشانه‌ای که ابزارها را از هم جدا می‌کند این است که مخزن کجاست و runner از کدام شبکه دیده می‌شود. اگر job در صف می‌ماند، اول برچسب و آنلاین بودن runner را ببینید نه اسکریپت را. اگر job سبز است و کانتینر کهنه است، اول `APP_TAG` روی `docker-1` را ببینید نه تعریف workflow را. این دو اشتباه برعکس هم وقت می‌گیرند: یکی خط لوله را بازنویسی می‌کند در حالی که فایل `.env` به‌روز نشده، دیگری اسکریپت را عوض می‌کند در حالی که runner اصلاً job را برنداشته.

قبل از اینکه ابزار دوم را «برای مقایسه» نصب کنید، یک شناسه را تا برگشت با همین ابزار فعلی تمام کنید. مقایسهٔ سه لاگ در یک روز، بدون یک برگشت موفق، به تیم یاد نمی‌دهد کدام ابزار سالم است. فقط سه جا برای کلید خصوصی می‌سازد.

اگر برگشت را همان روز نزده‌اید، این فصل را تمام‌شده حساب نکنید. برگشت در ساعت اداری ارزان است و شب قطعی گران.

## Best Practices

- یک تیم، یک کنترلر، یک تعریف برای شناسهٔ ایمیج. ابزار دوم را «موقتاً» کنار اولی بالا نیاورید.
- استقرار تولید فقط از `main` و فقط بعد از تست و پوش موفق. تأیید انسانی محیط (environment) در Actions، شاخهٔ محافظت‌شده در GitLab، و مجوز Job در Jenkins همان قفل انسانی است.
- برچسب قبلی را در رجیستری پاک نکنید تا وقتی برگشت را تمرین نکرده‌اید. بدون ایمیج قبلی، اسکریپت برگشت چیزی برای کشیدن ندارد.
- اسکریپت استقرار را در همان مخزن برنامه مرور کنید، ولی اجرای تولیدش فقط از روی دیسک سرور است. عوض کردن اسکریپت هم مثل عوض کردن برنامه باید از مسیر مرور عبور کند، نه ویرایش عجولانه روی سرور بدون اینکه مخزن را به‌روز کنید.
- وقتی خط لوله خراب است، مسیر دستی فصل استقرار مجاز است. بعد از احیای سرویس، همان تغییر باید به شکل کامیت برگردد تا نوبت بعدی خط لوله آن را بازنویسی نکند.
- صفحهٔ بعدی را بر اساس محل مخزن انتخاب کنید، نه بر اساس معروف بودن ابزار. بعد [سناریو](/docs/09-cicd/pipeline-scenario) را با همان ابزار یک بار تا برگشت اجرا کنید.
- شناسهٔ ایمیج را در سه جا یکی ببینید: لاگ job، `docker image ls` روی `docker-1`، و خط `APP_TAG` در `.env`. اگر دو تا از این سه فرق دارند، استقرار تمام نشده حتی اگر چراغ ابزار سبز باشد.
- راز را در فایل workflow با مقدار پیش‌فرض نگذارید. نبودن secret باید job را قرمز کند، نه اینکه با رمز خالی به رجیستری برسد.
