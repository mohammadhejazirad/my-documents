# نقشهٔ Ansible

## مقدمه

Ansible ابزار پیکربندی و اجرای کار از راه دور است. روی میزبان‌های مقصد عامل (agent) نصب نمی‌شود. از SSH وارد می‌شود، ماژول را می‌فرستد، و با Python همان میزبان کار را انجام می‌دهد. اگر بار دوم همان دستور را بزنید و چیزی عوض نشده باشد، باید گزارش `ok` بدهد نه اینکه فایل را دوباره از نو بسازد. به این خاصیت تکرارپذیری (idempotence) می‌گویند.

این فصل برای آزمایشگاه همین دانشنامه است. گرهٔ کنترل روی `mon-1.example.internal` (`10.10.1.40`) می‌نشیند. میزبان‌های مقصد `proxy`، `app-1` و `db-1` هستند. کاربر اتصال `ops` است و افزایش امتیاز با `sudo` انجام می‌شود. اسکریپت تک‌میزبانه هنوز در [فصل Bash](/docs/13-automation) است. Ansible وقتی لازم است که یک تعریف در Git باید روی چند ماشین یکسان بماند.

## مفهوم اصلی

دو بسته را قاطی نکنید.

`ansible-core` موتور و دستورهای `ansible` و `ansible-playbook` و ماژول‌های داخلی `ansible.builtin` است. `ansible` بستهٔ جامعه است: همان هسته به‌علاوهٔ مجموعه‌های (collection) منتخب مثل `ansible.posix` و بخشی از `community.general`.

در سپتامبر ۲۰۲۶، طبق جدول نگهداری رسمی Ansible، بستهٔ جاری جامعه سری ۱۴ است و به هستهٔ ۲.۲۱ وابسته است. آخرین انتشار دیده‌شده روی PyPI در ۸ سپتامبر ۲۰۲۶ نسخهٔ ۱۴.۴.۰ است. هستهٔ پایدار همان خط ۲.۲۱.۴ است. ۲.۲۲ هنوز بتا بوده و در این دانشنامه نصب نمی‌شود.

Ubuntu 26.04 در مخزن universe بسته‌ای قدیمی‌تر اما بسته‌بندی‌شده دارد: `ansible-core` نسخهٔ ۲.۲۰.۱، و بستهٔ `ansible` حدود ۱۳.۱ که همان هسته را همراه مجموعه‌ها می‌آورد. سری ۱۳ جامعه طبق جدول رسمی از ژوئن ۲۰۲۶ از نگهداری عادی خارج شده، ولی هستهٔ ۲.۲۰ تا مه ۲۰۲۷ در پنجرهٔ امنیت بالادست است. برای سرور تولید این دانشنامه پیش‌فرض همان بستهٔ Ubuntu است، چون با `apt` به‌روز می‌شود و به pip سیستمی وابسته نیست. اگر مجموعه‌ای می‌خواهید که فقط در سری ۱۴ هست، مسیر `pipx` در صفحهٔ نصب آمده است. قبل از نوشتن عدد در گزارش تغییر، `ansible --version` و `apt-cache policy ansible` را روی خود گرهٔ کنترل بخوانید.

میزبان مقصد Ansible نصب نمی‌کند. Python 3 کافی است. برای هستهٔ ۲.۲۰ و ۲.۲۱، Python مقصد طبق جدول رسمی از ۳.۹ تا ۳.۱۴ است. Ubuntu 26.04 و Debian 13 داخل این بازه‌اند.

## چرا استفاده می‌شود؟

ورود دستی به ده سرور و اجرای همان `apt install` سه شکست دارد: یکی جا می‌ماند، یکی دستور را با فلگ دیگری می‌زند، و هفتهٔ بعد کسی نمی‌داند چه چیزی اعمال شده. Playbook در Git همان دستور را با همان آرگومان نگه می‌دارد و `--check` نشان می‌دهد چه چیزی عوض خواهد شد قبل از اینکه عوض شود.

Ansible جای Terraform برای ساختن خود ابر، و جای اسکریپت بکاپ شبانه نیست. اگر کار فقط روی یک میزبان و فقط با shell است، فصل Bash کوتاه‌تر و روشن‌تر است.

## Architecture

```text
mon-1  10.10.1.40     گرهٔ کنترل
    ansible-playbook
    inventory + playbook در Git
            │  SSH به عنوان ops، کلید ed25519
            ▼
    proxy   10.10.1.5
    app-1   10.10.1.10
    db-1    10.10.1.20
            Python 3 از قبل روی سیستم
            Ansible نصب نیست
```

ترتیب خواندن سایدبار است: مفهوم، نصب، اینونتوری، دستور تک‌باره، Playbook، متغیر و fact، قالب و handler، نقش، Vault، نمونهٔ تولید، عیب‌یابی.

## Installation

نصب فقط روی گرهٔ کنترل است. دستور دقیق و تفاوت بستهٔ Ubuntu با `pipx` در [نصب](/docs/17-ansible/installation) است. تا آن صفحه را تمام نکرده‌اید Playbook ننویسید. میزبان بدون Python را هم همان صفحه با یک دستور `raw` یک‌باره درست می‌کند.

## Configuration

قرارهای این فصل، تا صفحه‌های بعدی خلافش را با دلیل نگفته باشند:

| قرار | مقدار |
| --- | --- |
| گرهٔ کنترل | `mon-1` / `10.10.1.40` |
| کاربر SSH | `ops` |
| کلید | `ed25519` |
| افزایش امتیاز | `become: true` و `sudo` |
| اینونتوری | داخل مخزن، نه فقط `/etc/ansible/hosts` |
| نام ماژول | نام کامل، مثل `ansible.builtin.apt` |
| بررسی کلید میزبان | روشن می‌ماند |

## Production Example

هفتهٔ اول فقط `ping` به سه میزبان است. هفتهٔ دوم یک Playbook بستهٔ پایه و منطقهٔ زمانی `Asia/Tehran` را روی `app` و `proxy` اعمال می‌کند و روی `db` فقط بسته‌هایی را می‌گذارد که صفحهٔ پایگاه اجازه داده. نمونهٔ کامل در [Playbook تولید](/docs/17-ansible/production) است. تا `--check` خروجی قابل‌فهم ندهد، `--ask-become-pass` را با عجله تبدیل به `NOPASSWD: ALL` نکنید.

## Security Notes

گرهٔ کنترل نقشهٔ همهٔ سرورها و گاهی رمز Vault را دارد. مثل یک میزبان مدیریتی محافظت می‌شود: SSH سخت، دیسک رمزنگاری‌شده اگر لپ‌تاپ است، و مخزن خصوصی. `host_key_checking = False` در تولید نوشته نمی‌شود. کاربر `ops` اگر `sudo` بدون رمز برای همه‌چیز داشته باشد، دزدیدن کلید SSH گرهٔ کنترل برابر است با root همهٔ مقصدها. محدودیت sudo در صفحهٔ نصب آمده است.

## Troubleshooting

اگر `ping` شکست خورد، قبل از دست زدن به Playbook این سه تا را جدا کنید: خود SSH با همان کاربر و کلید کار می‌کند یا نه، Python روی مقصد هست یا نه، و sudo رمز می‌خواهد یا نه. جدول نشانه‌ها در [عیب‌یابی](/docs/17-ansible/troubleshooting) است.

## Best Practices

- تعریف را در Git بگذارید و روی سرور فقط اجرا کنید.
- یک بار با `--check --diff` ببینید، بعد بدون check اجرا کنید.
- نام کوتاه ماژول (`apt`) را در فایل تازه ننویسید. نام کامل را بنویسید تا ده سال بعد معلوم باشد ماژول از کدام مجموعه آمده.
- گرهٔ کنترل را روی `db-1` نصب نکنید.
