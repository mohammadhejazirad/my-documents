# مفهوم Ansible

## مقدمه

Ansible یک زبان توصیف وضعیت دلخواه است که با SSH اعمال می‌شود. شما نمی‌نویسید «این پنج دستور را بزن». می‌نویسید «بستهٔ `nginx` نصب باشد و سرویسش فعال باشد». ماژول تصمیم می‌گیرد برای رسیدن به آن وضعیت چه کند، و اگر از قبل همان باشد کاری نمی‌کند.

این صفحه نصب نمی‌کند. واژه‌هایی را ثابت می‌کند که بقیهٔ فصل با آن‌ها حرف می‌زنند.

## مفهوم اصلی

گرهٔ کنترل (control node) ماشینی است که دستور `ansible-playbook` روی آن اجرا می‌شود. در این دانشنامه `mon-1` است. میزبان مدیریت‌شده (managed node) سروری است که کار روی آن انجام می‌شود. فهرست این میزبان‌ها اینونتوری (inventory) است. گروه (group) چند میزبان را یک نام می‌دهد، مثل `app` یا `db`.

ماژول (module) برنامهٔ کوچکی است که یک کار را تکرارپذیر انجام می‌دهد. `ansible.builtin.apt` بسته را به وضعیت `present` یا `absent` می‌رساند. `ansible.builtin.copy` فایل را با محتوا و مجوز خواسته‌شده می‌نویسد و اگر همان باشد بازنویسی بی‌دلیل نمی‌کند. Play فهرستی از کارها (task) روی یک گروه میزبان است. Playbook یک یا چند Play در یک فایل YAML است.

اجرای تک‌باره (ad hoc) یک ماژول را بدون فایل Playbook می‌زند. برای دیدن وضعیت خوب است. برای چیزی که باید ماه بعد هم همان باشد، Playbook است.

Fact اطلاعات خود میزبان است که Ansible با ماژول setup جمع می‌کند: خانوادهٔ سیستم‌عامل، آدرس، حافظه. متغیر چیزی است که شما می‌دهید: نام بسته، منطقهٔ زمانی، رمز. رمز در Vault می‌ماند نه در Playbook روشن.

نقش (role) یک Playbook را به پوشه‌های `tasks` و `handlers` و `templates` و `defaults` می‌شکند تا در چند پروژه تکرار شود. تا وقتی همهٔ کار در یک فایل صدخطی جا می‌شود، نقش اجباری نیست. از جایی که دو تیم همان پایه را می‌خواهند، نقش به‌درد می‌خورد.

مجموعه (collection) بسته‌ای از ماژول‌هاست. `ansible.builtin` همراهِ هسته است. بقیه با بستهٔ `ansible` یا با `ansible-galaxy` می‌آیند.

## چرا استفاده می‌شود؟

SSH و یک حلقهٔ Bash هم می‌تواند دستور را به ده میزبان بفرستد. فرق Ansible این است که ماژول وضعیت را می‌فهمد. حلقهٔ Bash `apt-get install` را هر بار اجرا می‌کند و خروجی را «تغییر» حساب می‌کند حتی اگر بسته باشد. ماژول apt اگر بسته با همان نسخه باشد `ok` می‌دهد و فقط وقتی واقعاً نصب یا ارتقا شود `changed` می‌دهد. همین تفاوت است که اجازه می‌دهد Playbook را هر شب اجرا کنید بدون اینکه سرویس بی‌دلیل reload شود.

## Architecture

```text
ansible-playbook site.yml
        │
        ├─ ansible.cfg     مسیر اینونتوری و نقش
        ├─ inventory       نام میزبان و گروه
        ├─ group_vars      متغیر هر گروه
        └─ play
              tasks → ماژول روی SSH
              handlers → فقط اگر task تغییر داده باشد
```

هیچ پورتی جز SSH (و اگر sudo لازم باشد همان نشست) باز نمی‌شود. سرویس `ansible` روی مقصد وجود ندارد که بالا نیاید.

## Installation

چیزی اینجا نصب نمی‌شود. پیش‌نیاز مفهومی این است که از گرهٔ کنترل به `ops@10.10.1.10` با کلید وارد شوید، همان‌طور که در [سخت‌سازی SSH](/docs/10-security/ssh-hardening) آمده. اگر این ورود دستی کار نکند، Ansible هم کار نمی‌کند.

## Configuration

واژه‌هایی که در فایل قدیمی اینترنت هنوز هست و در Playbook تازهٔ این فصل استفاده نمی‌شود:

| قدیمی | امروز |
| --- | --- |
| `sudo: yes` | `become: true` |
| `-m apt` در فایل دائمی | `ansible.builtin.apt` |
| `include` بدون توضیح | `import_tasks` یا `include_tasks` با دلیل |
| `host_key_checking = False` | بررسی کلید روشن |

`yes` و `no` در YAML برای بولی هنوز در نسخه‌های فعلی خوانده می‌شوند، ولی مقدار صریح `true` و `false` در فایل تازه خواناتر است و با هشدارهای جدیدتر کمتر برخورد می‌کند.

## Production Example

یک task درست این شکل است. وضعیت را می‌گوید، نه فهرست دستور shell را.

```yaml
- name: Ensure curl is installed
  ansible.builtin.apt:
    name: curl
    state: present
```

task غلطی که این فصل رد می‌کند:

```yaml
- name: Install curl
  ansible.builtin.shell: apt-get install -y curl
```

دومی هر بار اجرا می‌شود، کد خروج apt را با تغییر واقعی قاطی می‌کند، و اگر `apt` قفل باشد خطا را بدتر تفسیر می‌کنید. shell فقط وقتی مجاز است که ماژول معادل نداشته باشد و `changed_when` را خودتان نوشته باشید.

## Security Notes

Ansible به اندازهٔ همان SSH قدرت دارد. اگر Playbook با `become: true` و کاربر همه‌کاره اجرا شود، یک فایل YAML در مخزن عمومی برابر دستور root روی تولید است. مخزن Playbook خصوصی می‌ماند. متغیر رمز در Vault است. خروجی اجرا ممکن است محتوا را چاپ کند. callback دیباگ را روی تولید با verbosity بالا به چت نفرستید.

## Troubleshooting

اگر واژه‌ها را قاطی کنید نشانه‌اش این‌هاست. «Ansible روی سرور نصب نیست» برای میزبان مقصد طبیعی است. «Playbook چیزی عوض نکرد» اگر وضعیت از قبل درست باشد موفقیت است نه خرابی. `changed=0` و `failed=0` یعنی این بار کاری نمانده بود.

## Best Practices

- هر task یک نام انسانی دارد که در لاگ معلوم کند چه می‌خواسته، نه فقط اسم ماژول.
- یک Playbook یک هدف دارد. «همهٔ کارهایی که بلدیم» در یک فایل، review را غیرممکن می‌کند.
- قبل از نقش و Vault، یک Playbook تخت را تا `--check` سالم جلو ببرید.
