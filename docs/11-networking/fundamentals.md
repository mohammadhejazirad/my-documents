# مبانی شبکه

## مقدمه

قبل از DNS و گواهی باید بتوانید بگویید یک بسته از `app-1` به کجا می‌رود و چرا برنمی‌گردد. این صفحه همان زبان را روی Ubuntu Server 26.04 ثابت می‌کند: آدرس، ماسک، مسیر پیش‌فرض، پورت، فرق TCP و UDP، و resolver محلی. دستورها `ip` و `ping` و در صورت نیاز `traceroute` هستند.

میزبان نمونه `app-1.example.internal` با آدرس `10.10.1.10/16` است. دروازهٔ نمونه `10.10.0.1` است. اگر روی سرور واقعی `ip route` عدد دیگری نشان داد، همان خروجی برنده است. عددهای این صفحه قرارداد آزمایشگاه‌اند، نه کشف خودکار.

## مفهوم اصلی

آدرس IPv4 سی و دو بیت است. ماسک می‌گوید چند بیت اول «شبکه» است و چند بیت آخر «میزبان». نوشتن `10.10.0.0/16` یعنی شانزده بیت اول ثابت است. بیت‌های شبکه برابر `10.10` هستند. محدوده از `10.10.0.0` تا `10.10.255.255` است. ماسک نقطه‌ای همین پیشوند `255.255.0.0` است.

`10.10.1.10/16` یک میزبان داخل همان شبکه است، نه یک شبکهٔ جدا با ماسک `/24`. در این آزمایشگاه مسیریاب میانی بین `10.10.1.5` و `10.10.1.20` لازم نیست. هر دو روی یک لینک منطقی‌اند. اگر سازمان به‌جای این مدل تخت، برای هر رک یک `/24` جدا داده، ماسک میزبان همان است که روی کارت شبکه پیکربندی شده و مسیر بین رک‌ها از دروازه رد می‌شود. آن را با این صفحه قاطی نکنید. اول `ip addr` را بخوانید.

مسیر پیش‌فرض (default route) فقط برای مقصدهایی است که هیچ مسیر مشخص‌تری ندارند. مقصد `10.10.1.20` با مسیر متصل `10.10.0.0/16` جور می‌شود و سراغ دروازه نمی‌رود. مقصدی مثل سرور NTP عمومی با هیچ مسیر متصل جور نمی‌شود و به `10.10.0.1` می‌رود. اگر مسیر پیش‌فرض نباشد، `apt` و Let's Encrypt و `ping 1.1.1.1` شکست می‌خورند در حالی که `ping 10.10.1.5` سالم است.

پورت عدد شانزده‌بیتی کنار آدرس است. آدرس می‌گوید کدام میزبان. پورت می‌گوید کدام برنامه روی آن میزبان. SSH روی 22، HTTP روی 80، HTTPS روی 443، DNS روی 53. پورت‌های زیر 1024 را فقط پروسهٔ ممتاز می‌تواند گوش کند. گوش دادن روی `0.0.0.0:9090` یعنی همهٔ کارت‌ها، از جمله کارتی که روزی به اینترنت وصل می‌شود. در این دانشنامه سرویس مدیریت به آدرس داخلی همان میزبان می‌چسبد.

TCP جلسه دارد. شروعش دست‌دادن است و اگر کسی روی پورت گوش ندهد، هسته با RST جواب می‌دهد و ابزار شما `Connection refused` می‌گوید. UDP جلسه ندارد. نبود برنامه روی پورت UDP اغلب سکوت است، نه refused. DNS پرس‌وجوی معمولی را روی UDP/53 می‌فرستد و اگر پاسخ بزرگ باشد یا zone transfer باشد سراغ TCP/53 می‌رود. پس «DNS یعنی UDP» جملهٔ کاملی نیست. نامه و وب و SSH و MySQL روی TCP هستند.

## چرا استفاده می‌شود؟

عیب‌یابی بالاتر از این لایه بدون این واژه‌ها شلوغ می‌شود. «اینترنت قطعه» گاهی یعنی مسیر پیش‌فرض نیست، گاهی یعنی resolver به `127.0.0.53` اشاره می‌کند ولی `systemd-resolved` خواب است، گاهی یعنی فایروال بستهٔ ICMP را دور می‌ریزد و SSH سالم است. این‌ها سه اقدام مختلف‌اند.

`ping` زنده بودن تقریبی مسیر را می‌گوید و زنده بودن سرویس را نمی‌گوید. میزبانی که ping را فیلتر کرده می‌تواند SSH سالم داشته باشد. میزبانی که ping جواب می‌دهد می‌تواند روی پورت 443 هیچ برنامه‌ای نداشته باشد. هر دو را در Production می‌بینید.

## Architecture

```text
برنامه (Nginx، sshd، node)
        │  سوکت TCP یا UDP روی آدرس:پورت
        ▼
هسته، جدول مسیر
        │
        ├── مقصد داخل 10.10.0.0/16 ──► مستقیم از eth0
        │                              مبدأ 10.10.1.10
        └── هر مقصد دیگر ───────────► دروازه 10.10.0.1
                                       (مسیر default)

نام، جدا از مسیر:
برنامه
  │  getaddrinfo
  ▼
stub resolver  127.0.0.53:53     systemd-resolved
  │
  ▼
DNS بالادست، از netplan یا resolved.conf
```

`/etc/resolv.conf` روی Ubuntu 26.04 معمولاً یک پیوند نمادین است، نه فایلی که با ویرایشگر پر کنید.

```text
/etc/resolv.conf
    -> ../run/systemd/resolve/stub-resolv.conf
```

آن فایل stub فقط `nameserver 127.0.0.53` دارد. خود `systemd-resolved` روی این آدرس حلقه‌بک گوش می‌دهد و سؤال را به DNS بالادست می‌فرستد. بالادست را `resolvectl status` نشان می‌دهد. فایل `/run/systemd/resolve/resolv.conf` فهرست بالادست را دارد و stub نیست. اگر یک کانتینر یا chroot فایل resolv میزبان را کپی کند و به `127.0.0.53` برسد، داخل netns خودش کسی روی آن پورت نیست و DNS می‌میرد. برای کانتینر یا DNS بالادست واقعی را بدهید، یا از DNS داکر استفاده کنید، نه از کپی کور stub.

## Installation

ابزار مسیر و آدرس در بستهٔ `iproute2` است و روی سرور نصب است. `ping` از `iputils-ping` می‌آید و روی Ubuntu Server هست. `tracepath` هم اغلب با iputils هست و به نصب جدا نیاز ندارد.

`traceroute` کلاسیک بستهٔ دیگری است. روی Ubuntu 26.04 ممکن است اصلاً نصب نباشد و پوسته `command not found` بدهد. این خطا به معنی خراب بودن شبکه نیست.

```bash
traceroute -n 10.10.0.1
```

اگر دستور پیدا نشد:

```bash
sudo apt update
sudo apt install traceroute
traceroute -n -w 2 10.10.0.1
```

فلگ `-n` یعنی نام هر هاب را حل نکن. وقتی خود DNS مشکوک است، traceroute بدون `-n` پشت یک سؤال معکوس DNS می‌ایستد و شما فکر می‌کنید مسیر گیر کرده است.

`dig` را همین‌جا نصب نکنید مگر صفحهٔ رکورد را همان روز کار دارید. بستهٔ آن `bind9-dnsutils` است و در صفحهٔ وصل کردن دامنه نصب می‌شود.

`systemd-resolved` روی Ubuntu Server سرویس پیش‌فرض است. نصبش نکنید. فقط وضعیتش را ببینید.

```bash
systemctl is-active systemd-resolved
resolvectl status
```

## Configuration

آدرس پایدار را netplan نگه می‌دارد، نه یک دستور `ip addr add` که تا ریبوت زنده است. فایل‌ها زیر `/etc/netplan/` هستند و پسوندشان `yaml` است. قبل از جایگزین کردن فایل فروشنده، همان فایل موجود را بخوانید. نام کارت را از `ip -br link` بردارید. در نمونهٔ زیر کارت `eth0` است. روی سرور ابری ممکن است `ens3` یا `enp1s0` باشد.

```yaml
network:
  version: 2
  ethernets:
    eth0:
      addresses:
        - 10.10.1.10/16
      routes:
        - to: default
          via: 10.10.0.1
      nameservers:
        addresses:
          - 10.10.0.1
        search:
          - example.internal
```

اعمال و بررسی:

```bash
sudo netplan generate
sudo netplan apply
ip -br addr show eth0
ip route
resolvectl status
```

`netplan apply` ممکن است مختصر ارتباط SSH را قطع کند اگر آدرس یا دروازه را غلط نوشته باشید. از کنسول هایپروایزر کنار دستتان باشد. `netplan generate` فقط فایل را به پیکربندی تبدیل می‌کند و اگر YAML غلط باشد قبل از قطع شدن SSH خطا می‌دهد. اول generate، بعد apply.

DNS بالادست در این نمونه خود دروازه است، با این فرض که سازمان روی `10.10.0.1` resolver داخلی دارد. اگر چنین سرویس‌ای ندارید، آدرس resolver سازمان را بگذارید. `1.1.1.1` را روی سروری که باید نام `example.internal` را حل کند تنها بالادست نگذارید، چون آن نام در DNS عمومی وجود ندارد و نباید وجود داشته باشد.

در `resolvectl status` برای لینک `eth0` باید DNS بالادست و دامنهٔ جست‌وجو `example.internal` را ببینید. خط `Current DNS Server` همان جایی است که سؤال بعدی می‌رود.

اگر کسی قبلاً `/etc/resolv.conf` را با ویرایشگر عوض کرده و پیوند را شکسته، stub از مدار خارج شده است. نشانه‌اش این است که `ls -l /etc/resolv.conf` دیگر به `stub-resolv.conf` اشاره نمی‌کند و `resolvectl` یک چیز می‌گوید و فایل چیز دیگری. برگرداندن پیوند، بعد از این‌که مطمئن شدید `systemd-resolved` فعال است:

```bash
sudo ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
resolvectl query app-1.example.internal
```

این دستور را وقتی بزنید که عمداً پیوند شکسته شده، نه به‌عنوان عادت هر حادثه.

## Production Example

`app-1` ناگهان نمی‌تواند به `db-1` وصل شود. برنامه خطای timeout به `10.10.1.20` می‌دهد. از SSH روی `app-1` این مسیر را بروید.

### نشانه

سرویس برنامه بالا است. خطای لاگ، timeout به پورت دیتابیس روی `10.10.1.20` است. کاربر بیرونی هنوز سایت را می‌بیند چون خود پروکسی درگیر این مسیر نیست.

### فرضیه

یا آدرس `app-1` افتاده، یا مسیر `10.10.0.0/16` نیست، یا `db-1` گوش نمی‌دهد، یا فایروال بینشان بسته است. چون هر دو باید روی یک `/16` تخت باشند، فرض اول این است که یکی از دو میزبان دیگر آن آدرس را روی کارت ندارد.

### دستور مشاهده

```bash
ip -br addr
ip route get 10.10.1.20
ping -c 3 -W 1 10.10.1.20
```

خروجی سالم `ip route get`:

```text
10.10.1.20 dev eth0 src 10.10.1.10 uid 1000
    cache
```

یعنی هسته تصمیم گرفته بسته مستقیم از `eth0` با مبدأ `10.10.1.10` برود، نه از دروازه. اگر به‌جای این، `via 10.10.0.1` دیدید، ماسک یا مسیر را کسی عوض کرده و ترافیک داخلی را بی‌دلیل به روتر فرستاده است.

خروجی سالم ping:

```text
PING 10.10.1.20 (10.10.1.20) 56(84) bytes of data.
64 bytes from 10.10.1.20: icmp_seq=1 ttl=64 time=0.4 ms
64 bytes from 10.10.1.20: icmp_seq=2 ttl=64 time=0.3 ms

--- 10.10.1.20 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2040ms
```

اگر `ip route get` مستقیم است و ping صد درصد loss دارد، ICMP ممکن است فیلتر باشد. همان لحظه پورت سرویس را جدا امتحان کنید. ping منفی به‌تنهایی خاموش بودن دیتابیس نیست.

```bash
curl -sv --max-time 3 telnet://10.10.1.20:5432
```

`Connected` یعنی پورت باز است حتی اگر بعدش پروتکل را نفهمد و ببندد. `Connection refused` یعنی میزبان زنده است و روی 5432 شنونده نیست. timeout یعنی مسیر یا فیلتر.

### تصمیم

اگر `ip -br addr` آدرس `10.10.1.10/16` را ندارد، مشکل پیکربندی میزبان است. سراغ کوئری دیتابیس نروید.

اگر آدرس هست و `ip route get` مستقیم است و پورت refused است، شبکه سالم است و سرویس دیتابیس خواب است. ادامه در صفحهٔ دیتابیس و [دیتابیس کند](/docs/14-troubleshooting/database-slow) است، نه این‌جا.

اگر آدرس هست و پورت timeout است در حالی که از خود `db-1` همان پورت `ss` را نشان می‌دهد، فایروال میانی یا فایروال میزبان مقصد بسته است. [UFW](/docs/10-security/ufw) را روی `db-1` ببینید.

### اصلاح

برای مورد افتادن آدرس، netplan را به مقدار آزمایشگاه برگردانید، `netplan generate` را بدون خطا بگیرید، بعد apply کنید و دوباره `ip route get 10.10.1.20` را بزنید. تا وقتی این دستور `src 10.10.1.10` را نشان نداده، برنامه را restart نکنید. restart پروسهٔ گیرکرده را پنهان می‌کند و علت شبکه را پاک نمی‌کند.

### جلوگیری از تکرار

تغییر netplan را فقط از طریق فایل زیر `/etc/netplan/` بدهید و خروجی `ip route` بعد از reboot را یک بار ببینید. دستور دستی `ip addr add` بعد از reboot می‌میرد و حادثهٔ بعدی شبیه قطع تصادفی شبکه است.

برای دیدن مسیر بیرونی، وقتی داخلی سالم است و بیرون نه:

```bash
ip route get 1.1.1.1
traceroute -n -w 2 -m 8 1.1.1.1
```

هاب اول باید `10.10.0.1` باشد. اگر هاب اول نیست، مسیر پیش‌فرض غلط است.

## Security Notes

سرویس را به `0.0.0.0` نچسبانید مگر واقعاً باید از هر کارت دیده شود. Prometheus، Grafana، Netdata، دیتابیس و SSH مدیریتی در این دانشنامه روی آدرس `10.10.1.x` همان میزبان گوش می‌دهند و فایروال فقط شبکهٔ آزمایشگاه را راه می‌دهد. چسباندن به آدرس داخلی جلوی یک کارت دوم یا یک تونل اشتباهی را هم می‌گیرد.

ICMP را کورکورانه و بدون یادداشت مسدود نکنید. تیم عملیات با `ping` حادثه را از «میزبان مرده» جدا می‌کند. اگر سیاست سازمان ICMP را می‌بندد، در صفحهٔ عملیات بنویسید تا کسی از روی loss صددرصدی سرور را reboot نکند.

resolver باز روی `0.0.0.0:53` راه نیندازید. stub محلی `127.0.0.53` فقط از خود میزبان در دسترس است و همین درست است. یک resolver باز، سرور شما را وارد حملهٔ تقویتی DNS می‌کند.

بستهٔ `traceroute` چیز حساسی نیست، ولی هر بستهٔ اضافه را روی ایمیج پایه نصب نکنید «چون شاید به درد بخورد». وقتی دستور پیدا نشد همان موقع نصب کنید.

## Troubleshooting

`ping: connect: Network is unreachable` یعنی برای آن مقصد هیچ مسیری نیست، حتی پیش‌فرض. `ip route` را ببینید. این خطا با `No route to host` یکی نیست. دومی اغلب ICMP unreachable از یک روتر یا فیلتر است.

`ping: Temporary failure in name resolution` اصلاً به مسیر مربوط نیست. نام حل نشده. `resolvectl status` و `systemctl is-active systemd-resolved` را ببینید. اگر سرویس inactive است:

```bash
sudo systemctl enable --now systemd-resolved
resolvectl query archive.ubuntu.com
```

اگر سرویس فعال است ولی `resolvectl query` برای نام عمومی timeout می‌دهد و `ping 1.1.1.1` سالم است، بالادست DNS غلط است یا پورت 53 به سمت آن بسته است. آدرس را در netplan عوض کنید. فایل `/etc/resolv.conf` را با nameserver تصادفی پر نکنید.

اگر `resolvectl query app-1.example.internal` نام را از DNS عمومی می‌پرسد و `NXDOMAIN` می‌گیرد، دامنهٔ جست‌وجو یا DNS داخلی تنظیم نشده. نام بلند را امتحان کنید و `search` را در status ببینید.

ابزار `ss` برای دیدن شنونده، بعد از این‌که مسیر سالم بود:

```bash
ss -lntup
```

ستون آدرس را بخوانید. `10.10.1.10:22` یعنی SSH فقط روی آدرس داخلی است. `0.0.0.0:22` یعنی همهٔ کارت‌ها. `127.0.0.1:5432` یعنی فقط از خود میزبان. این ستون در حادثه از عدد پورت مهم‌تر است.

## Best Practices

- هر بار که آدرس می‌دهید پیشوند را هم بنویسید. `10.10.1.10` بدون `/16` ناقص است و آدم بعدی ماسک `/24` حدس می‌زند.
- اول `ip route get` به مقصد واقعی حادثه، بعد ping، بعد پورت. ترتیب را عوض نکنید.
- ping شکست‌خورده را مساوی خاموش بودن سرور نگیرید.
- `traceroute` را با `-n` بزنید تا DNS در مسیر عیب‌یابی شبکه دخالت نکند.
- `/etc/resolv.conf` را ویرایش نکنید. netplan یا drop-in مربوط به systemd-resolved را عوض کنید و با `resolvectl status` تأیید کنید.
- نام داخلی را فقط از resolver داخلی بخواهید. اگر مجبورید موقتاً `/etc/hosts` بنویسید، خط را با نام میزبان و دلیلش در یادداشت تغییر ثبت کنید.
- پورت مدیریت را در مستند سرویس بنویسید و روی آدرس داخلی bind کنید. کشف پورت با اسکن از اینترنت روش این تیم نیست.
