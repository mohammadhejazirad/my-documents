# وصل کردن دامنه به سرور

## مقدمه

وصل کردن دامنه یعنی یک نام عمومی به همان میزبانی برسد که Nginx روی آن برای همان نام تصمیم می‌گیرد. در آزمایشگاه آن میزبان پروکسی است: `proxy.example.internal` با آدرس داخلی `10.10.1.5`. در DNS عمومی به‌جای آدرس واقعی اینترنت، از `203.0.113.10` استفاده می‌کنیم. این آدرس TEST-NET-3 است، در RFC 5737 برای مستندات رزرو شده، و روی اینترنت مسیریابی نمی‌شود. روزی که دامنهٔ واقعی را می‌بندید، آدرس عمومی همان پروکسی را از پنل شبکهٔ سازمان می‌خوانید و جای این عدد می‌گذارید. عدد را از حافظه یا از یک سرور دیگر اختراع نکنید.

کار این صفحه بعد از [رکوردها](./dns-records) است و قبل از گواهی. تا وقتی `dig +short` آدرس پروکسی را برنگرداند، Certbot و گواهی پولی هر دو در حال اثبات مالکیت یک نام روی ماشینی هستند که شاید اصلاً ترافیک را نمی‌بیند.

## مفهوم اصلی

دو پیکربندی باید یک نام را بشناسند و این دو جای مختلفی هستند.

اولی DNS است. رکورد A می‌گوید `app.example.com` برابر `203.0.113.10` است. این جمله را سرور authoritative منطقه منتشر می‌کند. resolverها تا TTL آن را کش می‌کنند. تا وقتی TTL قبلی نگذشته، بخشی از کاربران هنوز IP قدیم را دارند. صبر کردن در این مرحله یک اقدام است، نه اتلاف وقت.

دومی `server_name` در Nginx است. بسته به پروکسی رسیده و Nginx باید بلوک درستی را انتخاب کند. اگر هیچ بلوکی با نام درخواست جور نباشد، بلوک پیش‌فرض جواب می‌دهد. آن بلوک ممکن است سایت دیگری باشد یا یک پاسخ خالی. نشانهٔ این اشتباه این است که `dig` درست است، پورت 443 باز است، و محتوا مال سرویس دیگری است یا گواهی نام دیگری است.

خود برنامه روی `10.10.1.10` لازم نیست نام عمومی را در DNS خصوصی تکرار کند. پروکسی به بالادست با آدرس داخلی وصل می‌شود. جدا کردن این دو باعث می‌شود دیتابیس و پورت برنامه به اینترنت اعلام نشوند.

## چرا استفاده می‌شود؟

تیم گاهی IP را در گروه پیام می‌فرستد و کار را تمام‌شده حساب می‌کند. کاربر بیرونی با IP خام یا گواهی نمی‌گیرد، یا نام را در مرورگر ذخیره نمی‌کند، و روز بعد که IP عوض شد همه چیز می‌میرد. نام پایدار است و IP پروکسی می‌تواند عوض شود، به شرطی که TTL را از قبل کم کرده باشید.

بدون `server_name` درست، یک سرور با چند سایت (virtual host) درخواست را به سایت اشتباه می‌دهد. این خطا در لاگ دسترسی دیده می‌شود اگر لاگ را خوانده باشید، و در کانفیگ اگر `nginx -t` را کافی بدانید دیده نمی‌شود. `nginx -t` نحو را چک می‌کند، نه این را که دنیا به این بلوک می‌رسد.

## Architecture

```text
مرورگر
   │  Host: app.example.com
   ▼
DNS ── A ── 203.0.113.10
   │
   ▼
کارت عمومی پروکسی
   │  NAT یا خود آدرس، بسته به شبکهٔ سازمان
   ▼
Nginx روی proxy.example.internal (10.10.1.5)
   │  server_name app.example.com
   │  پورت 80 و بعداً 443
   ▼
بالادست http://10.10.1.10:8080
   برنامه روی app-1 ، بدون رکورد عمومی
```

اگر سازمان بین اینترنت و پروکسی یک فایروال دارد، قاعده باید به `10.10.1.5` روی پورت 80 و 443 برود، نه به `10.10.1.10`. باز کردن پورت برنامه به اینترنت، پروکسی را دور می‌زند و گواهی را بی‌معنی می‌کند.

## Installation

`dig` روی ماشینی که از آن چک می‌کنید لازم است. همان بستهٔ صفحهٔ رکورد:

```bash
sudo apt update
sudo apt install bind9-dnsutils
```

Nginx باید روی پروکسی نصب و فعال باشد. نصب و معنی بلوک‌ها در [نصب Nginx](/docs/06-nginx/installation) و [ساختار کانفیگ](/docs/06-nginx/configuration) است. این صفحه فقط `server_name` و آزمون بیرونی را اضافه می‌کند. اگر واحد بالا نیست:

```bash
sudo systemctl enable --now nginx
sudo systemctl status nginx --no-pager
ss -lnt | grep ':80'
```

خط خروجی `ss` باید نشان دهد که پورت 80 روی پروکسی گوش می‌دهد. برای بستن دامنه، 80 کافی است. 443 را صفحهٔ گواهی اضافه می‌کند.

## Configuration

در پنل DNS منطقهٔ `example.com` یک رکورد بسازید.

| فیلد | مقدار |
| --- | --- |
| نام | `app` |
| نوع | A |
| مقدار | `203.0.113.10` |
| TTL | 300 در روز تغییر، 3600 بعد از پایدار شدن |

نام را `app.example.com.example.com` نسازید. اگر پنل منطقه را خودش اضافه می‌کند، در فیلد نام فقط `app` را بگذارید. اگر پنل نام کامل می‌خواهد، `app.example.com` را بگذارید و بعد با `dig` بفهمید کدام حالت بوده. تنها معیار، پاسخ `dig` است نه برچسب دکمهٔ ذخیره.

روی پروکسی یک فایل سایت بسازید، مثلاً `/etc/nginx/sites-available/app.example.com` ، و آن را در `sites-enabled` فعال کنید. اگر نصب شما از `conf.d` استفاده می‌کند، همان را به کار ببرید. هر دو الگو در فصل Nginx هست. این بلوک فقط برای اثبات رسیدن نام است و هنوز گواهی ندارد.

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name app.example.com;

    location / {
        proxy_pass http://10.10.1.10:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`server_name` باید عین همان نامی باشد که کاربر در مرورگر می‌زند. `example.com` به‌تنهایی درخواست `app.example.com` را نمی‌گیرد، مگر این‌که هر دو را در همان دستور نوشته باشید. چند نام را فقط وقتی در یک بلوک بگذارید که واقعاً یک سایت‌اند، مثل `app.example.com` و `www.example.com` بعد از این‌که CNAME دامنهٔ www را به app رسانده است.

فعال‌سازی و آزمون نحو:

```bash
sudo ln -s /etc/nginx/sites-available/app.example.com /etc/nginx/sites-enabled/app.example.com
sudo nginx -t
sudo systemctl reload nginx
```

`reload` اتصال‌های جاری را مثل `restart` نمی‌برد. اگر `nginx -t` خطا داد، reload نکنید. سرویس هنوز کانفیگ قبلی را دارد و این بهتر از پایین آوردن سایت با یک فایل ناقص است.

## Production Example

دامنه تازه به پروکسی اشاره شده و همکار می‌گوید «ذخیره کردم». شما باید تمام شدن را از بیرون ثابت کنید، نه از اسکرین‌شات پنل.

### نشانه

مرورگر داخل دفتر هنوز صفحهٔ قدیمی را نشان می‌دهد یا اصلاً نام را باز نمی‌کند. پنل DNS تیک سبز نشان می‌دهد.

### فرضیه

یا کش TTL هنوز آدرس قدیم را دارد، یا رکورد روی نام غلط ذخیره شده، یا Nginx نام را در `server_name` ندارد و بلوک پیش‌فرض جواب می‌دهد.

### دستور مشاهده

TTL را از خود پاسخ بخوانید، نه از حافظه.

```bash
dig +short app.example.com A
dig app.example.com A
```

خروجی سالم `dig +short` یک خط است:

```text
203.0.113.10
```

خروجی کامل، TTL باقی‌مانده را هم دارد:

```text
;; ANSWER SECTION:
app.example.com.        300     IN      A       203.0.113.10
```

اگر این خط آدرس دیگری است، هنوز نوبت Nginx نیست. اگر خالی است، رکورد منتشر نشده یا نام را اشتباه ساخته‌اید. یک بار هم مستقیم از میزبان پروکسی بپرسید. اگر پروکسی جواب درست می‌دهد و لپ‌تاپ نه، کش مسیر لپ‌تاپ است.

وقتی `dig +short` درست شد:

```bash
curl -sS -D - --max-time 8 -o /dev/null -H 'Host: app.example.com' http://203.0.113.10/
curl -sS -D - --max-time 8 -o /dev/null http://app.example.com/
```

در آزمایشگاه واقعی به‌جای `203.0.113.10` آدرس عمومی پروکسی را می‌گذارید. خط اول با هدر Host ثابت می‌کند که اگر بسته به خود پروکسی برسد، بلوک درست انتخاب می‌شود. خط دوم ثابت می‌کند DNS به‌علاوهٔ بلوک با هم کار می‌کنند.

روی پروکسی، درخواست واقعاً به این `server_name` خورده یا نه:

```bash
sudo nginx -T | grep server_name
```

باید `app.example.com` را در خروجی ببینید. `nginx -T` کانفیگ مؤثر را چاپ می‌کند، از جمله فایل‌هایی که include شده‌اند. اگر در ویرایشگر خط را می‌بینید و در `nginx -T` نه، فایل در `sites-enabled` نیست یا include نشده است.

### تصمیم

`dig +short` غلط یا خالی: در پنل DNS بمانید. Nginx را reload نکنید.

`dig` درست و `curl` با هدر Host روی IP پروکسی درست، ولی `curl` با نام غلط: هنوز resolver شما آدرس دیگری می‌بیند. صبر کنید یا از شبکه‌ای سؤال کنید که کش قدیمی ندارد. مدت انتظار برابر TTL باقی‌ماندهٔ همان جواب غلط است. اگر جواب غلط TTL برابر 3600 دارد، تا یک ساعت کاربرانی هستند که سرور قدیم را می‌بینند.

`dig` درست و هر دو curl غلط: `server_name` یا بالادست. اگر پاسخ 502 است، نام رسیده و `10.10.1.10:8080` جواب نداده. اگر پاسخ مال سایت دیگری است، درخواست به بلوک پیش‌فرض خورده است.

### اصلاح

برای بلوک پیش‌فرض، `server_name` را همان‌طور که در پیکربندی این صفحه است اصلاح کنید، `sudo nginx -t` را بدون خطا ببینید، بعد reload کنید و فقط همان `curl` نام را دوباره بگیرید.

برای 502، از خود پروکسی به بالادست وصل شوید.

```bash
curl -sS -D - --max-time 5 -o /dev/null http://10.10.1.10:8080/
```

اگر این‌جا refused است، برنامه روی `app-1` خواب است. دامنه سالم است. سراغ unit برنامه بروید، نه سراغ پاک کردن رکورد A.

### جلوگیری از تکرار

چک خروج از کار را سه خطی کنید و در یادداشت تغییر بگذارید: خروجی `dig +short` ، کد وضعیت `curl` به نام، و خروجی `nginx -t`. تا وقتی TTL را به 300 نیاورده‌اید، مهاجرت IP را شروع نکنید. بعد از پایدار شدن TTL را به 3600 برگردانید تا یک خرابی کوتاه DNS همه‌جا فوری قطعی نشود. جزئیات TTL در [رکوردها](./dns-records) است.

## Security Notes

آدرس خصوصی `10.10.1.5` را در رکورد عمومی A نگذارید. کاربران بیرون به آن نمی‌رسند و توپولوژی داخلی در لاگ‌های عمومی می‌ماند.

پورت 8080 برنامه را در فایروال لبه باز نکنید تا «تست دامنه راحت شود». تست از خود پروکسی با `curl` به `10.10.1.10` انجام می‌شود. باز کردن بالادست یعنی دور زدن هر هدر و محدودیتی که بعداً در [امنیت Nginx](/docs/06-nginx/security-rate-limit) می‌گذارید.

`server_name _;` یا `default_server` را با محتوای تولید پر نکنید. بلوک پیش‌فرض باید پاسخ کوتاه و بی‌اطلاع بدهد تا اسکن نام‌ها، سایت واقعی را پیدا نکند. سایت واقعی فقط با نام خودش جواب بدهد.

هدر `Host` را در `proxy_set_header` به بالادست می‌فرستیم تا برنامه نام را ببیند. این هدر را از کلاینت بدون بازنگری به سرویس‌های داخلی دیگر، مثل ابزار مدیریت، پروکسی نکنید. آن الگو راه مسموم کردن کش و دسترسی به vhost داخلی است. این بلوک فقط به برنامهٔ خودتان روی پورت 8080 می‌رود.

## Troubleshooting

`dig +short` چند خط برمی‌گرداند: بیش از یک رکورد A دارید. تا وقتی مهاجرت عمدی نیست، باید یک خط بماند. دو A یعنی کاربر تصادفی بین دو سرور تقسیم می‌شود.

`curl` خطای `Could not resolve host` می‌دهد در حالی که از تلفن بیرون نام باز می‌شود: resolver همان ماشینی که دستور را زده‌اید خراب است. `resolvectl query app.example.com` را با [مبانی](./fundamentals) مقایسه کنید. پنل DNS را دوباره ذخیره نکنید.

اتصال timeout به `203.0.113.10` در دنیای واقعی، وقتی به‌جایش IP واقعی پروکسی را گذاشته‌اید: مسیر یا فایروال لبه. روی پروکسی `ss -lnt` باید `:80` را نشان بدهد. اگر نشان می‌دهد و از بیرون timeout است، فایروال است نه Nginx. اگر از بیرون refused است، بسته به میزبان رسیده و شنونده ندارید.

محتوا از `http://10.10.1.5` داخل شبکه درست است ولی با نام عمومی نه: دارید با IP داخلی و بلوک پیش‌فرض حرف می‌زنید. نام را در URL بگذارید تا `server_name` انتخاب شود.

بعد از درست شدن HTTP، اگر HTTPS هنوز خطای نام گواهی می‌دهد، این صفحه کارش تمام است. بروید به [Let's Encrypt](./ssl-letsencrypt) یا [گواهی پولی](./ssl-commercial). هر کدام را که سازمان برای این نام انتخاب کرده، نه هر دو.

## Best Practices

- یک نام، یک A، یک `server_name` عین همان نام. اختلاف `www` را یا با CNAME به همین نام بیاورید و در `server_name` هر دو را بنویسید، یا اصلاً سرو نکنید.
- چک را با `dig +short` از بیرون شروع کنید. اسکرین‌شات پنل شاهد نیست.
- اگر جواب غلط است، به اندازهٔ TTL باقی‌مانده صبر کنید و رکورد را پشت سر هم عوض نکنید.
- `nginx -t` را قبل از reload عادت کنید. reload با کانفیگ شکسته، سایت را با کانفیگ قبلی نگه می‌دارد فقط اگر اصلاً reload را نزده باشید. اگر بزنید و تست را رد کرده باشد، Nginx reload را رد می‌کند. پس تست را خودتان اول ببینید تا پیام خطا را در زمان آرامش بخوانید.
- بالادست را با آدرس داخلی بنویسید. نام عمومی را داخل `proxy_pass` نگذارید، وگرنه یک حلقه از پروکسی به خود پروکسی می‌سازید.
- وقتی HTTP سالم شد، همان روز گواهی را صادر کنید. سایت روی پورت 80 بدون برنامهٔ بعدی برای 443 نباید در اینترنت بماند.
