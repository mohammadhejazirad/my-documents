# دامنه پشت IP سرور

## مقدمه

دامنه وقتی به کار می‌آید که کاربر به‌جای عدد، نام را بزند و آن نام به همان ماشینی برسد که سایت روی آن است. «پشت IP سرور» یعنی رکورد عمومی در نهایت به آدرس عمومی همان ماشین ختم شود. دو شکل رایج دارد. شکل اول رکورد A مستقیم است: نام برابر IP سرور، و مرورگر خودش به آن IP وصل می‌شود. شکل دوم پروکسی ابری است: نام از دید کاربر به لبهٔ ابرآروان یا Cloudflare می‌رسد و لبه به IP سرور، که به آن origin می‌گویند، وصل می‌شود.

صفحهٔ [وصل کردن دامنه](./domain-binding) شکل اول را با رکورد A و `server_name` گفته است. این صفحه انتخاب بین مستقیم و پروکسی است. جزئیات پنل هر سرویس در [ابرآروان](./arvancloud) و [Cloudflare](./cloudflare) است.

آدرس عمومی نمونه همچنان `203.0.113.10` است و روی اینترنت مسیریابی نمی‌شود. IP واقعی سرور را از پنل شبکهٔ خودتان بردارید.

## مفهوم اصلی

سرور یک آدرس عمومی دارد، یا پشت NAT یک آدرس که فایروال پورت ۴۴۳ را به `10.10.1.5` می‌فرستد. دامنه این آدرس را نمی‌داند تا وقتی در DNS ثبت شود. ثبت کردن فقط یک جمله است: این نام، این آدرس.

اگر پروکسی ابری خاموش باشد (ابر خاکستری، یا DNS only)، جمله همان است که مرورگر می‌بیند. گواهی را خود سرور باید داشته باشد. حمله و درخواست مستقیم به IP سرور ممکن است. Let's Encrypt با چالش HTTP روی پورت ۸۰ سرور کار می‌کند.

اگر پروکسی روشن باشد (ابر نارنجی در Cloudflare، نماد ابر در ابرآروان)، کاربر به IP شما وصل نمی‌شود. به IP لبه وصل می‌شود. لبه درخواست را به origin، یعنی همان IP سرور، بازمی‌فرستد. از دید کاربر IP سرور پنهان است، ولی در پنل DNS هنوز همان IP را نوشته‌اید. پنهان بودن کامل نیست: اگر جایی دیگر آن IP لو برود، پروکسی را دور می‌زنند مگر فایروال سرور فقط بازهٔ IP لبه را قبول کند.

سه چیز باید هم‌زمان درست باشد وگرنه پروکسی سایت را «خراب» نشان می‌دهد در حالی که سرور سالم است:

- origin روی ۸۰ یا ۴۴۳ از دید لبه باز باشد.
- گواهی بین لبه و origin با حالت SSL پنل جور باشد. حالت Flexible یعنی لبه تا سرور را بی‌رمز طی می‌کند و نباید حالت تولید باشد.
- Nginx هدر IP واقعی را از لبه باور کند، وگرنه لاگ و Fail2ban همه را یک IP می‌بینند.

## چرا استفاده می‌شود؟

رکورد مستقیم ساده‌تر است و عیب‌یابی‌اش یک `dig` است. پروکسی وقتی معنی دارد که کش لبه، گواهی لبه، یا مخفی کردن نسبی IP را بخواهید، یا مبدأ کاربر به شبکهٔ شما نزدیک نباشد.

پروکسی را برای «امن شدن خودبه‌خود» روشن نکنید. اگر حالت SSL غلط باشد، رمز بین لبه و سرور نیست. اگر فایروال هنوز به همهٔ دنیا روی ۴۴۳ باز باشد، دانستن IP سرور پروکسی را بی‌اثر می‌کند. اگر چالش HTTP را فراموش کنید، تمدید گواهی origin هفتهٔ بعد می‌خوابد.

برای آزمایشگاه داخلی که فقط `10.10.0.0/16` است، هیچ‌کدام از این دو پنل لازم نیست. این صفحه برای نام عمومی `app.example.com` است که کاربر بیرون از شبکه می‌زند.

## Architecture

```text
حالت مستقیم
    کاربر ── DNS A ── 203.0.113.10 ── Nginx روی پروکسی

حالت پروکسی
    کاربر ── DNS ── IP لبهٔ ابرآروان یا Cloudflare
                      │
                      └── origin 203.0.113.10
                            Nginx
                            server_name app.example.com
                            هدر IP واقعی
```

در هر دو حالت بالادست برنامه هنوز `10.10.1.10` است و رکورد عمومی به آن اشاره نمی‌کند. CDN جای فایروال داخلی و جای جدا بودن دیتابیس را نمی‌گیرد.

## Installation

روی خود سرور بستهٔ تازه‌ای برای «داشتن دامنه» نصب نمی‌شود. لازم است:

- پورت ۸۰ و ۴۴۳ روی پروکسی از بیرون، یا دست‌کم از لبه، باز باشد. [UFW](/docs/10-security/ufw).
- یک بلوک Nginx با `server_name` عین همان نام. [Nginx](/docs/06-nginx/configuration).
- ساعت درست برای گواهی. [بوت‌استرپ](/docs/04-server-management/initial-bootstrap).

ابزار چک از لپ‌تاپ:

```bash
sudo apt install bind9-dnsutils
dig +short app.example.com
curl -sI https://app.example.com
```

## Configuration

تصمیم را قبل از عوض کردن نیم‌سرور بنویسید.

| حالت | چه وقت | گواهی کاربر | گواهی تا سرور |
| --- | --- | --- | --- |
| مستقیم | یک سرور، تیم کوچک، عیب‌یابی ساده | Let's Encrypt روی خود Nginx | همان |
| پروکسی با Full strict | ترافیک عمومی، کش، مخفی کردن نسبی IP | گواهی لبه | گواهی معتبر روی origin |

Full strict یعنی لبه گواهی origin را واقعاً چک می‌کند. پس origin باید گواهی معتبر برای همان نام داشته باشد، نه گواهی خودامضا و نه فقط IP. صدور آن گواهی در حالت پروکسی با چالش HTTP گیر می‌کند، چون درخواست پورت ۸۰ به لبه می‌رسد نه لزوماً به مسیری که Certbot روی سرور گذاشته. دو راه تمیز: موقتاً پروکسی را برای همان رکورد خاموش کنید و Certbot را بزنید، یا چالش DNS. جزئیات هر پنل در صفحهٔ خودش است.

بعد از روشن کردن پروکسی، `dig` از بیرون باید IP لبه را نشان دهد نه `203.0.113.10`. اگر هنوز IP سرور را می‌بینید، یا پروکسی خاموش است، یا TTL قبلی نگذشته، یا دارید از DNS داخلی خود سرور سؤال می‌کنید. چک را از لپ‌تاپ بزنید.

Nginx باید نام را بشناسد حتی وقتی `Host` را لبه می‌فرستد. لبه معمولاً همان `Host` کاربر را به origin می‌دهد. `server_name` را به IP عوض نکنید.

## Production Example

سازمان `app.example.com` را خریده و سرور پروکسی یک IP عمومی دارد. هفتهٔ اول حالت مستقیم است: رکورد A به IP، Certbot، و `curl` از موبایل خارج از شرکت. وقتی این پایدار شد، اگر کش و لبه لازم شد، نیم‌سرور را به ابرآروان یا Cloudflare می‌دهند و پروکسی را روشن می‌کنند. همان روز یک بار از شبکهٔ بیرون `dig` می‌گیرند و یک بار لاگ Nginx را می‌بینند که IP کاربر را نشان می‌دهد نه فقط IP لبه.

اگر هر دو پنل را با هم روی یک نام روشن کنید، دو پروکسی پشت سر هم می‌سازید و عیب‌یابی را غیرممکن می‌کنید. یک نام، یک لبه.

## Security Notes

IP سرور را در کانال عمومی کنار آموزش «پروکسی روشن است پس امنیم» نگذارید. امنیت origin یعنی فایروال، SSH بسته‌شده به کلید، و ترجیحاً پذیرش ۸۰ و ۴۴۳ فقط از بازهٔ IP همان لبه، به شرطی که آن بازه را از مستند روز همان شرکت بگیرید و وقتی سایت از لبه خطای origin داد اول همان فهرست را مقصر بدانید نه Nginx را.

حالت Flexible را برای سایت ورود و کوکی روشن نکنید. رمز تا لبه هست و از لبه تا سرور نیست.

پنل DNS را با حساب مشترک بدون دومرحله‌ای نگذارید. کسی که رکورد را عوض کند، دامنه را برده است حتی اگر به سرور SSH نداشته باشد.

## Troubleshooting

| نشانه | معنی محتمل |
| --- | --- |
| `dig` هنوز IP سرور است بعد از روشن کردن پروکسی | TTL، یا کش resolver، یا نماد پروکسی ذخیره نشده |
| کاربر خطای 522 یا 524 یا خطای origin می‌بیند | لبه به سرور نمی‌رسد یا سرور دیر جواب می‌دهد. از خود سرور `ss -lnt` و از یک ماشین سوم `curl` به IP سرور |
| گواهی در مرورگر مال لبه است ولی حلقهٔ بازگشت بی‌نهایت است | origin به نام عمومی `proxy_pass` می‌کند و درخواست دوباره به لبه برمی‌گردد |
| Certbot تمدید نمی‌شود | چالش HTTP به لبه خورده. حالت پروکسی یا نوع چالش را با صفحهٔ همان شرکت جور کنید |
| همهٔ لاگ‌ها یک IP هستند | هدر IP واقعی در Nginx تنظیم نشده. صفحهٔ ابرآروان یا Cloudflare |
| سایت فقط داخل شرکت باز است | رکورد عمومی نیست یا فایروال فقط IP دفتر را راه داده |

## Best Practices

- اول حالت مستقیم را سالم کنید، بعد پروکسی را اضافه کنید. دو تغییر در یک ساعت را از هم جدا کنید.
- یک دامنه را هم‌زمان به دو CDN ندهید.
- IP سرور را در رکورد پروکسی‌شده هنوز درست نگه دارید. لبه از همان رکورد origin را پیدا می‌کند.
- بعد از هر تغییر DNS به اندازهٔ TTL صبر کنید و از شبکه‌ای غیر از خود سرور تست بگیرید.
