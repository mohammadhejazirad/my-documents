# دامنه با ابرآروان

## مقدمه

ابرآروان هم DNS است و هم، اگر نماد ابر را روشن کنید، شبکهٔ توزیع و پروکسی جلوی سرور. این صفحه دامنهٔ `app.example.com` را طوری تنظیم می‌کند که به IP عمومی پروکسی آزمایشگاه اشاره کند. در مثال، آن IP همان `203.0.113.10` است. روی سرور واقعی عدد را از پنل شبکه می‌گذارید.

مفهوم کلی حالت مستقیم و حالت پروکسی در [دامنه پشت IP](./cdn-origin) است. اینجا فقط کارهایی است که داخل پنل ابرآروان و روی Nginx انجام می‌شود.

مستند محصول عوض می‌شود. اگر اسم دکمه در پنل با این صفحه یکی نبود، همان کاری را بکنید که این صفحه معنی‌اش را گفته: نیم‌سرور، رکورد A به IP سرور، تصمیم دربارهٔ روشن بودن ابر، و گواهی. آدرس پنل معمول `https://panel.arvancloud.ir` است.

## مفهوم اصلی

تا وقتی نیم‌سرور دامنه در ثبت‌کننده (registrar) هنوز مال ابرآروان نشده، رکوردی که در پنل ابرآروان می‌سازید به دنیای بیرون گفته نمی‌شود. گام اول همیشه نیم‌سرور است، نه رکورد.

نیم‌سرورهایی که پنل بعد از افزودن دامنه نشان می‌دهد را عیناً کپی کنید. زوج رایج `ns1.arvancloud.ir` و `ns2.arvancloud.ir` است و گاهی `ns3` و `ns4` هم هستند. اگر پنل چیز دیگری نشان داد، پنل برنده است.

رکورد A نام `app` یا ریشهٔ `@` را به IP سرور می‌برد. نماد ابر دو حالت دارد. ابر خاموش یعنی فقط DNS: کاربر مستقیم به IP سرور می‌رود. ابر روشن یعنی ترافیک وب از لبهٔ آروان رد می‌شود و لبه به همان IP به عنوان origin وصل می‌شود. ایمیل را از این ابر رد نکنید. رکورد MX باید ابر خاموش بماند وگرنه نامه به لبهٔ HTTP می‌رود و گم می‌شود.

گواهی لبه را خود آروان برای دامنه‌ای که نیم‌سرورش پیش اوست صادر می‌کند، به شرطی که رکورد از همین پنل سرو شود. این گواهی بین کاربر و لبه است. بین لبه و سرور یک اتصال جداست. اگر در تنظیم HTTPS حالتی را انتخاب کنید که لبه تا سرور را چک کند، روی خود Nginx باید گواهی معتبر داشته باشید. صدور Let's Encrypt را در [صفحهٔ گواهی رایگان](./ssl-letsencrypt) ببینید. با ابر روشن، چالش HTTP-01 اغلب به لبه می‌خورد. برای صدور یا تمدید، یا ابر همان رکورد را موقتاً خاموش کنید، یا از چالش DNS استفاده کنید.

## چرا استفاده می‌شود؟

تیمی که دامنه و مخاطبش در ایران است اغلب لبه را نزدیک همان شبکه می‌خواهد، و نمی‌خواهد کاربر مستقیم به IP سرور برسد. ابرآروان این لبه را با DNS یکجا می‌دهد. اگر فقط DNS می‌خواهید و ترافیک باید مستقیم به سرور بخورد، همان پنل با ابر خاموش کافی است و گواهی فقط روی سرور است.

روشن کردن ابر بدون دست زدن به فایروال و بدون فهم گواهی origin، سایت را از بیرون خطای لبه نشان می‌دهد در حالی که از داخل شرکت، با دور زدن DNS، هنوز باز است. این دو نشانه را با هم اشتباه نگیرید.

## Architecture

```text
ثبت‌کنندهٔ دامنه
    نیم‌سرورهای پنل ابرآروان
            │
            ▼
پنل DNS ابرآروان
    A   app.example.com → 203.0.113.10
    ابر روشن برای وب
    MX بدون ابر
            │
            ▼
لبهٔ آروان  ← گواهی بین کاربر و لبه
            │
            ▼
origin  203.0.113.10:443
    Nginx روی 10.10.1.5
    server_name app.example.com
```

پورت ۲۲ را از لبه رد نکنید و رکورد جدا برای SSH نسازید که ابر روشن داشته باشد. مدیریت سرور مستقیم به IP یا از راه VPN است، با سخت‌سازی SSH.

## Installation

روی سرور بسته‌ای به نام arvan نصب نمی‌شود. کار پنل و کار Nginx است.

پیش‌نیاز سرور، قبل از روشن کردن ابر:

```bash
sudo ufw status verbose
sudo ss -lnt | grep -E ':80|:443'
sudo nginx -t
```

باید ۸۰ و ۴۴۳ شنونده داشته باشند و UFW به آن‌ها اجازه بدهد. اگر می‌خواهید بعداً فقط بازهٔ IP آروان را راه بدهید، اول یک بار با ابر روشن و فایروال باز به ۴۴۳ ثابت کنید سایت از بیرون باز است، بعد فهرست را تنگ کنید. تنگ کردن را در همان ساعتی انجام دهید که می‌توانید از کنسول، نه از خود HTTP، قفل را باز کنید.

## Configuration

ترتیب پنل:

1. دامنه را در پنل اضافه کنید و نیم‌سرورها را در ثبت‌کننده بگذارید. صبر کنید تا `dig NS app.example.com` همان نام‌ها را برگرداند. این انتظار ممکن است چند ساعت باشد و به TTL نیم‌سرور قبلی بستگی دارد.
2. رکورد A برای `app` و در صورت نیاز برای `@` و `www` بسازید. مقدار، IP عمومی سرور است.
3. برای رکورد وب تصمیم ابر را بگیرید. برای شروع عیب‌یابی، ابر خاموش باشد تا Certbot و `curl` به خود سرور بخورد. وقتی گواهی origin حاضر شد، ابر را روشن کنید.
4. MX و TXT مربوط به نامه را بدون ابر بگذارید.
5. در بخش HTTPS، حالتی را انتخاب کنید که اتصال لبه تا origin را رمزشده و چک‌شده می‌خواهد، نه حالتی که تا سرور HTTP ساده است.

روی Nginx، اگر ابر روشن است، IP که در access log می‌بینید IP لبه است مگر هدر واقعی را باور کنید. نام دقیق هدر را از مستند روز CDN آروان در همان پنل بخوانید. نمونه‌هایی که در استقرارها دیده می‌شود `X-Forwarded-For` و `ar-real-ip` است. هر نامی را که مستند فعلی گفت در `real_ip_header` بگذارید. نمونه برای `X-Forwarded-For`، فقط وقتی به لبه اعتماد دارید:

```nginx
real_ip_header X-Forwarded-For;
real_ip_recursive on;
set_real_ip_from 10.10.0.0/16;
```

خط `set_real_ip_from` باید بازهٔ IP لبه باشد، نه بازهٔ دفتر شما. بازه را از مستند آروان همان روز کپی کنید. اگر بازه را اشتباه بگذارید، هر مشتری می‌تواند هدر را جعل کند و خودش را IP دیگری جا بزند. تا وقتی فهرست رسمی را در فایل نیاورده‌اید، لاگ را با دانستن این محدودیت بخوانید و Fail2ban را روی آن هدر نبندید.

بلوک سایت همان است که در حالت مستقیم بود:

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    location / {
        proxy_pass http://10.10.1.10:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`proxy_pass` را به `https://app.example.com` ندهید. آن نام حالا به لبه برمی‌گردد و حلقه ساخته می‌شود.

## Production Example

ثبت‌کننده، نیم‌سرور را به آنچه پنل آروان نشان داده عوض می‌کند. تا `dig NS` درست نشده رکورد A را آزمایش نهایی حساب نکنید. بعد A را به IP سرور می‌دهید، ابر خاموش، Certbot روی سرور گواهی را می‌گیرد، `curl` از موبایل خارج از VPN کد ۲۰۰ می‌دهد.

همان روز ابر را روشن می‌کنید. `dig +short app.example.com` از لپ‌تاپ دیگر نباید `203.0.113.10` بماند. باید آدرس لبه باشد. سایت در مرورگر باز می‌شود و گواهی را لبه نشان می‌دهد. روی سرور `tail` لاگ دسترسی را می‌بینید. اگر همهٔ خط‌ها یک آدرس بودند، هدر IP واقعی هنوز در Nginx نیست و این را در یادداشت کار همان روز می‌نویسید، نه اینکه فکر کنید فقط یک کاربر دارید.

MX از اول ابر خاموش مانده و یک نامهٔ آزمایشی به صندوق دامنه هنوز می‌رسد.

## Security Notes

حساب پنل را با رمز مشترک تیم و بدون ورود دومرحله‌ای نگذارید. رکورد DNS از SSH مهم‌تر است اگر تنها کسی که دامنه را دارد همان پنل باشد.

ابر روشن، SSH را امن نمی‌کند. پورت ۲۲ را به دنیا باز نگذارید.

اگر فایروال را به بازهٔ IP آروان محدود می‌کنید، یک راه ورود خارج از HTTP نگه دارید: کنسول ماشین یا VPN. وگرنه با عوض شدن بازهٔ لبه، خودتان هم سایت را می‌بندید و راه تعمیر وب ندارید.

رمز و کلید API پنل را در مخزن مستندات و در اسکریپت جهان‌خوانا نگذارید.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| نیم‌سرور در `dig NS` هنوز ثبت‌کنندهٔ قبلی است | صبر TTL. در پنل ثبت‌کننده ذخیره شدن را دوباره ببینید |
| ابر روشن است و خطای اتصال به origin می‌آید | از یک VPS دیگر `curl -vk https://203.0.113.10 -H 'Host: app.example.com'` را نزنید اگر گواهی به IP صادر نشده. به‌جایش ابر را خاموش کنید و مستقیم نام را بزنید، یا از خود سرور `ss` و `nginx -t` را ببینید |
| تمدید Certbot شکست می‌خورد | ابر روشن است و چالش به سرور نمی‌رسد. موقتاً خاموش کنید یا چالش DNS |
| فقط صفحهٔ پیش‌فرض آروان یا خطای میزبان | `server_name` با نام رکورد یکی نیست، یا origin به پورت اشتباه می‌رود |
| نامه نمی‌رسد | MX ابر روشن دارد. خاموشش کنید |
| بعد از خاموش کردن ابر هنوز IP لبه دیده می‌شود | TTL رکورد پروکسی‌شده. صبر کنید |

## Best Practices

- MX و هر رکوردی که پروکسی HTTP نیست ابر خاموش باشد.
- اول گواهی روی خود سرور، بعد ابر روشن، با حالتی که اتصال تا origin را سست نکند.
- تغییرات پنل را یکی‌یکی بزنید و هر بار از شبکهٔ بیرون `dig` و `curl` بگیرید.
- فهرست IP لبه را تاریخ‌دار در مخزن پیکربندی بگذارید تا شش ماه بعد بدانید از کجا کپی شده.
