# نقشهٔ اتوماسیون و Bash

## مقدمه

این فصل ابزار شب‌های عملیات است: اسکریپتی که بکاپ را می‌گیرد، سلامت `app-1` را نگاه می‌کند، لاگ فشردهٔ کهنه را برمی‌دارد، و یک tag مشخص را به `/opt/apps/app/current` می‌رساند. مخاطب کسی است که به SSH دسترسی دارد و فردا صبح باید بداند کار دیشب انجام شده یا با وضعیت خروج غیرصفر ایستاده است.

ابزار این فصل Bash است، به‌علاوهٔ دو زمان‌بند: cron بستهٔ Ubuntu و timer خود systemd. Ansible و ارکستراسیون اینجا نیست. کاری که هفته‌ای یک‌بار روی یک میزبان تکرار می‌شود نباید پشت یک چارچوب اضافه قایم شود. کاری که از یک مخزن Git با tag منتشر می‌شود در [اسکریپت استقرار](/docs/13-automation/script-deploy) است و مسیر دستی اطرافش در [استقرار با SSH](/docs/08-deployment/manual-ssh).

آزمایشگاه همان شبکهٔ بقیهٔ دانشنامه است. `app-1.example.internal` برابر `10.10.1.10` است و برنامه زیر `/opt/apps` است. `db-1.example.internal` برابر `10.10.1.20` است. بکاپ زیر `/var/backups` می‌نشیند. کاربر انسانی مدیر `ops` است. کاربر `deploy` روی `app-1` اسکریپت استقرار و سلامت را اجرا می‌کند و پوستهٔ `/bin/bash` دارد، چون باید `git` و `npm` را صدا بزند. بکاپ `/etc` و بکاپ دیتابیس با root اجرا می‌شوند؛ دلیلش کنار همان اسکریپت نوشته شده، نه به‌خاطر عادت.

## مفهوم اصلی

اتوماسیون این فصل یعنی یک فایل متنی که بدون حضور آدم، با محیط فقیر زمان‌بند، همان کار را تکرار کند و اگر مبدأ نیست یا دستور وسط کار شکست، خروج غیرصفر بدهد و فایل نیمه‌کاره را به‌جا نگذارد.

هر اسکریپت این فصل این قرارداد را دارد:

| قاعده | چرا |
| --- | --- |
| شِبانگ `bash` و نه `sh` | روی Ubuntu و Debian،‏ `/bin/sh` همان dash است و نحو Bash را نمی‌فهمد |
| `set -euo pipefail` بلافاصله بعد از شِبانگ | شکست، متغیر خالی، و خطای وسط لوله مخفی نماند |
| قفل `flock` | اجرای دستی وسط اجرای زمان‌بندی‌شده نسخه را خراب نکند |
| لاگ با زمان | فردا صبح بشود فهمید کدام مرحله ایستاد |
| خروج ۰ فقط وقتی کار تمام شده | cron و systemd هر دو غیرصفر را شکست حساب می‌کنند |
| مسیر مطلق دستورهای حساس | `PATH` زمان‌بند، `PATH` نشست تعاملی شما نیست |

صفحهٔ مفهومی را قبل از اسکریپت بخوانید. اسکریپت‌ها همان قاعده‌ها را به کار می‌برند و دوباره تعریفشان نمی‌کنند، ولی هر کدام به‌تنهایی قابل اجرا هستند و به فایل مشترکی که در مخزن نیست وابسته نیستند.

## چرا استفاده می‌شود؟

کار دستی بکاپ سه شکست تکراری دارد. آدم فراموش می‌کند. آدم وقتی سرور کند است میانبر می‌زند و نسخهٔ قبلی را پاک می‌کند قبل از اینکه نسخهٔ جدید خوانده شده باشد. آدم رمز را در خط فرمان می‌گذارد و رمز در `ps` و در history می‌ماند.

اسکریپت این سه تا را از حافظهٔ شیفت خارج می‌کند، به شرطی که خود اسکریپت کوتاه و مبهم نباشد. اسکریپت صدخطی که فقط نویسنده می‌فهمد، از کار دستی خطرناک‌تر است چون همه به آن اعتماد می‌کنند. برای همین هر اسکریپت این فصل مسیر، قفل، نگهداری نسخه، و حالت شکست را در خود فایل دارد و صفحهٔ اطرافش می‌گوید روی کدام میزبان و با کدام کاربر بنشیند.

زمان‌بند لازم است چون اسکریپت به‌خودی‌خود ساعت ندارد. cron برای تیمی که سال‌ها فایل `/etc/cron.d` را خوانده آشناست. timer برای تیمی که بقیهٔ سرویس را با systemd اداره می‌کند یکپارچه‌تر است، چون خروجی در journal می‌ماند و واحد سرویس دو بار هم‌زمان شروع نمی‌شود. هر دو را در [cron](/docs/13-automation/cron) کامل یاد می‌گیرید. انتخاب با تیم است. جمع کردنشان ممنوع است.

## Architecture

```text
نشست تعاملی ops روی لپ‌تاپ
        │
        ▼
اسکریپت در /usr/local/sbin یا /opt/apps/app/bin
        │
        ├── یک زمان‌بند، نه هر دو
        │     ├── /etc/cron.d/نام-بدون-نقطه     کاربر در ستون ششم
        │     └── systemd timer + service       enable فقط روی timer
        │
        ├── flock روی یک فایل قفل مشخص
        ├── لاگ فایل زیر /var/log و logger
        └── وضعیت خروج
              ├── 0  کار تمام
              ├── 1  مبدأ نیست، دیسک، یا ابزار
              └── 2  قرارداد خود اسکریپت (سلامت: سرویس down، یا usage)

میزبان‌ها
  app-1   10.10.1.10   بکاپ فایل، سلامت، پاک‌سازی لاگ، استقرار
  db-1    10.10.1.20   بکاپ MySQL و PostgreSQL دیتابیس app
  مقصد بکاپ           /var/backups/files و /var/backups/db
```

اسکریپت استقرار timer شبانه ندارد. انتشار وقتی است که tag وجود دارد، نه رأس ساعت. سلامت هر پنج دقیقه منطقی است. بکاپ فایل و دیتابیس شبانه‌اند و نباید هم‌زمان با هم دیسک را پر کنند؛ در صفحهٔ خودشان از هم فاصله دارند.

خواندن فصل به این ترتیب است. اگر Bash را روی سرور نوشته‌اید، از ردیف پنجم شروع کنید ولی قرارداد `set -euo pipefail` را در صفحهٔ خطا رد نکنید.

## Installation

روی سرور تازه هر دو ابزار زمان‌بندی را نصب و روشن کنید، حتی اگر امشب فقط یکی را به کار می‌گیرید. نبودن بستهٔ cron وقتی کسی فایل `/etc/cron.d` می‌گذارد، شکست بی‌صداست.

```bash
sudo apt-get update
sudo apt-get install -y cron bash gawk findutils coreutils tar gzip util-linux
systemctl enable --now cron.service
systemctl status cron.service --no-pager
```

`bash` و `gawk` و `findutils` معمولاً از قبل روی Ubuntu Server هستند. نصب صریح‌شان جلوی سرور حداقلی را می‌گیرد که `flock` یا `timeout` ندارد. timer به بستهٔ جدا نیاز ندارد؛ systemd خودش هست. بررسی:

```bash
systemctl --version
systemctl list-timers --all --no-pager
```

منطقهٔ زمانی آزمایشگاه `Asia/Tehran` است. cron ساعت را از `/etc/localtime` می‌خواند و timezone جدا برای هر کاربر ندارد. timer هم عبارت تقویمی را با ساعت سیستم تفسیر می‌کند.

```bash
timedatectl set-timezone Asia/Tehran
timedatectl
```

کاربر `deploy` اگر از فصل‌های قبل ساخته نشده:

```bash
sudo adduser --disabled-password --gecos "app deploy" deploy
sudo chsh -s /bin/bash deploy
sudo install -d -o deploy -g deploy -m 0755 /opt/apps /home/deploy
```

`chsh` فقط روی `app-1` است. اگر حسابی هیچ دستوری اجرا نمی‌کند، پوستهٔ `/usr/sbin/nologin` درست است. `deploy` این فصل دستور اجرا می‌کند، پس nologin کار استقرار را می‌شکند. ورود SSH این کاربر با کلید `ed25519` است، نه با رمز، و نه با کلید `ssh-rsa`.

پوشهٔ بکاپ را root نگه می‌دارد. اسکریپت بکاپ فایل خودش حالت `0700` را دوباره اعمال می‌کند.

```bash
sudo install -d -o root -g root -m 0700 /var/backups/files /var/backups/db /root/.backup
```

## Configuration

قرارداد مسیرها را عوض نکنید، وگرنه صفحه‌های بعدی به مسیر خیالی اشاره می‌کنند.

| مسیر | مالک | حالت | محتوا |
| --- | --- | --- | --- |
| `/usr/local/sbin/backup-files.sh` | root:root | 0750 | بکاپ فایل، فقط root |
| `/usr/local/sbin/backup-db.sh` | root:root | 0750 | بکاپ دیتابیس، فقط root |
| `/usr/local/sbin/healthcheck.sh` | root:deploy | 0750 | سلامت، کاربر deploy |
| `/usr/local/sbin/log-cleaner.sh` | root:deploy | 0750 | پاک‌سازی، root یا deploy |
| `/opt/apps/app/bin/deploy.sh` | deploy:deploy | 0750 | استقرار، فقط deploy |
| `/var/backups/files` | root:root | 0700 | آرشیو `tar.gz` |
| `/var/backups/db` | root:root | 0700 | دامپ فشرده |
| `/root/.backup` | root:root | 0700 | فایل رمز با حالت 0600 |
| `/opt/apps/app/releases` | deploy:deploy | 0755 | یک پوشه برای هر tag |
| `/opt/apps/app/current` | deploy:deploy | symlink | انتشار در حال اجرا |

فایل داخل `/etc/cron.d` باید مالک root باشد، برای گروه و بقیه قابل نوشتن نباشد، و نامش فقط حرف و رقم و `_` و `-` باشد. نقطه در نام یعنی cron فایل را نادیده می‌گیرد. `backup-files` درست است. `backup-files.sh` هرگز اجرا نمی‌شود. جزئیات و نمونهٔ timer در صفحهٔ cron است.

قبل از سپردن فایل به زمان‌بند، روی همان سرور نحو را ببینید. این کار اسکریپت را اجرا نمی‌کند:

```bash
bash -n /usr/local/sbin/backup-files.sh
```

اگر `shellcheck` در مخزن تیم نصب است، همان را هم بزنید. دانشنامه نصبش را اجباری نمی‌کند چون بستهٔ پیش‌فرض Ubuntu Server نیست. `bash -n` هست.

## Production Example

یک کار کوچک را از ابتدا تا زمان‌بند این‌طور می‌نشانیم تا ترتیب فصل ملموس شود. اسکریپت واقعی سلامت در صفحهٔ خودش است؛ اینجا فقط ردیف تصمیم‌هاست.

1. اسکریپت را با کاربر درست، نه با root بی‌قید برای کاری که `deploy` باید مالک فایلش باشد، زیر مسیر جدول بالا بگذارید.
2. `bash -n` را بگذرانید.
3. یک‌بار با دست اجرا کنید و خروجی شکست را ببینید. برای سلامت، خاموش کردن آزمایشی سرویس روی VM آزمایشگاهی کافی است. روی `app-1` تولیدی این بازی را نکنید.
4. فقط یکی از این دو را بگذارید: یک فایل در `/etc/cron.d`، یا یک جفت unit سرویس و timer. دومی را `systemctl enable --now` فقط برای timer.
5. فردای همان روز لاگ و، اگر timer است، `systemctl list-timers` را ببینید. سکوت cron به‌تنهایی دلیل موفقیت نیست؛ ممکن است خروجی را دور ریخته باشد چون MTA نصب نیست.

بکاپ فایل و بکاپ دیتابیس را روی یک دقیقه نگذارید. نمونهٔ این فصل: فایل ساعت ۰۳:۱۰ به وقت تهران روی `app-1`، دامپ MySQL ساعت ۰۲:۲۰ و دامپ PostgreSQL ساعت ۰۲:۵۰ روی `db-1`. سلامت هر پنج دقیقه روی `app-1`. پاک‌سازی لاگ شب‌ها ۰۴:۲۰. استقرار بدون زمان‌بند ثابت.

## Security Notes

اسکریپت قابل اجرا با root یک مسیر حمله است اگر گروه یا بقیه بتوانند آن را عوض کنند. بعد از کپی، مالک و حالت را همان جدول بگذارید و فایل را از شاخهٔ خانگی `deploy` اجرا نکنید اگر `deploy` را چند نفر با `sudo` شریک‌اند. تغییر اسکریپت بکاپ باید از مسیر مدیر باشد.

رمز دیتابیس داخل اسکریپت، داخل crontab، و داخل آرگومان فرایند نمی‌آید. فایل حالت `0600` زیر `/root/.backup` است. آرشیو `/etc` اگر روزی مسیر رمز را هم جارو کند، خودش محرمانه است. اسکریپت بکاپ فایل حالت پوشه را `0700` و حالت آرشیو را `0600` می‌گذارد.

`deploy` روی `app-1` حق `sudo` نامحدود ندارد. فقط همان دستورهای `systemctl` که صفحهٔ استقرار فهرست کرده، آن هم با `NOPASSWD` و مسیر کامل `/usr/bin/systemctl`. افزودن `ALL` برای اینکه استقرار گیر نکند، همان root بی‌قید است.

لاگ نباید خط رمز، محتوای `.env`، یا آرگومان کامل `mysqldump` را چاپ کند. `set -x` روی این اسکریپت‌ها در تولید خاموش است چون trace را به journal می‌ریزد.

## Troubleshooting

| نشانه | علت محتمل | کار |
| --- | --- | --- |
| فایل cron را گذاشتید و هیچ اثری نیست | نام فایل نقطه دارد، یا مالک root نیست، یا سرویس cron خاموش است | `systemctl status cron` و نام فایل را با قاعدهٔ run-parts تطبیق دهید |
| دستور در نشست شما هست و در اسکریپت نیست | `PATH` تعاملی با محیط زمان‌بند فرق دارد | مسیر مطلق، یا `PATH` بالای اسکریپت |
| اسکریپت با `sh` خطای نحو می‌دهد | dash دستور Bash را دیده | با `bash` یا با شِبانگ اجرا کنید |
| دو نسخهٔ بکاپ هم‌زمان ساخته شده | هم cron مانده هم timer برای همان واحد | یکی را بردارید. قفل `flock` جلوی خراب شدن را می‌گیرد ولی خطای شبانه را حذف نمی‌کند |
| وضعیت ۰ است ولی فایل بکاپ نیست | اسکریپت وسط راه `exit 0` دارد یا `set -e` خاموش است | صفحهٔ خطا؛ خروج ۰ را فقط آخر کار بگذارید |
| `deploy` نمی‌تواند اسکریپت استقرار را اجرا کند | پوستهٔ nologin، یا مالک فایل root است | `getent passwd deploy` و `ls -l` روی خود اسکریپت |

اگر شکست فقط روی زمان‌بند است و با دست درست است، محیط را مقصر بدانید نه منطق دامپ را. یک خط `logger` یا یک اجرای دستی همان فایل با همان کاربر، فرق را نشان می‌دهد.

## Best Practices

- یک کار، یک زمان‌بند. قبل از افزودن timer، `grep` روی `/etc/cron.d` و `crontab -l` همان کاربر را بزنید.
- اسکریپت را جایی بگذارید که بستهٔ APT جایش را نگیرد. `/usr/local/sbin` برای کار سیستم و `/opt/apps/app/bin` برای کار خود برنامه.
- نسخهٔ نگه داشته‌شده را در خود اسکریپت عدد کنید. هفت نسخه برای فایل و دیتابیس در این فصل قرارداد است، نه یک انتخاب پنهان در cron.
- قبل از پاک کردن هر چیزی، یک اجرای dry-run داشته باشید. پاک‌سازی لاگ پیش‌فرضش همین است.
- خروجی موفق سلامت را ساکت نگه دارید تا نامهٔ cron فقط شکست را بیاورد. موفقیت بکاپ باید یک خط در فایل لاگ داشته باشد، چون سکوت در بکاپ مشکوک است.
- صفحه‌های این فصل را وقتی عوض می‌کنید که مسیر آزمایشگاه یا قرارداد خروج عوض شده باشد. عدد میزبان را در یک اسکریپت «راحت‌تر» نکنید و در بقیه جا نگذارید.
