# مبانی Bash

## مقدمه

اسکریپت شبانه با همان بش اجرا می‌شود که در SSH به شما نشسته است، ولی همان فایل‌های شروع را نمی‌خواند. بیشتر «روی لپ‌تاپ کار می‌کرد»ها از همین فرق می‌آیند: alias و `nvm` و `PATH` شخصی شما داخل cron نیست، و `/bin/sh` روی Ubuntu اصلاً Bash نیست.

این صفحه همان چند قاعده‌ای است که بقیهٔ فصل فرض می‌کند بلديد. مثال‌ها روی `app-1.example.internal` با آدرس `10.10.1.10` و کاربر `deploy` قابل اجرا هستند. هنوز بکاپ و استقرار نیست؛ هدف این است که یک فایل را سه جور اجرا کنید و خروجی متفاوتش را به محیط نسبت دهید، نه به شانس.

نسخهٔ Bash را از خود پوسته بخوانید. دانشنامه شمارهٔ patch اختراع نمی‌کند.

```bash
bash --version
ls -l /bin/sh /usr/bin/sh
```

روی Ubuntu 26.04 و Debian 13،‏ `/bin/sh` به dash اشاره می‌کند. دستورهای این فصل، از جمله `[[`، مخصوص Bash هستند و با `sh script.sh` نباید اجرا شوند.

## مفهوم اصلی

### شل ورود و شل غیرورود

شل ورود (login shell) پوسته‌ای است که argv صفرش با خط تیره شروع می‌شود، یا با `bash -l` صدا شده است. ورود SSH تعاملی همین است. شل غیرورود پوسته‌ای است که از داخل یک پوستهٔ دیگر، یا برای اجرای یک خط دستور، باز می‌شود.

فایل‌هایی که Bash 5 روی Ubuntu می‌خواند:

| نوع اجرا | چه می‌خواند |
| --- | --- |
| ورود تعاملی | `/etc/profile`، بعد اولین فایل موجود از `~/.bash_profile` و `~/.bash_login` و `~/.profile` |
| تعاملی غیرورود | `/etc/bash.bashrc` و بعد `~/.bashrc` |
| غیرتعاملی | هیچ‌کدام، مگر متغیر `BASH_ENV` به فایلی اشاره کند |

روی Ubuntu فایل `~/.profile` پیش‌فرض، اگر پوسته Bash باشد، `~/.bashrc` را هم source می‌کند. به همین خاطر ورود SSH معمولاً aliasهای `~/.bashrc` را هم دارد. این رفتار توزیع است، نه قاعدهٔ اسکریپت.

اسکریپت با شِبانگ، cron، و `ssh app-1 /usr/local/sbin/healthcheck.sh` غیرتعاملی‌اند. alias تعریف‌شده در `~/.bashrc` آنجا وجود ندارد. تابع و `export` نشست شما هم به فرایند فرزند ارث نمی‌رسد مگر همان متغیر را صادر کرده باشید و فرزند از همان نشست آمده باشد. cron اصلاً از نشست شما شروع نمی‌شود.

تشخیص از داخل خود پوسته:

```bash
shopt -q login_shell && printf 'login\n' || printf 'not login\n'
case $- in
  *i*) printf 'interactive\n' ;;
  *) printf 'not interactive\n' ;;
esac
printf '%s\n' "$0"
```

`bash -lc 'shopt -q login_shell'` شل ورود است. `bash -c 'shopt -q login_shell'` نیست. در خروجی، `$0` برای اسکریپت نام فایل است و برای `bash -c` همان `bash`.

اجرای دستور از راه SSH یک شل ورود تعاملی نمی‌سازد. `sshd` دستور را با پوستهٔ کاربر و فلگ خط فرمان اجرا می‌کند. اگر پوستهٔ `deploy` برابر `/bin/bash` باشد، باز هم `~/.bashrc` خوانده نمی‌شود. اگر کسی برای «درست شدن PATH» داخل اسکریپت `source ~/.bashrc` بگذارد، اسکریپت به تنظیم شخصی یک آدم وابسته می‌شود و روی کاربر `ops` رفتار دیگری دارد. این کار را نکنید. `PATH` را بالای خود اسکریپت بنویسید.

### چطور یک اسکریپت اجرا می‌شود

کرنل فایل را با `execve` باز می‌کند. اگر دو بایت اول `#!` باشد، مفسر همان خط را اجرا می‌کند و مسیر اسکریپت را به آن می‌دهد. قرارداد این دانشنامه:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

`env` داخل `PATH` دنبال `bash` می‌گردد. روی Ubuntu هم `/usr/bin/env` و هم `/usr/bin/bash` هستند، پس این شِبانگ با شِبانگ مطلق `/usr/bin/bash` در عمل یکی است، به شرطی که `PATH` زمان اجرا `/usr/bin` را داشته باشد. cron تاریخی گاهی `PATH` را به `/usr/bin:/bin` محدود می‌کند. صفحهٔ [cron](/docs/13-automation/cron) این را روی همین نسخهٔ بسته نشان می‌دهد. بالای اسکریپت یک `PATH` صریح بگذارید تا به آن یادداشت وابسته نمانید.

سه راه اجرا:

| روش | بیت اجرا لازم است؟ | پوستهٔ جدید؟ |
| --- | --- | --- |
| `./script.sh` بعد از `chmod +x` | بله | بله، مفسر شِبانگ |
| `bash script.sh` | خیر، فقط خواندن فایل | بله، همین `bash` |
| `source script.sh` یا `. script.sh` | خیر | خیر، داخل پوستهٔ فعلی |

راه سوم برای اسکریپت تولید ممنوع است. `exit` داخل فایل، نشست SSH شما را می‌بندد. `set -euo pipefail` داخل فایل، رفتار پوستهٔ فعلی را تا آخر نشست عوض می‌کند. `source` فقط برای کتابخانهٔ کوچکی است که خودتان همان لحظه در یک پوستهٔ تعاملی می‌خواهید، نه برای بکاپ.

`chmod +x` بیت اجرا را برای مالک یا گروه یا بقیه روشن می‌کند. خود Bash به این بیت نگاه نمی‌کند وقتی فایل را به‌عنوان آرگومان گرفته است. کرنل نگاه می‌کند وقتی مسیر فایل را مستقیم اجرا می‌کنید. بدون بیت اجرا، `./script.sh` خطای `Permission denied` می‌دهد. با بیت اجرا هم اگر فایل‌سیستم با `noexec` سوار شده باشد، `./script.sh` رد می‌شود و `bash script.sh` هنوز کار می‌کند، چون فایل اجرایی همان `/usr/bin/bash` است. `/tmp` را روی سرور تولیدی `noexec` نگه دارید و اسکریپت عملیات را آنجا نگذارید.

```bash
install -m 0750 -o root -g deploy /dev/null /usr/local/sbin/show-context.sh
# سپس متن اسکریپت را با ویرایشگر در همین مسیر بنویسید، نه با اجرای نسخهٔ خانگی
```

`install` فایل را با مالک و حالت درست می‌سازد. کپی از `/tmp` و فراموش کردن `chown` یعنی `deploy` یا هر کاربر دیگر می‌تواند اسکریپتی را که root هر پنج دقیقه اجرا می‌کند عوض کند.

### PATH

پوسته برای دستوری که اسلش ندارد در فهرست `PATH` می‌گردد و نتیجه را به یاد می‌سپارد. `command -v` محل را نشان می‌دهد. `type` اگر alias یا تابع باشد همان را می‌گوید، و به همین خاطر برای عیب‌یابی اسکریپت از `command -v` استفاده کنید که alias را مبنا قرار نمی‌دهد.

```bash
command -v systemctl
printf '%s\n' "$PATH"
```

نقطه (پوشهٔ جاری) را داخل `PATH` نگذارید. فایلی به نام `ls` در پوشه‌ای که واردش شده‌اید جای دستور واقعی اجرا می‌شود. اسکریپت تولید مسیر ابزار را یا مطلق می‌نویسد یا `PATH` را در خط‌های اول به مقدار شناخته‌شده تنظیم می‌کند:

```bash
export PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
```

این فهرست `/snap/bin` و مسیر `npm` نصب‌شده در خانهٔ کاربر را عمداً ندارد. اگر استقرار به `npm` نیاز دارد، صفحهٔ استقرار همان را جداگانه چک می‌کند، نه اینکه `PATH` همهٔ اسکریپت‌های root پهن شود.

### وضعیت خروج

هر فرایند یک عدد بین ۰ و ۲۵۵ برمی‌گرداند. صفر یعنی موفقیت. غیرصفر یعنی شکست، ولی عددها قرارداد خود برنامه هستند نه یک جدول جهانی، با چند استثنای پوسته و کرنل:

| کد | معنی رایج |
| --- | --- |
| 0 | موفق |
| 1 | خطای عمومی، انتخاب خود اسکریپت |
| 2 | در ابزارهای POSIX اغلب خطای usage؛ در سلامت این فصل یعنی سرویس down |
| 126 | فایل پیدا شد ولی قابل اجرا نبود |
| 127 | دستور پیدا نشد |
| 128 به‌علاوهٔ شمارهٔ سیگنال | فرایند با سیگنال مرده است. ۱۴۳ یعنی SIGTERM |

`$?` وضعیت آخرین دستور است و با دستور بعدی پاک می‌شود. اگر می‌خواهید نگهش دارید، همان لحظه در متغیر بریزید. آخرین دستور اسکریپت، اگر `exit` صریح نباشد، وضعیت کل اسکریپت است. برای بکاپ این ابهام خطرناک است: یک `echo` موفق در خط آخر، شکست `tar` را صفر می‌کند اگر `set -e` خاموش باشد. صفحهٔ [خطا و لاگ](/docs/13-automation/error-handling-logging) این را جزءبه‌جزء باز می‌کند. اینجا فقط صریح بنویسید:

```bash
exit 0
```

لوله بدون `pipefail` وضعیت آخرین دستور لوله را برمی‌گرداند. `false | true` موفق است. به همین خاطر شِبانگ این فصل تنها نیست و خط `set -euo pipefail` همراهش است.

### echo در برابر printf

`echo` در Bash، در dash، و در `/bin/echo` یک دستور نیست. Bash اگر آرگومان `-n` ببیند newline را حذف می‌کند. اگر `xpg_echo` روشن باشد بک‌اسلش را تفسیر می‌کند و پیش‌فرض Ubuntu خاموش است. dash رفتار دیگری دارد. داده‌ای که از فایل یا از کاربر می‌آید ممکن است خودش با `-n` شروع شود و `echo` آن را فلگ حساب کند.

`printf` فرمت ثابت دارد و در Bash و dash یکی است. برای یک خط متن:

```bash
printf '%s\n' "$message"
```

برای وضعیت و عدد:

```bash
printf 'status=%s path=%s\n' "$?" "$path"
```

`%s` مقدار را خام می‌نویسد و فلگ حسابش نمی‌کند. `%b` و `%d` را وقتی به کار ببرید که عمداً تفسیر یا عدد می‌خواهید. در اسکریپت‌های این فصل خط لاگ با `printf` ساخته می‌شود، نه با `echo`.

## چرا استفاده می‌شود؟

بدون این پنج موضوع، بقیهٔ فصل قابل اعتماد نیست. شرط و حلقه را می‌شود از روی نمونه تقلید کرد. محیط اجرا را نه. شیفت شب باید بداند چرا همان فایل با `bash script.sh` کار می‌کند، با `./script.sh` می‌گوید Permission denied، و داخل cron می‌گوید `npm: not found`. این‌ها سه اشکال مختلف‌اند: بیت اجرا، شِبانگ، و `PATH`.

`printf` هم از جنس همان سخت‌گیری است. یک پیام سلامت که با `-n` شروع شود و با `echo` چاپ شود، نامهٔ cron را خالی می‌کند و فکر می‌کنید سرور سالم است.

## Architecture

```text
cron یا ssh یا ترمینال
        │
        ▼
پوستهٔ والد (اغلب dash اگر SHELL پیش‌فرض cron باشد)
        │  فقط خط فرمان را اجرا می‌کند
        ▼
کرنل، شِبانگ #!/usr/bin/env bash
        │
        ▼
/usr/bin/env  →  /usr/bin/bash
        │
        ├── PATH صریح بالای اسکریپت
        ├── نمی‌خواند: ~/.bashrc و ~/.profile
        └── وضعیت خروج به زمان‌بند
```

`env` خودش یک اجراست. اگر روزی `PATH` آن‌قدر خالی باشد که `/usr/bin` داخلش نباشد، شِبانگ `env` هم می‌شکند و پیام هسته این است: `bad interpreter: No such file or directory`. درمان، پر کردن `PATH` در فایل crontab یا timer است، نه حذف شِبانگ. واحد systemd می‌تواند `Environment=PATH=...` داشته باشد. هر دو در صفحهٔ cron هستند.

## Installation

بستهٔ `bash` روی Ubuntu Server و Debian پایه است. نسخه را یادداشت نکنید؛ هر بار از دستور بخوانید. بستهٔ dash را برندارید تا `/bin/sh` به Bash وصل شود. اسکریپت‌های maintainer بسته‌ها فرض می‌کنند `/bin/sh` پوستهٔ POSIX کوچک است. عوض کردنش به Bash، بوت و نگهداری بسته را در معرض تفاوت‌های Bash می‌گذارد.

```bash
dpkg -s bash | awk '/^Package:|^Version:|^Status:/{print}'
command -v bash
command -v printf
```

`printf` هم builtin پوسته است و هم `/usr/bin/printf`. در اسکریپت، builtin استفاده می‌شود چون پوسته قبل از `PATH` سراغ builtin می‌رود. نیازی به نصب جدا نیست.

کاربر `deploy` برای تمرین این صفحه باید بتواند یک فایل در خانهٔ خودش بسازد. اسکریپت تولیدی را در خانه نگذارید.

```bash
sudo install -d -o deploy -g deploy -m 0755 /home/deploy/bin
```

## Configuration

چیزی به‌نام کانفیگ سراسری Bash برای اسکریپت تولید تنظیم نکنید. این‌ها را عمداً دست نزنید:

- `BASH_ENV` را در واحد systemd یا در crontab برای همهٔ کارها نگذارید. یک فایل پنهان دوباره به همهٔ اسکریپت‌ها source می‌شود و `set -e` را غیرقابل پیش‌بینی می‌کند.
- alias در `/etc/bash.bashrc` برای «کوتاه شدن دستور سرور» به اسکریپت نمی‌رسد، ولی همکار را گمراه می‌کند که فکر کند `ll` یک دستور واقعی است.
- `set -o xtrace` را در `/etc/bash.bashrc` روشن نکنید. هر پوستهٔ تعاملی دستورها را تکرار می‌کند و اگر کسی متغیر رمز را در خط فرمان گسترش دهد، روی صفحه می‌ماند.

تنها تنظیم سطح سیستم که این صفحه لازم دارد منطقهٔ زمانی است، چون نمایش ساعت در تمرین بعدی با `date` خوانده می‌شود. همان `Asia/Tehran` آزمایشگاه است.

اگر `~/.bashrc` کاربر `ops` را برای کار تعاملی شخصی‌سازی می‌کنید، خروجی دارای متن را در حالت غیرتعاملی خاموش نگه دارید. فایل پیش‌فرض Ubuntu این محافظ را دارد: اگر `$-` حرف `i` نداشت، برمی‌گردد. پاک کردنش باعث می‌شود ابزارهایی که `scp` یا `bash -c` می‌زنند خروجی زباله بگیرند و کپی فایل بشکند.

## Production Example

اسکریپت زیر فقط زمینهٔ اجرا را چاپ می‌کند. روی `app-1` بگذاریدش تا فرق سه روش اجرا را ببینید. کاری با دیسک و سرویس ندارد.

```bash
#!/usr/bin/env bash
set -euo pipefail

export PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

printf 'bash_version=%s\n' "${BASH_VERSION}"
printf 'argv0=%s\n' "$0"
printf 'uid=%s user=%s\n' "$(id -u)" "$(id -un)"
printf 'path=%s\n' "${PATH}"

case $- in
  *i*) printf 'interactive=yes\n' ;;
  *) printf 'interactive=no\n' ;;
esac

if shopt -q login_shell; then
  printf 'login_shell=yes\n'
else
  printf 'login_shell=no\n'
fi

if /bin/true; then
  printf 'true_status=0\n'
fi

false_status=0
/bin/false || false_status=$?
printf 'false_status=%s\n' "${false_status}"

message='-n this must be visible'
printf 'printf_message=%s\n' "${message}"

exit 0
```

نصب و سه اجرا، با کاربر `deploy`:

```bash
sudo install -m 0750 -o root -g deploy /dev/null /usr/local/sbin/show-context.sh
sudoedit /usr/local/sbin/show-context.sh
bash -n /usr/local/sbin/show-context.sh
sudo -u deploy /usr/local/sbin/show-context.sh
sudo -u deploy bash /usr/local/sbin/show-context.sh
```

هر دو باید `interactive=no` و `login_shell=no` بدهند و `false_status=1` باشد. خط `printf_message` باید با `-n` دیده شود. اگر کسی همان متن را با `echo` چاپ کند، `-n` خورده می‌شود و بقیهٔ متن بدون پیشوند یا حتی حذف‌شده به نظر می‌رسد.

اجرای ورود را فقط برای مقایسه بزنید، نه در cron:

```bash
sudo -u deploy bash -lc '/usr/local/sbin/show-context.sh'
```

این یکی `login_shell=yes` است، چون `-l` شل ورود می‌سازد و آن پوسته بعداً اسکریپت را اجرا می‌کند. خود اسکریپت هنوز غیرتعاملی است؛ `login_shell` مال همان فرایند Bash اسکریپت است و `-l` به فرزند ارث نمی‌رسد مگر خود فرزند هم ورود باشد. انتظار درست این اجرا: `login_shell=no` باز هم، چون شِبانگ یک Bash تازهٔ غیرورود است. اگر خروجی خلاف این بود، یعنی فایل را source کرده‌اید نه اجرا.

یک بار هم بیت اجرا را بردارید تا پیام هسته را ببینید، بعد برگردانید:

```bash
sudo chmod 0640 /usr/local/sbin/show-context.sh
sudo -u deploy /usr/local/sbin/show-context.sh
sudo chmod 0750 /usr/local/sbin/show-context.sh
```

خطا `Permission denied` است، نه خطای نحو. `bash -n` هنوز کار می‌کند چون فقط فایل را می‌خواند.

## Security Notes

بیت اجرا بدون مالک درست، مجوز حمله است. اگر `deploy` بتواند `/usr/local/sbin/show-context.sh` را بنویسد و cron آن را با root اجرا کند، محتوای فایل فردا هر دستوری است که `deploy` بخواهد. جدول مالک صفحهٔ [نقشه](/docs/13-automation) را برای اسکریپت واقعی رعایت کنید. تمرین این صفحه گروه `deploy` را فقط اجراکننده می‌کند، نه نویسنده.

`printf '%s'` را به `printf "$message"` ترجیح دهید. اگر متن پیام علامت درصد داشته باشد، شکل دوم آن را فرمت حساب می‌کند و یا خطا می‌دهد یا مقدار اضافه از آرگومان بعدی می‌دزدد. در اسکریپت سلامت، نام mount که کاربر یا نصب‌کننده ساخته می‌تواند درصد داشته باشد.

خروجی این اسکریپت نمونه رمز ندارد. اسکریپت واقعی نباید برای دیباگ کل محیط را با `export -p` چاپ کند. `PGPASSWORD` و هر متغیر شبیه آن اگر در محیط باشد در آن خروجی هست.

## Troubleshooting

| نشانه | علت | کار |
| --- | --- | --- |
| `bad interpreter: No such file or directory` و فایل هست | شِبانگ به مفسری اشاره می‌کند که نیست، یا انتهای خط ویندوزی است | `head -1` فایل را ببینید. `sed -i 's/\r$//'` فقط اگر `file` گفت CRLF |
| `Permission denied` با `./` | بیت اجرا نیست، یا `noexec` | `ls -l` و `findmnt -no OPTIONS -T .` |
| `syntax error` نزدیک `[[` وقتی با `sh` اجرا می‌کنید | dash | `bash script.sh` |
| `command not found` فقط در cron | `PATH` | `PATH` را داخل فایل cron و بالای اسکریپت بگذارید |
| alias در اسکریپت نیست | غیرتعاملی | دستور واقعی را بنویسید. alias را به اسکریپت راه ندهید |
| وضعیت اسکریپت ۰ است در حالی که دستور وسط شکست | `set -e` نیست و یک دستور موفق بعد از شکست آمده | صفحهٔ خطا |
| `printf` فقط `bash_version=` چاپ می‌کند و می‌میرد | `set -u` و متغیر خالی بدون پیش‌فرض | متغیر را مقدار اولیه بدهید. نحو پیش‌فرض در صفحهٔ متغیر است |

`bash -n` خطای نحو را می‌گیرد و خطای منطقی را نه. اسکریپتی که `exit 0` را خیلی زود زده از `bash -n` رد می‌شود و بکاپ را انجام نمی‌دهد.

## Best Practices

- خط اول شِبانگ، خط دوم `set -euo pipefail`. توضیح انگلیسی را بعد از این دو بگذارید تا کسی که فقط دو خط اول را می‌خواند محافظ را ببیند.
- اسکریپت تولید را source نکنید.
- `echo` را برای متن متغیر به کار نبرید. `printf '%s\n'` کوتاه‌تر از عیب‌یابی نامهٔ cron خالی نیست، ولی ارزان‌تر است.
- `PATH` را داخل اسکریپت بنویسید حتی اگر crontab هم `PATH` دارد. اجرای دستی و اجرای زمان‌بند باید یکی باشند.
- وضعیت را صریح `exit` کنید. برای ابزار این فصل، ۰ موفقیت است، ۱ خطای کار، و ۲ فقط جایی که صفحهٔ همان اسکریپت معنی جدا نوشته است.
- `/bin/sh` را به Bash عوض نکنید. شِبانگ هر فایل را جدا درست کنید.
- تمرین `show-context.sh` را بعد از اینکه فرق سه اجرا را دیدید از سرور تولیدی بردارید تا کنار اسکریپت‌های واقعی نماند.
