# فهرست کنترل دسترسی ACL

## مقدمه

مجوز کلاسیک سه جایگاه دارد: مالک، یک گروه، دیگران. وقتی `nima` باید لاگ `/opt/apps/portal` را بخواند و نباید عضو گروه `deploy` شود، جایگاه چهارمی لازم است. فهرست کنترل دسترسی (ACL) همان جایگاه است. این صفحه `setfacl` و `getfacl`، ماسک مؤثر، ACL پیش‌فرض روی دایرکتوری، و بکاپ با `rsync -A` را پوشش می‌دهد. اگر مدل `rwx` هنوز مبهم است اول [مجوز فایل](/docs/01-linux/permissions) را بخوانید. ACL جای گروه درست و جای `sudo` را نمی‌گیرد. اگر `nima` باید سرویس را ری‌استارت کند، کارش قانون [sudo](/docs/01-linux/sudo) است نه یک ACE نوشتن روی باینری.

ابزار در بستهٔ `acl` است. فایل‌سیستم باید ACL را بفهمد. ext4 و XFS روی Ubuntu 26.04 این قابلیت را پیش‌فرض دارند و لازم نیست کلمهٔ `acl` را به fstab اضافه کنید. vfat پارتیشن EFI این قابلیت را ندارد. ACL را روی `/boot/efi` امتحان نکنید.

## مفهوم اصلی

هر ورودی ACL یک نوع و یک نام و یک اجازه است. نوع‌های روزمره: `user` برای یک کاربر نام‌دار، `group` برای یک گروه نام‌دار، و ورودی‌های `user::` و `group::` و `other::` که همان سه بیت کلاسیک‌اند. دو دونقطهٔ پشت سر هم یعنی «مالک فایل» نه یک کاربر با نام خالی. در دستور، `u:nima:rX` کاربر نام‌دار است و `u::rwx` مالک.

حرف بزرگ `X` یعنی اجرا فقط اگر فایل از قبل برای کسی اجرایی بوده یا موضوع دایرکتوری است. حرف کوچک `x` اجرا را حتی روی فایل متنی هم می‌گذارد. برای دادن عبور روی دایرکتوری و اجرا نشدن فایل‌های متنی، در قانون بازگشتی از `X` استفاده کنید.

ماسک (`mask`) سقف حق ورودی‌های نام‌دار و حق گروه کلاسیک است. حق مؤثر برابر است با اشتراکِ حق ورودی و ماسک. اگر به `nima` حق `rwx` بدهید و ماسک `r--` باشد، `getfacl` کنار خط او `#effective:r--` نشان می‌دهد. هسته همان حق مؤثر را اجرا می‌کند نه عددی که در ورودی نوشته‌اید. `ls` فقط یک تقریب نشان می‌دهد و اگر علامت `+` ته مجوز باشد یعنی ACL هست. حقیقت را `getfacl` می‌گوید.

`chmod` ماسک را از نو می‌نویسد. بعد از `setfacl` اگر کسی `chmod 750` بزند، ممکن است حق مؤثر `nima` بی‌صدا کوتاه شود در حالی که خط `user:nima:rwx` هنوز در فهرست مانده. این اولین چیزی است که در عیب‌یابی نگاه می‌کنیم.

ACL پیش‌فرض (`default`) روی دایرکتوری است نه روی فایل. فایل و زیردایرکتوری تازه‌ساخته از آن کپی برمی‌دارند. فایل‌هایی که از قبل آن‌جا هستند عوض نمی‌شوند. پیش‌فرض با umask تعامل دارد. اگر بعد از تنظیم پیش‌فرض، فایل تازه حق نوشتن گروه را ندارد، اول یک فایل آزمایشی بسازید و `getfacl` بگیرید و پیش‌فرض را اصلاح کنید. حدس نزنید که «دیگر umask مهم نیست». روی لینوکس وقتی ACL پیش‌فرض هست، حالت درخواستی برنامه هنوز با ورودی‌های پیش‌فرض برش می‌خورد و نتیجه را باید با چشم دید.

بکاپ معمولی ACL را دور می‌ریزد. `cp` بدون `--preserve=xattr` یا بدون `-a`، و `rsync` بدون `-A`، فایل را با مجوز کلاسیک می‌سازند و فردا `nima` دیگر دسترسی ندارد. بازیابی‌ای که این را امتحان نکرده باشید بکاپ نیست.

## چرا استفاده می‌شود؟

گروه `deploy` را به انسان دادن، او را هم‌حق سرویس می‌کند. گروه تازه برای هر استثنای یک‌نفره هم انفجار گروه می‌سازد. ACL همان یک دایرکتوری را برای همان یک کاربر باز می‌کند و بقیهٔ دیسک را دست نمی‌زند. هزینهٔ این دقت دو چیز است: `ls` دیگر کافی نیست، و `chmod` بعدی می‌تواند ماسک را خراب کند. تیمی که این دو را در عیب‌یابی جا بیندازد، ACL را «غیرقابل اعتماد» می‌بیند در حالی که ابزار را نصفه خوانده.

برای پوشهٔ همکاری پایدار، ترکیب setgid صفحهٔ مجوز و ACL پیش‌فرض این صفحه از `2777` پایدارتر است. setgid گروه مالک فایل تازه را درست می‌کند. ACL پیش‌فرض حق نوشتن هم‌گروهی را حتی وقتی umask آدم `022` است نگه می‌دارد، به شرطی که خود پیش‌فرض را بعد از یک تست واقعی دیده باشید.

## Architecture

```text
getfacl /opt/apps/portal
  user::    حق مالک
  user:nima حق نام‌دار
  group::   حق گروه مالک
  mask::    سقف حق نام‌دار و گروه
  other::   دیگران
  default:  فقط اگر دایرکتوری باشد و برای شیء بعدی کپی شود

بکاپ
  rsync -aA     مجوز + مالک + ACL
  rsync -a      ACL می‌افتد، مجوز کلاسیک می‌ماند
  getfacl -R    متن قابل بازیابی با setfacl --restore
```

حق مؤثر `nima` برای رسیدن به یک فایل، اجتماع ACL آن فایل به‌تنهایی نیست. باید روی هر دایرکتوری مسیر حداقل عبور داشته باشد. `setfacl` روی خود فایل بدون `x` روی `/opt` و `/opt/apps` و `/opt/apps/portal` یعنی هنوز Permission denied. `namei -l` صفحهٔ مجوز مسیر کلاسیک را نشان می‌دهد. اگر آن حلقه‌ها `x` ندارند، ACL فایل را دست نزنید تا مسیر باز شود.

## Installation

```bash
sudo apt install acl
dpkg -l acl | awk '/^ii/ {print $2, $3}'
```

اگر `getfacl` گفت عملیات پشتیبانی نمی‌شود:

```text
getfacl: /boot/efi: Operation not supported
```

آن مسیر vfat است یا با `noacl` سوار شده. `findmnt -no FSTYPE,OPTIONS /boot/efi` را ببینید. برای `/opt` روی ext4 یا XFS این پیام یعنی فایل‌سیستم غیرعادی است نه نبودن بسته. `mount` را از صفحهٔ فایل‌سیستم بررسی کنید و سراغ فلگ عجیب نروید.

یک کاربر آزمایش را اگر از صفحهٔ کاربر نساخته‌اید بسازید. این‌جا فرض می‌کنیم `nima` حساب انسانی است و عضو `deploy` نیست:

```bash
id nima
getent group deploy
```

`nima` نباید در خروجی گروه `deploy` باشد.

## Configuration

دادن عبور و خواندن به `nima` روی درخت کد، بدون حق نوشتن:

```bash
sudo setfacl -m u:nima:rX /opt/apps/portal
sudo setfacl -R -m u:nima:rX /opt/apps/portal
sudo getfacl /opt/apps/portal
```

دستور اول فقط خود دایرکتوری است. دستور دوم بازگشتی است و فایل‌های فعلی را هم شامل می‌شود. هیچ‌کدام به‌تنهایی فایل فردا را پوشش نمی‌دهند. برای فایل فردا ACL پیش‌فرض لازم است:

```bash
sudo setfacl -d -m u:nima:rX /opt/apps/portal
sudo getfacl /opt/apps/portal
```

خروجی سالم دو بخش دارد. بخش دسترسی و بخش default. شکل خلاصه:

```text
# file: opt/apps/portal
# owner: root
# group: deploy
user::rwx
user:nima:r-x
group::r-x
mask::r-x
other::---
default:user::rwx
default:user:nima:r-x
default:group::r-x
default:mask::r-x
default:other::---
```

اگر `#effective:` دیدید، ماسک حق را بریده. نمونهٔ خراب:

```text
user:nima:rwx        #effective:r--
mask::r--
```

اصلاح ماسک، بدون پاک کردن ورودی کاربر:

```bash
sudo setfacl -m m:rX /opt/apps/portal
sudo getfacl -c /opt/apps/portal
```

`-c` کامنت را کوتاه می‌کند و برای خواندن در شیفت راحت‌تر است. حق مؤثر را بعد از هر `chmod` دوباره ببینید.

آزمایش ماسک با همان قدمی که معمولاً حادثه می‌سازد:

```bash
sudo setfacl -m u:nima:rwx /opt/apps/portal
sudo chmod 0750 /opt/apps/portal
sudo getfacl -c /opt/apps/portal
```

اگر حق مؤثر از `rwx` به `r-x` برگشت، `chmod` ماسک را با بیت گروه کلاسیک یکی کرده است. این رفتار هسته است نه باگ `setfacl`. یا دیگر بعد از ACL از `chmod` عددی استفاده نکنید، یا بلافاصله ماسک را برگردانید. برای عوض کردن بیت کلاسیک وقتی ACL دارید، خود `setfacl` امن‌تر است:

```bash
sudo setfacl -m u::rwx,g::r-x,o::--- /opt/apps/portal
```

برداشتن یک ورودی، بدون پاک کردن همه:

```bash
sudo setfacl -x u:nima /opt/apps/portal
```

برداشتن پیش‌فرض همان کاربر:

```bash
sudo setfacl -x d:u:nima /opt/apps/portal
```

پاک کردن همهٔ ACL نام‌دار و برگشت به مجوز کلاسیک:

```bash
sudo setfacl -b /opt/apps/portal
```

`-b` را بازگشتی نزنید تا وقتی `getfacl -R` را ذخیره نکرده‌اید. برگشت ندارد.

پوشهٔ همکاری `/var/ops/shared` که صفحهٔ مجوز با `2770` ساخته، این پیش‌فرض را می‌گیرد تا فایل تازه برای گروه `opsdata` نوشتنی بماند:

```bash
sudo setfacl -m g:opsdata:rwx /var/ops/shared
sudo setfacl -d -m g:opsdata:rwx /var/ops/shared
sudo setfacl -d -m o::--- /var/ops/shared
sudo -u ops touch /var/ops/shared/acl-test
sudo getfacl -c /var/ops/shared/acl-test
rm /var/ops/shared/acl-test
```

فایل تازه باید یک خط `group:opsdata:rw-` یا حق مؤثر معادل داشته باشد. اگر فقط `group::` دیدید و نوشتن نبود، پیش‌فرض اعمال نشده یا umask و حالت درخواستی `touch` حق را بریده‌اند. یک بار پیش‌فرض دایرکتوری را با `getfacl` ببینید. اگر بخش `default:` اصلاً نیست، دستور `-d` روی مسیر اشتباه رفته است.

## Production Example

`nima` باید لاگ فایل برنامه را بخواند و نباید کد را عوض کند. لاگ اگر به journal می‌رود، او به گروه `systemd-journal` یا به دستور `journalctl` از راه sudo نیاز دارد نه به ACL. این مثال برای وقتی است که برنامه واقعاً فایل زیر `/var/lib/portal/app.log` می‌نویسد.

```bash
sudo install -d -o deploy -g deploy -m 0750 /var/lib/portal
sudo install -o deploy -g deploy -m 0640 /dev/null /var/lib/portal/app.log
sudo setfacl -m u:nima:rx /var/lib/portal
sudo setfacl -m u:nima:r /var/lib/portal/app.log
sudo -u nima head -n 1 /var/lib/portal/app.log
```

`head` باید با حساب `nima` بدون sudo کار کند. اگر Permission denied داد، `sudo -u nima namei -l /var/lib/portal/app.log` را ببینید. اغلب `/var/lib` برای دیگران عبور دارد و حلقهٔ `/var/lib/portal` ندارد. ACL روی دایرکتوری باید `x` داشته باشد. `r` تنها روی دایرکتوری فهرست نام را می‌دهد نه باز کردن فایلی که نامش را می‌دانید. در عمل هر دو را با `rx` بدهید تا `ls` هم کار کند، مگر سیاست شما پنهان کردن نام فایل‌های کناری باشد. در آن حالت فقط `x` روی دایرکتوری و `r` روی همان یک فایل.

بکاپ با حفظ ACL. اسلش ته مبدأ یعنی محتوای پوشه، نه خود پوشهٔ تودرتو. مقصد را قبل از `--delete` با `ls` ببینید.

```bash
sudo install -d -o root -g root -m 0750 /var/backups/portal-acl
sudo rsync -aA /var/lib/portal/ /var/backups/portal-acl/
sudo getfacl -c /var/backups/portal-acl/app.log
```

باید همان خط `user:nima:r--` را ببینید. مقایسه با بکاپ غلط:

```bash
sudo rsync -a /var/lib/portal/ /var/backups/portal-noacl/
sudo getfacl -c /var/backups/portal-noacl/app.log
```

در مقصد دوم نباید ورودی `user:nima` باشد. اگر هست، یا `-A` جایی مانده یا مقصد از قبل ACL داشته. این تست را یک بار روی آزمایشگاه انجام دهید تا معنی فلگ را با چشم دیده باشید. بعد پوشهٔ `portal-noacl` را پاک کنید تا کسی آن را با بکاپ رسمی عوض نگیرد.

رونوشت متنی برای وقتی rsync در کار نیست، مثلاً می‌خواهید فقط ACL را روی درختی که فایل‌هایش را جدا کپی کرده‌اید برگردانید:

```bash
sudo getfacl -R /var/lib/portal > /var/backups/portal.acl
sudo chmod 0600 /var/backups/portal.acl
```

بازیابی:

```bash
sudo setfacl --restore=/var/backups/portal.acl
```

فایل متن مسیر کامل را داخل خودش دارد. اگر درخت را به مسیر دیگری منتقل کرده‌اید، restore یا خطا می‌دهد یا روی مسیر قدیمی می‌نویسد. قبل از restore چند خط اول فایل را بخوانید. این فایل رمز نیست ولی نقشهٔ دسترسی سرور است. `0600` بماند.

`tar` پیش‌فرض GNU روی Ubuntu با `--acls` این فراداده را نگه می‌دارد. بدون آن فلگ، آرشیو ACL را ندارد. اگر بکاپ سازمانی فقط `tar -czf` است، فرض کنید ACL رفته مگر خلافش را با یک بازیابی آزمایشی ثابت کرده باشید. دستور معادل:

```bash
sudo tar --acls -czf /var/backups/portal-acl.tar.gz -C /var/lib portal
```

بازیابی آزمایشی را در پوشهٔ خالی انجام دهید نه روی درخت زنده:

```bash
sudo mkdir -p /var/backups/restore-test
sudo tar --acls -xzf /var/backups/portal-acl.tar.gz -C /var/backups/restore-test
sudo getfacl -c /var/backups/restore-test/portal/app.log
```

## Security Notes

- ACL نوشتن برای یک انسان روی کدی که سرویس اجرا می‌کند، برابر است با عوض کردن برنامه در ری‌استارت بعدی. به `nima` روی `/opt/apps/portal` حداکثر `rX` بدهید.
- `setfacl -m o::rwx` و `setfacl -m m::rwx` برای «ببینیم درست شد» همان `777` است با شکل مودب‌تر. ماسک را به اندازهٔ نیاز بالا ببرید نه تا سقف.
- `setfacl -b -R` روی `/` یا روی `/home` دسترسی‌های استثنا را پاک می‌کند و بعضی سرویس‌ها را می‌خواباند. مسیر را محدود کنید.
- فایل `getfacl -R` را جهان‌خوانا نکنید. فهرست کاربرانی که به لاگ یا خانه دسترسی دارند اطلاعات عملیاتی است.
- rsync با `-A` و بدون فهمیدن مقصد، ACL را روی سروری کپی می‌کند که شاید کاربر `nima` آنجا uid دیگری داشته باشد. ACL با نام کاربر ذخیره می‌شود و getfacl نام را نشان می‌دهد، ولی اگر باینری فقط uid نگه داشته باشد و نام در مقصد نباشد، ورودی به عدد تبدیل می‌شود و به آدم دیگری می‌چسبد. بعد از بازیابی روی سرور دوم `getfacl` باید نام `nima` را نشان بدهد نه یک uid تنها را.
- ACL جایگزین `nosuid` و `noexec` نیست. کسی که `rwx` روی یک دایرکتوری داده دارد همچنان نمی‌تواند از دیسک `noexec` اجرا کند، و برعکس `noexec` جلوی خواندن راز را نمی‌گیرد.

## Troubleshooting

| نشانه | علت محتمل | کار |
| --- | --- | --- |
| `setfacl: Operation not supported` | فایل‌سیستم ACL ندارد، اغلب vfat | `findmnt` و مسیر دیگری انتخاب کنید |
| `getfacl` حق را نشان می‌دهد، برنامه Permission denied | حق مؤثر بریده یا یک دایرکتوری مسیر `x` ندارد | خط `#effective` و `namei -l` |
| بعد از `chmod` دسترسی `nima` رفته | ماسک از نو حساب شده | `getfacl` و `setfacl -m m:rX` |
| فایل تازه ACL ندارد | فقط روی فایل‌های موجود `-m` زده‌اید | `setfacl -d` روی دایرکتوری |
| بکاپ فردا ACL ندارد | rsync بدون `-A` یا tar بدون `--acls` | تست getfacl روی مقصد |
| `setfacl: No such file or directory` موقع restore | مسیر داخل فایل acl با دیسک یکی نیست | چند خط اول `/var/backups/portal.acl` |
| `ls` علامت `+` ندارد ولی دیروز داشتید | ACL پاک شده یا روی لینک نگاه می‌کنید | `getfacl` روی مسیر واقعی نه لینک بی‌فلگ |

اگر `setfacl` گفت کاربر وجود ندارد، `id nima` را روی همان سرور بزنید. ACL نام را در لحظهٔ دستور به uid تبدیل می‌کند. ساختن کاربر بعد از setfacl، ورودی قدیمی را به او وصل نمی‌کند.

ابزار `getfacl` روی لینک نمادین پیش‌فرض خود لینک را دنبال می‌کند. اگر رفتار عجیب دیدید مسیر را با `readlink -f` یکی کنید تا دو مسیر مختلف را تنظیم نکرده باشید.

## Best Practices

- اول گروه را درست کنید. ACL برای استثناست نه برای هر دسترسی.
- بعد از `setfacl` یک بار با همان کاربر واقعی، نه با روت، فایل را بخوانید. روت همیشه موفق است و تست روت بی‌معنی است.
- `chmod` عددی را بعد از ACL عادت نکنید. اگر مجبورید، همان لحظه `getfacl` و ماسک را ببینید.
- پیش‌فرض دایرکتوری را برای درختی بگذارید که فایل تازه می‌گیرد. بازگشتی تنها روی وضع امروز کافی نیست.
- بکاپ رسمی `rsync -aA` است. یک بار در سال یک فایل را در پوشهٔ خالی برگردانید و `getfacl` بگیرید.
- روی EFI و هر vfat وقت صرف ACL نکنید. آنجا نمی‌نشیند.
