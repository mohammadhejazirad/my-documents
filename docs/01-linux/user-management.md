# مدیریت کاربر و گروه

## مقدمه

هر فرآیند روی سرور با یک uid اجرا می‌شود. اگر آن uid صفر باشد، باگ برنامه برابر است با در اختیار گرفتن سیستم. این صفحه دو حساب استاندارد آزمایشگاه را می‌سازد و بقیهٔ حساب‌ها را با همان قاعده اضافه یا تعطیل می‌کند. `ops` انسان است، پوستهٔ تعاملی دارد، و عضو گروه `sudo` است. `deploy` سرویس را اجرا می‌کند، پوستهٔ تعاملی ندارد، و عضو `sudo` نیست. ساخت یونیتی که با `deploy` بالا بیاید در [مدیریت سرویس](/docs/01-linux/service-management) است. معنی عددی مجوز خانهٔ این کاربرها در [مجوز فایل](/docs/01-linux/permissions) است.

ابزار این صفحه `useradd` و `usermod` و `groupadd` و `chage` است. ویرایش مستقیم `/etc/passwd` با یک ویرایشگر معمولی لازم نیست و اگر همزمان خود ابزار هم فایل را بنویسد خط را نصف می‌کند. اگر روزی مجبور شدید فایل را دستی باز کنید، `sudo vipw` و `sudo vigr` قفل را رعایت می‌کنند. مسیر عادی همان دستورهاست.

Ubuntu و Debian در این دستورها یکی‌اند. فرق عملی این است که نصب‌کنندهٔ Ubuntu کاربر اول را عضو گروه `sudo` می‌کند و روت را بدون رمز ورود می‌گذارد. نصب‌کنندهٔ Debian ممکن است اول رمز روت بپرسد. در هر دو حال، ورود SSH روت را باز نمی‌کنیم و کار مدیر با `sudo` است. خود قانون sudo در صفحهٔ [sudo](/docs/01-linux/sudo) نوشته می‌شود.

## مفهوم اصلی

سه فایل حقیقت حساب‌اند. `/etc/passwd` نام، uid، gid اصلی، خانه، و پوسته را دارد و جهان‌خواناست. رمز این‌جا نیست. `/etc/shadow` رمز هش‌شده، قفل، و تاریخ انقضا را دارد و فقط روت می‌خواند. `/etc/group` اعضای گروه را دارد. گروه اضافی کاربر در فیلد چهارم `/etc/group` است نه در `/etc/passwd`. به همین دلیل `usermod -G` بدون `-a` خطرناک است: فهرست گروه اضافی را جایگزین می‌کند و عضویت `sudo` را برمی‌دارد.

بازهٔ uid در `/etc/login.defs` است. کاربر سیستم معمولاً زیر ۱۰۰۰ است و کاربر انسان از ۱۰۰۰ به بالا. `useradd --system` از بازهٔ سیستم برمی‌دارد. `deploy` باید سیستم باشد تا در فهرست انسان‌ها و در سیاست رمز انسان‌ها قاطی نشود. مشخص کردن uid با دست فقط وقتی درست است که چند سرور باید یک عدد مشترک داشته باشند، مثلاً برای NFS. در آزمایشگاه بگذارید ابزار عدد را انتخاب کند و بعد با `id` همان عدد را یادداشت کنید.

پوستهٔ `/usr/sbin/nologin` ورود تعاملی را با یک پیام رد می‌کند و وضعیت خروج غیرصفر می‌دهد. `/bin/false` هم ورود را می‌بندد ولی پیام نمی‌دهد. برای حساب سرویس `nologin` را بگذارید و وجودش را در `/etc/shells` چک کنید. قفل رمز با `usermod --lock` فقط فیلد رمز در shadow را با `!` بی‌اثر می‌کند. کلید SSH هنوز کار می‌کند. این تفاوت را پایین، در امنیت، جدی بگیرید. انقضای حساب با `chage -E` یا `usermod --expiredate` حتی ورود با کلید را هم می‌بندد، چون خود حساب گذشته است نه فقط رمزش.

`/etc/skel` قالب خانهٔ کاربر تازه‌ای است که با `-m` ساخته می‌شود. فایل‌هایی مثل `.bashrc` از این‌جا کپی می‌شوند. عوض کردن skel، خانهٔ کاربر قبلی را عوض نمی‌کند. حساب سیستم را با خانهٔ پر از اسکلت بشری نسازید مگر به آن خانه واقعاً نیاز دارید. برای `deploy` خانهٔ کوچک زیر `/var/lib/deploy` کافی است. کد برنامه آن‌جا نمی‌نشیند. کد زیر `/opt/apps/portal` است و مال روت می‌ماند تا فرآیند سرویس نتواند باینری خودش را عوض کند.

عمر رمز با `chage` روی حساب انسان اعمال می‌شود. `PASS_MAX_DAYS` در `login.defs` فقط پیش‌فرض کاربر بعدی است. کاربر فعلی را باید با `chage` جدا تنظیم کنید. برای `deploy` رمز قابل ورود نمی‌گذاریم، پس سیاست ۹۰ روزهٔ انسان درباره‌اش بی‌معنی است. حساب سرویس منقضی نمی‌شود مگر خود سرویس باید تعطیل شود.

## چرا استفاده می‌شود؟

حساب مشترک `root` یا یک `ops` که همه با یک کلید واردش می‌شوند، بعد از رفتن یک نفر قابل پس گرفتن نیست مگر همهٔ کلیدها را عوض کنید. حساب جدا به‌علاوهٔ گروه `sudo` یعنی حذف یک انسان برابر است با قفل همان حساب، نه تعویض رمز جمعی وسط حادثه.

اجرای سرویس با `ops` هم غلط است. `ops` می‌تواند `sudo` کند. هر خواندن فایل محیط یا هر باگ وب یعنی یک قدم تا روت. `deploy` اگر فقط حق خواندن کد و نوشتن در `/var/lib/portal` را داشته باشد، همان باگ داخل همان مرز می‌ماند. مرز را صفحهٔ مجوز و یونیت systemd با `User=` و `ProtectSystem=` می‌سازند. این صفحه فقط هویت را می‌سازد. بدون هویت درست، آن یونیت یا بالا نمی‌آید یا با روت بالا می‌آید.

## Architecture

```text
انسان                         سرویس
ops                           deploy
uid >= 1000                   uid سیستمی
پوسته /bin/bash               پوسته /usr/sbin/nologin
گروه اصلی ops                 گروه اصلی deploy
گروه اضافه sudo               بدون sudo
خانه /home/ops                خانه /var/lib/deploy
رمز با انقضا                  رمز قفل، ورود با کلید هم ندارد
        \                         /
         \                       /
          فرآیندهای مدیر     portal.service
          از راه sudo         User=deploy
```

گروه `sudo` از قبل روی Ubuntu وجود دارد. لازم نیست `groupadd sudo` بزنید و اگر بزنید با gid بستهٔ `sudo` تصادم می‌کنید. گروه تازه‌ای مثل `opsdata` را خودمان می‌سازیم وقتی چند انسان باید روی یک دایرکتوری مشترک بنویسند بدون اینکه همه مدیر باشند. آن الگو در صفحهٔ مجوز با بیت setgid ادامه پیدا می‌کند.

## Installation

ببینید نصب چه ساخته است:

```bash
id ops
getent passwd ops
getent group sudo
grep nologin /etc/shells
```

خروجی سالم `id` برای مدیر آزمایشگاه شبیه این است:

```text
uid=1000(ops) gid=1000(ops) groups=1000(ops),27(sudo),4(adm)
```

عدد gid گروه `sudo` ممکن است ۲۷ نباشد. نام `sudo` معیار است نه عدد. اگر `ops` در این فهرست نیست و هنوز یک نشست روت دارید:

```bash
sudo usermod -aG sudo ops
```

نشست فعلی گروه جدید را نمی‌بیند. `ops` باید یک بار خارج و وارد شود. تا آن لحظه `sudo` ممکن است بگوید کاربر در sudoers نیست در حالی که `getent group sudo` او را نشان می‌دهد. این تناقض با نشست کهنه است نه با فایل.

اگر `ops` اصلاً ساخته نشده، از کنسول روت:

```bash
sudo useradd --create-home --shell /bin/bash --comment "Lab operator" ops
sudo usermod -aG sudo ops
sudo passwd ops
```

`passwd` رمز را تعاملی می‌پرسد. آن را `change-me` نگذارید اگر نصب‌کننده رمز قوی می‌خواهد، و اگر برای آزمایشگاه کوتاه گذاشتید همان روز عوضش کنید. رمز در دستور `useradd` روی خط فرمان نمی‌آید تا در `ps` و در history نماند.

کاربر سرویس:

```bash
sudo useradd \
  --system \
  --create-home \
  --home-dir /var/lib/deploy \
  --shell /usr/sbin/nologin \
  --comment "Service account for /opt/apps" \
  --user-group \
  deploy
sudo install -d -o root -g deploy -m 0750 /opt/apps/portal
sudo install -d -o deploy -g deploy -m 0750 /var/lib/portal
```

`--user-group` گروه اصلی همنام با کاربر می‌سازد. `--system` uid را از بازهٔ سیستم می‌گیرد و معمولاً رمز را قفل می‌سازد. بررسی:

```bash
getent passwd deploy
getent shadow deploy
sudo passwd -S deploy
```

ستون دوم `passwd -S` برای حساب قفل `L` است. پوسته باید `/usr/sbin/nologin` باشد. خانه `/var/lib/deploy` است. اگر `grep nologin /etc/shells` خالی بود، روی Ubuntu 26.04 غیرعادی است. بستهٔ `login` را سالم فرض نکنید و `dpkg -l login` را ببینید. سراغ پوستهٔ `/bin/bash` برای `deploy` نروید فقط چون یک سرویس از shell شکایت کرده. آن شکایت را جدا بررسی کنید.

## Configuration

اسکلت کاربر انسان در `/etc/skel` است. برای دیدن اینکه کاربر بعدی چه فایلی می‌گیرد:

```bash
ls -la /etc/skel
```

فایل تازه‌ای که این‌جا بگذارید فقط به `useradd -m` بعدی کپی می‌شود. برای عوض کردن پرامپت `ops` همین حالا، فایل خانهٔ خود او را ویرایش کنید نه skel را. یک فایل اسکلت مفید برای آزمایشگاه، یادآوری است که تاریخچهٔ شل رمز را نگه ندارد. آن را در skel بگذارید اگر سیاست سازمان است، و بدانید کاربر فعلی را پوشش نمی‌دهد.

گروه مشترک داده، بدون حق sudo:

```bash
sudo groupadd opsdata
sudo usermod -aG opsdata ops
id ops
```

برداشتن از گروه، بدون دست زدن به بقیهٔ گروه‌ها:

```bash
sudo gpasswd -d ops opsdata
```

`usermod -G opsdata ops` را نزنید. بدون `-a` خروجی بعدی `id` احتمالاً دیگر `sudo` ندارد و شما خودتان را از مدیریت قفل کرده‌اید. اگر این اتفاق افتاد و نشست `sudo` هنوز باز است، همان نشست را نبندید و `sudo usermod -aG sudo ops` را بزنید. اگر هیچ نشستی با sudo نمانده، از کنسول هایپروایزر وارد شوید. روت Ubuntu رمز ورود ندارد. کنسول GRUB به حالت recovery در آزمایشگاه ممکن است پوستهٔ روت بدهد. این راه را برای تولید به‌عنوان در پشتی رها نکنید. قبل از دستکاری گروه، یک نشست دوم sudo باز کنید.

عمر رمز برای انسان. حداکثر ۹۰ روز، حداقل یک روز بین دو تعویض، هشدار ۱۴ روز مانده، و انقضای خود حساب خالی تا وقتی آدم در سازمان است:

```bash
sudo chage --maxdays 90 --mindays 1 --warndays 14 ops
sudo chage -l ops
```

شکل خروجی:

```text
Last password change                                    : Sep 23, 2026
Password expires                                        : Dec 22, 2026
Password inactive                                       : never
Account expires                                         : never
Minimum number of days between password change          : 1
Maximum number of days between password change          : 90
Number of days of warning before password expires       : 14
```

تاریخ را سرور با منطقهٔ `Asia/Tehran` نشان می‌دهد. اگر `Last password change` برابر `password must be changed` بود، ورود بعدی مجبور به تعویض است. این همان وضعی است که نصب cloud-init با `expire: true` می‌سازد.

قفل موقت رمز یک انسان، مثلاً وقتی لپ‌تاپش گم شده ولی هنوز نمی‌خواهید حساب منقضی شود:

```bash
sudo usermod --lock ops
sudo passwd -S ops
```

ستون وضعیت `L` می‌شود. برگرداندن:

```bash
sudo usermod --unlock ops
```

قفل رمز کلید SSH را نمی‌بندد. برای بستن واقعاً دسترسی:

```bash
sudo usermod --expiredate 1 ops
sudo chage -l ops
```

مقدار `1` یعنی تاریخ انقضا در گذشته (دوم ژانویهٔ ۱۹۷۰). `Account expires` دیگر `never` نیست. برگرداندن وقتی آدم برگشته و هویتش را از نو تأیید کرده‌اید:

```bash
sudo usermod --expiredate '' ops
sudo usermod --unlock ops
```

رشتهٔ خالی برای `--expiredate` انقضا را برمی‌دارد. کلید قبلی را برنگردانید. فایل `authorized_keys` را خالی کنید و کلید تازه بگیرید، چون دلیلی که حساب را بستید ممکن است همان کلید بوده باشد.

تعطیل کردن سرویس‌دهندهٔ `deploy` وقتی برنامه بازنشسته شده، نه قبل از آن:

```bash
sudo systemctl disable --now portal.service
sudo usermod --expiredate 1 deploy
```

اول سرویس را متوقف کنید. منقضی کردن حساب زیر یک واحد در حال اجرا، فرآیند فعلی را لزوماً نمی‌کشد ولی ری‌استارت بعدی را می‌خواباند و وسط حادثه علت را قاطی می‌کند.

## Production Example

ورود یک همکار تازه به سرور `app-1`. نام نمونه `nima` است. او مدیر است پس گروه `sudo` می‌گیرد. اگر فقط به لاگ نیاز دارد، او را در `sudo` نگذارید و به‌جایش ACL خواندن روی یک مسیر مشخص بدهید. آن کار صفحهٔ ACL است.

```bash
sudo useradd --create-home --shell /bin/bash --comment "Nima ops" --groups sudo nima
sudo passwd nima
sudo chage --maxdays 90 --mindays 1 --warndays 14 nima
```

`--groups` در خود `useradd` گروه اضافی اولیه است و چون حساب تازه است چیزی را پاک نمی‌کند. برای حساب موجود همیشه `usermod -aG` امن‌تر است تا عادت دست خطرناک نشود.

کلید را خود نیا می‌سازد و فقط خط عمومی را می‌فرستد:

```bash
sudo install -d -o nima -g nima -m 0700 /home/nima/.ssh
sudo install -o nima -g nima -m 0600 /dev/null /home/nima/.ssh/authorized_keys
```

خط `ssh-ed25519 ...` را در آن فایل بگذارید. از `echo` با ریدایرکت روت استفاده نکنید و بعد فراموش کنید `chown` کنید. اگر فایل مال روت بماند، sshd آن را برای `nima` قبول نمی‌کند.

رفتن نیا از تیم:

```bash
sudo usermod --expiredate 1 nima
sudo usermod --lock nima
sudo mv /home/nima/.ssh/authorized_keys /var/backups/nima.authorized_keys.disabled
sudo chage -l nima
```

خانه را همان روز پاک نکنید. ممکن است تنها کپی یک اسکریپت عملیاتی باشد. بکاپ را نگه دارید و پاک کردن خانه را بعد از تحویل کار انجام دهید: `sudo userdel -r nima` خانه و mail را برمی‌دارد. بدون `-r` حساب می‌رود و خانه می‌ماند. `userdel` اگر فرآیند باز باشد شکست می‌خورد. اول `sudo pgrep -a -u nima` و نشست‌ها را ببندید.

چند سرور. حساب `deploy` لازم نیست uid یکسان داشته باشد تا وقتی فایل بین سرورها با NFS اشتراک نمی‌شود. در این آزمایشگاه اشتراک خانگی نداریم. اگر روزی داشتید، uid را در لحظهٔ `useradd --uid` ثابت کنید نه با `usermod -u` بعد از پر شدن دیسک از فایل. عوض کردن uid صاحب فایل‌های موجود را تنها نمی‌گذارد. `find /opt/apps -user OLD` بعد از تغییر هنوز لازم است.

بررسی شبانهٔ ساده، بدون اسکریپت:

```bash
getent passwd | awk -F: '$3>=1000 && $3<65534 {print $1, $3, $7}'
sudo chage -l ops
sudo passwd -S deploy
```

خط اول انسان‌ها و پوسته‌شان را نشان می‌دهد. `nobody` با uid 65534 نباید این‌جا بیاید. اگر `deploy` پوستهٔ bash داشت، کسی برای راحتی دیباگ پوسته‌اش را عوض کرده. همان را به `nologin` برگردانید مگر دلیل مکتوب دارید:

```bash
sudo usermod --shell /usr/sbin/nologin deploy
```

## Security Notes

- `usermod --lock` و `passwd -l` کلید SSH را باطل نمی‌کنند. برای قطع دسترسی انسان، حساب را منقضی کنید و `authorized_keys` را بردارید.
- `deploy` را در گروه `sudo` یا `adm` نگذارید. گروه `adm` روی Ubuntu اغلب خواندن لاگ را می‌دهد و برای یک حساب سرویس بیشتر از نیاز است.
- رمز را در `useradd -p` روی خط فرمان نگذارید. هش روی خط دستور در لیست فرآیندها دیده می‌شود. `passwd` تعاملی یا ابزار مدیریت رمز سازمان کافی است.
- حساب مشترک بین آدم‌ها نسازید. گروه مشترک بسازید.
- `/etc/shadow` را در تیکت کپی نکنید حتی اگر هش است. هش ضعیف را می‌شود آفلاین آزمود.
- `NOPASSWD` و قانون sudo را این‌جا ننویسید. حساب سرویس اگر باید یک دستور را بدون رمز بزند، آن استثنا در فایل جدا و با مسیر کامل دستور است، در صفحهٔ sudo.
- ورود روت با رمز را برای «راحتی کنسول» فعال نکنید. کنسول هایپروایزر راه بازیابی است.

## Troubleshooting

| نشانه | علت محتمل | کار |
| --- | --- | --- |
| `useradd: user 'deploy' already exists` | تلاش قبلی نیمه‌کاره مانده | `getent passwd deploy` و اگر پوسته غلط است `usermod` نه ساخت دوباره |
| `useradd: UID is already in use` | `--uid` تکراری | بدون `--uid` بگذارید ابزار انتخاب کند |
| sudo بعد از `usermod -G` از بین رفت | `-a` جا افتاده و گروه sudo پاک شده | نشست باز را نبندید، `usermod -aG sudo ops` |
| SSH می‌گوید حساب منقضی است | `chage -E` یا expire نصب | `chage -l` و فقط اگر باید برگردد `--expiredate ''` |
| رمز درست است، کلید هنوز وارد می‌شود بعد از lock | قفل رمز کلید را نمی‌بندد | انقضای حساب و حذف authorized_keys |
| سرویس با `User=deploy` بالا نمی‌آید | خانه یا گروه نیست، یا حساب منقضی است | `getent passwd deploy` و `journalctl -u portal.service` |
| `nologin` پیام عجیب یا خود شل باز می‌شود | مسیر پوسته غلط است | `getent passwd` فیلد آخر باید `/usr/sbin/nologin` باشد |

تست اینکه `deploy` واقعاً پوسته نمی‌گیرد، از طرف روت و بدون دادن رمز به او:

```bash
sudo -u deploy -s
```

اگر `nologin` درست باشد این دستور همان پیام غیرتعاملی را چاپ می‌کند و برمی‌گردد، نه یک پرامپت. اگر پرامپت bash دیدید، پوسته هنوز تعاملی است. با `exit` بیرون بیایید و `usermod --shell` را تکرار کنید. توجه کنید `sudo -u deploy /bin/bash` پوسته را دور می‌زند حتی اگر nologin باشد، چون شما صریحاً باینری را گفته‌اید و خودتان روت‌اید. این تست را با `-s` انجام دهید تا پوستهٔ ثبت‌شدهٔ حساب استفاده شود.

`sudo -u deploy /usr/bin/id` باید uid همان کاربر را چاپ کند حتی با nologin. اگر این هم شکست خورد، حساب منقضی یا خانهٔ غیرقابل استفاده است نه خود پوسته.

## Best Practices

- یک انسان، یک حساب، از uid بالای ۱۰۰۰، با `chage` نود روزه. یک سرویس، یک حساب سیستمی با `nologin` و بدون عضویت sudo.
- گروه اضافه را فقط با `usermod -aG` تغییر دهید. قبلش یک نشست sudo دوم باز باشد.
- خانهٔ `deploy` را `/var/lib/deploy` بگذارید و کد را به مالکیت او ندهید. نوشتن وضعیت سرویس در `/var/lib/portal` است.
- رفتن آدم را با انقضای حساب و برداشتن کلید تمام کنید. `userdel -r` را بعد از تحویل فایل‌ها بزنید نه وسط شیفت.
- skel را برای کاربر بعدی بدانید نه راه عوض کردن کاربر فعلی.
- uid را دستی ثابت نکنید مگر اشتراک فایل بین سرورها واقعاً وجود دارد.
