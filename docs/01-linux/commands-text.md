# پردازش متن

## مقدمه

`grep`، `awk` و `sed` متن را روی سرور می‌خوانند یا عوض می‌کنند، بدون اینکه ویرایشگر تعاملی روی فایل Production باز شود. هر سه از ابزار گنو روی Ubuntu Server 26.04 هستند، نه نسخهٔ BSD که روی macOS است. همین فرق، اسکریپت کپی‌شده از یک وبلاگ مک را روی `app-1` یا برعکس می‌شکند. نسخه را از خود ابزار بخوانید:

```bash
grep --version | head -n 1
awk --version | head -n 1
sed --version | head -n 1
```

`awk` پیش‌فرض Ubuntu همان `gawk` است. `sed` پیش‌فرض GNU sed است. اگر `sed --version` رشتهٔ GNU را نشان نداد، بقیهٔ این صفحه را با فرض دیگری اجرا نکنید.

خطر خانواده این‌هاست: `grep` وقتی چیزی پیدا نکند کد ۱ برمی‌گرداند و اسکریپت با `set -e` می‌میرد. `awk` اگر شمارهٔ ستون را از روی قالب لاگ اشتباه فرض کنید، جمع بی‌معنی ولی خوش‌ظاهر چاپ می‌کند. `sed -i` بدون بکاپ فایل را همان لحظه عوض می‌کند و روی پیوند نمادین، خود پیوند را با یک فایل معمولی جایگزین می‌کند. هیچ‌کدام سؤال نمی‌پرسند.

آزمایشگاه: برنامه روی `app-1.example.internal` یعنی `10.10.1.10`، لاگ nginx در `/var/log/nginx`، و پیکربندی سایت در `/etc/nginx/sites-available/shop.conf`. پایگاه روی `db-1` است (`10.10.1.20`). جست‌وجوی فایل قبل از باز کردن متن در [دستورهای فایل](/docs/01-linux/commands-files) است.

## grep

### توضیح

`grep` خط‌هایی را چاپ می‌کند که با الگو جور باشند. شکل پرتکرار این دانشنامه `grep -R -n -E` است، ولی پیش‌فرض روزمره اغلب `-r` است نه `-R`. فرق را بدانید و بعد انتخاب کنید.

- `-n` شمارهٔ خط را جلوی هر جور شدن می‌گذارد. در تیکت بدون شمارهٔ خط، فایل هزارخطی قابل ارجاع نیست.
- `-E` عبارت منظم گسترش‌یافته است (همان چیزی که قدیم `egrep` بود). `|` به‌معنی «یا» است و پرانتز گروه می‌سازد، بدون بک‌اسلش اضافه.
- `-F` الگو را رشتهٔ ثابت می‌گیرد، نه عبارت منظم. نقطه، ستاره و کروشه معنی خاص ندارند. برای آدرس IP، نام دامنه، و مسیر فایل همین را بخواهید. `-F` هم سریع‌تر است هم غافلگیرتان نمی‌کند.
- `-R` بازگشتی است و پیوندهای نمادین را دنبال می‌کند، حتی پیوندی که وسط درخت پیدا شود.
- `-r` هم بازگشتی است، ولی پیوند را فقط وقتی دنبال می‌کند که خود آن پیوند را روی خط فرمان داده باشید. پیوندی که وسط پیمایش دیده شود باز نمی‌شود.
- `-l` فقط نام فایل را می‌دهد. `-c` تعداد خط جور را. `-q` ساکت است و فقط کد خروج می‌گذارد. `--include` و `--exclude` نام را محدود می‌کنند.

فرق `-F` و `-E` در یک نقطه معلوم می‌شود. در `-E` نقطه یعنی «هر نویسه». الگوی `10.10.1.10` بدون فرار دادن نقطه، `10a10b1c10` را هم جور می‌کند. برای آدرس آزمایشگاه `-F` درست است.

کد خروج را حفظ کنید، چون اسکریپت به آن تکیه می‌کند:

| کد | معنی |
| --- | --- |
| ۰ | حداقل یک جور شدن |
| ۱ | فایل خوانده شد و هیچ خطی جور نشد |
| ۲ | خطا: فایل نیست، مجوز نیست، یا الگوی عبارت منظم شکسته است |

کد ۱ شکست برنامهٔ `grep` نیست. یعنی «خبری نبود». با `set -e` یا `set -o pipefail` همین کد، اسکریپت یا خط لوله را قطع می‌کند و دستور بعدی که می‌خواستید در هر دو حال اجرا شود اجرا نمی‌شود. کد ۲ را هرگز مثل ۱ درمان نکنید. یکی «لاگ تمیز است» است و دیگری «اصلاً لاگ را ندیدم».

جست‌وجو از `/` با `-R` ممنوع است. `-R` اگر به پیوندی به `/` یا به دیسک بکاپ برسد، از درختی که فکر می‌کنید بیرون می‌زند و هم کند است هم ممکن است فایل دستگاه را به‌اشتباه متن فرض کند.

### مثال واقعی

عبارت منظم روی لاگ خطای nginx، با شمارهٔ خط، فقط در فایل‌های همین دایرکتوری و بدون دنبال کردن پیوند:

```bash
grep -n -E 'error|fatal' /var/log/nginx/error.log | head
```

```text
1842:2026/09/23 02:14:11 [error] 912#912: *44 connect() failed (111: Connection refused) while connecting to upstream, client: 10.10.1.5
1901:2026/09/23 02:16:02 [error] 912#912: *51 upstream timed out (110: Connection timed out)
```

رشتهٔ ثابت برای آدرس `app-1`. نقطه نباید «هر نویسه» باشد:

```bash
grep -n -F '10.10.1.10' /etc/nginx/sites-available/shop.conf
grep -n -F 'app.example.com' /var/log/nginx/access.log | head
```

```text
12:    server_name app.example.com;
18:        proxy_pass http://10.10.1.10:3000;
44021:10.10.1.5 - - [23/Sep/2026:02:14:01 +0330] "GET /health HTTP/1.1" 200 12 "-" "curl/8.5.0"
```

بازگشتی روی درخت انتشار، با محدود کردن پسوند. اینجا `-r` را ترجیح می‌دهیم تا پیوند `current` اگر به بیرون اشاره داشت محتوا را دوباره و از جای دیگر نخواند. `-R` را فقط وقتی بزنید که عمداً می‌خواهید پیوند وسط درخت باز شود:

```bash
grep -r -n -E --include='*.js' 'ECONNREFUSED|deprecated' /opt/apps/shop/releases/20260923-0210 | head
```

کد خروج را در پوسته ببینید، نه اینکه حدس بزنید:

```bash
grep -F -q '10.10.1.20' /etc/nginx/sites-available/shop.conf
echo "grep_exit=$?"
grep -F -q 'this-string-is-absent' /etc/nginx/sites-available/shop.conf
echo "grep_exit=$?"
```

```text
grep_exit=0
grep_exit=1
```

اگر فایل اصلاً نباشد کد ۲ است:

```text
grep: /var/log/nginx/missing.log: No such file or directory
grep_exit=2
```

### کاربرد Production

روی `app-1` وقتی پروکسی `10.10.1.5` خطای 502 می‌دهد، اول `error.log` را با `-n -E` برای `upstream` و `connect()` ببینید. اگر خط، `Connection refused` به `127.0.0.1:3000` باشد، nginx بالاست و فرایند Node گوش نمی‌دهد. آن را با `ss` در [سوکت](/docs/01-linux/commands-network) تأیید کنید، نه با ری‌استارت کور.

اسکریپت سلامت که باید هم در صورت دیدن خطا و هم در صورت ندیدن خطا ادامه دهد، کد ۱ را داخل `if` مصرف می‌کند. `if` کد را خودش برمی‌دارد و `set -e` اسکریپت را نمی‌کشد:

```bash
#!/bin/bash
set -euo pipefail
log=/var/log/nginx/error.log
if grep -F -q 'Connection refused' "$log"; then
  echo "upstream refused on app-1" >&2
  exit 1
fi
echo "no connection refused in current error log"
```

شکل غلط، `grep` لخت زیر `set -e` است. اگر رشته نباشد اسکریپت همان‌جا می‌ایستد و `echo` بعدی هرگز نمی‌رسد، در حالی که از نظر عملیاتی «نبودن خطا» موفقیت است. `|| true` هم غلط است، چون کد ۲ (مجوز، فایل نیست، دیسک) را هم موفقیت جلوه می‌دهد. اگر باید کد را خودتان نگه دارید، ۱ را بپذیرید و ۲ را شکست حساب کنید:

```bash
set +e
grep -F -q 'Connection refused' /var/log/nginx/error.log
status=$?
set -e
if [ "$status" -eq 2 ]; then
  echo "grep failed to read the log" >&2
  exit 2
fi
```

روی `db-1` برای گشتن در لاگ PostgreSQL همان `-F` را برای نام پایگاه و نام کاربر استفاده کنید. `-R` روی `/var/lib/postgresql` نزنید. آنجا دادهٔ دودویی است و یک پیوند اشتباه شما را از لاگ بیرون می‌برد.

### وقتی خراب می‌شود

```text
grep: /var/log/nginx/error.log: Permission denied
grep: Unmatched ( or \(
bash: /usr/bin/grep: Argument list too long
```

اولی کد ۲ است. `ops` عضو گروه `adm` نیست. `sudo grep` برای خواندن لاگ، نه `chmod 644` روی لاگ تا grep راحت شود. دومی الگوی `-E` شکسته است و باز هم کد ۲ است. آن را با «چیزی پیدا نشد» اشتباه نگیرید. سومی مال باز شدن ستاره در پوسته است، قبل از `grep`. به‌جای `grep x /var/log/nginx/*` از `grep -r -F x /var/log/nginx` استفاده کنید، یا نام‌ها را با `find` بدهید. جزئیات سقف آرگومان در صفحهٔ فایل است.

`-R` روی درختی که `current` به یک مسیر بالا اشاره کند، یا حلقهٔ پیوند داشته باشد، یا خیلی طول می‌کشد یا همان فایل را چند بار نشان می‌دهد. اگر خروجی تکرار عجیب داشت، `ls -ld` را روی پیوندها ببینید و به `-r` برگردید.

`grep -q` با خط لوله و `pipefail` هم کد ۱ را به کل لوله می‌دهد. ساکت بودن یعنی خروجی نیست، نه اینکه کد ۰ باشد.

## awk

### توضیح

`awk` هر خط را به ستون می‌شکند و روی ستون حساب می‌کند. جداکنندهٔ پیش‌فرض، فاصلهٔ پشت‌سرهم است. قالب combined لاگ nginx این ستون‌ها را با همان شکستن می‌دهد، به شرطی که مسیر درخواست فاصله نداشته باشد:

| ستون | محتوا در access.log |
| --- | --- |
| ۱ | آدرس کلاینت |
| ۹ | کد وضعیت HTTP |
| ۱۰ | اندازهٔ بدنه به بایت |

ستون ۹ فقط به‌خاطر شکل استاندارد خط درست درمی‌آید: زمان داخل کروشه دو ستون است، و درخواست سه‌تکه (`GET`، مسیر، پروتکل) سه ستون. User-Agent فاصله دارد. به ستون‌های بعد از ۱۰ اعتماد نکنید. این روش ابزار شیفت است، نه پارسر دائمی لاگ. اگر قالب `log_format` را در nginx عوض کرده‌اید، شمارهٔ ستون را دوباره با یک خط واقعی بشمارید.

`-F` جداکننده را عوض می‌کند. برای فایل `/etc/passwd` جداکننده دونقطه است. الگوی انتخاب خط قبل از آکولاد برنامه می‌آید و داخل فنس دستور دیده می‌شود، نه در نثر.

جمع و شمارش در بلوک `END` انجام می‌شود، یعنی بعد از آخرین خط. اگر ستون اندازه خالی یا خط تیره باشد (وقتی nginx اندازه را ندارد)، آن را به جمع اضافه نکنید. مقایسه با یک الگوی عددی داخل همان دستور است.

### مثال واقعی

یک خط واقعی را اول با شمارهٔ ستون ببینید تا فرض‌تان با فایل یکی باشد:

```bash
awk '{ print NR, NF, "status="$9, "bytes="$10 }' /var/log/nginx/access.log | head -n 3
```

```text
1 14 status=200 bytes=12
2 14 status=200 bytes=48211
3 15 status=404 bytes=153
```

شمارش کد وضعیت و جمع بایت. فقط مقدار عددی وارد جمع می‌شود:

```bash
awk '$10 ~ /^[0-9]+$/ { bytes += $10 } { count[$9]++ }
     END { for (code in count) print code, count[code]; print "BYTES", bytes+0 }' \
  /var/log/nginx/access.log
```

```text
200 184220
301 940
404 1204
502 37
BYTES 4821930044
```

فیلتر یک ساعت شلوغ، فقط خطاهای ۵xx، از روی خود فایل بدون `grep` جدا:

```bash
awk '$4 ~ /23\/Sep\/2026:02:/ && $9 ~ /^5/ { print $1, $9, $7 }' \
  /var/log/nginx/access.log | head
```

```text
10.10.1.5 502 /api/orders
10.10.1.5 502 /api/orders
```

خواندن `/etc/passwd` برای دیدن پوستهٔ کاربر سرویس. اینجا جداکننده دونقطه است و آکولاد برنامه داخل فنس می‌ماند:

```bash
awk -F: '$1 == "deploy" { print $1, $3, $7 }' /etc/passwd
```

```text
deploy 1001 /usr/sbin/nologin
```

اگر این خط پوستهٔ تعاملی نشان داد، کاربر سرویس بیش از حد اختیار دارد. اصلاحش در [مدیریت کاربر](/docs/01-linux/user-management) است، نه با `awk`.

### کاربرد Production

روی `app-1` بعد از یک کندی، سؤال این نیست که «چند خط لاگ داریم». سؤال این است که سهم 502 در پنجرهٔ حادثه چقدر است و آیا بایت پاسخ یک‌دفعه افت کرده. دستور شمارش بالا را روی access.log همان ساعت اجرا کنید و عدد 502 را کنار خروجی `ss` و `systemctl status` بگذارید. اگر 502 زیاد است و Node به `127.0.0.1:3000` گوش نمی‌دهد، مشکل بالادست nginx است نه خود گواهی.

روی `db-1` از `awk` برای شکستن خروجی `df` یا یک دامپ متنی کوچک استفاده کنید، نه برای خواندن فایل دادهٔ PostgreSQL. یک جمع ساده روی لاگ متنی کندی کوئری، اگر چنین لاگی را خودتان با قالب مشخص نوشته‌اید، همان الگو را دارد: ستون را با یک خط نمونه ثابت کنید، بعد جمع بگیرید.

خروجی `awk` را اگر به اسکریپت می‌دهید با `LC_ALL=C` اجرا کنید تا جداکنندهٔ اعشار و رقم عوض نشود. جمع را در پوسته با عدد فارسی یا جداکنندهٔ هزارگان دوباره تفسیر نکنید.

### وقتی خراب می‌شود

```text
awk: cannot open "/var/log/nginx/access.log" (Permission denied)
awk: cmd. line:1: { print $9
awk: cmd. line:1:          ^ unexpected newline or end of string
```

اولی مجوز است. دومی برنامهٔ ناتمام است: نقل‌قول پوسته تمام شده و `awk` دستور را ناقص دیده. کل برنامه را داخل نقل‌قول تکی بگذارید تا پوسته `$9` را متغیر خودش حساب نکند. اگر با نقل‌قول دوتایی بنویسید، bash خیلی از `$`ها را می‌بلعد و `awk` ستون خالی می‌بیند و جمع را صفر چاپ می‌کند، بدون خطای نحوی. صفرِ بی‌صدا بدتر از خطا است.

اگر `NF` برای خط معمولی ۱۴ نیست، یا قالب لاگ عوض شده یا مسیر درخواست فاصله داشته. جمع را دور بریزید و یک خط خام را در تیکت بگذارید. خطای «جمع غلط» پیامی چاپ نمی‌کند.

فایل خیلی بزرگ را با `awk` روی دیسکی که خودش پر است اجرا نکنید اگر خروجی را دوباره روی همان دیسک می‌نویسید. خروجی را به `head` بدهید یا روی میزبان دیگری ببرید. پر شدن دیسک در [عیب‌یابی دیسک](/docs/14-troubleshooting/disk-full) است.

## sed

### توضیح

`sed` جریان متن را با دستورهایی مثل جایگزینی عوض می‌کند. دستور `s` الگو را با متن جدید عوض می‌کند. بدون `g` فقط اولین جور شدن هر خط عوض می‌شود. جداکنندهٔ `s` لازم نیست اسلش باشد. برای مسیر فایل از `|` استفاده کنید تا اسلش‌های مسیر را فرار ندهید.

Ubuntu 26.04 بستهٔ GNU sed دارد. دو رفتاری که باید از BSD sed جدا بدانید:

- `sed -i` بدون پسوند بکاپ در گنو مجاز است و فایل را درجا عوض می‌کند. در sed مک، آرگومان بعدی پسوند بکاپ فرض می‌شود و همان دستور یا خطا می‌دهد یا فایل را به شکل دیگری کپی می‌کند. اسکریپت مک را روی `app-1` کور اجرا نکنید و اسکریپت این دانشنامه را هم با فرض مک ننویسید.
- شکل قابل قبول برای پیکربندی Production این است: `sed -i.bak`. فایل `نام.bak` کنار اصل می‌ماند تا `diff` بگیرید. وقتی مطمئن شدید، بکاپ را برمی‌دارید. ویرایش اول هرگز بدون پسوند نیست.

GNU sed برای `-i` فایل موقت می‌سازد و آن را روی همان مسیر `rename` می‌کند. اگر مسیر خودِ یک پیوند نمادین باشد و `--follow-symlinks` نداده باشید، پیوند با یک فایل معمولی عوض می‌شود و هدف اصلی دست‌نخورده می‌ماند. روی `app-1` مسیر `current` پیوند به انتشار است. `sed -i` را روی خود `current` نزنید. یا فایل معمولی داخل `releases/...` را ویرایش کنید، یا اگر واقعاً هدف پیوند را می‌خواهید `--follow-symlinks` بگذارید و قبل و بعد `ls -ld` بگیرید.

`sed` موفق، حتی اگر هیچ خطی عوض نشده باشد، کد ۰ برمی‌گرداند. «دستور خطا نداد» یعنی الگو هم جور شده نیست. همیشه `diff` با `.bak` یا `grep -n` بعد از ویرایش.

قبل از `systemctl reload nginx` باید `nginx -t` موفق باشد. `sed` این را بلد نیست.

### مثال واقعی

بالادست Node را عوض می‌کنید و بکاپ کنار فایل می‌ماند. جداکننده `|` است چون در متن اسلش نداریم ولی عادت مسیر را خراب نمی‌کند:

```bash
sudo sed -i.bak 's|10.10.1.10:3000|10.10.1.10:3001|' /etc/nginx/sites-available/shop.conf
sudo diff -u /etc/nginx/sites-available/shop.conf.bak /etc/nginx/sites-available/shop.conf
sudo nginx -t
```

```text
--- /etc/nginx/sites-available/shop.conf.bak
+++ /etc/nginx/sites-available/shop.conf
@@ -16,7 +16,7 @@
-        proxy_pass http://10.10.1.10:3000;
+        proxy_pass http://10.10.1.10:3001;
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

بدون پسوند بکاپ، فقط وقتی که همان تغییر را قبلاً با `.bak` تمرین کرده‌اید و فایل تحت git یا بکاپ دیگری است:

```bash
sudo sed -i 's|10.10.1.10:3001|10.10.1.10:3000|' /etc/nginx/sites-available/shop.conf
```

این شکل GNU است. روی macOS همان خط آرگومان‌ها را جابه‌جا تفسیر می‌کند. در runbook بنویسید «GNU sed روی Ubuntu 26.04»، نه «sed همه‌جا».

دیدن جایگزینی بدون نوشتن روی دیسک، برای وقتی که هنوز مطمئن نیستید:

```bash
sed -n 's|proxy_pass http://10.10.1.10:3000|proxy_pass http://127.0.0.1:3000|p' \
  /etc/nginx/sites-available/shop.conf
```

`-n` چاپ پیش‌فرض را خاموش می‌کند و `p` فقط خط عوض‌شده را نشان می‌دهد. فایل اصلی دست نمی‌خورد. این را قبل از `-i` اجرا کنید.

اگر کسی `sed -i` را روی پیوند زده باشد، اثرش این است:

```bash
ls -ld /opt/apps/shop/current
sudo sed -i.bak 's/shop/shop/' /opt/apps/shop/current
ls -ld /opt/apps/shop/current
```

```text
lrwxrwxrwx 1 deploy deploy 32 Sep 23 02:14 /opt/apps/shop/current -> releases/20260923-0210
-rw-r--r-- 1 root root 1842 Sep 23 02:40 /opt/apps/shop/current
```

پیوند از بین رفته و یک فایل معمولی جایش آمده. انتشار واقعی ویرایش نشده. درمان این مثال، برگرداندن پیوند است نه تکرار `sed`. با `--follow-symlinks` هدف ویرایش می‌شد و پیوند می‌ماند. برای پیکربندی nginx اصلاً از مسیر پیوندی رد نشوید.

### کاربرد Production

تغییر بالادست یا `server_name` روی `app-1` این ترتیب را دارد: `sed -n` برای دیدن، بعد `sed -i.bak`، بعد `diff`، بعد `nginx -t`، بعد `systemctl reload nginx`. اگر `nginx -t` شکست خورد، فایل را از `.bak` برگردانید و reload نکنید. reload با پیکربندی شکسته، فرایند قبلی را نگه می‌دارد فقط اگر اصلاً به reload نرسید. `restart` با فایل شکسته سرویس را پایین نگه می‌دارد.

روی `db-1` اتصال PostgreSQL را با `sed` روی `pg_hba.conf` عوض نکنید مگر اینکه خط را دقیقاً بشناسید و بلافاصله `postgresql` را reload کنید و یک اتصال آزمایشی از `app-1` به `10.10.1.20` بگیرید. یک جایگزینی کلی روی کلمهٔ `trust` یا `md5` می‌تواند قانون دیگری را هم عوض کند. برای این فایل، ویرایش دستی کوتاه اغلب از یک `s` سراسری امن‌تر است. اگر `sed` می‌زنید، `g` نگذارید مگر اینکه هر تکرار در همان خط واقعاً باید عوض شود، و diff را خط‌به‌خط بخوانید.

فایل `.bak` را روی سرور رها نکنید اگر رمز دارد. `.env.bak` همان‌قدر محرمانه است که `.env`. حالت فایل را با `ls -l` ببینید. `sed -i` گاهی مالک را به کسی که دستور را زده عوض می‌کند، چون فایل را از نو ساخته. اگر `shop.conf` یک‌دفعه مال `root:root` با حالت دیگری شد، قبل از حادثهٔ بعدی درستش کنید. جزئیات مالک در صفحهٔ مجوز است.

### وقتی خراب می‌شود

```text
sed: -e expression #1, char 12: unknown option to `s'
sed: couldn't open temporary file /etc/nginx/sites-available/sedXXXXXX: Permission denied
sed: no input files
```

اولی یعنی در متن جایگزین نویسهٔ جداکننده آمده. مسیر با اسلش را با جداکنندهٔ `|` بنویسید. دومی یعنی دایرکتوری فایل برای شما قابل نوشتن نیست، حتی اگر خود فایل را با `sudo` جای دیگری بتوانید بخوانید. `sed -i` باید کنار فایل، فایل موقت بسازد. سومی یعنی نام فایل به دستور نرسیده. اغلب نقل‌قول اشتباه است.

شکست منطقی بدون پیام: الگو جور نشده، کد خروج ۰ است، و شما reload می‌کنید و فکر می‌کنید پورت عوض شده. `diff` خالی یعنی هیچ تغییری نبوده. `grep -n -F` را بعد از `sed` تکرار کنید.

اگر `.bak` از اجرای قبلی مانده باشد، `sed -i.bak` بدون تعارف روی همان بکاپ می‌نویسد. بکاپِ بکاپ نمی‌سازد. قبل از اجرای دوم، `.bak` را جایی با نام تاریخ بردارید وگرنه تنها نسخهٔ قبل از هر دو تغییر از بین می‌رود.

ویرایش همزمان دو نفر با `sed -i` آخرین نویسنده را نگه می‌دارد و هشدار قفل نمی‌دهد. روی `shop.conf` یک نفر باید تغییر را صاحب باشد.

## Best Practices

- برای IP و دامنه و مسیر، `grep -F`. برای «یا» منطقی، `-E`. شمارهٔ خط را با `-n` نگه دارید. `-r` پیش‌فرض جست‌وجوی درخت است و `-R` فقط وقتی پیوند وسط درخت عمدی است.
- کد ۱ یعنی پیدا نشد و در اسکریپت باید داخل `if` دیده شود. کد ۲ خطا است و نباید با `|| true` قورت برود. `set -euo pipefail` را دور نزنید. شرط را درست بنویسید.
- در `awk` یک خط نمونه را با `NF` چاپ کنید، بعد جمع بگیرید. ستون ۹ و ۱۰ مال قالب combined پیش‌فرض nginx است. User-Agent را ستون حساب نکنید. نقل‌قول برنامه تکی باشد تا پوسته `$` را نبلعد.
- روی Ubuntu فقط GNU sed را فرض کنید. ویرایش پیکربندی با `-i.bak`، بعد `diff`، بعد آزمون سرویس (`nginx -t`)، بعد reload. `-i` بدون پسوند مال عجلهٔ دوم است نه تغییر اول.
- `sed -i` را روی پیوند `current` نزنید. بدون `--follow-symlinks` پیوند را نابود می‌کند. فایل `.bak` محرمانه را جا نگذارید و مالک فایل را بعد از ویرایش با `ls -l` ببینید.
- لاگ و پیکربندی `db-1` را با جایگزینی سراسری «هر چه بود» عوض نکنید. یک قانون `pg_hba` اشتباه یعنی یا قطعی برنامه است یا باز شدن دسترسی.
