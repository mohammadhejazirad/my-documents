# sudo

## مقدمه

`sudo` یک دستور را با کاربر دیگری، معمولاً روت، اجرا می‌کند و همان اجرا را لاگ می‌کند. جایگزین ورود با حساب روت است، نه میانبر برای خاموش کردن رمز. این صفحه فایل قانون را طوری می‌نویسد که یک اشتباه نحوی همهٔ مدیران را قفل نکند، و طوری که حساب `deploy` نتواند هر دستوری را بدون رمز بزند. ساخت خود حساب‌ها در [مدیریت کاربر و گروه](/docs/01-linux/user-management) است. اگر به‌جای اجرای یک دستور فقط باید فایلی را بخواند، [ACL](/docs/01-linux/acl) کافی و کم‌خطرتر است.

روی Ubuntu گروه مدیر `sudo` است. خط پیش‌فرض داخل `/etc/sudoers` به اعضای این گروه اجازه می‌دهد هر دستوری را با رمز خودشان بزنند. Debian هم اگر بستهٔ `sudo` نصب باشد و کاربر را در همان گروه گذاشته باشید همین مدل را دارد. گروه `wheel` مال این توزیع‌ها نیست. اگر راهنمایی `wheel` گفت، آن را در Ubuntu نسازید تا دو سیاست موازی نداشته باشید.

## مفهوم اصلی

`/etc/sudoers` فایل اصلی است و با `visudo` ویرایش می‌شود. `visudo` قبل از جایگزینی، دستور زبان را چک می‌کند و اگر خراب باشد فایل قبلی را نگه می‌دارد. ویرایش با `nano` مستقیم این توری را ندارد. یک نویسهٔ اضافه یعنی `sudo` برای همه خطا می‌دهد، از جمله برای تعمیری که می‌خواهید همان لحظه انجام دهید.

ته فایل اصلی یک خط با معنی خاص است: `#includedir /etc/sudoers.d`. آن `#` این‌جا کامنت نیست. دستور وارد کردن پوشه است. فایل‌های آن پوشه به سیاست اضافه می‌شوند. قانون محلی ما این‌جا می‌ماند تا به‌روزرسانی بستهٔ `sudo` فایل اصلی را عوض کند و قانون سازمان پاک نشود.

نام فایل داخل این پوشه نباید نقطه یا مد داشته باشد. `sudo` فایلی را که در نامش `.` هست یا به `~` ختم می‌شود نادیده می‌گیرد تا فایل موقت ویرایشگر و بکاپ بسته به‌اشتباه اجرا نشود. پس `ops-deploy` درست است و `ops.conf` بی‌صدا بی‌اثر است. `visudo -f` همان فایل نقطه‌دار را هم از نظر نحو می‌پذیرد. شکست را فقط موقع اجرا می‌بینید، وقتی `sudo -l` قانون را نشان نمی‌دهد. این را در عیب‌یابی با خروجی واقعی آورده‌ام.

`NOPASSWD` برچسب یک دستور است نه شایستگی یک انسان. شکل ممنوع در این دانشنامه `NOPASSWD: ALL` است. یعنی هر دستور، به‌عنوان روت، بدون رمز، بدون لاگِ تصمیم انسانی. شکل مجاز این است که یک حساب مشخص فقط یک مسیر مطلق با آرگومان مشخص را بدون رمز بزند. `ops` این برچسب را نمی‌گیرد. او رمز خودش را می‌زند و عضویتش در گروه `sudo` کافی است. `deploy` اگر اصلاً لازم دارد سرویس را reload کند، فقط همان یک دستور را می‌گیرد.

تطابق دستور تحت‌اللفظی است و مسیر باید مطلق باشد. `systemctl` بدون مسیر، یا با وایلدکارت، راه‌فرار است. خود `systemctl` اگر کل زیر‌دستورهایش مجاز باشد می‌تواند واحد دیگری را خاموش کند یا `edit` کند. قانون را تا نام واحد و زیر‌دستور محدود کنید. محیط اجرا با `env_reset` پیش‌فرض پاک می‌شود. `SETENV` و نگه داشتن `LD_LIBRARY_PATH` را به قانون اضافه نکنید.

مهلت رمز پیش‌فرض چند دقیقه است. `sudo -v` آن را تازه می‌کند و `sudo -k` پاک می‌کند. این مهلت راحتی است نه احراز هویت دائمی. در اسکریپت، به مهلت یک نشست تعاملی تکیه نکنید. اسکریپت یا غیرتعاملی شکست می‌خورد یا باید قانون `NOPASSWD` محدود داشته باشد.

## چرا استفاده می‌شود؟

ورود مستقیم روت رمز مشترک می‌سازد، لاگ را به «کسی با روت آمد» تقلیل می‌دهد، و بستن دسترسی یک نفر را غیرممکن می‌کند. `sudo` نام کاربر واقعی را در syslog و journal می‌نویسد. می‌شود دید `nima` دیروز `apt upgrade` زده نه اینکه «روت زده».

اجرای همیشگی پوستهٔ روت با `sudo -i` این فایده را کم می‌کند، چون دستورهای داخل آن پوسته دیگر تک‌به‌تک از sudo نمی‌گذرند. برای کار تعاملی، هر دستور مدیریتی را با `sudo` جدا بزنید. پوستهٔ روت را برای وقتی نگه دارید که یک خط لوله واقعاً به روت در هر دو طرف نیاز دارد، و همان را کوتاه کنید.

حساب سرویس پوسته و رمز تعاملی ندارد. اگر واحد systemd باید reload شود، خود systemd این کار را با `systemctl reload` مدیر انجام می‌دهد. `NOPASSWD` برای `deploy` فقط وقتی معنی دارد که یک اسکریپت استقرار، بدون انسان، همان یک reload را بزند. آن اسکریپت نباید `ALL` داشته باشد و نباید تحت مالکیت خود `deploy` باشد، وگرنه باگ برنامه قانون را تبدیل به پوستهٔ روت می‌کند.

## Architecture

```text
ops  --رمز خودش-->  گروه sudo  -->  /etc/sudoers
                                      %sudo ALL=(ALL:ALL) ALL
                                      #includedir /etc/sudoers.d
                                              |
                                              v
                                    /etc/sudoers.d/ops-deploy
                                    deploy فقط reload و status
                                    یک واحد مشخص، بدون رمز

journal  برچسب sudo  چه کسی، چه دستوری، قبول یا رد
```

فایل اصلی را دست نمی‌زنیم. قانون تازه فقط در پوشه است. ترتیب خواندن فایل‌های پوشه لغت‌نامه‌ای است. اگر دو فایل یک چیز را خلاف هم بگویند، آخرین تطبیق برنده است نه سخت‌گیرانه‌ترین. یک فایل `zz-relax` می‌تواند فایل `aa-strict` را بی‌اثر کند. نام را طوری بگذارید که این اتفاق تصادفی نباشد و از فایل دوم برای «موقت، قول می‌دهم برمی‌گردانم» استفاده نکنید.

## Installation

بسته معمولاً با خود سیستم هست، چون کاربر نصب عضو گروه sudo است. اگر دستور پیدا نشد:

```bash
apt-cache policy sudo
sudo apt install sudo
```

اگر هیچ مدیر sudo ندارید، `apt install` را هم نمی‌توانید با sudo بزنید. از کنسول بازیابی باید وارد شوید. پیشگیری: قبل از آزمایش این صفحه دو نشست باز داشته باشید.

بررسی وضع فعلی، بدون عوض کردن چیزی:

```bash
id ops
sudo -l
sudo -l -U deploy
ls -l /etc/sudoers /etc/sudoers.d
```

`sudo -l` برای خودتان رمز می‌پرسد و دستورهای مجاز را نشان می‌دهد. برای `deploy` باید تقریباً هیچ دستور مفیدی نباشد، یا فقط همان reload اگر این صفحه را قبلاً تمام کرده‌اید. `ls` باید فایل اصلی را `0440` و مال `root:root` نشان بدهد. پوشهٔ `sudoers.d` هم باید برای دیگران غیرقابل نوشتن باشد.

یک بار نحو کل پیکربندی را بسنجید:

```bash
sudo visudo -c
```

خروجی سالم:

```text
/etc/sudoers: parsed OK
/etc/sudoers.d/README: parsed OK
```

اگر فایل دیگری از قبل هست و OK نیست، همان را با `visudo -f` باز کنید قبل از اینکه فایل جدید اضافه کنید. README داخل پوشه را پاک نکنید. نامش نقطه ندارد و sudo آن را می‌خواند، ولی محتوایش توضیح است نه قانون اجرایی، چون کامنت است. اگر روزی کسی آنجا قانون فعال گذاشت، آن قانون واقعی است. فایل را دوره‌ای بخوانید.

## Configuration

قانون `deploy` را با visudo بسازید نه با ریدایرکت شل. visudo اگر نحو بد باشد فایل را نصب نمی‌کند.

```bash
sudo visudo -f /etc/sudoers.d/ops-deploy
```

محتوا:

```text
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl reload portal.service, /usr/bin/systemctl status portal.service
```

`ALL` اول یعنی از هر میزبانی که این فایل رویش باشد. `(root)` یعنی فقط به‌عنوان روت، نه به‌عنوان هر کاربر. فهرست دستور ویرگول‌جدا است و هر کدام مسیر مطلق دارد. reload و status همان واحد `portal.service` است. `restart` را عمداً نداده‌ام تا اسکریپت نتواند سرویس را بچرخاند اگر reload کافی است. اگر استقرار شما واقعاً restart می‌خواهد، همان زیر‌دستور را صریح اضافه کنید نه `systemctl` خالی را.

چیزهایی که در این فایل نمی‌نویسیم:

```text
ops ALL=(ALL) NOPASSWD: ALL
deploy ALL=(ALL) NOPASSWD: ALL
%sudo ALL=(ALL) NOPASSWD: ALL
```

هیچ‌کدام حتی «موقت» قبول نیست. رمز `ops` فراموش‌شدنی است و راه درست بازنشانی رمز از کنسول است، نه برداشتن رمز sudo.

حالت فایل را visudo خودش `0440` می‌گذارد. اگر فایل را جای دیگری ساخته‌اید:

```bash
sudo chown root:root /etc/sudoers.d/ops-deploy
sudo chmod 0440 /etc/sudoers.d/ops-deploy
sudo visudo -c
```

اگر `visudo -c` خطا داد، sudo ممکن است کل پوشه را نادیده بگیرد یا همان فایل را رد کند. پیام، شمارهٔ خط را دارد. فایل را دوباره با `visudo -f` باز کنید. تا OK ندیده‌اید نشست روت فعلی را نبندید.

تست به‌جای `deploy`، بدون دادن پوسته به او:

```bash
sudo -l -U deploy
sudo -u deploy sudo -n /usr/bin/systemctl status portal.service
```

`-n` یعنی اگر رمز خواست شکست بخور، معطل پرامپت نمان. status حتی وقتی واحد هنوز نصب نشده پیام خودش را می‌دهد، ولی نباید `a password is required` بگوید. یک دستور خارج از قانون باید شکست بخورد:

```bash
sudo -u deploy sudo -n /usr/bin/systemctl restart ssh.service
```

خروجی سالم این شکست:

```text
sudo: a password is required
```

یا اینکه دستور در فهرست مجاز نیست. هر دو یعنی قانون گسترده نشده. اگر restart بدون رمز اجرا شد، قانون شما `ALL` است یا مسیر را بیش از حد باز کرده‌اید. فایل را همان لحظه تنگ کنید.

برای خوانایی قانون‌های بیشتر از دو دستور، نام مستعار دستور مجاز است. باز هم هر مسیر مطلق است:

```text
Cmnd_Alias PORTAL_OPS = /usr/bin/systemctl reload portal.service, /usr/bin/systemctl status portal.service
deploy ALL=(root) NOPASSWD: PORTAL_OPS
```

نام مستعار را در همان فایل محلی بگذارید. لازم نیست فایل اصلی را باز کنید.

## Production Example

استقرار فرضی می‌خواهد بعد از کپی فایل، سرویس را reload کند و انسان پای نشست نیست. اسکریپت مال روت است، `root:deploy` با حالت `0750`، و فقط همان sudo محدود را صدا می‌زند. خود اسکریپت را `deploy` نمی‌تواند بنویسد.

```bash
sudo install -o root -g deploy -m 0750 /dev/null /usr/local/sbin/portal-reload
```

محتوا را با `visudo` قاطی نکنید. این یک اسکریپت شل است:

```bash
sudo tee /usr/local/sbin/portal-reload >/dev/null <<'EOF'
#!/bin/sh
set -eu
exec /usr/bin/sudo -n /usr/bin/systemctl reload portal.service
EOF
sudo chown root:deploy /usr/local/sbin/portal-reload
sudo chmod 0750 /usr/local/sbin/portal-reload
```

`set -eu` اگر sudo رد کند اسکریپت را با وضعیت غیرصفر تمام می‌کند. تست:

```bash
sudo -u deploy /usr/local/sbin/portal-reload
```

اگر واحد `portal.service` هنوز وجود ندارد، systemctl خطا می‌دهد. آن خطا با خطای sudo فرق دارد. متن `Failed to reload portal.service: Unit portal.service not found` یعنی sudo اجازه داده و واحد نیست. بروید سراغ صفحهٔ [مدیریت سرویس](/docs/01-linux/service-management). متن `password is required` یعنی قانون sudo دیده نشده.

لاگ را در journal ببینید:

```bash
journalctl -t sudo --since "today" --no-pager
```

باید نام `deploy` و مسیر `systemctl` را ببینید. اگر این خط‌ها نیست، یا دستور واقعاً اجرا نشده یا journal پایدار نیست و بوت شده‌اید. صفحهٔ [journalctl](/docs/01-linux/journalctl) را برای ماندگاری لاگ ببینید. بدون لاگ، sudo فقط یک در است نه یک حسابرسی.

مهلت را در پایان کار تعاملی پاک کنید تا نشست باز روی میز، دستور بعدی را بی‌رمز نزند:

```bash
sudo -k
```

اگر سازمان می‌خواهد مهلت صفر باشد، در فایل جدا این را بگذارید نه در فایل اصلی:

```text
Defaults timestamp_timeout=0
```

این خط رمز را برای هر دستور `ops` دوباره می‌پرسد. آن را اول در آزمایشگاه امتحان کنید. فراموش کردنش وسط حادثه مدیر را عصبانی می‌کند ولی قفلش نمی‌کند. `NOPASSWD: ALL` را به‌عنوان «راه حل عصبانیت» اضافه نکنید.

## Security Notes

- `NOPASSWD: ALL` برای `ops`، برای `deploy`، و برای `%sudo` ممنوع است. استثنای بدون رمز فقط مسیر مطلق و آرگومان ثابت است.
- فایل قانون را `deploy` نباید بنویسد. اگر می‌تواند `/etc/sudoers.d` را بنویسد، دیگر به sudo نیاز ندارد تا روت شود.
- اسکریپتی که sudo صدا می‌زند مال روت باشد. اگر مال `deploy` و نوشتنی باشد، متن اسکریپت را عوض می‌کند و قانون شما را به هر کاری که آن متن بگوید گسترش می‌دهد، در حد همان دستوری که مجاز است. به همین دلیل حتی دستور مجاز نباید `bash` یا `python` بدون آرگومان قفل‌شده باشد.
- ویرایشگر پیش‌فرض visudo اگر فایل پشتیبان `ops-deploy~` بسازد، sudo آن را نادیده می‌گیرد. اتفاقی خوب است. فایل پشتیبان را به‌عنوان نسخهٔ دوم نگه ندارید. یکی باید حقیقت باشد.
- `sudo -i` و `sudo su -` را در اسکریپت نگذارید. در کار تعاملی هم عادت نکنید.
- رمز sudo همان رمز حساب است. آن را در متغیر محیطی یا در فایل واحد systemd نگذارید. حساب سرویس نباید رمز sudo داشته باشد. او یا `NOPASSWD` محدود دارد یا اصلاً sudo ندارد.

## Troubleshooting

| نشانه | علت محتمل | کار |
| --- | --- | --- |
| `sudo: parse error` نزدیک خطی از sudoers | نحو خراب است و شاید هنوز فایل قدیمی فعال باشد | نشست باز را نبندید، `sudo visudo -f` همان فایل |
| `visudo -c` سالم است، `sudo -l -U deploy` قانون را ندارد | نام فایل نقطه دارد یا `#includedir` پاک شده | `ls /etc/sudoers.d` و `grep includedir /etc/sudoers` |
| `deploy is not allowed to run` | قانون برای دستور دیگری است یا کاربر عوضی است | `sudo -l -U deploy` عین مسیر را مقایسه کنید |
| `a password is required` با وجود NOPASSWD | دستور دقیقاً همان رشته نیست. مثلاً `restart` به‌جای `reload` | مسیر را از `command -v systemctl` بگیرید |
| همهٔ sudoها می‌گویند policy plugin error | فایل `0440` نیست یا مالک روت نیست | از نشست روت `chmod 0440` و `chown root:root` |
| بعد از ویرایش، هنوز رفتار قدیم | فایل دوم دیرتر قانون را باز می‌کند | `ls /etc/sudoers.d` و آخرین تطبیق |

بازیابی وقتی sudo کاملاً مرده و تنها نشست هم بسته شده: کنسول VM یا recovery. Ubuntu روت را با `su` بدون رمز راه نمی‌دهد. در GRUB می‌شود برای یک بوت، init را پوسته کرد. آن روش را این‌جا به‌صورت دستور آماده نمی‌آورم چون روی سرور تولیدی همان دستور یک در پشتی دائمی می‌شود اگر کسی آن را در پیکربندی بوت ماندگار کند. پیشگیری عملی این صفحه همان دو نشست باز و `visudo` است، نه حفظ یک پوستهٔ روت همیشگی.

اگر `#includedir` را تصادفاً کامنت واقعی کرده‌اید، قانون پوشه هرگز خوانده نمی‌شود و `visudo -c` باز هم ممکن است فقط فایل اصلی را OK نشان بدهد. خط را به شکل `#includedir /etc/sudoers.d` برگردانید، با همان هش چسبیده به کلمه.

تست منفی را بعد از هر تغییر قانون تکرار کنید: دستوری که نباید مجاز باشد، با `sudo -n`، باید رمز بخواهد یا رد شود.

## Best Practices

- فایل اصلی `/etc/sudoers` را برای سلیقه عوض نکنید. قانون سازمان در `/etc/sudoers.d` با نام بدون نقطه باشد.
- فقط `visudo` و `visudo -f` و `visudo -c`. اگر OK نیست، کسی خارج نشود.
- `ops` با رمز و از راه گروه `sudo`. `deploy` بدون گروه sudo و حداکثر با یک فهرست کوتاه `NOPASSWD`.
- مسیر دستور را از `command -v` بردارید. `systemctl` در عمل `/usr/bin/systemctl` است. اگر روزی مسیر عوض شد قانون می‌شکند و این شکست امن‌تر از وایلدکارت است.
- لاگ `journalctl -t sudo` را در حادثهٔ «چه کسی این را ری‌استارت کرد» اول ببینید.
- هر قانون تازه یک تست مثبت و یک تست منفی دارد. تست منفی را همان روز بنویسید و اجرا کنید.
