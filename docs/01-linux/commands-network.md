# دیدن سوکت و مسیر

## مقدمه

این صفحه سوکت را نشان می‌دهد: کدام فرایند به کدام پورت گوش می‌دهد و اتصال‌ها در چه حالتی هستند. جدول مسیریابی و معنای آدرس در [مبانی شبکه](/docs/11-networking/fundamentals) است. اینجا ابزار مشاهده روی خود میزبان است، نه طراحی شبکه.

دو دستور با یک کار تاریخی‌اند و وضعیتشان روی Ubuntu Server 26.04 یکی نیست. `ss` از بستهٔ `iproute2` است و روی سرور هست. هسته را از راه netlink می‌پرسد. `netstat` از بستهٔ `net-tools` است و در نصب پیش‌فرض نیست. runbook قدیمی که فقط `netstat -tulpn` دارد روی `app-1` تازه با `command not found` می‌میرد. هر دو را بلد باشید تا خروجی قدیمی را بخوانید، ولی دستور روزمره `ss` است.

بودن بسته را حدس نزنید:

```bash
apt-cache policy iproute2 net-tools
command -v ss
command -v netstat || true
ss -V
```

`ss -V` را در تیکت بنویسید اگر رفتار فیلتر با این صفحه فرق داشت. عدد نسخه را از پیش ننویسید.

آزمایشگاه: `proxy` روی `10.10.1.5` به nginx روی `app-1` (`10.10.1.10`) وصل می‌شود. برنامهٔ Node روی همان میزبان به `127.0.0.1:3000` گوش می‌دهد. PostgreSQL روی `db-1` (`10.10.1.20`). اگر پورت بالا نیست، قدم بعدی `systemctl` است نه نصب دوبارهٔ بسته.

خطر این صفحه تفسیر غلط حالت سوکت است. `TIME-WAIT` معمولاً سالم است. `CLOSE-WAIT` انباشته یعنی برنامه سوکت را نمی‌بندد. سرویس `active` بدون خط `LISTEN` یعنی فرایند هست و به درخواستی که می‌فرستید گوش نمی‌دهد. و برعکس، `ss` کد خروج را فقط به‌خاطر بسته بودن پورت غیرصفر نمی‌کند. اسکریپت باید خروجی را ببیند.

## netstat

### توضیح

`netstat` خروجی را از `/proc/net` می‌خواند. بستهٔ `net-tools` سال‌هاست حالت نگهداری قدیمی دارد و Ubuntu آن را در سیستم پایهٔ 26.04 نمی‌گذارد. اگر runbook یا یک هم‌تیمی هنوز خروجی‌اش را می‌فرستد، باید بتوانید ستون‌ها را بخوانید. برای کار جدید دستور را به `ss` ترجمه کنید، نه اینکه `net-tools` را روی همهٔ میزبان‌ها استاندارد کنید.

نصب فقط وقتی لازم است که باید یک اسکریپت کهنه را موقتاً اجرا کنید:

```bash
sudo apt update
sudo apt install net-tools
dpkg -S "$(command -v netstat)"
```

`dpkg -S` باید بسته را `net-tools` نشان بدهد. اگر `command -v netstat` خالی بود، همان جملهٔ «پیش‌فرض نیست» را دارید نه یک خرابی شبکه.

شکل آشنای runbook قدیمی `netstat -tulpn` است. `-t` تی‌سی‌پی، `-u` یودی‌پی، `-l` فقط گوش‌دهنده، `-p` نام فرایند، `-n` عددی بدون تلاش DNS. بدون `-n` ممکن است برای هر آدرس معکوس DNS معطل شوید، درست وسط حادثه. `-p` برای سوکت کاربران دیگر به امتیاز root نیاز دارد وگرنه ستون برنامه خالی یا خط تیره است.

ستون‌ها: Proto، Recv-Q، Send-Q، Local Address، Foreign Address، State، و PID/Program name. در خط `LISTEN` آدرس خارجی `0.0.0.0:*` یعنی «هنوز همتا نداریم»، نه اینکه به همه‌جا وصلید. آدرس محلی `0.0.0.0:443` یعنی روی همهٔ رابط‌ها گوش می‌دهید. `127.0.0.1:3000` یعنی فقط از خود میزبان قابل اتصال است. `10.10.1.10:5432` یعنی فقط روی آن آدرس.

`netstat -s` خلاصهٔ شمارنده است، معادل تقریبی `ss -s`، با جزئیات بیشتر و قالب متنی کهنه. برای تیکت امروز `ss -s` کافی و کوتاه‌تر است.

### مثال واقعی

بعد از نصب موقت، همان دو پرسمان که مردم با `netstat` بلدند، روی `app-1`:

```bash
sudo netstat -tulpn
sudo netstat -s | head -n 20
```

```text
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      640/sshd
tcp        0      0 0.0.0.0:443             0.0.0.0:*               LISTEN      812/nginx
tcp        0      0 127.0.0.1:3000          0.0.0.0:*               LISTEN      1842/node
tcp        0      0 10.10.1.10:443          10.10.1.5:51234         ESTABLISHED 812/nginx
udp        0      0 127.0.0.53:53           0.0.0.0:*                           520/systemd-resolve
```

ترجمهٔ همان مشاهده به ابزار اصلی، تا کنار هم ببینید یکی‌اند:

```bash
sudo ss -lptn
sudo ss -lun
```

`-lptn` گوش‌دهندهٔ تی‌سی‌پی عددی با فرایند است. یودی‌پی در `ss` با `-u` جدا می‌شود چون حالت `LISTEN` یودی‌پی با تی‌سی‌پی یکی نیست. `netstat -tulpn` هر دو را در یک جدول قاطی می‌کند و این تنها راحتی واقعی آن است، نه دلیل ماندنش.

### کاربرد Production

اگر نیمه‌شب فقط خروجی `netstat` یک هم‌تیم از `app-1` در تیکت است، از روی آن تصمیم بگیرید و بعد خودتان `ss` بگیرید. در نمونهٔ بالا `443` روی nginx است و `3000` فقط روی حلقهٔ محلی. پروکسی `10.10.1.5` حق دارد به ۴۴۳ وصل شود و حق ندارد مستقیم به ۳۰۰۰ برسد. اگر کسی Node را به `0.0.0.0:3000` عوض کند، `netstat` آن را با `0.0.0.0:3000` نشان می‌دهد و یعنی پورت برنامه پشت فایروال میزبان، اگر باز باشد، از کل `10.10.1.0/24` دیده می‌شود. آن را با [UFW](/docs/10-security/ufw) ببندید و برنامه را به `127.0.0.1` برگردانید. خود `netstat` چیزی را امن نمی‌کند.

روی `db-1` خط قدیمی `0.0.0.0:5432` یعنی پستگرس روی همهٔ رابط‌ها گوش می‌دهد. انتظار این آزمایشگاه گوش دادن روی `10.10.1.20` یا حداقل محدود به شبکهٔ داخلی است، نه روی رابطی که نباید وجود داشته باشد. دیدن این خط شروع بررسی `listen_addresses` است، نه نصب `net-tools` روی بقیهٔ رک.

بسته را بعد از تمام شدن کار کهنه لازم نیست حذف کنید، ولی در image استاندارد و در اسکریپت سلامت به `netstat` تکیه نکنید. فردا یک نصب حداقلی دوباره `command not found` می‌دهد.

### وقتی خراب می‌شود

```text
netstat: command not found
(Not all processes could be identified, non-owned process info
 will not be shown, you would have to be root to see it all.)
```

اولی خرابی شبکه نیست. `sudo apt install net-tools` اگر واقعاً به خود `netstat` نیاز دارید، وگرنه همان لحظه `ss` را اجرا کنید و وقت را سر apt نگذارید. پیام دوم یعنی `-p` بدون root. پورت را می‌بینید و PID را نه. برای «کی گوش می‌دهد» باید `sudo` باشد. بدون PID، nginx و یک کانتینر هر دو می‌توانند ادعا کنند مال آن‌هاست.

`netstat` ممکن است روی میزبان شلوغ کند باشد چون `/proc/net/tcp` را می‌خواند. اگر وسط حادثه فرمان «گیر کرد»، اغلب معکوس DNS است. Ctrl+C و دوباره با `-n`. اگر باز هم کند است، به `ss` بروید و منتظر `netstat` نمانید.

خروجی خالی `netstat -tulpn` بدون خطا یعنی واقعاً چیزی با آن فیلتر گوش نمی‌دهد، یا فیلتر را بد زده‌اید. قبل از ری‌استارت سرویس، یک بار `ss -lptn` را هم ببینید تا مطمئن شوید ابزار کهنه چیزی را پنهان نکرده.

## ss

### توضیح

`ss` ابزار اصلی دیدن سوکت است. گزینه‌هایی که هر شیفت لازم دارد:

- `-l` فقط گوش‌دهنده.
- `-p` فرایند صاحب سوکت. برای فرایند دیگران، `sudo`.
- `-t` تی‌سی‌پی و `-u` یودی‌پی. `-n` عددی، بدون DNS.
- `-a` شامل غیر گوش‌دهنده هم. بدون `-l` و با `-a` جدول شلوغ می‌شود.
- `-s` خلاصهٔ تعداد، نه فهرست خط‌به‌خط.

`ss -lptn` یعنی: تی‌سی‌پی، فقط LISTEN، با نام فرایند، عددی. این اولین دستور روی `app-1` است وقتی کسی می‌گوید سایت بالا نیست.

فیلتر را یک آرگومان نقل‌قول‌شده بدهید تا پوسته آن را نشکند. مثال‌ها پایین، داخل فنس‌اند. فیلتر `sport` پورت محلی است و `dport` پورت دور. `dst` آدرس مقصد است.

حالت (State) تی‌سی‌پی را این‌طور بخوانید:

| حالت | معنی عملی |
| --- | --- |
| LISTEN | سوکت منتظر اتصال تازه است. اگر این خط برای پورت سرویس نیست، از بیرون به شما جواب نمی‌دهند |
| ESTAB | اتصال برقرار است. در `ss` نام را کوتاه می‌بینید |
| TIME-WAIT | یکی از دو طرف بسته شدن را تمام کرده و سوکت هنوز چند ده ثانیه نگه داشته می‌شود تا بسته‌های دیررس قاطی اتصال بعدی نشوند. انبوه بودنش بعد از یک موج اتصال کوتاه طبیعی است |
| CLOSE-WAIT | طرف دور بسته، طرف محلی هنوز `close` نکرده. انبوه بودنش باگ برنامه است، نه «کمبود پورت» |
| SYN-SENT | ما داریم وصل می‌شویم و جواب دست‌دادن نیامده. مقصد خاموش است، فیلتر شده، یا مسیر نیست |
| SYN-RECV | دست‌دادن نصفه به سمت ما. موج آن می‌تواند بار یا پویش باشد |
| FIN-WAIT-1 و FIN-WAIT-2 | بستن از سمت ما شروع شده و هنوز تمام نشده |

`ss` اگر هیچ خطی چاپ نکند معمولاً کد ۰ برمی‌گرداند. «پورت ۴۴۳ گوش نمی‌دهد» را باید با دیدن خروجی بفهمید، نه با `echo $?`. این برعکس `grep` است که نبودن الگو کد ۱ می‌دهد. در اسکریپت، خروجی را به `grep -q` بدهید و کد ۱ grep را داخل `if` بگذارید، همان‌طور که در [پردازش متن](/docs/01-linux/commands-text) آمده، تا `set -e` اسکریپت را بی‌جهت نکشد و کد ۲ (خطای خود grep) را هم قورت ندهید.

وقتی پورت مورد انتظار در `-l` نیست، زنجیره این است: `systemctl is-active` و `systemctl status` همان واحد، بعد `journalctl -u` برای خطای bind، بعد دوباره `ss`. خیلی وقت‌ها سرویس `failed` است چون پورت را کس دیگری گرفته، یا `active` است ولی به آدرس دیگری گوش می‌دهد، یا اصلاً واحد را enable نکرده‌اید و بعد از بوت بالا نیامده. `ss` جای `systemctl` نیست و `systemctl` جای `ss` نیست. هر دو را بخواهید. واحد و لاگ در [مدیریت سرویس](/docs/01-linux/service-management) و [journalctl](/docs/01-linux/journalctl) است.

### مثال واقعی

گوش‌دهنده‌های تی‌سی‌پی روی `app-1`:

```bash
sudo ss -lptn
sudo ss -lptn 'sport = :443'
sudo ss -lptn 'sport = :3000'
sudo ss -s
```

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      511        0.0.0.0:443       0.0.0.0:*    users:(("nginx",pid=812,fd=8))
LISTEN 0      511      127.0.0.1:3000      0.0.0.0:*    users:(("node",pid=1842,fd=20))
LISTEN 0      128        0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=640,fd=3))
Total: 248
TCP:   42 (estab 18, closed 6, orphaned 0, timewait 6)
```

عددهای `ss -s` با بار عوض می‌شوند. چیزی که باید ببینید وجود دارد: یک خط برای ۴۴۳ و یک خط برای ۳۰۰۰. اگر فیلتر پورت هیچ خطی نداد، آن پورت روی هیچ آدرسی LISTEN نیست.

اتصال‌های برقرار به پایگاه، از خود `app-1`:

```bash
sudo ss -tnp state established dst 10.10.1.20
```

```text
State Recv-Q Send-Q Local Address:Port   Peer Address:Port Process
ESTAB 0      0      10.10.1.10:48122    10.10.1.20:5432 users:(("node",pid=1842,fd=22))
```

اگر این خط نیست، برنامه اصلاً به `db-1` وصل نشده. قبل از دستکاری PostgreSQL، لاگ خود Node را ببینید.

انباشت CLOSE-WAIT، که دیگر «طبیعی بعد از ترافیک» نیست:

```bash
sudo ss -tan state close-wait | head
```

سرستون را بشمارید. اگر ده‌ها خط مال PID همان `node` است، فرایند اتصال مرده را رها کرده. ری‌استارت واحد بعد از دیدن این الگو معنی دارد. ری‌استارت بدون این مشاهده یعنی حدس.

یودی‌پی محلی، برای وقتی DNS میزبان شک دارید:

```bash
sudo ss -lunp
```

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
UNCONN 0      0      127.0.0.53%lo:53        0.0.0.0:*    users:(("systemd-resolve",pid=520,fd=14))
```

`UNCONN` برای یودی‌پی عادی است. آن را با «اتصال شکسته» اشتباه نگیرید.

nginx روی Ubuntu اغلب دو سوکت برای یک پورت می‌سازد، یکی IPv4 و یکی IPv6. اگر اسکریپت فقط `0.0.0.0:443` را بگردد و خط دوم را نادیده بگیرد، گاهی به اشتباه می‌گوید پورت بالا نیست:

```bash
sudo ss -lptn 'sport = :443'
```

```text
LISTEN 0 511 0.0.0.0:443 0.0.0.0:* users:(("nginx",pid=812,fd=8))
LISTEN 0 511    [::]:443    [::]:* users:(("nginx",pid=812,fd=9))
```

`[::]` یعنی همهٔ آدرس‌های IPv6. پروکسی `10.10.1.5` از IPv4 می‌آید، پس خط `0.0.0.0:443` یا `10.10.1.10:443` همان چیزی است که برای این آزمایشگاه لازم است. خط IPv6 به‌تنهایی به معنی در دسترس بودن از `10.10.1.0/24` نیست.

شمارش حالت‌ها وقتی جدول شلوغ است، بدون ری‌استارت احساسی:

```bash
sudo ss -tan state time-wait | wc -l
sudo ss -tan state close-wait | wc -l
sudo ss -tan state syn-sent | wc -l
```

`wc` سرستون را هم می‌شمارد. عدد کوچک time-wait بعد از ترافیک عادی است. close-wait که با هر بار اجرا بزرگ‌تر می‌شود باگ فرایندی است که در ستون Process همان دستور، بدون `state`، با `-p` دیده می‌شود.

### کاربرد Production

سایت از بیرون خطای 502 می‌دهد و `systemctl is-active nginx` روی `app-1` کلمهٔ `active` چاپ می‌کند. این کافی نیست. `ss -lptn 'sport = :443'` باید nginx را نشان بدهد و `ss -lptn 'sport = :3000'` باید Node را روی `127.0.0.1` نشان بدهد. سه حالت پرتکرار:

- ۴۴۳ نیست و nginx فعال است: پیکربندی به آدرس دیگری bind کرده یا `nginx -t` بعد از reload قبلی رد شده و فرایند قدیمی مرده. `journalctl -u nginx -n 50 --no-pager` و `nginx -t`.
- ۴۴۳ هست و ۳۰۰۰ نیست: nginx سالم است و بالادست نیست. `systemctl status shop.service` و سیگنال را از [صفحهٔ پردازش](/docs/01-linux/commands-process) با عجله نزنید تا status را ببینید.
- هر دو LISTEN هستند و از خود میزبان `curl -fsS` به `127.0.0.1:3000/health` جواب می‌دهد، ولی از `10.10.1.5` نه: یا nginx به رابط اشتباه گوش می‌دهد (`127.0.0.1:443` به‌جای آدرسی که پروکسی می‌بیند) یا فایروال است. `ss` فرق `127.0.0.1:443` و `0.0.0.0:443` و `10.10.1.10:443` را در ستون آدرس محلی نشان می‌دهد. فایروال را جدا ببینید.

روی `db-1` انتظار این است که `ss -lptn 'sport = :5432'` آدرس `10.10.1.20` را نشان بدهد، و از `app-1` اتصال ESTAB به همان پورت دیده شود. اگر روی `db-1` خط LISTEN نیست، `systemctl status postgresql` و لاگ واحد را بخوانید. کلاستر 18 اگر به‌خاطر پر بودن دیسک یا پیکربندی `listen_addresses` بالا نیاید، پورت را نمی‌گیرد در حالی که بستهٔ PostgreSQL نصب است. نصب بودن بسته را با گوش دادن پورت یکی ندانید.

اسکریپت سلامت روی خود `app-1` که نباید با کد ۱ بی‌جهت بمیرد و نباید پورت بسته را موفقیت حساب کند:

```bash
#!/bin/bash
set -euo pipefail
if ! sudo ss -lptn 'sport = :3000' | grep -q ':3000'; then
  echo "node not listening on app-1" >&2
  systemctl status shop.service --no-pager >&2 || true
  exit 1
fi
```

`if` کد ۱ را وقتی پورت نیست از `grep` می‌گیرد و به `exit 1` خودمان تبدیل می‌کند. `systemctl status` روی واحد مرده غیرصفر است. اینجا `|| true` فقط برای چاپ وضعیت است، چون تصمیم خروج را خودمان جداگانه گرفته‌ایم. اگر `ss` اصلاً نباشد، `set -e` قبل از `if` اسکریپت را می‌کشد و این درست است: ابزار مشاهده خراب است و نباید بگوییم سرویس سالم است.

### وقتی خراب می‌شود

```text
ss: command not found
Cannot open netlink socket: Operation not permitted
```

اولی یعنی `iproute2` روی این سیستم حداقلی نیست، که برای Ubuntu Server غیرعادی است. `apt-cache policy iproute2` و نصب از مخزن اوبونتو، نه کپی باینری. دومی یعنی جایی بدون حق کافی، مثلاً بعضی محیط‌های محدود، netlink بسته است. `sudo ss` را امتحان کنید. اگر با sudo هم netlink نبود، مشکل قابلیت محیط است نه پورت سرویس.

فیلتر بد، پیام نحوی می‌دهد یا هیچ خطی نمی‌دهد در حالی که پورت بالا است:

```text
ss: bison bawled (while parsing filter): "syntax error!"
```

نقل‌قول فیلتر را درست کنید. بدون نقل‌قول، پوسته `>` یا پرانتز را اگر در فیلتر پیشرفته باشد می‌خورد. شکل‌های این صفحه را همان‌طور که داخل فنس آمده اجرا کنید.

اشتباه تفسیری که پیامی ندارد: دیدن `TIME-WAIT` زیاد و ری‌استارت nginx. بعد از موج اتصال کوتاه این حالت طبیعی است و با ری‌استارت فقط قطعی تازه می‌سازید. `CLOSE-WAIT` زیاد را برعکس، رها نکنید. و سرویس `active` را با «پورت در دسترس پروکسی» یکی ندانید تا آدرس ستون Local را بخوانید.

`Recv-Q` روی یک خط LISTEN که مدام بالا می‌ماند یعنی صف پذیرش پر است و برنامه `accept` نمی‌کند. یک خط LISTEN هنوز کافی نیست. اگر صف گوش دادن پر باشد، `curl` از بیرون زمان تمام می‌کند در حالی که `ss -l` پورت را نشان می‌دهد. آن مشاهده را کنار `%CPU` همان PID در `ps` بگذارید.

حالت برعکس «پورت بالا نیست»: واحد اصلاً بالا نمی‌آید چون پورت را فرایند دیگری گرفته. در `journalctl -u shop.service` این را می‌بینید:

```text
bind() to 127.0.0.1:3000 failed (98: Address already in use)
```

`systemctl status` اینجا `failed` است، نه اینکه پورت خاموش باشد. مالک واقعی را `ss` می‌گوید:

```bash
sudo ss -lptn 'sport = :3000'
```

اگر PID یک `node` مانده از استقرار قبلی است، اول همان را با SIGTERM جمع کنید، همان سیاست [صفحهٔ پردازش](/docs/01-linux/commands-process)، بعد `systemctl start shop.service`. start دوباره تا وقتی آن PID هست خطای ۹۸ را تکرار می‌کند. کشتن nginx به‌جای آن PID، ۴۴۳ را هم پایین می‌آورد و ۵۰۲ را بدتر می‌کند.

## Best Practices

- روزمره فقط `ss`. `netstat` را برای خواندن خروجی کهنه بلد باشید. `net-tools` را وارد image استاندارد نکنید. اگر لازم شد، با apt نصب شود و `dpkg -S` بسته‌اش را نشان بدهد.
- اولین دستور حادثه روی `app-1`: `sudo ss -lptn` و فیلتر پورت ۴۴۳ و ۳۰۰۰. روی `db-1`: پورت ۵۴۳۲ و آدرس محلی `10.10.1.20`. عددی کار کنید تا DNS معکوس شما را معطل نکند.
- `systemctl is-active` را با LISTEN یکی ندانید. اگر پورت نیست: status، journal واحد، `nginx -t` اگر وب‌سرور است، دوباره `ss`.
- `TIME-WAIT` را باگ نخوانید. `CLOSE-WAIT` انباشته را باگ محلی بخوانید. `SYN-SENT` ماندگار یعنی مقصد یا مسیر، از جمله `db-1` که گوش نمی‌دهد.
- کد خروج `ss` خالی بودن پورت را نمی‌گوید. در اسکریپت خروجی را با `grep` داخل `if` بسنجید.
- آدرس `0.0.0.0` و `127.0.0.1` تصمیم امنیتی‌اند. برنامه را به حلقهٔ محلی محدود کنید و فقط nginx را سمت `proxy` بگذارید. فایروال جای گوش دادن روی همهٔ رابط‌ها را پر نمی‌کند، ولی برعکسش هم صادق است: بستن در UFW را با `ss` تأیید نمی‌کنید. هر دو را ببینید.
