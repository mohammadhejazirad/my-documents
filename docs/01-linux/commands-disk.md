# دیسک و اتصال

## مقدمه

`mount` نشان می‌دهد کدام دستگاه به کدام مسیر وصل است. `df` ظرفیت فایل‌سیستم را می‌گوید. `du` جمع اندازهٔ درخت فایل را. این سه تا را به‌جای هم به کار نبرید. حادثهٔ پرتکرار این است که `df` نود درصد را نشان می‌دهد، `du` روی همان مسیر خیلی کمتر جمع می‌کند، و کسی شروع می‌کند فایل پاک کند بدون اینکه بفهمد فضا مال یک فایل حذف‌شده است که هنوز باز است، یا مال فایل‌هایی که زیر یک mountpoint پنهان شده‌اند.

هر سه ابزار روی Ubuntu Server 26.04 هستند: `mount` و `findmnt` از `util-linux`، `df` و `du` از `coreutils`. `lsof` و `fuser` ممکن است در نصب حداقلی نباشند و برای «چه کسی دستگاه را گرفته» لازم می‌شوند. نسخه را از بسته بخوانید:

```bash
findmnt --version | head -n 1
df --version | head -n 1
du --version | head -n 1
apt-cache policy lsof psmisc
```

`fuser` در بستهٔ `psmisc` است. اگر نبود: `sudo apt install lsof psmisc`. وسط پر بودن دیسک، اگر apt خودش جا می‌خواهد، اول یک فایل بزرگ معلوم را جابه‌جا یا فشرده کنید، نه اینکه مخزن تازه اضافه کنید.

آزمایشگاه: برنامه روی `app-1` (`10.10.1.10`) و لاگ زیر `/var/log`. PostgreSQL 18 روی `db-1` (`10.10.1.20`) با داده زیر `/var/lib/postgresql/18/main`. بکاپ زیر `/var/backups`. نوع فایل‌سیستم و گزینهٔ `tune2fs` در [فایل‌سیستم](/docs/01-linux/filesystems) است. روش مرحله‌به‌مرحلهٔ دیسک پر در [دیسک پر](/docs/14-troubleshooting/disk-full) است. اینجا خود دستور است.

خطر عملی: `umount` دیسک دادهٔ روشن، `rm` روی مسیری که فکر می‌کنید دیسک جداست ولی هنوز روی ریشه است، و اعتماد به `df -h` وقتی خطا `No space left on device` است ولی جا نشان می‌دهد. آن حالت اغلب inode است و با `df -i` دیده می‌شود.

## mount

### توضیح

`mount` بدون آرگومان فهرست فعلی را از جدول هسته می‌خواند. برای کار روزمره `findmnt` خواناتر است: درخت، نوع، منبع، و گزینه‌ها. `findmnt -T /مسیر` می‌گوید آن مسیر روی کدام فایل‌سیستم است. قبل از پاک‌کردن هر چیز بزرگ این را بزنید. اگر انتظار دیسک داده را داشتید و `findmnt` ریشه را نشان داد، دارید روی دیسک سیستم جا خالی می‌کنید یا بدتر، فایل را جایی حذف می‌کنید که سرویس از جای دیگری می‌خواند.

`/etc/fstab` جدول اتصال هنگام بوت است. systemd با `systemd-fstab-generator` آن را به واحد mount تبدیل می‌کند. شش ستون: دستگاه، نقطهٔ اتصال، نوع، گزینه‌ها، dump، و ترتیب بررسی. دستگاه را با `UUID=` بنویسید نه با `/dev/sdb`. نام `sdX` بعد از اضافه شدن دیسک یا تغییر ترتیب شناسایی عوض می‌شود و بوت بعدی داده را جای غلط می‌گذارد یا اصلاً mount نمی‌کند.

UUID را از دیسک بخوانید:

```bash
lsblk -f
sudo blkid
```

گزینهٔ `nofail` برای دیسک بکاپی که اجازه دارید بدون آن هم بالا بیایید. بدون `nofail`، نبودن همان دیسک می‌تواند بوت را به حالت اضطراری ببرد و `db-1` با دیسک دادهٔ سالم ولی بدون دیسک بکاپ بالا نیاید. `noatime` نوشتن زمان دسترسی را کم می‌کند. `nodev` و `nosuid` و `noexec` را روی نقطهٔ بکاپ که نباید از آنجا برنامه اجرا شود بگذارید، نه کورکورانه روی `/var/lib/postgresql`.

بعد از ویرایش fstab:

```bash
sudo systemctl daemon-reload
sudo findmnt --verify
sudo mount -a
```

`findmnt --verify` خطاهای فستب را قبل از بوت بعدی نشان می‌دهد. `mount -a` هر چه در فستب است و هنوز وصل نیست را وصل می‌کند. این دو را به‌جای ری‌استارت کل ماشین استفاده کنید.

`umount` نقطهٔ اتصال یا دستگاه را جدا می‌کند. اگر کسی هنوز فایل باز دارد یا دایرکتوری جاری‌اش آنجاست، هسته رد می‌کند. پیام رایج `target is busy` است. آن‌وقت `lsof` یا `fuser`، نه تکرار بی‌فایده و نه `umount -l` به‌عنوان عادت. جدا کردن تنبل (`-l`) مسیر را از درخت نام فوراً برمی‌دارد ولی نوشتن روی فایل‌سیستم واقعی را تا بستن آخرین استفاده‌کننده ادامه می‌دهد. روی دیسک پایگاه یعنی فکر می‌کنید جدا شده، در حالی که پستگرس هنوز می‌نویسد، و یک mount دوباره می‌تواند وضعیت را قایم کند. روی `db-1` از `-l` استفاده نکنید.

`fuser -m` نشان می‌دهد کدام PID نقطه را گرفته. `fuser -km` همان‌ها را می‌کشد. شکل `-k` را روی `/var/lib/postgresql` نزنید. کشتن اتصال باز، توقف کثیف پایگاه است. اول ببینید PID چیست. اگر پوستهٔ خودتان است، `cd /` و دوباره `umount`. اگر پستگرس است، `systemctl stop postgresql` و بعد `umount`.

### مثال واقعی

دیدن اینکه دادهٔ واقعی کجاست، روی `db-1`:

```bash
findmnt -T /var/lib/postgresql/18/main
findmnt --verify
```

```text
TARGET                 SOURCE    FSTYPE OPTIONS
/var/lib/postgresql    /dev/sdb1 ext4   rw,noatime,noexec
```

اگر این دستور `/` را نشان داد، دیسک داده وصل نیست و هر فایلی که پستگرس ساخته روی همان فایل‌سیستم ریشه است. تا وقتی mount نشود، `du` روی نقطهٔ اتصال آن فایل‌های پنهان‌شونده را نشان می‌دهد. بعد از mount موفق، همان فایل‌ها زیر دستگاه جدید قایم می‌شوند و همچنان روی ریشه جا می‌گیرند. این یکی از دلیل‌های «پاک کردم ولی `df` روی `/` تکان نخورد» است.

یک خط فستب برای دیسک بکاپ، با UUID واقعی از `blkid` خودتان، نه این نمونه:

```text
UUID=7c2a1e0e-4b6a-4f1a-9c3d-2a11b0e6d4f8 /var/backups ext4 defaults,noatime,nofail,nodev,nosuid,noexec 0 2
```

اتصال و بررسی:

```bash
sudo systemctl daemon-reload
sudo findmnt --verify
sudo mount /var/backups
findmnt /var/backups
```

جدا کردن وقتی پوسته مزاحم است:

```bash
sudo umount /var/backups
cd /
sudo umount /var/backups
sudo lsof +f -- /var/backups | head
sudo fuser -vm /var/backups
```

خروجی نوعی وقتی هنوز کسی آنجاست:

```text
COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
bash    2201 ops   cwd    DIR   8,17     4096  128 /var/backups
                     USER        PID ACCESS COMMAND
/var/backups:        ops        2201 ..c.. bash
```

`cwd` یعنی دایرکتوری جاری. از آن پوسته بیرون بیایید و `umount` را تکرار کنید. لازم نیست فرایند را بکشید.

### کاربرد Production

روی `db-1` قبل از هر پاک‌سازی داخل `/var/lib/postgresql/18/main` یک بار `findmnt -T` بگیرید. اگر منبع، دیسک داده نیست، پستگرس را متوقف کنید، نقطه را خالی از فایل پنهان کنید یا فایل‌ها را به دیسک درست منتقل کنید، بعد دیسک را با UUID در fstab وصل کنید و سرویس را بالا بیاورید. بالا آوردن PostgreSQL وقتی داده روی ریشهٔ کوچک است، همان دیسک را پر می‌کند و کلاستر را هم ناسازگار با دیسک اصلی می‌کند اگر هر دو جا نوشته باشید.

دیسک بکاپ را با `nofail` وصل کنید تا خرابی دیسک دوم، خود پایگاه را از بوت نیندازد. بکاپ ناموفق را جدا پایش کنید. `nofail` به معنی «نبود بکاپ مهم نیست» نیست. یعنی «نبود دیسک بکاپ نباید ماشین را در emergency نگه دارد».

روی `app-1` معمولاً یک فایل‌سیستم ریشه کافی است. باز هم `findmnt -T /var/log` را ببینید. اگر لاگ را به دیسک جدا برده‌اید و آن دیسک mount نشده، nginx روی ریشه لاگ می‌نویسد تا `/` پر شود، و شما روی دیسک خاموش دنبال فایل می‌گردید.

`mount -a` را در اسکریپت هر دقیقه اجرا نکنید. یک بار بعد از تغییر fstab کافی است. تکرار آن روی خطای پیکربندی، لاگ را پر از شکست تکراری می‌کند.

### وقتی خراب می‌شود

```text
mount: /var/backups: wrong fs type, bad option, bad superblock on /dev/sdb1
umount: /var/backups: target is busy.
findmnt: /etc/fstab: parse error at line 6
```

اولی یعنی نوع در fstab با دیسک یکی نیست، یا دیسک خالی است و هنوز فایل‌سیستم ندارد. `blkid` و `lsblk -f` را ببینید. فایل‌سیستم نسازید تا مطمئن شوید این همان دیسک خالی است نه دیسک داده. `mkfs` خارج از این صفحه است و روی دیسک اشتباه یعنی از دست رفتن پایگاه.

دومی همان مشغول بودن است. `lsof` و `fuser -vm`، بعد تصمیم. اگر فقط پوسته است `cd /`. اگر سرویس است `systemctl stop`. `fuser -km` و `umount -l` راه‌حل صفحهٔ حادثه نیستند.

سومی یعنی یک نویسهٔ غلط در fstab و `mount -a` شاید نصف خط‌ها را وصل کرده باشد. `findmnt --verify` را قبل از ری‌استارت درست کنید. ری‌استارت با fstab شکسته می‌تواند ماشین را بالا نیاورد و آن‌وقت به کنسول نیاز دارید نه به SSH.

`mount` موفق روی نقطه‌ای که از قبل فایل داشت، آن فایل‌ها را پاک نمی‌کند. فقط پنهانشان می‌کند. اگر بعد از mount فضا روی `/` برنگشت، نقطه را فقط وقتی جدا کنید که سرویس از آن استفاده نمی‌کند، بعد محتوای پنهان را با `du` ببینید.

## df

### توضیح

`df` فضای فایل‌سیستم را از دید هسته نشان می‌دهد، نه جمع فایل‌هایی که شما اجازهٔ خواندنشان را دارید. شکل خوانا با نوع فایل‌سیستم: `df -hT`. `-h` واحد انسانی است و `-T` نوع را در ستون می‌گذارد تا ext4 را با tmpfs قاطی نکنید. `tmpfs` پر، دیسک فیزیکی را پر نکرده. حافظه است.

`df -h` جا را نشان می‌دهد و `df -i` inode را. inode تمام یعنی جای بایت هست ولی جای ورودی فایل جدید نیست. خطا در هر دو حالت اغلب یکی است: `No space left on device`. بدون `df -i` ساعت‌ها فایل بزرگ می‌گردید و چیزی پیدا نمی‌کنید، چون فایل بزرگ مقصر نیست. میلیون فایل ریز (نشست، کش، صف ایمیل، سوکت باقی‌مانده) inode را می‌خورد.

`df` بلوک رزرو ریشه را در ستون Available برای کاربر عادی کم می‌کند. روی ext4 پیش‌فرض حدود پنج درصد رزرو است. برای همین `Used` به‌علاوهٔ `Available` با `Size` یکی درنمی‌آید. این اختلاف با `du` یکی نیست. رزرو فایل قابل پاک کردن نیست. تغییر درصد رزرو در صفحهٔ فایل‌سیستم است و روی دیسک داده، قبل از دست زدن، بکاپ و دلیل می‌خواهد.

اختلاف مهم‌تر `df` و `du` این‌هاست:

- فایلی با `rm` از دایرکتوری حذف شده ولی یک فرایند هنوز آن را باز دارد. `du` دیگر نامی نمی‌بیند و جمع نمی‌کند. `df` تا بستن توصیف‌گر، بلوک‌ها را اشغال‌شده می‌داند. این همان حالتی است که «پاک کردم و فضا برنگشت».
- `du` بدون حق خواندن، دایرکتوری را رد می‌کند و کمتر جمع می‌کند. `df` کل فایل‌سیستم را از هسته می‌گوید.
- `du` اگر از `/` بدون `-x` شروع شود وارد mountهای دیگر می‌شود و یک بار همه‌چیز را نشان می‌دهد. `df` هر فایل‌سیستم را جدا می‌گوید. مقایسهٔ این دو عدد بی‌معنی است تا هر دو را به یک دستگاه محدود کنید.
- بلوک رزرو و فراداده در `du` به‌صورت فایل دیده نمی‌شوند.

کشف فایل حذف‌شدهٔ هنوز باز با `lsof` است. `+L1` یعنی تعداد پیوند کمتر از یک، یعنی نام در دایرکتوری نمانده:

```bash
sudo lsof +L1
```

در ستون نام، `(deleted)` می‌آید و SIZE/OFF اندازهٔ هنوز اشغال‌شده است. فضا وقتی آزاد می‌شود که آن PID توصیف‌گر را ببندد. برای لاگ، این اغلب یعنی reload اگر برنامه واقعاً فایل را دوباره باز کند، و خیلی وقت‌ها یعنی restart واحد. `rm` دوباره هیچ اثری ندارد. نوشتن در `/proc/PID/fd/...` برای خالی کردن فایل حذف‌شده شکننده است و این صفحه آن را دستور استاندارد نمی‌کند. سرویس را کنترل‌شده باز و بسته کنید.

`df` مسیر را به فایل‌سیستم حاوی آن مسیر گرد می‌کند. `df -hT /var/lib/postgresql/18/main` همان دستگاهی را نشان می‌دهد که `findmnt -T` می‌گوید. اگر هر دو می‌گویند `/`، دیسک داده در این عدد نیست.

### مثال واقعی

```bash
df -hT
df -hT /var/lib/postgresql/18/main
df -i
```

روی `db-1` که دیسک داده جدا و تقریباً پر است:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda2      ext4   40G   12G   26G  32% /
/dev/sdb1      ext4  200G  188G  2.1G  99% /var/lib/postgresql
tmpfs          tmpfs 1.6G  1.2M  1.6G   1% /run
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sdb1      ext4  200G  188G  2.1G  99% /var/lib/postgresql
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda2      2621440 186440 2435000    8% /
/dev/sdb1     13107200 842110 12265090    7% /var/lib/postgresql
```

اینجا بایت پر است و inode نه. پاک کردن لاگ متنی روی `/` کمکی به `/var/lib/postgresql` نمی‌کند. باید روی همان دستگاه جا باز شود، با ابزار نگهداری پایگاه نه با `rm` روی فایل جدول.

حالت inode پر روی `app-1`، در حالی که `df -h` هنوز جا نشان می‌دهد:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda2      ext4   40G   18G   20G  48% /
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda2      2621440 2621440      0  100% /
touch: cannot touch '/var/cache/shop/session-1': No space left on device
```

فایل حذف‌شده که `df` را بالا نگه داشته:

```bash
sudo lsof +L1
```

```text
COMMAND   PID     USER   FD   TYPE DEVICE    SIZE/OFF NLINK NODE NAME
postgres  912 postgres    7u   REG   8,17  2147483648     0 12345 /var/lib/postgresql/18/main/log/old.log (deleted)
```

حدود دو گیگابایت هنوز مال PID نهصد و دوازده است. `du` این را در جمع درخت نشان نمی‌دهد.

### کاربرد Production

روی `db-1` آستانه را روی فایل‌سیستم `/var/lib/postgresql` بگذارید نه فقط روی `/`. `df -hT` اگر نود درصد همان دیسک را نشان داد، قبل از حذف فایل نام فایل را با `du` در بخش بعد پیدا کنید و اگر جمع `du` خیلی کوچک‌تر از `Used` بود اول `lsof +L1` را بگیرید. restart پستگرس فضا را برمی‌گرداند فقط اگر علت همان توصیف‌گر باز باشد، و restart یعنی قطعی. زمانش را بدانید. اگر علت، خود دادهٔ زنده است، restart هیچ بایتی را پس نمی‌دهد.

روی `app-1` هر وقت `No space left` دیدید و `df -hT` زیر هشتاد درصد بود، همان دقیقه `df -i` بگیرید. نشست PHP یا کش ریز زیر `/var/cache` یا `/tmp` inode را تمام می‌کند در حالی که بایت آزاد است. پاک‌سازی با `find` و محدودیت سن، از [صفحهٔ فایل](/docs/01-linux/commands-files)، نه `rm -rf /tmp`.

عدد `df` را در تیکت با نام دستگاه و نقطهٔ mount بنویسید. «دیسک نود درصد است» بدون اینکه بگویید کدام، روی ماشینی با دو دیسک بی‌فایده است.

### وقتی خراب می‌شود

```text
df: /var/lib/postgresql/18/main: Permission denied
df: /run/user/1000/doc: No such file or directory
```

اولی یعنی از آن مسیر رد نمی‌شوید. `df -hT` بدون مسیر، یا `sudo df -hT /var/lib/postgresql`، عدد فایل‌سیستم را می‌دهد. این خطا به معنی پر بودن نیست. دومی اغلب مال یک نقطهٔ کهنه است و کل دستور را در بعضی نسخه‌ها پر از هشدار می‌کند. به نقطهٔ مشخص سؤال کنید تا هشدار قاطی عدد اصلی نشود.

اگر `df` و `du -x` را روی یک نقطه مقایسه کردید و `df` خیلی بزرگ‌تر بود، سه چیز را به ترتیب ببینید: `lsof +L1`، mount پنهان با `findmnt`، و اینکه `du` خطای `Permission denied` چاپ کرده و بخشی را جا انداخته. تا این سه تا را خط نزنید فایل تصادفی پاک نکنید.

`df -h` روی فایل‌سیستم صد درصد هم ممکن است برای root هنوز کمی جا نشان بدهد به‌خاطر رزرو، و برای `deploy` نه. سرویس با کاربر `deploy` شکست می‌خورد در حالی که پوستهٔ root هنوز فایل می‌سازد. هر دو را با همان کاربر سرویس امتحان نکنید روی دیسک داده. فقط بدانید اختلاف ستون Avail با تجربهٔ root طبیعی است و درمانش پاک کردن رزرو در حادثه نیست.

## du

### توضیح

`du` درخت را می‌گردد و بلوک تخصیص‌یافته را جمع می‌کند. شکل پیدا کردن مقصر روی یک فایل‌سیستم:

```bash
sudo du -xh --max-depth=1 /var | sort -h
```

- `-x` از فایل‌سیستم جاری بیرون نمی‌رود. بدون آن، `du /` دیسک داده و بکاپ و حتی بعضی مانت‌ها را داخل یک عدد قاطی می‌کند و شما فکر می‌کنید `/var` عظیم است در حالی که نصف عدد مال `/var/lib/postgresql` روی دستگاه دیگر است.
- `-h` واحد خوانا. `sort -h` مرتب‌سازی انسانی گنو است. `sort -n` روی `1.2G` غلط مرتب می‌کند چون به حرف G اهمیت نمی‌دهد آن‌طور که باید با واحد مخلوط.
- `--max-depth=1` فقط یک لایه را نشان می‌دهد تا اول دایرکتوری مقصر معلوم شود. بعد همان دستور را روی همان دایرکتوری تکرار کنید و پایین بروید. `--max-depth=0` فقط خود مسیر است، معادل عملی `du -sh`.

`-x` مانت متصل به دستگاه دیگر را کنار می‌گذارد. bind mount از همان دستگاه را کنار نمی‌گذارد، چون فایل‌سیستم عوض نشده. اگر `/var/backups` با bind از جای دیگری روی همان دیسک آمده، `du -x /` ممکن است محتوا را دو بار ببیند. `findmnt` را نگاه کنید. اگر bind هست، از مسیر اصلی جمع بگیرید نه از هر دو.

`du` فایل حذف‌شدهٔ باز را نمی‌بیند. اگر جمع این دستور خیلی کوچک‌تر از `Used` در `df` است، به بخش `df` برگردید و `lsof +L1` بگیرید. اختلاف را با پاک کردن دوبارهٔ همان درخت «درست» نکنید.

`du` بدون sudo روی دایرکتوری ریشه یا خانهٔ کاربران دیگر `Permission denied` می‌دهد و عدد را کمتر از واقعیت چاپ می‌کند، اغلب با کد خروج غیرصفر. برای حادثهٔ دیسک، `sudo` استفاده کنید و خطای مجوز را در خروجی نادیده نگیرید. آن خطا یعنی یک تکهٔ درخت در جمع نیست.

`--inodes` به‌جای بایت، تعداد ورودی را جمع می‌کند. وقتی `df -i` صد درصد است ابزار پیدا کردن مقصر همین است، نه `du -h` که شاید دایرکتوری ریز را کوچک نشان دهد.

### مثال واقعی

لایهٔ اول `/var` روی `app-1`، محدود به همان فایل‌سیستم:

```bash
sudo du -xh --max-depth=1 /var | sort -h
```

```text
12M     /var/spool
40M     /var/tmp
120M    /var/cache
1.4G    /var/lib
18G     /var/log
20G     /var
```

لاگ مقصر است. یک لایه پایین‌تر:

```bash
sudo du -xh --max-depth=1 /var/log | sort -h
```

```text
8.0K    /var/log/private
24M     /var/log/apt
1.1G    /var/log/nginx
16G     /var/log/journal
18G     /var/log
```

journal را با پاک کردن کور `/var/log/journal` خالی نکنید. سیاست نگهداری journald جای خودش را دارد. برای nginx، فایل قدیمی فشرده با `find` و سن مشخص، همان صفحهٔ فایل. اول این عدد را داشته باشید تا بدانید کدام دایرکتوری ارزش تلاش دارد.

روی `db-1` فقط دیسک داده، و جداگانهٔ تعداد inode:

```bash
sudo du -xh --max-depth=1 /var/lib/postgresql | sort -h
sudo du -xh --max-depth=1 --inodes /var/lib/postgresql | sort -h
```

```text
1.2G    /var/lib/postgresql/18/main/pg_wal
186G    /var/lib/postgresql/18/main/base
188G    /var/lib/postgresql
12      /var/lib/postgresql
840000  /var/lib/postgresql/18/main/base
```

اگر `base` بزرگ است، این دادهٔ زنده است نه زباله. کوچک کردنش کار SQL و نگهداری است، نه `du` و `rm`. اگر `pg_wal` غیرعادی بزرگ است، علت را در خود PostgreSQL پیدا کنید (همتا که WAL را برنمی‌دارد، یا آرشیو گیر کرده). حذف فایل WAL با دست یعنی خرابی کلاستر.

inode پر از نشست‌های ریز روی `app-1`:

```bash
sudo du -xh --max-depth=1 --inodes /var | sort -h
```

```text
120     /var/log
40      /var/lib
2100000 /var/cache
2101000 /var
```

بعد فقط زیر `/var/cache` پایین بروید تا پوشهٔ نشست پیدا شود. پاک‌سازی با `find` و `-mtime`، بعد از دیدن فهرست، نه با `rm` روی کل کش.

### کاربرد Production

شب پر شدن دیسک روی `app-1` این ترتیب است: `df -hT` و `df -i`، `findmnt -T` روی مسیری که سرویس در آن می‌نویسد، بعد `du -xh --max-depth=1` از `/` یا از `/var`، بعد یک لایه پایین‌تر، بعد تصمیم. اگر اختلاف `df` با جمع `du` به اندازهٔ گیگابایت است، قبل از حذف `sudo lsof +L1`. اغلب یک لاگ nginx است که چرخیده و `rm` شده ولی worker هنوز فایل قدیمی را باز دارد. reload کردن nginx بعد از اینکه فهمیدید PID مال nginx است فضا را برمی‌گرداند، چون worker فایل را می‌بندد. reload را به‌خاطر یک PID از `postgres` روی `app-1` نزنید. PID را بخوانید.

روی `db-1` همان ترتیب روی `/var/lib/postgresql`. اگر `du` گفت فضا داخل `base` است، فایل را از پوسته حذف نکنید. اگر `lsof` گفت یک لاگ حذف‌شده هنوز باز است، توقف و شروع کنترل‌شدهٔ PostgreSQL فضا را پس می‌دهد و قطعی کوتاه است. این را در پنجرهٔ تغییر انجام دهید، نه به‌عنوان اولین دستور بعد از دیدن درصد.

خروجی `du` را در تیکت نگه دارید. دفعهٔ بعد معلوم است کدام دایرکتوری رشد کرده. یک عدد تنها از `df` روند را نشان نمی‌دهد.

### وقتی خراب می‌شود

```text
du: cannot read directory '/var/lib/postgresql/18/main': Permission denied
du: cannot access '/var/log/nginx/access.log': No such file or directory
sort: invalid option -- 'h'
```

اولی بدون sudo است و جمع را دروغ می‌کند. دومی یعنی بین خواندن دایرکتوری و stat کردن، فایل حذف یا عوض شده. روی لاگ شلوغ طبیعی است. دستور را تکرار کنید. اگر مدام است، سرویس دارد فایل را سریع عوض می‌کند و عدد شما تقریبی است نه دقیق. سومی یعنی `sort` گنو نیست، یا گزینه را به دستور غلط چسبانده‌اید. روی Ubuntu 26.04 `sort -h` هست. اگر خطا گرفتید، `sort --version` را ببینید و خروجی `du` را بدون `-h` با `sort -n` مرتب کنید تا واحدها قاطی نشوند. برای آن حالت `du -x --max-depth=1` بدون `-h` عدد بایت خام می‌دهد.

`du` خیلی کند روی درخت میلیونی inode پر، خودش دیسک را مشغول می‌کند. `--max-depth=1` را از بالا شروع کنید تا مجبور نشوید همان لحظه کل `base` پستگرس را stat کنید. اگر دیسک آن‌قدر شلوغ است که حتی `du` تمام نمی‌شود، `df` و `lsof +L1` را اول داشته باشید. شاید اصلاً لازم نباشد درخت را بگردید.

جمعی که از `df` بزرگ‌تر است معمولاً یعنی یا دو بار شمردن bind mount، یا مقایسه با واحد غلط (`du -sh` روی `/` در برابر یک خط `df` از یک فایل‌سیستم). `-x` و `findmnt` را دوباره ببینید. عدد بزرگ‌تر از کل دیسک را جدی نگیرید تا مسیر را محدود کنید.

## Best Practices

- قبل از پاک‌کردن، `findmnt -T` همان مسیر. اگر دیسک مورد نظر mount نیست، دارید یا روی ریشه فایل می‌ریزید یا فایل پنهان زیر نقطهٔ اتصال دارید.
- در fstab دستگاه را با UUID بنویسید. دیسک بکاپ `nofail` داشته باشد. بعد از ویرایش `daemon-reload` و `findmnt --verify` و فقط بعد `mount -a`. نام `/dev/sdX` در fstab ممنوع.
- `umount` مشغول را با `lsof` و `fuser -vm` تشخیص دهید. پوسته را با `cd /` کنار بزنید. سرویس را با systemd متوقف کنید. `umount -l` و `fuser -km` را روی دیسک پایگاه استفاده نکنید.
- `df -hT` و `df -i` هر دو. خطای `No space left` با جا در `-h` یعنی inode تا خلافش ثابت شود. درصد را با نام دستگاه در تیکت بنویسید.
- اگر `df` پر است و `du -xh --max-depth=1` جمع خیلی کوچک‌تری دارد، `lsof +L1` برای فایل `(deleted)`. فضا با بستن توصیف‌گر برمی‌گردد نه با `rm` دوباره.
- با `-x` روی همان فایل‌سیستم بمانید و لایه‌لایه پایین بروید. `base` و `pg_wal` پستگرس را با دست خالی نکنید. لاگ را با قاعدهٔ سن و فهرست قبلی حذف کنید.
