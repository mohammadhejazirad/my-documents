# فایل‌سیستم

## مقدمه

پارتیشن و LV فقط ظرف‌اند. تا وقتی روی‌شان فایل‌سیستم نسازید و در `/etc/fstab` با UUID سوارشان نکنید، بوت بعدی دیسک را نمی‌شناسد یا، بدتر، دستگاه را با نام `/dev/vda2` صدا می‌زند و روزی که نام هسته عوض شد به حالت اضطراری می‌رود. ساخت خود LV در [پارتیشن‌بندی](/docs/01-linux/partitioning) است. این صفحه انتخاب ext4 یا XFS، گزینهٔ mount، فایل fstab، و دو ابزار بازرسی `tune2fs` و `xfs_info` را تمام می‌کند.

میزبان مرجع Ubuntu Server 26.04 است. ابزارها روی Debian 13 هم هستند: `e2fsprogs` برای ext4 و `xfsprogs` برای XFS. اگر `mkfs.xfs` پیدا نشد بسته را نصب کنید، نه اینکه سراغ فایل‌سیستم دیگری بروید چون دستور در PATH نبود.

## مفهوم اصلی

ext4 فایل‌سیستم پیش‌فرض نصب Ubuntu برای `/` و `/boot` است. ژورنال دارد، آنلاین بزرگ می‌شود، و آفلاین کوچک می‌شود. برای ریشه و `/boot` انتخاب این دانشنامه است چون ابزار بازیابی و عادت نصب‌کننده با آن یکی است. بلوک رزرو پیش‌فرض حدود ۵ درصد است تا فرآیند روت وقتی دیسک از نظر کاربر پر است هنوز بتواند بنویسد. روی یک LV دادهٔ چندصد گیگی این ۵ درصد فضای مرده است و با `tune2fs -m` پایین آورده می‌شود. روی `/` همان ۵ درصد را نگه دارید.

XFS برای بار نوشتن سنگین و فایل بزرگ طراحی شده و آنلاین با `xfs_growfs` بزرگ می‌شود. کوچک نمی‌شود. اگر `/var` یا دادهٔ دیتابیس را XFS کردید، طرح ظرفیت باید رشدی باشد نه «اگر زیاد بود برمی‌گردانیم». تعمیرش با `xfs_repair` فقط وقتی امن است که فایل‌سیستم سوار نباشد. `xfs_info` برعکس، ابزار خواندن است و روی فایل‌سیستم سوار کار می‌کند.

`mount` سوار کردنِ همین نشست است. `/etc/fstab` سوار کردنِ بوت بعدی است. systemd با generator خودش هر خط fstab را به یک واحد `.mount` تبدیل می‌کند. خط خراب یعنی `local-fs.target` معطل می‌ماند و بوت به حالت اضطراری می‌رود. به همین دلیل قبل از ری‌بوت `findmnt --verify` و `mount -a` را می‌زنیم.

UUID شناسهٔ فایل‌سیستم است نه شناسهٔ پارتیشن. با `mkfs` عوض می‌شود و با جابه‌جایی نام `/dev/vda` عوض نمی‌شود. برچسب (`LABEL=`) خوانا است ولی در سازمان تکراری می‌شود. دو دیسک با برچسب `root` یعنی بوت شانسی. در fstab سرور از `UUID=` استفاده کنید. نام LVM مثل `/dev/vg0/lv_var` از UUID فایل‌سیستم پایدارتر از `/dev/vda` است، ولی باز هم اگر فایل‌سیستم را از نو بسازید و LV را نگه دارید، UUID جدید باید در fstab بیاید. یک منبع حقیقت کافی است: UUID.

گزینهٔ mount سه تای پرتکرارشان این‌ها هستند:

- `nodev` یعنی از روی این درخت نمی‌شود دستگاه (device node) ساخت یا استفاده کرد. روی `/home` درست است. روی `/` غلط است چون `/dev` اگرچه معمولاً mount جداست، عادت و برخی مسیرهای بازیابی به دستگاه روی ریشه وابسته‌اند. مهم‌تر از آن: این گزینه را جایی بگذارید که کاربر عادی می‌نویسد، نه روی سیستم‌عامل.
- `nosuid` بیت setuid و setgid فایل‌های اجرایی این درخت را بی‌اثر می‌کند. روی `/home` و `/tmp` درست است. روی `/` یا `/usr` یعنی `sudo` و `passwd` دیگر کار نمی‌کنند.
- `noexec` اجرای فایل از این درخت را ممنوع می‌کند. برای دیسک آرشیو و بکاپ خوب است. برای `/var` خوب نیست چون بسته و برخی سرویس‌ها از زیر `/var` اجرا می‌شوند. برای `/home` هم اگر مدیر از خانهٔ خودش اسکریپت می‌زند دردسر می‌سازد. `/tmp` با `noexec` سخت‌تر است و بعضی نصب‌کننده‌ها را با Permission denied می‌خواباند. در آزمایشگاه روی `/tmp` نمی‌گذاریم. اگر سازمان بخواهد، حالت شکست همین صفحه را از قبل بشناسید.

`defaults` روی ext4 شامل `rw` و `relatime` است. `noatime` را سراسری نکنید. سودش کم است و چند ابزار که زمان دسترسی فایل را می‌خواهند غافلگیر می‌شوند. فقط جایی که اندازه گرفتید و نوشتار atime واقعاً گران است، آن هم روی یک LV داده، نه روی `/`.

## چرا استفاده می‌شود؟

fstab با نام دستگاه کوتاه، تا روز اضافه شدن یک دیسک SCSI سالم است. آن روز هسته ترتیب را عوض می‌کند، `/` از دیسک دیگری mount می‌شود یا اصلاً بالا نمی‌آید، و دادهٔ سالم را خراب به حساب می‌آورید. UUID این کلاس حادثه را حذف می‌کند.

گزینهٔ `noexec` و `nosuid` جایگزین مجوز فایل نیستند. یک فایل `0755` روی دیسکی که `noexec` است اجرا نمی‌شود حتی اگر مالک روت باشد. برعکس، `noexec` جلوی نوشتن اسکریپت مخرب را نمی‌گیرد. فقط اجرای همان‌جا را می‌گیرد. مجوز در [مجوز فایل](/docs/01-linux/permissions) است. اگر به نفر سوم دسترسی می‌دهید و نمی‌خواهید گروه را باز کنید، [ACL](/docs/01-linux/acl) است نه یک mount سراسری شلخته.

جدا بودن فایل‌سیستم `/var` که در صفحهٔ پارتیشن ساخته شد این‌جا به یک خط fstab تبدیل می‌شود. بدون آن خط، LV هست ولی بوت آن را سوار نمی‌کند و داده زیر پوشهٔ خالی `/var` روی ریشه نوشته می‌شود. این باگ بی‌صدا است. `df` دو بار، یک بار قبل از mount دستی و یک بار بعد، آن را نشان می‌دهد.

## Architecture

```text
بوت
 └─ systemd-fstab-generator
      /etc/fstab  را به واحد .mount تبدیل می‌کند
      │
      ├─ /            UUID  lv_root   ext4   defaults
      ├─ /boot        UUID  vda2      ext4   defaults
      ├─ /boot/efi    UUID  vda1      vfat   umask=0077
      ├─ /var         UUID  lv_var    ext4   defaults
      ├─ /home        UUID  lv_home   ext4   defaults,nodev,nosuid
      ├─ /opt         UUID  lv_opt    ext4   defaults
      └─ swap         UUID  lv_swap   swap   sw

ابزار بازرسی
  tune2fs -l     فقط ext4
  xfs_info       فقط xfs
```

ردیف ششم fstab برای ext4 روی ریشه `1` است و برای بقیهٔ فایل‌سیستم‌های محلی `2`. برای swap و برای vfat مقدار سنتی Ubuntu روی فیلد آخر `0` یا `1` است. نمونهٔ پایین همان چیزی است که بوت این آزمایشگاه باید داشته باشد. فیلد پنجم dump امروز عملاً `0` است.

اگر `/var` را XFS ساخته‌اید، فقط نوع همان خط عوض می‌شود. بقیهٔ طرح می‌ماند. `/boot` را XFS نکنید. GRUB در این دانشنامه ext4 می‌خواند و تنوع بوت‌لودر را بی‌دلیل زیاد نمی‌کنیم. EFI فقط vfat است. میان‌افزار FAT می‌فهمد نه ext4.

## Installation

ابزار را نصب کنید و نوع چیزی که واقعاً روی دیسک است را بخوانید. حدس نزنید.

```bash
sudo apt install e2fsprogs xfsprogs
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /
lsblk -f
```

ساخت فایل‌سیستم فقط روی LV خالی، و فقط اگر صفحهٔ پارتیشن را هنوز نزده‌اید یا LV را از نو می‌سازید. تکرار `mkfs` داده را پاک می‌کند.

```bash
sudo mkfs.ext4 -L root /dev/vg0/lv_root
```

نمونهٔ XFS برای یک LV داده که عمداً فقط رشد می‌کند:

```bash
sudo mkfs.xfs -L var /dev/vg0/lv_var
```

اگر LV از قبل ext4 است و داده دارد، این دستور را نزنید. `mkfs.xfs` می‌گوید امضا وجود دارد و بدون پاک کردن امضا ادامه نمی‌دهد. آن امتناع را دور نزنید.

UUID تازه را بردارید:

```bash
sudo blkid -s UUID -s TYPE -s LABEL
```

شکل یک خط:

```text
/dev/mapper/vg0-lv_root: LABEL="root" UUID="11111111-2222-4333-8444-555555555555" TYPE="ext4"
```

UUID واقعی این شکل را دارد ولی عددش مال دیسک شماست. مقدار صفحه را در fstab کپی نکنید. vfat یک UUID کوتاه مثل `A1B2-C3D4` دارد. همان را کامل بگذارید.

## Configuration

فایل `/etc/fstab` سرور برنامه، بعد از جایگزینی UUIDها:

```text
UUID=11111111-2222-4333-8444-555555555555  /          ext4  defaults              0  1
UUID=aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee  /boot      ext4  defaults              0  2
UUID=A1B2-C3D4                              /boot/efi  vfat  umask=0077            0  1
UUID=22222222-3333-4444-8555-666666666666  /var       ext4  defaults              0  2
UUID=33333333-4444-4555-8666-777777777777  /home      ext4  defaults,nodev,nosuid 0  2
UUID=44444444-5555-4666-8777-888888888888  /opt       ext4  defaults              0  2
UUID=55555555-6666-4777-8888-999999999999  none       swap  sw                    0  0
```

`umask=0077` روی EFI یعنی فایل میان‌افزار برای کاربر عادی خواندنی نیست. این پارتیشن جای اسکریپت نیست. خط `/home` دستگاه و setuid را می‌بندد و اجرا را باز می‌گذارد تا ابزار مدیر که از خانه اجرا می‌شود نشکند. دیسک بکاپ جدا، اگر روزی اضافه شد، `noexec,nodev,nosuid` می‌گیرد و اگر نبودنش نباید بوت را متوقف کند گزینهٔ `nofail` هم می‌گیرد. `nofail` را روی `/` و `/var` نگذارید. بوت بدون آن‌ها بوت سالمی نیست و بهتر است بایستد تا داده را جای غلط بنویسید.

قبل از ری‌بوت:

```bash
sudo findmnt --verify
sudo mount -a
findmnt -R /
```

`mount -a` خط‌هایی را که از قبل سوارند دوباره سوار نمی‌کند و خط جدید یا خراب را همان لحظه نشان می‌دهد. اگر خطا داد، ری‌بوت نکنید. fstab را درست کنید و دوباره `mount -a` بزنید. `findmnt --verify` خط و فیلد بد را می‌گوید. نمونهٔ شکست وقتی UUID را با دست غلط کپی کرده‌اید:

```text
/var
   [E] cannot detect on-disk filesystem type
```

یا هنگام بوت، اگر این را ندیده باشید و ری‌بوت کرده باشید، کنسول می‌ماند روی انتظار برای دستگاه. از شل اضطراری:

```bash
blkid
cat /etc/fstab
```

UUID چاپ‌شدهٔ `blkid` را با خط fstab یکی کنید. بعد:

```bash
systemctl daemon-reload
mount -a
```

`daemon-reload` واحد mount تولیدشده از fstab را نو می‌کند. بدون آن، `mount` دستی ممکن است کار کند و بوت بعدی هنوز واحد کهنه را بخواهد.

گزینه را موقت امتحان کنید بدون اینکه fstab را دست بزنید:

```bash
sudo mount -o remount,nosuid,nodev /home
findmnt -no OPTIONS /home
```

اگر برنامه شکست، `sudo mount -o remount,defaults /home` برمی‌گرداند. وقتی مطمئن شدید، همان گزینه را در fstab بنویسید. remount تا ری‌بوت دوام ندارد.

برای دیدن اینکه مسیر واقعاً روی کدام فایل‌سیستم است:

```bash
df -hT / /var /home /opt /boot
findmnt -T /var/log
```

`findmnt -T` فایل‌سیستمِ حاوی آن مسیر را نشان می‌دهد. اگر `/var/log` هنوز روی `/` است، یا LV را سوار نکرده‌اید یا روی پوشهٔ اشتباه سوار کرده‌اید.

## Production Example

بازرسی ext4 ریشه. این دستور چیزی را عوض نمی‌کند:

```bash
sudo tune2fs -l /dev/vg0/lv_root
```

در خروجی به این فیلدها نگاه کنید: `Filesystem state` باید `clean` باشد، `Reserved block count` روی ریشه نزدیک ۵ درصد بلوک‌ها بماند، `Filesystem UUID` همان رشتهٔ fstab باشد، و `Default mount options` هرچه هست با خط fstab در تناقض عملی نباشد. اگر state برابر `not clean` است، فایل‌سیستم را remount نکنید که «تمیز شود». برنامهٔ fsck بوت یا یک `e2fsck` آفلاین را جدی بگیرید.

کم کردن رزرو روی `/var` که جداست و بزرگ شده، از ۵ درصد به ۱ درصد:

```bash
df -h /var
sudo tune2fs -m 1 /dev/vg0/lv_var
df -h /var
```

`-m` درصد است. روی `/` این کار را نکنید. اگر `/var` از جنس XFS است `tune2fs` خطا می‌دهد. آن خطا یعنی نوع را اشتباه گرفته‌اید، نه اینکه ابزار خراب است:

```text
tune2fs: Bad magic number in super-block while trying to open /dev/vg0/lv_var
```

آن‌وقت:

```bash
sudo xfs_info /var
```

خروجی سالم نام نقطهٔ mount، `agcount`، اندازهٔ بلوک (معمولاً ۴۰۹۶)، و `crc=1` را برای XFS امروزی نشان می‌دهد. اگر `xfs_info` گفت فایل‌سیستم XFS نیست، `lsblk -f` را باور کنید و دستور ext4 را برگردانید. رشد XFS بعد از `lvextend` بدون فلگ `-r`:

```bash
sudo xfs_growfs /var
sudo xfs_info /var
```

`xfs_growfs` روی فایل‌سیستمی که LV‌اش بزرگ نشده باشد هیچ ظرفیتی اضافه نمی‌کند و معمولاً می‌گوید اندازه عوض نشد. اول `sudo lvs` را ببینید.

تعمیر، فقط آفلاین. برای ext4:

```bash
sudo umount /home
sudo e2fsck -f /dev/vg0/lv_home
sudo mount /home
```

برای XFS، فایل‌سیستم باید umount باشد و `-L` را بدون دلیل نزنید. `-L` ژورنال را دور می‌ریزد و آخرین نوشتن‌ها را ممکن است قربانی کند. فقط وقتی `xfs_repair` صریحاً گفت ژورنال را نمی‌تواند بازپخش کند و بکاپ دارید:

```bash
sudo umount /var
sudo xfs_repair /dev/vg0/lv_var
sudo mount /var
```

اگر umount به‌خاطر مشغول بودن شکست خورد، `sudo lsof +f -- /var` یا `sudo fuser -vm /var` را ببینید. فرآیند را ببندید. `umount -l` بوت را سالم نمی‌کند و فایل‌سیستم را در وضعیت گمراه‌کننده رها می‌کند. در آزمایشگاه از آن برای «تمام کردن سریع» استفاده نکنید.

یک دیسک آرشیو جدا با گزینهٔ سخت. فرض: LV تازهٔ `/dev/vg0/lv_backup` با ext4 و نقطهٔ `/var/backups`. این مسیر در قرارداد دانشنامه ریشهٔ بکاپ است. اگر `/var/backups` امروز روی خود `/var` است، انتقالش به LV جدا یعنی یک بار داده را جا به جا کنید، نه اینکه خط fstab را روی پوشهٔ پر سوار کنید و فکر کنید داده منتقل شده.

```bash
sudo mkfs.ext4 -L backups /dev/vg0/lv_backup
sudo tune2fs -m 0 /dev/vg0/lv_backup
sudo blkid /dev/vg0/lv_backup
```

خط fstab:

```text
UUID=66666666-7777-4888-8999-aaaaaaaaaaaa  /var/backups  ext4  defaults,nodev,nosuid,noexec,nofail  0  2
```

`nofail` یعنی نبودن این دیسک بوت را متوقف نکند. بکاپ نرفتن را باید جای دیگری بفهمید، نه با بالا نیامدن سرور. `noexec` یعنی اسکریپتی که داخل آرشیو است از همین مسیر اجرا نشود. برای برگرداندن فایل، آن را به مسیر اجرایی کپی کنید نه اینکه `noexec` را بردارید.

## Security Notes

- `nosuid` و `noexec` را روی `/` یا `/usr` نگذارید. `sudo` و کتابخانه‌های اجرایی می‌شکنند و ممکن است راه ورود مدیر فقط کنسول اضطراری بماند.
- EFI با `umask=0077` بماند. جهان‌خوانا کردن `/boot/efi` کمکی به عملیات نمی‌کند.
- `tune2fs -m 0` روی `/` رزرو روت را برمی‌دارد. پر شدن کامل `/` یعنی حتی `journalctl` هم ممکن است نتواند روی دیسک بنویسد اگر journal آنجا باشد. رزرو ریشه را دست نزنید.
- `xfs_repair -L` و `e2fsck -y` را در اسکریپت ورود خودکار نگذارید. اول گزارش را بخوانید.
- فایل‌سیستم جهان‌نوشتنی با `exec` زیر خانهٔ کاربر، به‌علاوهٔ یک cron روت که از آن مسیر اجرا می‌کند، معادل دادن روت است. cron مدیر فقط از مسیری اجرا شود که کاربر عادی نتواند بنویسد. مجوز آن مسیر در صفحهٔ مجوز است.
- UUID را در تیکت عمومی به‌عنوان راز حساب نکنید، ولی fstab را هم با ویرایشگر اشتراکی بدون بازبینی عوض نکنید. یک خط اضافه با UUID دیسک اشتباه، بوت را به دیسک دیگری می‌برد.

## Troubleshooting

| نشانه | علت محتمل | کار |
| --- | --- | --- |
| بوت: `Timed out waiting for device` | UUID در fstab با دیسک نمی‌خواند | از emergency: `blkid` و اصلاح fstab و `daemon-reload` |
| `mount -a` می‌گوید already mounted و `df` اندازهٔ قدیم است | خط جدید اعمال نشده یا روی مسیر غلطید | `findmnt -T` همان مسیر |
| `tune2fs: Bad magic number` | دستگاه XFS یا swap یا خالی است | `lsblk -f` و ابزار همان نوع |
| `xfs_growfs: not a mounted XFS filesystem` | نقطهٔ mount غلط است یا هنوز ext4 است | `findmnt /var` |
| برنامه می‌گوید Permission denied هنگام exec از `/tmp` | جایی `noexec` گذاشته‌اید | `findmnt -no OPTIONS /tmp` و برداشتن noexec اگر همان علت است |
| `sudo` ناگهان می‌گوید effective uid is not 0 | `nosuid` روی فایل‌سیستمی که باینری sudo آنجاست | از کنسول remount بدون nosuid. sudo اغلب روی `/usr` است |
| بعد از ری‌بوت `/var` خالی است | خط fstab نیست و داده روی ریشه زیر پوشه مانده | umount اگر سوار است، داده را از پوشه بردارید، بعد LV را سوار کنید |
| `findmnt --verify` هشدار bind یا گزینهٔ تکراری | دو خط برای یک نقطه | fstab را یک‌بار از بالا بخوانید |

حالت اضطراری رمز روت یا نشست `sulogin` می‌خواهد. اگر روت رمز ندارد، از ISO زنده دیسک را mount کنید و fstab مهمان را زیر `/mnt` اصلاح کنید. chroot وقتی لازم است که initramfs را هم نو کنید، نه برای یک ویرایش سادهٔ fstab.

اگر فقط یک گزینهٔ mount بوت را شکسته، از ISO:

```bash
sudo mount /dev/vg0/lv_root /mnt
sudo mount /dev/vg0/lv_var /mnt/var
sudo nano /mnt/etc/fstab
```

فراموش نکنید `/var` جدا را هم سوار کنید اگر fstab واقعی آنجا نیست. fstab روی ریشه است نه روی `/var`. پس برای اصلاح fstab فقط mount ریشه کافی است. mount کردن `/var` را وقتی لازم دارید که لاگ را هم ببینید.

## Best Practices

- fstab را با UUID بنویسید. قبل از هر ری‌بوت `findmnt --verify` و `mount -a` بگیرید.
- `/` و `/boot` روی این دانشنامه ext4 می‌مانند. XFS را برای داده‌ای بگذارید که فقط بزرگ می‌شود و تعمیرش را تمرین کرده‌اید.
- `nodev,nosuid` روی `/home`. `noexec,nodev,nosuid` روی آرشیو. هیچ‌کدام روی `/`.
- رزرو ۵ درصد را برای ریشه نگه دارید و روی LV داده با `tune2fs -m 1` یا `0` کم کنید. روی XFS این کلید وجود ندارد.
- `xfs_info` و `tune2fs -l` را قبل از تعمیر اجرا کنید تا نوع و UUID را با چشم ببینید.
- گزینهٔ تازه را اول `remount` کنید. وقتی برنامهٔ واقعی هنوز کار کرد، آن را به fstab منتقل کنید.
