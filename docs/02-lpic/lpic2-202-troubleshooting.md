# عیب‌یابی ۲۰۲

## مقدمه

آزمون ۲۰۲ از شما می‌خواهد یک سرویس خراب را با شواهد جدا کنید، نه این که همه‌چیز را با هم restart کنید. این صفحه روش ثابت را روی آزمایشگاه پیاده می‌کند: ظرفیت، دیسک، شبکه، سرویس، لاگ. سناریوی ترکیبی این است که `app.example.com` بالا نمی‌آید. روش کلی حادثه، وقتی از یک وب‌سرور بزرگ‌تر است، در [نقشهٔ عیب‌یابی](/docs/14-troubleshooting) است. موردهای آماده: [سرور بالا نمی‌آید](/docs/14-troubleshooting/server-down)، [دیسک پر](/docs/14-troubleshooting/disk-full)، [مشکل شبکه](/docs/14-troubleshooting/network-problem). اینجا همان ترتیب را برای هدف آزمون، با خروجی نمونهٔ وب، کوتاه و قابل تکرار می‌کنیم.

میزبان `app-1` است. صفحهٔ سالم آزمایشگاه همان فایل [سرویس وب](/docs/02-lpic/lpic2-202-web) است: Nginx روی پورت ۸۰ و جملهٔ `app.example.com via lab`.

## مفهوم اصلی

هر لایه اگر خراب باشد، لایهٔ بالاتر را دروغ‌زن نشان می‌دهد. دیسک پر باعث شکست سرویس می‌شود و شما در لاگ سرویس دنبال باگ برنامه می‌گردید. نام خراب باعث می‌شود curl دامنه‌ای به میزبان دیگری برود و شما Nginx سالم را عوض کنید. به همین دلیل ترتیب مشاهده از منبع مشترک به سرویس خاص است.

پنج سؤال، به همین ترتیب:

1. ظرفیت: CPU و حافظه و بار، ماشین را غیرقابل استفاده کرده است یا نه.
2. دیسک: بلوک یا inode جایی که سرویس می‌نویسد تمام شده است یا نه.
3. شبکه: به آدرس خود میزبان می‌رسید و پورت گوش می‌دهد، و نام به همین آدرس حل می‌شود یا نه.
4. سرویس: واحد درست فعال است یا واحد دیگری جایش نشسته.
5. لاگ: همان واحد، در همین بوت، آخرین خطا را چه نوشته.

تا وقتی سؤال قبلی جواب «سالم» نداده، پیکربندی لایهٔ بعد را ویرایش نکنید. restart بدون خواندن لاگ، زمان خطا را عوض می‌کند و گاهی علامت را پاک می‌کند.

## چرا استفاده می‌شود؟

تیکت «سایت پایین است» چهار معنی متفاوت دارد: میزبان خاموش، پورت بسته، HTTP خطا، یا فقط نام از شبکهٔ کاربر. هر کدام صاحب متفاوتی دارد. روش پنج‌لایه جلوی این را می‌گیرد که اپراتور شب، اول BIND را reload کند چون دیروز مشکل DNS بوده.

برای آزمون، همین ترتیب نمرهٔ سؤال سناریویی را می‌سازد. مصحح دنبال دستوری است که فرضیه را رد کند. `systemctl restart` فرضیه را رد نمی‌کند؛ فقط وضعیت را عوض می‌کند.

## Architecture

```text
تیکت: app.example.com بالا نمی‌آید
    │
    ├─ ۱ ظرفیت     uptime, free, nproc
    ├─ ۲ دیسک       df -hT, df -i  روی / و /var
    ├─ ۳ شبکه       ip, ping به 10.10.1.10, ss پورت 80, getent یا dig
    ├─ ۴ سرویس      systemctl is-active nginx apache2
    └─ ۵ لاگ        journalctl -u nginx -b ، error.log
            │
            ▼
       یک علت، یک تغییر، دوباره همان شاهد از لایهٔ ۳
```

اگر لایهٔ ۱ یا ۲ خراب است، مسیر از این صفحه خارج می‌شود و به [CPU](/docs/14-troubleshooting/high-cpu) یا [دیسک پر](/docs/14-troubleshooting/disk-full) می‌رود. اگر نام خراب است و IP سالم است، به [DNS](/docs/02-lpic/lpic2-202-dns) و [شبکهٔ ۱۰۲](/docs/02-lpic/lpic1-102-networking). اگر پورت مال Apache است، به صفحهٔ وب. این صفحه صاحب همهٔ آن تعمیرها نیست؛ صاحب ترتیب است.

## Installation

ابزار این روش روی سرور پایه هست: `systemctl`، `journalctl`، `ss`، `df`، `curl`. اگر `curl` نیست:

```bash
sudo apt update
sudo apt install curl
```

چیز دیگری نصب نکنید تا علامت را عوض نکرده باشید. به‌خصوص Apache را «برای مقایسه» بالا نیاورید. یک شنوندهٔ جدید یعنی لایهٔ ۴ را خودتان خراب کرده‌اید.

خط پایه را وقتی سایت سالم است یک‌بار ذخیره کنید تا شب با حافظه مقایسه نکنید:

```bash
systemctl is-active nginx
sudo ss -lntup | awk '/:80|:22/'
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: app.example.com' http://127.0.0.1/
```

کد ۳۰۰ یا ۲۰۰ خط پایهٔ این آزمایشگاه است. ۳۰۰ اگر به جایی بپرد، و ۲۰۰ برای فایل ثابت صفحهٔ وب. عدد را در یادداشت میزبان بنویسید.

## Configuration

این صفحه فایل دائمی اضافه نمی‌کند. «پیکربندی» روش یعنی چه چیزی را در تیکت بنویسید تا نفر بعدی از صفر شروع نکند.

قالب یادداشت:

```text
زمان:
میزبان: app-1.example.internal
نشانه: 
لایه ۱:
لایه ۲:
لایه ۳:
لایه ۴:
لایه ۵:
تغییر:
شاهد بعد از تغییر:
```

هر لایه یک خط خروجی واقعی باشد، نه جملهٔ «به نظر سالم بود». اگر دستوری خطا داد، خود خطا را بگذارید. خطا داده است، نه این که لایه سالم است.

زمان را از `timedatectl` همان اول بنویسید. اگر ساعت غلط باشد، ترتیب `journalctl` را اشتباه می‌خوانید. تنظیم ساعت در [مدیریت ۲۰۱](/docs/02-lpic/lpic2-201-administration) است و وسط حادثهٔ وب فقط وقتی اولویت دارد که گواهی یا لاگ را نتوانید زمان‌بندی کنید.

## Production Example

نشانه: از ایستگاه مدیر مرورگر به `http://app.example.com` نمی‌رود. شما روی `app-1` نشست دارید. لایه‌ها را با خروجی نمونهٔ یک حادثهٔ واقعی این آزمایشگاه طی کنید. اعداد میزبان شما ممکن است فرق کند؛ شکل تصمیم نباید فرق کند.

لایهٔ ۱، ظرفیت. بار از تعداد هسته کمتر است و حافظه هنوز موجود است.

```bash
nproc
uptime
free -h
```

```text
2
 02:10:01 up 12 days, load average: 0.08, 0.12, 0.09
               total        used        free      available
Mem:           1.9Gi       600Mi       200Mi       1.1Gi
```

تصمیم: ظرفیت علت این تیکت نیست. به سراغ کشتن فرایند نروید.

لایهٔ ۲، دیسک. اگر اینجا ۱۰۰ درصد بود، Nginx ممکن است حتی لاگ خطا را ننویسد و شما فکر کنید «لاگ چیزی نمی‌گوید».

```bash
df -hT / /var
df -i / /var
```

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/vda2      ext4   39G   12G   26G  32% /
```

تصمیم: جا هست. اگر Use% بالای ۹۵ بود، همان‌جا به صفحهٔ دیسک پر بروید و بقیهٔ این سناریو را روی میزبانِ بدون جا ادامه ندهید.

لایهٔ ۳، شبکه. اول عدد، بدون نام.

```bash
ip -br addr show ens18
ping -c 2 -W 1 10.10.1.10
curl -sv --max-time 5 http://10.10.1.10/ -o /dev/null
sudo ss -lntup | awk 'NR==1 || /:80/'
```

خروجی این حادثه:

```text
ens18 UP 10.10.1.10/24
64 bytes from 10.10.1.10: icmp_seq=1 ttl=64
* connect to 10.10.1.10 port 80 failed: Connection refused
```

و `ss` هیچ خط `:80` ندارد. تصمیم: میزبان و آدرس زنده‌اند، شنوندهٔ ۸۰ نیست. DNS و مجوز فایل هنوز متهم نیستند، چون اصلاً به HTTP نرسیده‌اید.

لایهٔ ۴، سرویس.

```bash
systemctl is-active nginx apache2
systemctl --failed --no-legend
```

```text
inactive
active
```

Apache بالا است ولی `ss` پورت ۸۰ را نشان نداد؟ پس یا روی پورت دیگری است یا واحد active است و فرایند گوش نمی‌دهد. در این سناریو فرض سازگار با connection refused این است که هر دو inactive باشند. اگر در میزبان شما apache فعال است و پورت را گرفته، خروجی `ss` فرایند apache را نشان می‌دهد و تصمیم صفحهٔ وب است: Apache را disable کنید و Nginx را برگردانید. هر دو حالت را با `ss` از هم جدا کنید، نه با اسم واحد تنها.

برای حادثهٔ «هیچ‌کس روی ۸۰ نیست»:

```bash
sudo systemctl start nginx
systemctl is-active nginx
```

اگر start شکست خورد، هنوز کانفیگ را تصادفی عوض نکنید. لایهٔ ۵.

لایهٔ ۵، لاگ همین بوت.

```bash
sudo journalctl -u nginx -b --no-pager | tail -n 30
```

نمونهٔ علت اول:

```text
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
nginx.service: Failed with result 'exit-code'.
```

این با `ss` خالی جور درنمی‌آید مگر شنونده بین دو فرمان آمده باشد. نمونهٔ علت دوم که با پورت خالی جور است، خطای نحو است و سرویس اصلاً نمانده:

```text
nginx: [emerg] unexpected end of file, expecting ";" or "}" in /etc/nginx/sites-enabled/app.example.com:12
```

تصمیم: `sudo nginx -t` ، همان خط فایل را با نسخهٔ سالم صفحهٔ وب مقایسه کنید، تست را سبز کنید، بعد start. یک تغییر. سپس شاهد لایهٔ ۳ را تکرار کنید.

```bash
sudo nginx -t
sudo systemctl start nginx
curl -sS -H 'Host: app.example.com' http://127.0.0.1/
```

اگر این بار کد ۴۰۳ آمد، شبکه و سرویس سالم‌اند و به مجوز رسیده‌اید. لاگ خطا:

```bash
sudo tail -n 20 /var/log/nginx/error.log
namei -l /var/www/app.example.com/index.html
```

`Permission denied` به‌علاوهٔ یک دایرکتوری بدون بیت عبور برای دیگران، یعنی `chmod 755` روی همان دایرکتوری، نه `chmod 777` روی درخت. بعد curl را دوباره بگیرید. باید جملهٔ آزمایشگاه را ببینید.

اگر از خود سرور سالم است و از ایستگاه مدیر نه، تازه آن وقت نام و فایروال را جدا کنید:

```bash
getent hosts app.example.com
dig +short app.example.com A
```

اگر نام به چیزی غیر از `10.10.1.10` حل شد، Nginx را دوباره دست نزنید. مشکل لایهٔ نام است.

## Security Notes

در عیب‌یابی، مجوز را شل نکنید تا «تمام شود». ۷۷۷ روی `/var/www` یا روی کلید، حادثهٔ امنیتی تازه‌ای است که سایت را هم برمی‌گرداند و فردا بدتر است. مسیر را با `namei` محدود کنید.

لاگ را در تیکت عمومی کامل نچسبانید اگر کوکی یا پارامتر نشست داخل access log است. خط emerg و کد وضعیت کافی است.

`systemctl cat nginx` را بخوانید قبل از این که واحد را از نو بنویسید. بازنویسی واحد بسته‌شده با ارتقای بعدی برمی‌گردد یا بدتر، drop-in فراموش‌شده رفتار را دو تکه می‌کند. تغییر واحد در [systemd](/docs/01-linux/systemd) است.

ابزار پایش را خاموش نکنید چون «مزاحم لاگ» است. اگر هشدار غلط می‌دهد، آستانه را در [پایش منبع](/docs/12-monitoring/resource-monitoring) درست کنید.

## Troubleshooting

علامت: هر پنج لایه سالم‌اند و کاربر هنوز می‌گوید سایت نیست. از شبکهٔ او یک شاهد بگیرید، نه از حلقهٔ محلی. `curl -sv --max-time 5 http://10.10.1.10/` روی ایستگاه مدیر. اگر آنجا timeout است و روی سرور ۲۰۰ است، مسیر یا فایروال بین شماست. `sudo nft list ruleset` و صفحهٔ UFW، نه یک Nginx دیگر.

علامت: `journalctl -u nginx` خالی است. یا واحد هرگز در این بوت صدا نشده، یا نام واحد عوض است. `systemctl list-units --type=service | awk '/nginx|apache/'` را ببینید. لاگ فایل ممکن است هنوز در `/var/log/nginx/error.log` باشد حتی اگر journal خالی بماند؛ هر دو را ببینید و یکی را شاهد کافی ندانید وقتی دیگری خطا دارد.

علامت: curl کد ۲۰۰ می‌دهد و مرورگر نه. کش مرورگر، HTTPS اجباری، یا هدر میزبان. با `curl -H 'Host: app.example.com'` از ایستگاه مقایسه کنید. اگر HTTP سالم است و HTTPS نه، گواهی یا پورت ۴۴۳ جداست و در فصل SSL است، نه یک خطای ریشهٔ فایل.

علامت: سرویس هر چند دقیقه می‌میرد. لایهٔ ۱ را دوباره ببینید؛ OOM killer در `journalctl -b -k` خط `Killed process` می‌گذارد. آن وقت حافظه علت است و نحو Nginx نه. صفحهٔ [حافظه](/docs/14-troubleshooting/memory-leak) را باز کنید.

اگر خود SSH قطع است، این صفحه از راه شبکه قابل اجرا نیست. مسیر [سرور بالا نمی‌آید](/docs/14-troubleshooting/server-down) و کنسول است.

## Best Practices

- پنج لایه را به ترتیب بنویسید حتی وقتی «مطمئنید» مشکل از کانفیگ است. دو خط خروجی، ارزان‌تر از یک ویرایش غلط است.
- یک تغییر، بعد تکرار همان curl. دو تغییر همزمان، علت بهبود را گم می‌کند.
- `ss` را بر `is-active` ترجیح دهید وقتی سؤال این است که پورت مال کیست.
- Apache و Nginx را با هم به‌عنوان راه‌حل بالا نیاورید. یکی باید شنونده باشد.
- ساعت و پر بودن دیسک را قبل از تفسیر لاگ ببینید.
- وقتی لایه از این صفحه خارج شد، به فصل ۱۴ یا صفحهٔ همان سرویس بروید و روش را آنجا ادامه دهید، نه این که همهٔ تعمیرها را این‌جا جمع کنید.

## تمرین

سناریو را روی کاغذ با خروجی زیر تمام کنید، بعد اگر VM تمرینی دارید فقط لایهٔ شاهد را زنده بگیرید و سرویس سالم را خراب نکنید.

خروجی فرضی شب حادثه:

```text
uptime: load average: 0.02, 0.05, 0.04
df -hT / : 40% used
curl http://10.10.1.10/ : Connection refused
ss پورت 80: خالی
is-active nginx: failed
is-active apache2: inactive
journal: bind() to 0.0.0.0:80 failed (98: Address already in use)
```

سؤال‌ها:

1. کدام لایه‌ها سالم‌اند و چرا خط journal با `ss` خالی هنوز یک تناقض است؟
2. اولین تغییر مجاز چیست و کدام تغییر ممنوع است؟
3. بعد از بالا آمدن Nginx اگر curl کد ۴۰۳ داد، کدام لایه تازه متهم شده است؟

دستور زنده، فقط شاهد، بدون خراب کردن:

```bash
systemctl is-active nginx
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: app.example.com' http://127.0.0.1/ || true
df -hT / | awk 'NR==1 || NR==2'
```

## پاسخ تمرین

لایهٔ ظرفیت و دیسک با این عددها سالم‌اند. لایهٔ شبکه تا حد رسیدن به میزبان سالم است و شنونده ندارد. سرویس nginx در حالت failed است و apache فعال نیست. تناقض: journal می‌گوید هنگام تلاش، پورت اشغال بوده، ولی الان `ss` خالی است. یعنی چیزی که پورت را گرفته بوده تمام شده، یا روی پورت دیگری بوده، یا بین دو مشاهده رفته است. قبل از ویرایش فایل سایت، یک‌بار دیگر `ss` و `journalctl -u nginx -u apache2 -b` را با هم بگیرید. اگر هنوز هیچ شنونده‌ای نیست، `nginx -t` را بزنید. اگر نحو سالم است، `systemctl start nginx` اولین تغییر مجاز است. اگر نحو خطای همان خط bind را دیگر نشان نمی‌دهد و خط تازه‌اش خطای فایل است، اول نحو.

تغییر ممنوع: نصب یک وب‌سرور سوم، `chmod 777`، باز کردن فایروال روی همهٔ پورت‌ها، و reload کردن BIND. هیچ‌کدام connection refused ناشی از نبود شنونده را توضیح نمی‌دهند.

اگر بعد از start کد ۴۰۳ آمد، لایه‌های شبکه و سرویس انجام شده‌اند و لایهٔ مجوز فایل، که در لاگ خطا و `namei` دیده می‌شود، متهم است. آن را با کمترین بیت عبور لازم درست کنید و curl را تکرار کنید.

شاهد زنده روی سیستم سالم باید `active` و کد ۲۰۰ باشد، مگر هنوز سایت را نساخته‌اید که آن وقت اول صفحهٔ وب است نه این تمرین. دیسک زیر ۹۵ درصد بماند. اگر کد ۰۰۰ گرفتید، curl اصلاً وصل نشده و همان لایهٔ ۳ زنده است؛ خروجی را در قالب یادداشت بنویسید و از لایهٔ ۴ ادامه دهید.
