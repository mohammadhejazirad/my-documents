# دیسک و فایل‌سیستم

## مقدمه

هدف ۱۰۲.۱ و ۱۰۴ از آزمون ۱۰۱ دربارهٔ چیدمان دیسک، ساخت فایل‌سیستم، سوار کردن، سلامت فایل‌سیستم، و سهمیه (quota) است. LVM در ۱۰۱ فقط ویژگی پایه است؛ گسترش و RAID و LUKS در [ذخیرهٔ ۲۰۱](/docs/02-lpic/lpic2-201-storage) است. مفهوم فایل‌سیستم روزمره در [پارتیشن](/docs/01-linux/partitioning)، [فایل‌سیستم](/docs/01-linux/filesystems) و [دستور دیسک](/docs/01-linux/commands-disk) است. این صفحه همان کار را از دید آزمون به‌علاوهٔ دیسکی که نباید روش ریشه را خراب کند می‌نویسد.

تمام دستورهای تخریبی این صفحه روی دیسک خالی آزمایشگاه‌اند. در مثال، آن دیسک `/dev/sdb` است. اگر `lsblk` چیز دیگری نشان داد، متن را کورکورانه اجرا نکنید.

## مفهوم اصلی

جدول پارتیشن می‌گوید هر تکهٔ دیسک از کجا تا کجاست. MBR جدول قدیمی است: چهار ورودی اصلی، دیسک بزرگ‌تر از حدود ۲ ترابایت را درست پوشش نمی‌دهد، و کد بوت BIOS در همان سکتور اول می‌نشیند. GPT جدول UEFI است: پارتیشن زیاد، دیسک بزرگ، و یک پارتیشن سیستم EFI از نوع FAT. روی GPT یک MBR محافظ هم هست تا ابزار قدیمی دیسک را خالی نبیند.

فایل‌سیستم روی پارتیشن یا روی حجم منطقی ساخته می‌شود، نه روی خود جدول. `mkfs.ext4` و `mkfs.xfs` داده را پاک می‌کنند. سوار کردن (mount) آن فایل‌سیستم را به یک مسیر وصل می‌کند. `/etc/fstab` همین وصل را بعد از بوت تکرار می‌کند. شناسهٔ درست UUID است، نه نام `sdb1` که با عوض شدن ترتیب دیسک می‌لغزد.

LVM سه لایه دارد. Physical Volume روی دیسک یا پارتیشن است. Volume Group آن‌ها را یک استخر می‌کند. Logical Volume چیزی است که فایل‌سیستم روش می‌نشیند و در `/dev/vgname/lvname` دیده می‌شود. در ۱۰۱ باید این سه اسم و دستور ساخت را بلد باشید، نه لزوماً جابه‌جایی زندهٔ داده.

سهمیه سقف مصرف یک کاربر یا گروه روی یک فایل‌سیستم است، نه سقف کل دیسک. SMART وضعیت سلامت خود دیسک را از کنترلر می‌پرسد و با پر بودن فایل‌سیستم فرق دارد.

## چرا استفاده می‌شود؟

ریشه، `/var` و `/home` اگر یک پارتیشن باشند، پر شدن لاگ یا خانهٔ کاربر سرویس را هم می‌خواباند. هدف ۱۰۲.۱ دقیقاً همین طراحی است: ESP جدا برای UEFI، و معمولاً `/var` جایی که لاگ و صف نامه رشد می‌کند. روی سرور کوچک آزمایشگاه یک ریشهٔ تنها قابل قبول است، به شرطی که پایش دیسک روشن باشد.

سهمیه وقتی لازم می‌شود که `deploy` و کاربران انسانی روی یک حجم فایل می‌ریزند. بدون سهمیه، یک آپلود اشتباه کل حجم را پر می‌کند و حتی لاگ ورود دیگر نوشته نمی‌شود.

SMART قبل از مرگ دیسک اغلب شمارندهٔ سکتور جایگزین‌شده را بالا می‌برد. دیدن آن شمارنده جایگزین پشتیبان نیست، ولی زمان می‌خرد.

## Architecture

چیدمان پیشنهادی یک VM تازه در این آزمایشگاه، وقتی دیسک سیستم ۴۰ گیگ است:

```text
/dev/vda   GPT
  vda1   512M   FAT32   ESP      سوار روی /boot/efi
  vda2   بقیه   ext4    ریشه     سوار روی /

/dev/sdb   دیسک داده، خالی، فقط تمرین
  sdb1   20G    LVM PV
           └─ vgdata/lvbackup   ext4   /srv/backup
  sdb2   2G     swap
```

ریشه را در تمرین پارتیشن‌بندی نکنید. اگر تولید واقعی می‌سازید، `/var` جدا برای لاگ و دیتابیس تصمیم درستی است و طرحش در [پارتیشن](/docs/01-linux/partitioning) آمده است. ESP باید FAT بماند. هسته روی `/boot` است که می‌تواند همان ریشه باشد یا پارتیشن جدا؛ GRUB باید آن را بخواند.

ابزار جدول: `parted` صریح است، `fdisk` در util-linux جدید GPT را هم بلد است، `gdisk` مخصوص GPT است. آزمون هر سه نام را دارد. مثال اجرایی این صفحه `parted` است.

## Installation

ابزار پارتیشن و ext4 روی سیستم پایه هستند. سهمیه و SMART بستهٔ جدا می‌خواهند. LVM اغلب با نصب سرور آمده؛ اگر دستور `pvs` نبود بسته‌اش `lvm2` است.

```bash
sudo apt update
sudo apt install lvm2 quota smartmontools
sudo systemctl enable --now smartmontools
```

وضعیت سرویس:

```bash
systemctl is-active smartmontools
smartctl --version | head -n 1
```

`smartmontools.service` گاهی فقط oneshot تنظیم است و واحد در حال اجرا `smartd` است. `systemctl status smartmontools` را بخوانید. اگر `active` نبود و `smartd` هم نبود، واحد را از روی نام بسته‌ای که `dpkg -L smartmontools | grep systemd` نشان می‌دهد روشن کنید.

## Configuration

شناسایی، قبل از هر نوشتن:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,MODEL
findmnt /
```

اگر `/dev/sdb` در خروجی نیست، دیسک تمرین را به VM وصل کنید و دوباره بخوانید. اگر تنها دیسک `vda` است و ریشه روی آن است، همین‌جا توقف کنید.

ساخت جدول GPT و یک پارتیشن داده. این دستور محتوای `sdb` را از بین می‌برد.

```bash
sudo parted /dev/sdb --script mklabel gpt
sudo parted /dev/sdb --script mkpart data ext4 1MiB 20GiB
sudo parted /dev/sdb --script set 1 lvm on
sudo parted /dev/sdb --script mkpart swap linux-swap 20GiB 22GiB
sudo parted /dev/sdb --script print
```

LVM مقدماتی و فایل‌سیستم:

```bash
sudo pvcreate /dev/sdb1
sudo vgcreate vgdata /dev/sdb1
sudo lvcreate -L 10G -n lvbackup vgdata
sudo mkfs.ext4 -L backup /dev/vgdata/lvbackup
sudo mkswap /dev/sdb2
sudo mkdir -p /srv/backup
```

UUID را بردارید و در fstab بگذارید. نمونهٔ زیر را با UUID خودتان عوض کنید.

```bash
sudo blkid /dev/vgdata/lvbackup /dev/sdb2
```

دو خط fstab، با UUID واقعی:

```text
UUID=PUT-BACKUP-UUID  /srv/backup  ext4  defaults,usrquota,grpquota  0  2
UUID=PUT-SWAP-UUID    none         swap  sw                          0  0
```

ستون آخر برای ext4 عدد ۲ است تا `fsck` در بوت ترتیب داشته باشد. ریشه همیشه ۱ است. swap صفر است.

```bash
sudo mount /srv/backup
sudo swapon -a
findmnt /srv/backup
swapon --show
```

گزینهٔ `usrquota,grpquota` روی ext4 سهمیهٔ کاربر و گروه را روشن می‌کند. سهمیهٔ پروژه (`prjquota`) روی ext4 همان شیار گروه را مصرف می‌کند؛ همزمان با `grpquota` روی یک حجم ext4 ترکیب نکنید. روی XFS سهمیه با گزینهٔ mount متفاوت است و `quotacheck` همان مسیر ext4 را ندارد. این تمرین ext4 است.

فعال کردن سهمیه بعد از سوار شدن:

```bash
sudo quotacheck -cugm /srv/backup
sudo quotaon -v /srv/backup
```

`edquota` ویرایشگر را باز می‌کند. برای تمرین غیرتعاملی سقف را با `setquota` می‌گذاریم تا به vi وابسته نباشد. واحد بلوک ۱ کیلوبایت است. نرم ۱۰۰ مگابایت و سخت ۱۵۰ مگابایت برای کاربر `deploy`:

```bash
sudo setquota -u deploy 102400 153600 0 0 /srv/backup
sudo repquota -s /srv/backup
```

اگر کاربر `deploy` هنوز نیست، این دستور شکست می‌خورد. ساخت کاربر در [مدیریت کاربر](/docs/01-linux/user-management) است؛ برای تمرین می‌توانید موقت `ops` را بگذارید.

SMART، فقط خواندن:

```bash
sudo smartctl --scan
sudo smartctl -H /dev/sdb || true
sudo smartctl -i /dev/vda || true
```

روی NVMe اگر `-H /dev/nvme0n1` خطا داد، `/dev/nvme0` را امتحان کنید. دیسک مجازی اغلب SMART واقعی ندارد و `SMART support is: Unavailable` می‌دهد. این خرابی دیسک فیزیکی نیست.

## Production Example

روی `app-1` لاگ پر شده و نمی‌خواهید ریشه را بزرگ کنید چون دیسک VM تمام شده. دیسک تازه `/dev/sdc` به ماشین اضافه شده و باید فقط `/var/log` را نجات دهد. این کار تولید است و توقف سرویس می‌خواهد. ترتیب کوتاه:

1. `lsblk` و مطمئن شوید `sdc` خالی است و `vda` ریشه است.
2. پارتیشن و `mkfs.ext4` روی `sdc1`.
3. `rsync -a /var/log/ /mnt/newlog/` در وقتی سرویس‌هایی که لاگ می‌نویسند متوقف‌اند، یا از روش [دیسک پر](/docs/14-troubleshooting/disk-full) اگر فقط باید فوری جا باز کنید.
4. UUID را در fstab برای `/var/log` بگذارید و `findmnt` را بعد از reboot ببینید.

سلامت فایل‌سیستم ext4 را فقط وقتی حجم سوار نیست بگیرید. `e2fsck` روی حجم سوارِ خواندنی-نوشتنی داده را خراب می‌کند.

```bash
sudo umount /srv/backup
sudo e2fsck -f /dev/vgdata/lvbackup
sudo mount /srv/backup
```

`-f` یعنی حتی اگر سیستم فایل «تمیز» علامت خورده باشد بررسی کن. روی ریشه این کار را از مدیا زنده انجام دهید، نه با `umount /`.

XFS را `e2fsck` نزنید. ابزارش `xfs_repair` است و آن هم حجم را سوار نمی‌خواهد. بررسی بدون تغییر: `sudo xfs_repair -n /dev/vgdata/lvbackup`.

فضای خالی و inode دو عدد جدا هستند. پر شدن inode با `df -h` که هنوز جا نشان می‌دهد سازگار است.

```bash
df -hT /srv/backup
df -i /srv/backup
```

## Security Notes

`mkfs` و `parted mklabel` برگشت‌ناپذیرند. آن‌ها را داخل اسکریپتی که دستگاه را با نام `sdb` پیدا می‌کند نگذارید. نام پایدار `/dev/disk/by-id` را در اسکریپت تولید استفاده کنید و باز هم قبل از اجرا چاپ کنید.

fstab اشتباه یعنی بوت اضطراری. بعد از ویرایش، `sudo mount -a` را قبل از reboot بزنید. اگر خطا داد، reboot نکنید.

سهمیه جایگزین مجوز فایل نیست. `deploy` اگر روی `/srv/backup` مالک دایرکتوری خودش نباشد اصلاً نمی‌نویسد، چه سهمیه باشد چه نباشد. مجوز در [مجوزها](/docs/01-linux/permissions) است.

`smartctl -a` سریال دیسک را نشان می‌دهد. آن خروجی را در تیکت عمومی نفرستید اگر سیاست سازمان سریال سخت‌افزار را دادهٔ داخلی می‌داند. نتیجهٔ PASS یا FAIL کافی است.

## Troubleshooting

علامت: `mount: unknown filesystem type` . بستهٔ ابزار فایل‌سیستم نصب نیست، مثلاً `xfsprogs` برای XFS، یا نوع در fstab غلط تایپ شده. `blkid` نوع واقعی را می‌گوید.

علامت: بوت می‌ایستد و ریشه فقط‌خواندنی است. یک خط fstab غلط است. از [بوت](/docs/02-lpic/lpic1-101-boot) به حالت اضطراری بروید، `mount -o remount,rw /` ، خط را اصلاح کنید، `mount -a` را بسنجید.

علامت: `quotaon` می‌گوید سهمیه پشتیبانی نمی‌شود. گزینهٔ mount را فراموش کرده‌اید. `findmnt -o OPTIONS /srv/backup` باید `usrquota` را نشان دهد. بعد `sudo mount -o remount /srv/backup`.

علامت: `repquota` عدد می‌دهد ولی کاربر هنوز بیشتر از سخت نوشته است. فرآیندهایی که فایل باز دارند تا وقتی فایل بسته نشود بلوک را رها نمی‌کنند. `sudo lsof +L1` را روی همان مسیر ببینید. این با سهمیهٔ «خراب» فرق دارد.

اگر `pvcreate` گفت دیسک در حال استفاده است، یا سوار است یا جدول پارتیشن هنوز امضای فایل‌سیستم قدیمی دارد. تا وقتی `findmnt` و `lsblk` مصرف‌کننده را نشان می‌دهند، امضا را با ابزار wipe پاک نکنید.

## Best Practices

- UUID در fstab. نام `sdX` فقط در جلسهٔ تعاملی و بعد از `lsblk`.
- ESP را ext4 نکنید. UEFI آن را به‌عنوان FAT می‌خواهد.
- LVM سطح ۱۰۱ یعنی ساخت PV و VG و LV. گسترش آنلاین و snapshot را به صفحهٔ ۲۰۱ بسپارید تا دو روش وسط حادثه قاطی نشود.
- سهمیه را روی حجم داده بگذارید، نه به‌عنوان اولین واکنش روی ریشه.
- SMART را برای دیسک فیزیکی بخوانید. روی دیسک مجازی «Unavailable» را تیکت بحرانی نکنید.
- `fsck` را روی فایل‌سیستم سوار اجرا نکنید.

## تمرین

دیسک خالی را با `lsblk` معرفی کنید. اگر دیسک خالی ندارید، تمرین نوشتنی را انجام ندهید و فقط بخش خواندنی را جواب دهید.

بخش خواندنی:

```bash
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT
findmnt -no SOURCE,FSTYPE,UUID /
df -hT /
df -i /
```

بخش نوشتنی، فقط اگر `/dev/sdb` خالی و بدون mount است: جدول GPT، یک حجم منطقی ۱۰ گیگ در گروه `vgdata`، سوار روی `/srv/backup`، و سهمیهٔ نرم ۵۰ مگابایت برای `ops`.

سؤال‌ها:

1. چرا MBR برای دیسک ۴ ترابایتی انتخاب بدی است؟
2. فرق پر شدن بلوک با پر شدن inode چیست و کدام دستور دومی را نشان می‌دهد؟
3. چرا `e2fsck` را روی `/` سوارشده نمی‌زنیم؟

## پاسخ تمرین

بخش خواندنی باید ریشه را روی پارتیشنی از دیسک سیستم نشان دهد، با نوع ext4 یا xfs، و درصد استفاده. inode باقی‌مانده معمولاً خیلی بیشتر از درصد بلوک است. اگر هر دو بالای ۹۰ درصد بودند، قبل از تمرین نوشتنی به [دیسک پر](/docs/14-troubleshooting/disk-full) بروید.

بخش نوشتنی موفق یعنی `findmnt /srv/backup` منبع `/dev/mapper/vgdata-lvbackup` یا `/dev/vgdata/lvbackup` را نشان دهد و `repquota -s /srv/backup` برای `ops` سقف نرم ۵۱۲۰۰ بلوک یک‌کیلوبایتی را نشان دهد. پنجاه مگابایت برابر ۵۱۲۰۰ بلوک یک‌کیلوبایتی است.

دستور سقف، بعد از `quotaon`:

```bash
sudo setquota -u ops 51200 102400 0 0 /srv/backup
sudo repquota -s /srv/backup
```

1. MBR آدرس‌دهی ۳۲بیتی سکتور دارد و حدود ۲ ترابایت را پوشش می‌دهد. دیسک ۴ ترابایتی GPT می‌خواهد. علاوه بر این، بوت UEFI به ESP روی GPT تکیه می‌کند.
2. بلوک یعنی بایت داده. inode یعنی تعداد فایل. `df -h` اولی را نشان می‌دهد و `df -i` دومی را. حجم می‌تواند از نظر بایت خالی و از نظر تعداد فایل تمام باشد.
3. چون فایل‌سیستم در حال تغییر است و بررسیِ همراه با ترمیم، ساختار را با نوشتن همزمان برنامه ناسازگار می‌کند. ریشه را از مدیا زنده، وقتی سوار نیست یا فقط فقط‌خواندنی و بدون ترمیم است، بررسی کنید. روی حجم تمرین، اول `umount`.
