# امنیت LPIC-1

## مقدمه

هدف ۱۱۰ آزمون ۱۰۲ امنیت میزبان را در سه تکه می‌خواهد: حسابرسی و sudo و درگاه باز، خاموش کردن سرویس اضافه و سایهٔ رمز، و رمزنگاری با SSH و GnuPG. عمق تولیدی همان موضوع در [کاربر و فایل](/docs/10-security/users-and-files)، [sudo](/docs/01-linux/sudo)، [مجوز](/docs/01-linux/permissions) و [سخت‌سازی SSH](/docs/10-security/ssh-hardening) است. این صفحه سناریوی آزمون را روی OpenSSH حدود ۱۰.۲ که با Ubuntu 26.04 می‌آید اجرا می‌کند و آن فصل‌ها را خط به خط تکرار نمی‌کند.

سیاست این دانشنامه فقط کلید `ed25519` است. DSA در OpenSSH 10 حذف شده است. الگوریتم امضای قدیمی `ssh-rsa` با شا-۱ را هم پیشنهاد نکنید.

## مفهوم اصلی

مجوز فایل سه دسته دارد: مالک، گروه، دیگران. هر دسته خواندن و نوشتن و اجرا دارد. روی دایرکتوری، بیت اجرا یعنی اجازهٔ عبور، نه اجرای یک برنامه. بیت setuid یعنی فایل با امتیاز مالک اجرا شود نه امتیاز اجراکننده. setgid روی دایرکتوری یعنی فایل تازه‌ساخته گروه دایرکتوری را به ارث می‌برد. بیت چسبنده (sticky) روی دایرکتوری یعنی هر کس فقط فایل خودش را پاک کند؛ `/tmp` همین است.

umask عددی است که از مجوز پیش‌فرض کم می‌شود. برای فایل، سقف معمول ۶۶۶ است و برای دایرکتوری ۷۷۷. umask برابر `027` فایل تازه را ۶۴۰ و دایرکتوری را ۷۵۰ می‌سازد. این یک مجوز اجباری روی فایل‌های موجود نیست.

sudo یک دروازهٔ موقت به فرمان مشخص است، نه جایگزینی برای ورود با کاربر root. فایل مؤثر `/etc/sudoers` به‌علاوهٔ تکه‌های `/etc/sudoers.d` است و فقط با `visudo` باید ویرایش شود تا یک غلط املایی ورود مدیر را نبندد.

SSH دو جفت کلید جدا دارد. کلید میزبان در `/etc/ssh/ssh_host_*` هویت خود سرور است. کلید کاربر در `~/.ssh` هویت انسان است. قاطی کردن این دو، یا کپی کلید میزبان موقع کلون، همان حادثهٔ معماری است که در [معماری](/docs/02-lpic/lpic1-101-architecture) آمد.

## چرا استفاده می‌شود؟

setuid فراموش‌شده در `/usr/local` یعنی هر کاربر محلی می‌تواند به امتیاز root برسد اگر آن باینری قابل سوءاستفاده باشد. آزمون پیدا کردنش را با `find` می‌خواهد. تولید هم همان فرمان را در خط پایهٔ تغییر می‌گذارد.

رمز عبور SSH، حتی رمز قوی، در برابر تلاش انبوه ضعیف است. OpenSSH 10 روی ایمیج ابری Ubuntu اغلب از قبل `PasswordAuthentication no` دارد. روی نصب ISO ممکن است مقدار مؤثر هنوز yes باشد، چون پیش‌فرض کامپایل‌شدهٔ بالادستی yes است و فایل اصلی فقط همان را کامنت کرده. تصمیم را `sshd -T` می‌گوید نه حافظهٔ آزمون.

`PermitRootLogin` پیش‌فرض بالادستی `prohibit-password` است: ریشه با رمز نه، با کلید شاید. سیاست این تیم `no` است. ورود ریشه را با sudo انجام می‌دهیم تا لاگ، نام انسان را داشته باشد.

## Architecture

```text
انسان ops
  │  کلید خصوصی ed25519 روی ایستگاه خودش
  ▼
sshd روی app-1:22
  ├─ کلید میزبان /etc/ssh/ssh_host_ed25519_key
  ├─ سیاست مؤثر: خروجی sshd -T
  │     PasswordAuthentication
  │     PermitRootLogin
  │     PubkeyAuthentication
  │     PerSourcePenalties
  └─ ~/.ssh/authorized_keys   فقط کلید عمومی

بعد از ورود
  sudo  ── visudo ── /etc/sudoers.d/ops
  مجوز فایل و umask نشست
```

`PerSourcePenalties` از OpenSSH 9.8 هست و در نسخهٔ ۱۰ Ubuntu پیش‌فرض روشن است. یعنی منبعی که زیاد خطا می‌کند برای مدتی بلاک می‌شود، بدون Fail2ban. این جای فهمیدن Fail2ban را نمی‌گیرد؛ هم‌پوشانی‌شان در [امنیت ۲۰۲](/docs/02-lpic/lpic2-202-security) است.

TCP wrapper و فایل `hosts.allow` را آزمون هنوز نام می‌برد. systemd و سوکت‌های امروزی به آن تکیه نمی‌کنند. برای SSH از `AllowUsers` و فایروال استفاده کنید، نه از hosts.allow به‌تنهایی. xinetd هم روی این سرورها نصب نیست.

## Installation

OpenSSH سرور اگر نیست:

```bash
sudo apt update
sudo apt install openssh-server
sudo systemctl enable --now ssh
ss -lnt 'sport = :22'
```

بستهٔ `sudo` روی Ubuntu Server هست. GnuPG برای بخش آزمون رمز فایل:

```bash
sudo apt install gnupg
gpg --version | head -n 1
ssh -V
```

`ssh -V` باید OpenSSH را نشان دهد و عدد اصلی‌اش ۱۰ باشد، شبیه `OpenSSH_10.2`. عدد دقیق patch را از خروجی بردارید.

کلید کاربر را روی ایستگاه مدیر بسازید، نه روی سرور. اگر مجبورید روی خود `app-1` تمرین کنید، با کاربر `ops` باشد.

```bash
ssh-keygen -t ed25519 -a 64 -C "ops@app-1.example.internal"
```

رمز عبور کلید را خالی نگذارید مگر کلید فقط روی یک میزبان مهروموم‌شدهٔ اتوماسیون باشد و سیاست جدا داشته باشد. مسیر پیش‌فرض `~/.ssh/id_ed25519` است. فایل خصوصی باید حالت ۶۰۰ باشد و عمومی ۶۴۴. `ssh-keygen` این را خودش می‌گذارد.

## Configuration

مقدار مؤثر دیمون را چاپ کنید. این دستور کانفیگ را تفسیرشده نشان می‌دهد، شامل drop-inهای `/etc/ssh/sshd_config.d`.

```bash
sudo sshd -T | awk 'BEGIN{IGNORECASE=1} $1 ~ /^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication|persourcepenalties)$/'
```

نمونهٔ مطلوب تولید:

```text
permitrootlogin no
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
persourcepenalties yes
```

اگر رمز هنوز yes است، یک فایل جدا بسازید تا ارتقای بسته فایل اصلی را برنگرداند. اول مطمئن شوید کلید `ops` در `authorized_keys` هست و یک نشست SSH دوم باز است. وگرنه خودتان را قفل می‌کنید.

```bash
sudo tee /etc/ssh/sshd_config.d/10-ops.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
AllowUsers ops
EOF
sudo sshd -t
sudo systemctl reload ssh
```

`sshd -t` اگر چیزی چاپ نکرد و خروج صفر داشت، نحو درست است. `AllowUsers ops` یعنی هیچ کاربر دیگری حتی با کلید درست وارد نمی‌شود. کاربر `deploy` را به این فهرست اضافه نکنید؛ او سرویس است نه انسان. اگر اتوماسیون باید وارد شود، کاربر جدا با کلید جدا و فرمان محدود لازم دارد، نه باز کردن رمز.

کپی کلید عمومی به سرور، از ایستگاه مدیر:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub ops@10.10.1.10
```

اگر رمز از قبل خاموش است و هنوز کلیدی نیست، از کنسول محلی فایل `authorized_keys` را بسازید. مجوز دایرکتوری خانه نباید برای دیگران نوشتنی باشد وگرنه sshd کلید را نادیده می‌گیرد. `StrictModes yes` پیش‌فرض است.

sudo برای `ops` روی Ubuntu از قبل از راه گروه `sudo` هست. سیاست اضافه‌ای که فقط فرمان مشخصی را بدون رمز اجازه دهد، در فایل جدا:

```bash
sudo visudo -f /etc/sudoers.d/ops-disk
```

محتوا یک خط است، بدون نوشتن ALL:

```text
ops ALL=(root) NOPASSWD: /usr/bin/du, /usr/bin/df
```

`visudo` نحو را می‌سنجد. `NOPASSWD` روی `ALL` را در آزمایشگاه هم عادت نکنید. توضیح مدل sudo در [sudo](/docs/01-linux/sudo) است.

umask نشست `ops` را در `~/.bashrc` بگذارید اگر سیاست تیم ۲۷ است:

```bash
umask 027
umask
```

فایل تازه‌ای در `/tmp/umask-test` بسازید و `ls -l` بگیرید. باید `-rw-r-----` باشد. بعد فایل تمرین را پاک کنید. umask سراسری ورود در `/etc/login.defs` کلید `UMASK` است و ممکن است pam آن را عوض کند. مقدار نشست را با فرمان `umask` بدون آرگومان ببینید، نه فقط با خواندن یک فایل.

پیدا کردن setuid روی فایل‌سیستم ریشه، بدون عبور به دیسک دیگر:

```bash
sudo find / -xdev -perm -4000 -type f -printf '%m %p\n' 2>/dev/null
```

`-perm -4000` یعنی بیت setuid روشن باشد، بقیهٔ بیت‌ها هر چه هستند. خروج معمول شامل `passwd` و `sudo` است. چیزی زیر `/tmp` یا `/home` یا `/usr/local` غیرعادی است و باید توضیح داشته باشد.

رمز و سن حساب، هدف ۱۱۰.۱:

```bash
sudo chage -l ops
```

قفل ورود تعاملی موقت با `sudo passwd -l کاربر` رمز را خراب نمی‌کند ولی ورود با رمز را می‌بندد. کلید SSH ممکن است هنوز کار کند. برای بستن کامل، `usermod -L` کافی نیست؛ باید کلید و پوسته و sudo را هم ببینید. ساخت و حذف کاربر در [مدیریت کاربر](/docs/01-linux/user-management) است.

سقف فرایند نشست آزمون را `ulimit -a` نشان می‌دهد. برای یک سرویس، سقف را در واحد systemd بگذارید نه در پروفایل.

GnuPG در حد آزمون: ساخت کلید تعاملی با `gpg --full-generate-key` روی ایستگاه مدیر است و در سرور تولید برای «شاید لازم شد» کلید نسازید. رمز کردن یک فایل گزارش:

```bash
printf 'disk ok\n' > /tmp/lab-note.txt
gpg --batch --yes -r ops@app-1.example.internal -e /tmp/lab-note.txt
```

اگر هنوز کلیدی برای آن هویت نیست، دستور شکست می‌خورد. این شکست بهتر از ساختن بی‌سروصدای یک کلید بدون نسخهٔ ابطال است. ابطال و اعتماد کلید را همان روزی که کلید را می‌سازید بنویسید. فایل `.gpg` بدون کلید خصوصی قابل برگشت نیست؛ کلید خصوصی را در مخزن نگذارید.

## Production Example

خط پایهٔ امنیتی `app-1` بعد از تحویل VM، یک صفحه در یادداشت تغییر است نه یک اسکن مبهم. این چهار خروجی را ذخیره کنید.

```bash
sudo sshd -T | awk 'BEGIN{IGNORECASE=1} $1 ~ /^(passwordauthentication|permitrootlogin|persourcepenalties)$/'
sudo find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -printf '%m %p\n' 2>/dev/null
sudo awk '/^[^#]/' /etc/sudoers /etc/sudoers.d/* 2>/dev/null
ss -lntup
```

بیت ۲۰۰۰ یعنی setgid. فهرست setuid را با فهرست هفتهٔ قبل مقایسه کنید. یک باینری تازه در `/usr/local/bin` بدون تیکت، حادثه است حتی اگر «فقط یک ابزار» باشد.

پورت غیرمنتظره را با هدف ۱۰۹ که در [شبکهٔ ۱۰۲](/docs/02-lpic/lpic1-102-networking) است معنی کنید. اگر `ss` پورت ۲۳ یا ۲۱ نشان داد، سرویس را خاموش و خاموش در بوت کنید:

```bash
sudo systemctl disable --now inetd.service 2>/dev/null || true
systemctl --type=service --state=running
```

سرویس ناشناس را همان لحظه purge نکنید. اول بفهمید چه بسته‌ای آن را آورده: `dpkg -S` روی دودویی. خاموش کردن کافی است تا تصمیم پاک کردن جدا باشد.

ورودها را آزمون با `who` و `w` و `last` می‌خواهد.

```bash
who
last -n 5
```

`last` ورود موفق و reboot را از `/var/log/wtmp` می‌خواند. اگر خالی است، یا میزبان نو است یا لاگ چرخیده. این به‌تنهایی نشانهٔ نفوذ نیست.

## Security Notes

کلید خصوصی `id_ed25519` را به سرور کپی نکنید «تا از آنجا به جاهای دیگر بروید». روی سرور فقط کلید عمومی در `authorized_keys` می‌ماند. پرش به میزبان بعدی باید از ایستگاه مدیر باشد، یا با یک کلید واسط که سیاست خودش را دارد.

`PermitRootLogin yes` حتی برای یک ساعت عیب‌یابی، رمز ریشه را در معرض همان پویشی می‌گذارد که `PerSourcePenalties` فقط کمی کندش می‌کند. از کنسول هایپروایزر وارد شوید.

خروجی `chage` و `last` نام انسان است. در کانال عمومی تیم نچسبانید اگر سیاست دسترسی حداقل است.

اسکن `nmap` مال همین هدف است و فقط داخل آزمایشگاه. یک مثال کافی است:

```bash
sudo nmap -sT -p 22,80,443 10.10.1.10
```

اسکن گستردهٔ شبکهٔ سازمان و هر آدرسی بیرون `10.10.1.0/24` خارج از این تمرین است. اگر `nmap` نصب نیست، برای همین یک بررسی `ss` روی خود میزبان دقیق‌تر است چون نام فرایند را هم می‌دهد. نصب: `sudo apt install nmap`.

## Troubleshooting

علامت: `Permission denied (publickey)` بعد از بستن رمز.

کلید اشتباه، مجوز خانه، یا `AllowUsers`. از کنسول:

```bash
sudo tail -n 30 /var/log/auth.log 2>/dev/null || sudo journalctl -u ssh -n 30 --no-pager
ls -ld /home/ops /home/ops/.ssh
ls -l /home/ops/.ssh/authorized_keys
```

دایرکتوری خانه نباید برای گروه یا دیگران نوشتنی باشد. `.ssh` معمولاً ۷۰۰ و `authorized_keys` ۶۰۰ یا ۶۴۴. اگر لاگ گفت `Authentication refused: bad ownership`، همان مجوز را درست کنید نه این که `StrictModes` را خاموش کنید.

علامت: `sshd -t` خطا می‌دهد و reload را نزده‌اید. سرویس هنوز سیاست قدیمی را دارد. فایل drop-in را اصلاح کنید و دوباره `-t` بزنید. اگر reload کرده‌اید و نشست‌های جدید مرده‌اند، نشست باز فعلی را نبندید؛ از همان نشست برگردانید.

علامت: `find` خیلی طول می‌کشد. بدون `-xdev` وارد `/proc` و دیسک‌های دیگر می‌شود. همان فلگ صفحه را استفاده کنید. خطاهای مجوز بدون `sudo` طبیعی است و با `2>/dev/null` پنهانشان کرده‌ایم؛ یک‌بار بدون پنهان کردن اجرا کنید اگر شک دارید چیزی جا مانده.

علامت: sudo می‌گوید `ops is not in the sudoers file`. گروه را با `getent group sudo` ببینید. افزودن به گروه تا ورود بعدی کامل اثر نمی‌گذارد. `newgrp` یا یک SSH تازه لازم است.

## Best Practices

- سیاست SSH را در `/etc/ssh/sshd_config.d` بگذارید و با `sshd -T` اثبات کنید. فایل اصلی پر از کامنت، وضعیت مؤثر نیست.
- فقط ed25519. اگر سؤال آزمون اسم `id_dsa` را آورد، بدانید میراث آزمون است و روی OpenSSH 10 ساخته نمی‌شود.
- setuid را دوره‌ای فهرست کنید. هر مورد خارج از بسته‌های توزیع باید صاحب تیکت باشد.
- sudo را به فرمان محدود کنید. `NOPASSWD: ALL` پاسخ تمرین این صفحه نیست.
- umask را با ساخت یک فایل آزمایشی ثابت کنید. خواندن یک خط کانفیگ به‌تنهایی اثبات نمی‌کند pam مقدار دیگری اعمال نکرده باشد.
- اسکن را به آزمایشگاه و به پورت مشخص محدود کنید.

## تمرین

سناریو: VM تازهٔ `app-1` را به شما داده‌اند. باید قبل از دادن آدرس به تیم، رمز SSH را ببندید، ورود ریشه را ممنوع کنید، و فهرست setuid غیرعادی را خالی تحویل دهید. یک نشست کنسول را باز نگه دارید.

```bash
sudo sshd -T | awk 'BEGIN{IGNORECASE=1} $1 ~ /^(passwordauthentication|permitrootlogin)$/'
sudo find / \( -path /proc -o -path /sys \) -prune -o -perm -4000 -type f -printf '%p\n' 2>/dev/null
umask
```

بعد فایل `/etc/ssh/sshd_config.d/10-ops.conf` را مطابق بخش کانفیگ بسازید، `sshd -t` بزنید و سرویس را reload کنید. با یک نشست تازه، ورود با رمز باید شکست بخورد و ورود با کلید باید بماند.

سؤال کوتاه:

1. پیش‌فرض بالادستی `PermitRootLogin` چیست و سیاست این دانشنامه چیست؟
2. umask برابر ۰۲۷ روی فایل تازه چه حالتی می‌سازد؟
3. چرا setuid روی اسکریپت پوسته را راه نمی‌اندازیم؟

## پاسخ تمرین

قبل از تغییر، خروجی ممکن است `passwordauthentication yes` و `permitrootlogin prohibit-password` باشد، به‌خصوص روی نصب غیر ابری. بعد از reload، `sshd -T` باید `no` و `no` نشان دهد. نشست قدیمی SSH را ملاک نگیرید؛ سیاست روی احراز هویت تازه اعمال می‌شود.

فهرست setuid باید فقط مسیرهای بسته‌ای مثل `/usr/bin/sudo` و `/usr/bin/passwd` باشد. اگر `/tmp` یا خانهٔ کاربر در فهرست بود، بیت را بردارید و بپرسید چه کسی گذاشته: `sudo chmod u-s مسیر`. باینری ناشناس را اجرا نکنید.

1. پیش‌فرض بالادستی `prohibit-password` است. سیاست این دانشنامه `PermitRootLogin no` است تا ریشه حتی با کلید هم از راه SSH نیاید.
2. فایل از سقف ۶۶۶ با umask ۰۲۷ به ۶۴۰ می‌رسد، یعنی خواندن و نوشتن برای مالک و خواندن برای گروه. دایرکتوری از ۷۷۷ به ۷۵۰ می‌رسد.
3. چون پوسته موقع اجرا فایل اسکریپت را دوباره باز می‌کند و بین چک مجوز و اجرا می‌شود فایل را عوض کرد. کار ممتاز از sudo یا سرویس systemd باشد. اشارهٔ همین موضوع در هدف اسکریپت‌نویسی ۱۰۵ هم هست و جواب عملی همان است.
