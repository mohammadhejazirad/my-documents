# شبکهٔ LPIC-1

## مقدمه

هدف ۱۰۹ آزمون ۱۰۲ شبکه را از دید میزبان کلاینت می‌خواهد: آدرس و ماسک، پورت‌های معروف، پیکربندی ماندگار، دستور `ip` و `ss`، و حل نام. مسیریابی پیشرفته، فایروال و Netplan سرور در [شبکهٔ ۲۰۱](/docs/02-lpic/lpic2-201-networking) است. مفهوم آدرس و TCP در [مبانی شبکه](/docs/11-networking/fundamentals) است و مرجع `ss` در [دستور شبکه](/docs/01-linux/commands-network). این صفحه روی چیزی می‌ایستد که اپراتور را شب بیدار می‌کند: «اسم حل نمی‌شود» در حالی که آدرس عددی باز است.

آزمایشگاه `10.10.1.0/24` است. میزبان این مثال `app-1.example.internal` با آدرس `10.10.1.10` و کارت `ens18` است. دروازهٔ فرضی `10.10.1.1` است.

## مفهوم اصلی

آدرس بدون طول پیشوند معنی کامل ندارد. `10.10.1.10/24` یعنی میزبان `.10` در شبکه‌ای که ۲۴ بیت اولش ثابت است و بقیهٔ آدرس‌های `.1` تا `.254` هم‌پخش محلی‌اند، اگر واقعاً روی یک لینک باشند. آزمون CIDR را در برابر ماسک نقطه‌دار می‌سنجد: `/24` همان `255.255.255.0` است.

آدرس‌های `10.0.0.0/8` و `172.16.0.0/12` و `192.168.0.0/16` خصوصی‌اند و روی اینترنت عمومی مسیریابی نمی‌شوند. `10.10.1.0/24` داخل همان محدوده است. دامنهٔ `example.com` و `example.internal` برای مستندند، نه برای ثبت جهانی.

TCP نشست و پورت دارد. UDP نشست ندارد. ICMP پیامی مثل `ping` است و باز بودنش اثبات نمی‌کند پورت ۸۰ باز است. پورت‌هایی که هدف ۱۰۹.۱ صریحاً نام می‌برد را باید بشناسید: ۲۰ و ۲۱ انتقال فایل، ۲۲ SSH، ۲۳ تلنت، ۲۵ نامه، ۵۳ نام، ۸۰ و ۴۴۳ وب، ۱۲۳ زمان، و بقیهٔ فهرست آزمون (۱۱۰، ۱۳۹، ۱۴۳، ۱۶۱، ۱۶۲، ۳۸۹، ۴۶۵، ۵۱۴، ۶۳۶، ۹۹۳، ۹۹۵). روی این سرورها تلنت و FTP را روشن نمی‌کنیم؛ فقط شماره را برای خواندن `ss` بلد باشید.

حل نام چند منبع دارد و ترتیبش را `/etc/nsswitch.conf` در خط `hosts` می‌گوید. روی Ubuntu 26.04 معمولاً اول فایل، بعد stub محلی systemd-resolved است.

## چرا استفاده می‌شود؟

اگر نام خراب باشد و شما nginx را بازنشانی کنید، حادثه همان‌جا می‌ماند و فقط یک تغییر بی‌ربط به تاریخچه اضافه می‌شود. ترتیب درست این است: آیا بسته به آدرس عددی می‌رسد، آیا پورت گوش می‌دهد، آیا نام به همان آدرس تبدیل می‌شود. این سه سؤال سه دستور دارند: `ping` یا `curl` به IP، `ss`، و `resolvectl` یا `getent`.

دلیل دوم ماندگاری است. `ip addr add` تا reboot بعدی دوام دارد و بعد غیب می‌شود. آزمون پیکربندی ماندگار را جدا از دستور زنده می‌خواهد.

## Architecture

```text
برنامه (curl، ssh)
    │
    ▼
nsswitch  خط hosts
    ├─ files      /etc/hosts
    └─ resolve    stub روی 127.0.0.53   Ubuntu 26.04
          │
          ▼
    systemd-resolved
          ├─ DNS سرور از Netplan یا DHCP
          └─ دامنهٔ جستجو

هسته
    جدول آدرس رابط ens18
    جدول مسیر (پیش‌فرض از راه 10.10.1.1)
    سوکت‌هایی که ss نشان می‌دهد
```

Ubuntu Server 26.04 شبکهٔ ماندگار را با Netplan به systemd-networkd می‌دهد، نه با NetworkManager. آزمون ۱۰۹.۲ روی `nmcli` تأکید دارد چون خیلی از دسکتاپ‌ها و بعضی ایمیج‌ها NetworkManager دارند. سرور این دانشنامه را با `nmcli` پیکربندی نکنید اگر `networkctl` رابط را مدیریت می‌کند؛ دو مدیر با هم آدرس را دزدیده از دست هم عوض می‌کنند. Debian 13 ممکن است هنوز ifupdown و فایل `/etc/network/interfaces` باشد. فرق عملی در [شبکهٔ ۲۰۱](/docs/02-lpic/lpic2-201-networking) است. در ۱۰۲ کافی است بدانید `ifup` و `ifdown` مال همان مدل قدیمی‌اند.

`/etc/resolv.conf` روی Ubuntu اغلب پیوند به `/run/systemd/resolve/stub-resolv.conf` است و فقط `nameserver 127.0.0.53` دارد. ویرایش مستقیم این فایل بعد از reboot یا ریستارت resolved از بین می‌رود. سرور DNS واقعی را `resolvectl status` نشان می‌دهد.

## Installation

ابزار `ip` و `ss` در بستهٔ `iproute2` از قبل نصب‌اند. `ping` گاهی جداست. ابزار پرسش DNS در بستهٔ `bind9-dnsutils` است و برای عیب‌یابی لازم می‌شود.

```bash
sudo apt update
sudo apt install iproute2 iputils-ping bind9-dnsutils
```

وضعیت حل‌کننده:

```bash
systemctl is-active systemd-resolved
ls -l /etc/resolv.conf
```

خروجی سالم Ubuntu:

```text
active
lrwxrwxrwx 1 root root ... /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
```

اگر روی Debian 13 سرویس resolved غیرفعال بود و `/etc/resolv.conf` یک فایل معمولی با `nameserver` بود، همان فایل منبع حقیقت است. آنجا `resolvectl` را به زور راه نیندازید مگر بدانید چه کسی قرار است DNS را مدیریت کند.

## Configuration

دیدن وضعیت زنده. این دستورها چیزی را ذخیره نمی‌کنند.

```bash
ip -br addr show ens18
ip route
ip route get 10.10.1.20
```

نمونه:

```text
ens18    UP    10.10.1.10/24 fe80::.../64
default via 10.10.1.1 dev ens18 proto static
10.10.1.0/24 dev ens18 proto kernel scope link src 10.10.1.10
10.10.1.20 via 10.10.1.1 dev ens18 src 10.10.1.10 uid 1000
```

اگر مقصد هم‌شبکه باشد، خط `ip route get` به‌جای via، دستگاه را مستقیم نشان می‌دهد. مسیر پیش‌فرض فقط وقتی استفاده می‌شود که مقصد در جدول مسیر طولانی‌تری جور نشود.

افزودن موقت یک مسیر برای شبکهٔ دیگر، تا قبل از reboot، برای آزمون لازم است. روی تولید بعد از آزمون مسیر را پاک کنید یا در Netplan ماندگارش کنید.

```bash
sudo ip route add 10.20.0.0/16 via 10.10.1.5 dev ens18
ip route show 10.20.0.0/16
sudo ip route del 10.20.0.0/16
```

`10.10.1.5` پروکسی آزمایشگاه است. فقط اگر آن میزبان واقعاً مسیر `10.20.0.0/16` را می‌داند این مسیر را ماندگار کنید. مسیر سیاه‌چاله ترافیک را بی‌صدا دور می‌ریزد.

فایل میزبان برای نام‌هایی که نباید به DNS تکیه کنند، مثل خود `app-1` هنگام خراب بودن نام:

```text
127.0.0.1 localhost
10.10.1.10 app-1.example.internal app-1
```

نام میزبان کوتاه و نام کامل هر دو بیایند. اگر این خط نباشد، بعضی سرویس‌ها موقع بالا آمدن نام خودشان را حل نمی‌کنند و دیر استارت می‌شوند.

ترتیب حل نام را بخوانید، حفظ نکنید:

```bash
awk '/^hosts:/{print}' /etc/nsswitch.conf
resolvectl status ens18
```

خط `hosts` شبیه `files resolve [!UNAVAIL=return] dns` است. یعنی اول `/etc/hosts`، بعد resolved. اگر resolved بالا باشد، رسیدن به DNS فایل `resolv.conf` طول می‌کشد. برای یک پرسش مستقیم از سرور مشخص، `dig` را با `@` بزنید تا این زنجیره را دور بزنید.

```bash
dig +short @10.10.1.5 app-1.example.internal A
getent hosts app-1.example.internal
```

`getent` از همان مسیر nsswitch می‌رود و برای آزمون بهتر از `ping` است، چون به ICMP وابسته نیست.

گوش دادن پورت. `ss` جایگزین `netstat` است. آزمون هنوز `netstat` را نام می‌برد؛ روی این سیستم اگر نبود نصبش نکنید، `ss` را بلد باشید.

```bash
ss -lntup
ss -lnt 'sport = :22'
```

`-l` گوش‌دهنده، `-n` عدد به‌جای اسم، `-t` مربوط TCP، `-u` مربوط UDP، `-p` فرایند. دیدن فرایند به امتیاز root نیاز دارد وگرنه نام برنامه خالی می‌ماند.

## Production Example

کاربر می‌گوید `app.example.com` باز نمی‌شود. از روی `app-1` و از ایستگاه مدیر این جداسازی را انجام دهید.

اول عدد، بدون نام:

```bash
ping -c 2 -W 1 10.10.1.10
curl -sv --max-time 5 http://10.10.1.10/ -o /dev/null
```

اگر ping جواب داد و curl گفت connection refused، شبکه و میزبان زنده‌اند و سرویسی روی ۸۰ نیست. بروید سراغ [وب](/docs/02-lpic/lpic2-202-web) نه DNS.

اگر نام از ایستگاه مدیر حل نمی‌شود ولی از خود سرور با IP باز است:

```bash
getent hosts app.example.com
resolvectl query app.example.com
dig +time=2 +tries=1 app.example.com A
```

`resolvectl query` کد خطا و سروری که جواب داده را نشان می‌دهد. خروجی خراب معمول:

```text
app.example.com: resolve call failed: No appropriate name servers or networks for name found
```

یا `SERVFAIL`، یا یک آدرس قدیمی که دیگر مال این سرور نیست. اگر `/etc/hosts` همان نام را به IP غلط داده باشد، `getent` همان غلط را برمی‌گرداند و `dig @8.8.8.8` چیز دیگری. آن وقت فایل میزبان را اصلاح کنید، نه سرور DNS جهان را.

اگر فقط نام‌های `example.internal` خراب‌اند و نام‌های عمومی سالم‌اند، مشکل زون داخلی است و محلش [DNS](/docs/02-lpic/lpic2-202-dns) است. اگر هیچ نامی حل نمی‌شود، `resolvectl status` را ببینید: لینک بالادست down است یا هیچ DNS سروری از DHCP نیامده. آدرس موقت برای برگرداندن ارتباط، فقط روی میزبان Debian بدون resolved، گذاشتن یک `nameserver` در `resolv.conf` است. روی Ubuntu خط را داخل Netplan در بخش nameservers بگذارید و `sudo netplan try` بزنید. مثال YAML در صفحهٔ ۲۰۱ است.

پورت ۲۲ باید قبل از دست‌کاری فایروال باز بماند:

```bash
ss -lnt 'sport = :22'
```

اگر خالی بود، `systemctl status ssh` . واحد سرویس روی این توزیع `ssh` است نه `sshd`.

## Security Notes

`ping` از کار افتاده به‌معنی قطع بودن لینک نیست. بعضی فایروال‌ها ICMP را می‌بندند و TCP روی ۲۲ سالم است. تصمیم را با `ss` و `curl` بگیرید.

تلنت (۲۳) و FTP ساده را برای «تست شبکه» نصب نکنید. آزمون شمارهٔ پورت را می‌خواهد، نه سرویس روشن. انتقال فایل این تیم با SSH است، در [آرشیو و انتقال](/docs/01-linux/commands-archive-transfer).

`/etc/hosts` را با ده‌ها نام تولید پر نکنید. یک رکورد کهنه آنجا از DNS درست جلو می‌زند چون `files` اول است. فقط نام خود میزبان و استثناهای عملیاتی کوتاه.

در `dig` اگر از سرور DNS عمومی استفاده می‌کنید، نام داخلی `example.internal` را آنجا نپرسید و انتظار جواب درست نداشته باشید. آن نام نباید به اینترنت نشت کند. پرسش عمومی را برای یک نام عمومی بزنید.

## Troubleshooting

علامت: `Temporary failure in name resolution`.

زنجیره را از پایین بشمارید.

```bash
ip -br link show ens18
ip route show default
resolvectl status
awk '/^hosts:/{print}' /etc/nsswitch.conf
getent hosts app-1.example.internal
```

اگر رابط `DOWN` است، DNS مقصر نیست. اگر مسیر پیش‌فرض نیست، فقط آدرس هم‌شبکه قابل دسترسی است. اگر resolved فعال است و `DNS Servers` خالی است، Netplan یا DHCP سرور نام نداده. اگر `getent` برای نام خود میزبان جواب دارد ولی نام عمومی ندارد، فایل hosts سالم است و بالادست DNS خراب است.

علامت: `ping` به نام جواب می‌دهد و برنامه هنوز خطای نام می‌دهد. ممکن است برنامه آدرس v6 را اول بگیرد و مسیر v6 نداشته باشید. `getent ahosts نام` هر دو خانواده را نشان می‌دهد. تا وقتی v6 واقعی ندارید، رکورد AAAA شکسته در DNS بدتر از نبودنش است. رکوردها در [رکوردهای DNS](/docs/11-networking/dns-records) توضیح داده شده‌اند.

علامت: بعد از reboot آدرس دستی `ip addr add` نیست. این خرابی دستور نیست؛ ماندگار نبوده. محل ماندگار Ubuntu فایل `/etc/netplan` است.

ابزار قدیمی `ifconfig` و `route` و `netstat` اگر نصب نباشند، معادل‌شان `ip addr` و `ip route` و `ss` است. برای آزمون اسم قدیمی را بشناسید و روی سرور بستهٔ `net-tools` را فقط به‌خاطر عادت نصب نکنید.

## Best Practices

- اول IP، بعد پورت، بعد نام. ترتیب را در تیکت همان‌طور بنویسید.
- `ss -lntup` را با امتیاز کافی بگیرید وگرنه فکر می‌کنید هیچ فرایندی به پورت وصل نیست.
- روی Ubuntu 26.04 سرور نام را در stub حل‌کننده ببینید، نه با ویرایش `/etc/resolv.conf`.
- NetworkManager و networkd را همزمان مدیر یک رابط نکنید. سرور این آزمایشگاه networkd از راه Netplan است.
- مسیر موقتی که برای آزمون اضافه کردید را همان جلسه حذف کنید.

## تمرین

سناریو: از روی `app-1` نام `db-1.example.internal` حل نمی‌شود، ولی شما حدس می‌زنید دیتابیس روی `10.10.1.20` زنده است. شبکه را دست‌کاری دائمی نکنید.

```bash
ip -br addr
ip route show default
getent hosts db-1.example.internal || echo 'getent-failed'
getent hosts 10.10.1.20
ping -c 2 -W 1 10.10.1.20
ss -lnt 'sport = :22'
resolvectl query db-1.example.internal || true
```

سؤال‌ها:

1. اگر ping به `10.10.1.20` موفق باشد و `getent` شکست بخورد، مشکل در مسیر پیش‌فرض است یا در حل نام؟
2. چرا نوشتن `nameserver` داخل `/etc/resolv.conf` روی Ubuntu 26.04 فردا صبح ممکن است رفته باشد؟
3. پورت ۵۳ و ۲۲ هر کدام مال کدام سرویس‌اند؟

## پاسخ تمرین

اگر میزبان `db-1` روشن و روی همین شبکه باشد، ping دو جواب می‌گیرد و `ss` روی خود `app-1` خط `:22` را نشان می‌دهد. `getent hosts 10.10.1.20` ممکن است فقط همان عدد را برگرداند اگر نام معکوس نداشته باشید؛ این خرابی جداگانه‌ای نیست. `resolvectl query` یا نام را به `10.10.1.20` ترجمه می‌کند یا خطا می‌دهد. اگر خطا داد و ping موفق بود، برای کار فوری همان عدد را استفاده کنید و رکورد را بعداً در DNS یا، برای یک استثنای کوتاه، در `/etc/hosts` درست کنید.

1. حل نام. رسیدن به IP یعنی مسیر تا آن میزبان هست. شکست `getent` یعنی nsswitch، فایل hosts، یا DNS.
2. چون آن فایل پیوند به stub تولیدشدهٔ systemd-resolved است و سرویس آن را از نو می‌نویسد. سرور نام ماندگار را باید از راه Netplan یا پیکربندی resolved داد.
3. پورت ۵۳ مال DNS است، هم UDP برای پرسش معمولی و هم TCP برای انتقال زون و جواب بزرگ. پورت ۲۲ مال SSH است. روشن کردن سرویس نام روی هر میزبان لازم نیست؛ کلاینت فقط باید بداند سرور نام کجاست.
