# شبکهٔ پیشرفته

## مقدمه

هدف ۲۰۵ آزمون ۲۰۱ پیکربندی شبکهٔ سرور، ابزار پیشرفته، و عیب‌یابی مسیر است. پایهٔ آدرس و حل نام در [شبکهٔ ۱۰۲](/docs/02-lpic/lpic1-102-networking) مانده است. فایروال روزمرهٔ این تیم UFW است و دستورهای عملیاتی‌اش را [UFW](/docs/10-security/ufw) نگه می‌دارد. اینجا باید هر دو لایه را درست ببینید: UFW چه می‌نویسد، و `nft list ruleset` چه چیزی واقعاً داخل هسته است، و این با `iptables-nft` چه فرقی دارد.

Ubuntu 26.04 پیش‌فرضش nftables در هسته است و UFW جلوی آن است. UFW خودش موتور جدا نیست. Debian 13 هم هستهٔ nftables دارد، ولی مدیر ماندگارش ممکن است ifupdown باشد نه Netplan.

## مفهوم اصلی

مسیر (route) تصمیم هسته است که بستهٔ بعد را به کدام همسایه بدهد. مسیر متصل از آدرس خود رابط ساخته می‌شود. مسیر پیش‌فرض آخرین انتخاب است. مسیر مشخص‌تر برنده است، نه مسیر بالاتر در فایل. `ip route` جدول زنده است. تا وقتی در Netplan یا interfaces نباشد، reboot پاکش می‌کند.

فایروال لینوکس سال‌ها با دستور `iptables` و جدول filter و nat دیده می‌شد. هستهٔ فعلی آن جدول‌ها را با nftables پیاده کرده است. بستهٔ `iptables` روی Ubuntu یک رابط سازگاری به نام iptables-nft است: همان دستور قدیمی، ترجمه به قوانین nft. `iptables-legacy` موتور قدیمی است. قاطی کردن legacy با nft روی یک میزبان، دو نسخه از حقیقت می‌سازد که هیچ‌کدام کامل نیستند.

UFW قانون ساده را می‌گیرد و به همین پشت‌صحنه می‌نویسد. برای عملیات روزمره همان کافی است. وقتی قانون «هست» ولی اثر ندارد، باید ruleset واقعی را دید، نه فقط `ufw status`.

پیوند (bond) چند کارت را یک رابط منطقی می‌کند تا قطع یک کابل لینک را نبرد. پل (bridge) چند رابط را در یک دامنهٔ لایهٔ ۲ می‌گذارد، شبیه سوئیچ. سرور برنامهٔ این آزمایشگاه به bond نیاز اجباری ندارد؛ شناخت و یک فایل Netplan برای وقتی است که میزبان دو کارت دارد یا باید به ماشین مجازی لینک بدهد.

## چرا استفاده می‌شود؟

یک `ip route add` نیمه‌شب سرویس را برمی‌گرداند و صبح بعد از reboot دوباره می‌خوابد. هدف ۲۰۵ دقیقاً فرق این دو را می‌خواهد. اپراتور تولید باید بداند ماندگاری روی Ubuntu فایل YAML زیر `/etc/netplan` است.

دلیل دوم فایروال این است که آزمون هنوز `iptables -L` نشان می‌دهد. اگر آن دستور را بزنید و فکر کنید جدول خالی یعنی حفاظتی نیست، اشتباه می‌کنید: UFW ممکن است قانون را در nft گذاشته باشد و خروجی iptables-nft هم همان را نشان دهد، یا برعکس شما در حال دیدن کش command اشتباه باشید. یک دستور مرجع لازم است. آن دستور `nft list ruleset` است.

## Architecture

```text
Ubuntu Server 26.04
  /etc/netplan/*.yaml
        │  netplan generate
        ▼
  systemd-networkd          آدرس، مسیر، bond، bridge
        │
        ▼
  هسته: جدول مسیر، رابط ens18 یا bond0

فایروال
  ufw  (روزمره، صفحهٔ امنیت)
    └─► iptables-nft  (سازگاری دستور قدیمی)
          └─► nftables در هسته
                nft list ruleset   حقیقت قابل خواندن

Debian 13 ممکن است به‌جای Netplan
  /etc/network/interfaces    ifupdown
```

فایل‌های Netplan به ترتیب نام خوانده می‌شوند. `00-` زودتر از `50-` است. کلید تکراری را فایل دیرتر برنده می‌شود، پس دو فایل برای یک کارت ننویسید.

`renderer: networkd` برای سرور درست است. `NetworkManager` مال دسکتاپ است. آزمون `nmcli` را بلد می‌خواهد؛ روی این میزبان اگر `nmcli` گفت دستگاه unmanaged است، طبیعی است.

## Installation

ابزار مسیر از قبل هست. nft و UFW را صریح نصب کنید اگر ایمیج حداقلی است. UFW را در این صفحه فعال نکنید تا وقتی قانون SSH را در صفحهٔ UFW دیده‌اید. فعال کردن با سیاست پیش‌فرض ممکن است نشست را ببرد.

```bash
sudo apt update
sudo apt install nftables
sudo apt install ufw
iptables -V
command -v netplan
```

خروجی مورد انتظار روی Ubuntu 26.04 شبیه این است:

```text
iptables v1.8.11 (nf_tables)
/usr/sbin/netplan
```

کلمهٔ `nf_tables` یعنی iptables-nft. اگر پرانتز گفت `legacy`، این میزبان از حالتی که این فصل فرض کرده فاصله دارد و نباید هر دو ابزار را همزمان قانون تازه بدهید.

روی Debian بدون Netplan، `command -v netplan` خالی است و `ls /etc/network/interfaces` فایل را نشان می‌دهد. همان را منبع حقیقت بگیرید.

## Configuration

جدول مسیر و یک پرسش مشخص:

```bash
ip route
ip route get 10.10.1.20
ip rule show
```

`ip rule` سیاست چندجدوله را نشان می‌دهد. روی سرور معمولی فقط قانون‌های پیش‌فرض local و main است. اگر کسی جدول دوم ساخته باشد و شما فقط `ip route` را ببینید، مسیر «غایب» را اشتباه تشخیص می‌دهید.

دیدن فایروال بدون تغییر. هر دو لایه:

```bash
sudo ufw status verbose
sudo nft list ruleset
sudo iptables -S
```

اگر UFW خاموش باشد، `nft list ruleset` ممکن است خالی یا فقط زنجیره‌های Docker و سیستم باشد. خالی بودن به‌معنی «امن» نیست؛ یعنی قانون drop ندارید. تفاوت دستورها این است که `iptables -S` شکل سازگاری جدول filter نسخهٔ ۴ را نشان می‌دهد و قانون inet یا ipv6 را ممکن است نصفه نشان دهد. `nft list ruleset` خانوادهٔ `inet` را یکجا نشان می‌دهد، همان چیزی که هم v4 و هم v6 را پوشش می‌دهد.

یک ruleset آموزشی که آزمون می‌فهمد، فقط برای خواندن شکل دستور. آن را روی میزبانی که UFW یا Docker مدیریتش می‌کند بار نکنید. مالک قانون باید یکی باشد.

```text
table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;
        iif "lo" accept
        ct state established,related accept
        ip saddr 10.10.1.0/24 tcp dport 22 accept
    }
}
```

این متن را `nft -f` ندهید مگر UFW را قبلاً خاموش کرده باشید و کنسول داشته باشید و بدانید سیاست drop پورت‌های دیگر را هم می‌بندد. عملیات روزمره به‌جای این فایل: `sudo ufw allow OpenSSH` و بقیه در صفحهٔ UFW. بعد از تغییر UFW، دوباره `nft list ruleset` بگیرید تا ببینید UFW همان قصد را به زنجیرهٔ خودش ترجمه کرده است.

نمونهٔ Netplan برای دو کارت در حالت active-backup. فقط وقتی هر دو نام در `ip -br link` هستند اعمال کنید. آدرس `10.10.1.10/24` مال `app-1` است. اگر این فایل را روی میزبانی بگذارید که همان آدرس را جای دیگری دارد، تعارض آدرس می‌سازید.

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens18:
      dhcp4: false
    ens19:
      dhcp4: false
  bonds:
    bond0:
      interfaces:
        - ens18
        - ens19
      addresses:
        - 10.10.1.10/24
      routes:
        - to: default
          via: 10.10.1.1
      nameservers:
        addresses:
          - 10.10.1.5
      parameters:
        mode: active-backup
        mii-monitor-interval: 100
```

نام فایل پیشنهادی `/etc/netplan/50-bond.yaml` است. اعمال امن:

```bash
sudo netplan generate
sudo netplan try
```

`netplan try` شمارش معکوس دارد. اگر SSH قطع شد صبر کنید تا برگردد. اگر ماند، Enter را بزنید تا تأیید شود. `netplan apply` بدون try، برگشت خودکار ندارد.

شناخت bridge، بدون این که آزمایشگاه را به هایپروایزر تبدیل کنیم. یک رابط روی پل:

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens19:
      dhcp4: false
  bridges:
    br0:
      interfaces:
        - ens19
      addresses:
        - 10.10.1.10/24
      routes:
        - to: default
          via: 10.10.1.1
      parameters:
        stp: true
        forward-delay: 4
```

bond و bridge را همزمان روی همان کارت، هر کدام در یک فایل، فعال نکنید. یکی را انتخاب کنید. STP روی پل جلوی حلقه را می‌گیرد و چند ثانیه یادگیری دارد؛ اگر فوروارده‌دلی را صفر کنید ممکن است حلقه بسازید.

معادل ذهنی ifupdown روی Debian، برای یک آدرس ساده نه برای کپی کور:

```text
auto ens18
iface ens18 inet static
    address 10.10.1.10/24
    gateway 10.10.1.1
    dns-nameservers 10.10.1.5
```

بستهٔ لازم `ifupdown` است و اعمالش `sudo ifreload -a` یا `ifdown` و `ifup` روی همان رابط است. ifdown روی رابط SSH همان نشست را می‌برد. Netplan را روی Debian نصب نکنید فقط چون این صفحه YAML دارد، مگر استاندارد تیم یکی باشد.

جلورانی IP فقط اگر این میزبان واقعاً راهیاب است. روی `app-1` باید خاموش بماند. روش sysctl در [کرنل](/docs/02-lpic/lpic2-201-kernel) است.

## Production Example

تیم شبکه می‌گوید زیرشبکهٔ پشتیبان `10.10.2.0/24` از راه `10.10.1.5` در دسترس است و `app-1` باید برای بکاپ شبانه آنجا را ببیند. اول زنده امتحان کنید:

```bash
sudo ip route add 10.10.2.0/24 via 10.10.1.5 dev ens18
ip route get 10.10.2.1
ping -c 2 -W 1 10.10.2.1
```

اگر ping شکست، مسیر را همان لحظه حذف کنید و به سراغ دروازه بروید. اگر کار کرد، ماندگارش کنید. روی Ubuntu یک فایل جدا بهتر از چسباندن ته فایلی است که installer ساخته.

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens18:
      routes:
        - to: 10.10.2.0/24
          via: 10.10.1.5
```

این تکه فقط مسیر اضافه می‌کند اگر فایل دیگری آدرس همان کارت را داده باشد. Netplan فایل‌ها را ادغام می‌کند، ولی ادغام اشتباه دو `addresses` دردسر است. بعد از `netplan try`، مسیر دستی را پاک کنید تا دو منبع نداشته باشید: `sudo ip route del 10.10.2.0/24`. سپس `ip route` باید هنوز مسیر را از networkd نشان دهد.

اگر فردا `traceroute 10.10.2.1` از رابط اشتباه خارج شد، `ip route get` را باور کنید نه حدس را. `tracepath` بدون امتیاز خام هم برای آزمون قابل قبول است.

## Security Notes

`policy drop` بدون استثنای پورت ۲۲، مدیریت را قطع می‌کند. هر تمرین nft یا UFW با کنسول خارج از SSH شروع می‌شود. قانون SSH باید محدود به `10.10.1.0/24` باشد اگر همهٔ مدیران در همین آزمایشگاه‌اند. باز کردن ۲۲ روی `0.0.0.0/0` برای راحتی تمرین، سرور را به پویش اینترنت می‌سپارد اگر کارت عمومی هم داشته باشد. این میزبان‌ها عمومی نیستند؛ باز هم عادت را خراب نکنید.

قانون accept گستردهٔ `ct state new` بدون پورت، فایروال را نمایشی می‌کند. UFW را با `ufw status` خالی رها نکنید و خیال نکنید nft خالی همان سیاست است.

bond حالت balance یا LACP با سوئیچی که همراهی نمی‌کند، لینک را نصفه می‌کند و گاهی حلقه می‌سازد. active-backup کم‌دردسرترین حالت برای دو کابل مستقل است. با تیم شبکه قبل از `netplan try` حرف بزنید.

Docker اگر نصب شود قانون nft خودش را می‌نویسد و UFW را دور می‌زند. آن تعارض مال [امنیت ۲۰۲](/docs/02-lpic/lpic2-202-security) و فصل Docker است. اینجا فقط اگر `nft list ruleset` زنجیرهٔ docker دید، قبل از قانون دستی جدید با صاحب میزبان هماهنگ کنید.

## Troubleshooting

علامت: `netplan try` می‌گوید خطا در YAML. اغلب تورفتگی یا یک تب به‌جای فاصله است. `sudo netplan generate` خط را دقیق‌تر می‌گوید. فایل را با ویرایشگر ذخیره کنید نه با کپی از چت که فاصله‌ها را خراب کند.

علامت: آدرس روی `ens18` نیست و bond هم بالا نیست. نام کارت در YAML با `ip -br link` یکی نیست. Netplan دستگاه ناشناس را نادیده می‌گیرد و ممکن است DHCP قبلی را هم حذف کرده باشد. از کنسول نام واقعی را بگذارید.

علامت: `iptables -L` خالی است و هنوز پورت بسته است. `sudo nft list ruleset` و `sudo ufw status` را هر دو بگیرید. ممکن است سیاست در جدول inet باشد یا ufw شمارهٔ v6 را جدا بسته باشد. `ss -lnt` نشان می‌دهد کسی گوش می‌دهد یا نه؛ فایروال گوش دادن را حذف نمی‌کند، بسته را قبل از برنامه دور می‌ریزد. پس ss باز و curl از بیرون بسته، یعنی فیلتر.

علامت: مسیر هست و `ping` به دروازه خودش جواب نمی‌دهد. مشکل لایهٔ ۲ یا ARP است. `ip neigh show` را ببینید. اگر FAILED ماند، کابل، VLAN، یا آدرس تکراری محتمل‌تر از جدول مسیر است.

ابزار آزمون `tcpdump` برای دیدن این که بسته اصلاً خارج می‌شود:

```bash
sudo tcpdump -ni ens18 host 10.10.1.20 and icmp
```

در یک نشست دیگر ping کنید. اگر بسته خارج شد و جواب نیامد، مقصر سمت مقابل یا فیلتر مسیر است. `tcpdump` را بی‌فیلتر روی تولید رها نکنید؛ حجم و دادهٔ نشست را می‌گیرد.

## Best Practices

- تغییر زنده با `ip`، ماندگاری با Netplan روی Ubuntu و با interfaces روی Debian اگر Netplan نیست.
- یک مالک برای فایروال: UFW برای این تیم. `nft list ruleset` برای دیدن، نه برای یک فایل موازی که همان chain را دوباره تعریف کند.
- `iptables -V` را در حادثه نگاه کنید. legacy و nft را مخلوط نکنید.
- `netplan try` قبل از `apply`.
- bond و bridge را بشناسید و فقط با کارت واقعاً موجود و با هماهنگی سوئیچ اعمال کنید.
- جلورانی را روی سرور برنامه روشن نکنید.

## تمرین

سناریو: بعد از reboot، `app-1` آدرس `10.10.1.10/24` را دارد ولی دیگر به `10.10.1.20` نمی‌رسد. پینگ به `10.10.1.1` جواب می‌دهد. کسی دیروز یک مسیر دستی اضافه کرده بود.

```bash
ip -br addr show ens18
ip route
ip route get 10.10.1.20
sudo ufw status
sudo nft list ruleset | head -n 20
```

سؤال‌ها:

1. چرا مسیر دیروز غیب شده؟
2. `iptables` با پسوند `nf_tables` با `nft list ruleset` چه نسبتی دارد؟
3. فرق bond با bridge را در یک جمله بگویید.

## پاسخ تمرین

اگر هر دو میزبان روی `10.10.1.0/24` باشند و دروازه جواب بدهد، `ip route get 10.10.1.20` باید خروجی دستگاه `ens18` و مبدأ `10.10.1.10` بدهد، بدون نیاز به مسیر دستی. نرسیدن در این حالت بیشتر فیلتر یا ARP یا خاموش بودن مقصد است، نه نبود مسیر پیش‌فرض. اگر مقصد تمرین شما عمداً پشت `10.10.1.5` در شبکهٔ دیگری است، `ip route get` هنوز از پیش‌فرض می‌رود و دیروز کسی مسیر مشخص‌تر گذاشته بوده که با reboot رفته است.

برگشت موقت، فقط برای اثبات: `sudo ip route add 10.10.2.0/24 via 10.10.1.5` و بعد از اثبات، ماندگار کردن در Netplan و حذف مسیر دستی. اگر همان شبکهٔ `/24` محلی است، مسیر اضافه نکنید.

1. `ip route add` در جدول زنده است و در Netplan نوشته نشده بود. reboot جدول را از نو از کانفیگ ماندگار می‌سازد.
2. `iptables` در حالت nf_tables مترجم دستور قدیمی به nftables است. `nft list ruleset` خود قوانین هسته را نشان می‌دهد، شامل چیزی که از همان ترجمه یا از UFW آمده. اگر نسخه legacy باشد، این دو دیگر یک منبع نیستند.
3. bond چند کارت را یک لینک برای همان میزبان می‌کند؛ bridge چند رابط را در یک بخش لایهٔ ۲ به هم وصل می‌کند تا میزبان‌های آن طرف، همسایهٔ هم دیده شوند.
