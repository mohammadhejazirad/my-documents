# معماری لینوکس

## مقدمه

هدف ۱۰۱ آزمون LPIC-1 از سخت‌افزار و بوت شروع می‌شود و به بسته و فایل‌سیستم می‌رسد. این صفحه بخش معماری را برای اپراتور سرور می‌نویسد: هسته (kernel) چه چیزی را از فضای کاربر (user space) جدا می‌کند، استاندارد سلسله‌مراتب فایل‌سیستم (FHS) روی دیسک Ubuntu 26.04 واقعاً چه شکلی است، و بسته (package) چطور یک فایل را به یک سرویس وصل می‌کند. بوت در [صفحهٔ بوت](/docs/02-lpic/lpic1-101-boot) است. دستور روزمرهٔ `apt` در [مدیریت بسته](/docs/01-linux/apt-package-management) است و اینجا تکرار نمی‌شود.

این صفحه man page هسته نیست. اگر به پارامتر یک ماژول نیاز دارید، `modprobe` و `modinfo` را همین‌جا در حد ۱۰۱ می‌بینید و عمق ۲۰۱ در [کرنل](/docs/02-lpic/lpic2-201-kernel) است.

## مفهوم اصلی

هسته تنها برنامه‌ای است که با سخت‌افزار حرف می‌زند و بقیه را زمان‌بندی می‌کند. هر چیز دیگر، از پوسته تا `nginx`، یک فرایند در فضای کاربر است و فقط از راه فراخوان سیستمی (system call) وارد هسته می‌شود. اگر فرایند کاربر segfault بدهد، هسته همان فرایند را می‌کشد. اگر درایور داخل هسته oops کند، ممکن است کل ماشین قفل شود. به همین دلیل درایور آزمایشی را داخل هستهٔ تولید بار نمی‌کنیم.

دستگاه‌ها برای فضای کاربر فایل به نظر می‌رسند. این سه مسیر را آزمون و شیفت هر دو می‌پرسند:

| مسیر | چیست | نمونهٔ کار |
| --- | --- | --- |
| `/dev` | گره‌ای که udev برای دستگاه ساخته | `/dev/vda`، `/dev/null` |
| `/proc` | پنجرهٔ هسته به فرایند و وضعیت، روی دیسک نیست | `/proc/cpuinfo`، `/proc/meminfo` |
| `/sys` | مدل دستگاه در sysfs، مناسب خواندن و بعضی تنظیم‌های سخت‌افزار | `/sys/class/net` |

udev وقتی هسته دستگاه را دید گرهٔ `/dev` را می‌سازد. dbus روی سرور بدون میزکار نقش کوچکی دارد؛ آزمون اسمش را در کنار sysfs می‌آورد، ولی عیب‌یابی دیسک از `/sys` و `dmesg` شروع می‌شود نه از یک گذرگاه دسکتاپ.

توزیع (distribution) یعنی هسته به‌علاوهٔ فضای کاربر بسته‌بندی‌شده و یک مدیر سرویس. Ubuntu 26.04 و Debian 13 هر دو deb هستند، هر دو systemd را به‌عنوان PID 1 دارند، و هر دو ادغام `/usr` را تمام کرده‌اند: `/bin` پیوند به `/usr/bin` است. آزمون هنوز معنی تاریخی `/bin` را می‌پرسد. روی دیسک باید هر دو را بلد باشید.

## چرا استفاده می‌شود؟

بدون این مدل، اپراتور فایل لاگ را با درایور اشتباه می‌گیرد و بسته‌ای را حذف می‌کند که سه سرویس به کتابخانه‌اش وابسته‌اند. وزن هدف ۱۰۲.۳ (کتابخانهٔ مشترک) کم است، ولی یک `LD_LIBRARY_PATH` اشتباه در واحد systemd دقیقاً همان شکلی از خرابی را می‌سازد که نیمه‌شب شبیه «باگ برنامه» دیده می‌شود.

شناخت ماشین مجازی (virtual machine) هم مال همین هدف است، بند ۱۰۲.۶. کلون کردن یک ایمیج بدون عوض کردن هویت ماشین، دو میزبان با یک کلید میزبان SSH می‌سازد. آن وقت هشدار شناسایی میزبان یا اعتماد به میزبان اشتباه هر دو ممکن است.

## Architecture

```text
فضای کاربر
  ops ── bash ── apt, sshd, nginx, systemd (PID 1)
        │
        │  system call
        ▼
هسته
  زمان‌بند، حافظه، فایل‌سیستم، پشتهٔ شبکه، ماژول
        │
        ▼
سخت‌افزار یا دستگاه مجازی هایپروایزر
  دیسک، کارت ens18، CPU

فایل‌های رابط
  /proc   وضعیت هسته و فرایند
  /sys    دستگاه
  /dev    گرهٔ دستگاه، ساختهٔ udev
  /run    سوکت و PID زمان اجرا، tmpfs
```

چیدمان دیسک که آزمون انتظار دارد، با واقعیت usrmerge:

| مسیر آزمون | نقش تاریخی | روی Ubuntu 26.04 و Debian 13 |
| --- | --- | --- |
| `/bin` و `/sbin` | دستور ضروری بوت | پیوند به `/usr/bin` و `/usr/sbin` |
| `/lib` | کتابخانه و ماژول | پیوند به `/usr/lib` |
| `/usr` | برنامه‌های نصب‌شده | محل واقعی دودویی و کتابخانه |
| `/etc` | کانفیگ میزبان | متن و واحدهای drop-in، نه دودویی |
| `/var` | دادهٔ متغیر | لاگ، کش apt، ایمیل صف |
| `/home` | خانهٔ کاربر انسانی | خانهٔ `ops` |
| `/tmp` | موقت، اغلب tmpfs | چسبنده (sticky) برای همه |
| `/opt` | نرم‌افزار خارج از بسته | ریشهٔ برنامهٔ این دانشنامه `/opt/apps` |
| `/boot` | هسته و initramfs و GRUB | جدا از ESP |
| `/proc` و `/sys` و `/dev` و `/run` | مجازی | در fstab لازم نیست دست‌نویس شوند |

بستهٔ deb فایل‌ها را کپی می‌کند، اسکریپت نگهدارنده را اجرا می‌کند و پایگاه `/var/lib/dpkg` را به‌روز می‌کند. `apt` وابستگی و مخزن را مدیریت می‌کند. مخزن Ubuntu 26.04 به شکل deb822 در `/etc/apt/sources.list.d/ubuntu.sources` است. فرم تک‌خطی `sources.list` هنوز کار می‌کند. جزئیات آینه در [مخزن و آینه](/docs/01-linux/apt-repository-mirror) است.

روی توزیع RPM آزمون این معادل‌ها را می‌خواهد. آزمایشگاه ما آن دستورها را اجرا نمی‌کند.

| کار | Debian و Ubuntu | RPM |
| --- | --- | --- |
| نصب فایل محلی | `dpkg -i` | `rpm -i` |
| نصب از مخزن | `apt install` | `dnf install` یا `zypper install` |
| صاحب یک فایل | `dpkg -S` | `rpm -qf` |
| محتوای بسته | `dpkg -L` | `rpm -ql` |

## Installation

بسته‌ای برای «معماری» نصب نمی‌شود. ابزار دیدن سخت‌افزار روی سرور حداقلی گاهی جداست. `pciutils` و `usbutils` را اگر دستورها پیدا نشدند نصب کنید.

```bash
sudo apt update
sudo apt install pciutils usbutils
```

واحد systemd از قبل PID 1 است. این را با شمارهٔ فرایند ثابت می‌کنید، نه با اسم توزیع.

```bash
ps -p 1 -o pid,comm,args
```

خروجی سالم:

```text
    PID COMMAND         COMMAND
      1 systemd         /usr/lib/systemd/systemd --system --deserialize=...
```

اگر `comm` چیزی غیر از `systemd` بود، این میزبان مبنای صفحات بعدی نیست. SysVinit و Upstart را آزمون به‌عنوان آگاهی تاریخی می‌خواهد؛ روی 26.04 و Debian 13 مدیر سرویس نیستند.

## Configuration

سخت‌افزار را قبل از نصب درایور ببینید. `lspci` گذرگاه PCI را نشان می‌دهد و `-nn` شناسهٔ عددی فروشنده را هم می‌گذارد تا ماژول را با حدس اسم پیدا نکنید.

```bash
lspci -nn | head
lsusb
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT
```

نمونه روی VM آزمایشگاه:

```text
00:03.0 Ethernet controller [0200]: Red Hat, Inc. Virtio network device [1af4:1000]
NAME   SIZE TYPE MOUNTPOINT
vda     40G disk
├─vda1 512M part /boot/efi
└─vda2  39G part /
```

کارت `ens18` در `/sys/class/net/ens18` است. آدرس سخت‌افزاری:

```bash
cat /sys/class/net/ens18/address
```

اگر `ens18` نبود، نام را از `ip -br link` بردارید. پیش‌بینی نام (predictable name) به اسلات مجازی وابسته است و بین هایپروایزرها فرق می‌کند.

کتابخانهٔ مشترک را با `ldd` ببینید و با `ldconfig` به کش لینکر اضافه کنید. کش از `/etc/ld.so.conf` و تکه‌های `/etc/ld.so.conf.d` ساخته می‌شود.

```bash
ldd /usr/bin/ssh
ldconfig -p | awk '/libcrypto/{print; exit}'
```

`ldd` ممکن است وابستگی «not found» نشان دهد. آن را با نصب بسته‌ای که فایل را دارد حل کنید (`apt-file` یا `dpkg -S` بعد از نصب)، نه با کپی دستی یک `.so` از اینترنت. اگر خودتان کتابخانه‌ای را در `/usr/local/lib` گذاشتید، یک فایل `.conf` در `ld.so.conf.d` بسازید و `sudo ldconfig` بزنید. متغیر `LD_LIBRARY_PATH` فقط برای یک فرایند اشکال‌زدایی است. در واحد سرویس نگذاریدش؛ کتابخانهٔ غیرمنتظره را جلوتر از کتابخانهٔ سیستم بار می‌کند.

ماژول هسته در حد ۱۰۱: ببینید چیست و آیا بار است. سیاه‌کردن و پارامتر بوت مال [صفحهٔ کرنل](/docs/02-lpic/lpic2-201-kernel) است.

```bash
lsmod | head
modinfo -n virtio_net 2>/dev/null || true
```

## Production Example

تصویر `app-1` را برای ساخت `app-2` کلون کرده‌اید. برنامه بالا می‌آید، ولی از لپ‌تاپ `ops` هشدار می‌دهد که هویت SSH میزبان عوض شده، و دو ماشین در پایش با یک machine-id دیده می‌شوند. این همان بند ۱۰۲.۶ است.

قبل از تحویل کلون این کارها را روی ماشین جدید بکنید، نه روی ماشین منبع:

```bash
sudo truncate -s 0 /etc/machine-id
sudo rm -f /etc/ssh/ssh_host_*
sudo systemd-machine-id-setup
sudo ssh-keygen -A
sudo systemctl restart ssh
hostnamectl status
```

اگر تصویر cloud-init دارد و قرار است قالب بماند، `sudo cloud-init clean` روی قالب اجرا می‌شود و روی میزبان زندهٔ تولید، بی‌دلیل، اجرا نمی‌شود. hostname جدید باید در `/etc/hostname` و `/etc/hosts` یکی باشد. روش نام میزبان در [مدیریت ۲۰۱](/docs/02-lpic/lpic2-201-administration) و بوت‌استرپ در [سی دقیقهٔ اول](/docs/04-server-management/initial-bootstrap) است.

بعد از این کار، کلید عمومی میزبان جدید را خودتان یک‌بار با کنسول می‌خوانید و در `known_hosts` ایستگاه مدیر جایگزین می‌کنید. خروجی `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` را از روی کانال دیگری که هنوز به SSH وابسته نیست مقایسه کنید.

## Security Notes

`/proc` اطلاعات فرایندها را به هر کاربر محلی نشان می‌دهد، از جمله خط فرمان که گاهی رمز را اشتباهی داخلش گذاشته‌اند. سرویس را طوری بنویسید که رمز در `argv` نباشد. مجوز `/proc` را با chmod «امن» نکنید؛ هسته آن را دوباره می‌سازد و بعضی محدودیت‌ها مال `hidepid` در mount است که اگر ندانید مانیتورینگ را هم کور می‌کند.

`LD_LIBRARY_PATH` و `LD_PRELOAD` در محیط سرویس‌های شبکه ممنوع عملیاتی است، مگر برای یک اشکال‌زدایی موقت که همان روز برداشته شود. کتابخانهٔ جهان‌شمول را با بسته نصب کنید تا به‌روزرسانی امنیتی به آن برسد.

حذف بسته با `dpkg --remove` کانفیگ را در `/etc` جا می‌گذارد و `--purge` کانفیگ بسته‌شده را هم می‌برد. روی تولید، purge را وقتی می‌زنید که مسیر کانفیگ را دیده باشید و نسخهٔ پشتیبان داشته باشید. جزئیات فایل و مجوز در [مجوزها](/docs/01-linux/permissions) است.

## Troubleshooting

علامت: برنامه می‌گوید `error while loading shared libraries` و فایل را نام می‌برد.

```bash
ldd /opt/apps/myapp/bin/myapp
dpkg -S libssl.so.3 || true
apt-cache search libssl | head
```

اگر `ldd` یک خط `not found` دارد، بستهٔ گم‌شده را نصب کنید. اگر همهٔ کتابخانه‌ها پیدا می‌شوند و فقط سرویس systemd خطا می‌دهد، محیط واحد را ببینید؛ اغلب یک مسیر دستی در فایل واحد مانده است.

```bash
systemctl show myapp.service -p Environment -p EnvironmentFiles
```

علامت دیگر: `lspci` خالی است یا دستور نیست. اول `sudo apt install pciutils`. اگر باز هم خالی بود، احتمالاً ظرف (container) بدون دسترسی به گذرگاه PCI هستید، نه یک هستهٔ خراب. داخل کانتینر انتظار دیدن کارت میزبان را نداشته باشید.

`/proc/meminfo` را با عدد داخل مانیتورینگ مقایسه کنید. اگر `MemAvailable` کم است، معماری خراب نیست؛ ظرفیت در [پایش منبع](/docs/12-monitoring/resource-monitoring) پیگیری می‌شود.

## Best Practices

- معنی تاریخی FHS را برای آزمون بلد باشید و برای کار، `readlink -f /bin` بزنید تا پیوند usrmerge را ببینید.
- دستگاه را با نام پایدار در `/dev/disk/by-uuid` یا `/dev/disk/by-id` به کانفیگ بدهید، نه با `sdb` که بعد از افزودن دیسک جابه‌جا می‌شود.
- کتابخانه را از بسته بگیرید. `ldconfig` را فقط بعد از تغییر واقعی مسیر کتابخانه اجرا کنید.
- کلون VM را قبل از پیوستن به شبکهٔ مدیریت، از نظر machine-id و کلید میزبان SSH یکتا کنید.
- ماژول و sysctl تولیدی مال صفحهٔ کرنل و [امنیت کرنل](/docs/10-security/kernel) است. اینجا فقط ببینید چه چیزی بار شده تا تصویر درست باشد.

## تمرین

روی `app-1` این زنجیره را اجرا کنید و سه پاسخ را از روی خروجی خودتان بنویسید، نه از حفظ.

```bash
ps -p 1 -o comm=
readlink -f /bin /sbin /lib
lspci -nn | awk 'NR==1{print}'
ldd /bin/ls
cat /proc/meminfo | awk '/MemTotal|MemAvailable/'
```

سؤال‌ها:

1. PID 1 چیست و چرا مهم است که systemd باشد؟
2. چرا `/bin/ls` با `ldd` به `/usr/lib` وصل است، در حالی که آزمون می‌گوید کتابخانه‌ها در `/lib` هستند؟
3. اگر همین دیسک را کلون کنید و machine-id را دست نزنید، کدام دو هویت بین دو میزبان مشترک می‌ماند و کدام را باید جداگانه عوض کنید؟

## پاسخ تمرین

`comm` باید `systemd` باشد. `readlink` باید مسیر `/usr/bin` و `/usr/sbin` و `/usr/lib` را نشان دهد، یا معادل multiarch مثل `/usr/lib/x86_64-linux-gnu`. خط `lspci` یک کنترلر است، نه خطا. `ldd` برای `ls` باید `libc` را با مسیر پیدا کند و `not found` نداشته باشد. `MemAvailable` کمتر یا برابر `MemTotal` است.

1. PID 1 والد یتیم‌ها و مدیر بوت فضای کاربر است. اگر systemd نباشد، واحدها، journal و هدف‌های بوت این دانشنامه معنی دیگری دارند.
2. چون usrmerge انجام شده و `/lib` خودش پیوند است. آزمون محل تاریخی را می‌پرسد؛ لینکر روی این توزیع فایل را زیر `/usr/lib` پیدا می‌کند. هر دو جمله درست‌اند اگر قید توزیع را بگویید.
3. machine-id مشترک می‌ماند و باید با خالی کردن `/etc/machine-id` و `systemd-machine-id-setup` جدا شود. کلیدهای `/etc/ssh/ssh_host_*` هم مشترک می‌مانند و باید حذف و با `ssh-keygen -A` ساخته شوند. hostname را هم باید عوض کنید وگرنه در DNS و `/etc/hosts` دو ماشین یک نام دارند. این سومی را سؤال صریح نخواسته بود، ولی در تولید همراه همان کار است.
