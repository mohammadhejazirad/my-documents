# شل و Bash

## مقدمه

هدف ۱۰۵ آزمون ۱۰۲ دو بخش است: محیط پوسته هنگام ورود، و اسکریپت کوچک. اسکریپت تولیدی این دانشنامه، با قفل و لاگ و خروج غیرصفر، در [مبانی Bash](/docs/13-automation/bash-basics) و صفحه‌های بعدی همان فصل است. اینجا محیط ورود، `PATH`، نقل‌قول (quoting) و یک اسکریپت نگهداری کوتاه را طوری می‌نویسیم که هم سؤال آزمون را پوشش دهد و هم روی Ubuntu 26.04 چیزی را خراب نکند که فقط در bash تعاملی کار می‌کند.

کاربر تمرین `ops` است. اسکریپت را زیر `/usr/local/sbin` می‌گذاریم تا به بستهٔ سیستم نچسبد.

## مفهوم اصلی

پوسته برنامهٔ فضای کاربر است که خط را می‌خواند و فرایند می‌سازد. روی Ubuntu و Debian، `/bin/sh` پیوند به dash است، نه bash. dash پوستهٔ POSIX است و آرایه، `[[` و خیلی از بسط‌های bash را ندارد. `/bin/bash` پوستهٔ تعاملی پیش‌فرض کاربر انسانی است. اسکریپتی که شِبنگ `#!/bin/sh` دارد حق استفاده از ویژگی خاص bash را ندارد. اسکریپتی که `#!/bin/bash` دارد روی این سرور bash را صریح می‌خواهد و اگر روزی به ایمیج بدون bash کپی شود، همان خط اول شکست می‌خورد.

پوستهٔ ورود (login shell) همان است که با SSH یا کنسول، از نو وارد می‌شوید. پوستهٔ تعاملی غیرورود همان است که داخل نشست باز می‌کنید، یا اسکریپتی که bash آن را با `-c` تعاملی صدا نمی‌زند. فایل تنظیم این دو یکی نیست. آزمون این اسم‌ها را می‌خواهد: `/etc/profile`، `/etc/bash.bashrc`، `~/.profile`، `~/.bashrc`، و به‌ندرت `~/.bash_profile` و `~/.bash_login`.

`PATH` فهرست دایرکتوری‌هایی است که پوسته در آن‌ها به ترتیب دنبال نام فرمان می‌گردد. اولین فایل اجرایی پیدا‌شده برنده است. به همین دلیل خالی بودن امنیتی `PATH` در اسکریپت، و بودن دایرکتوری جاری داخل `PATH`، هر دو خطرناک‌اند.

## چرا استفاده می‌شود؟

سرویسی که از systemd بالا می‌آید `~/.bashrc` را نمی‌خواند. اگر متغیر را فقط آنجا export کنید، در SSH خودتان هست و در واحد سرویس نیست. این اختلاف منبع واقعی «روی سیستم من کار می‌کرد» است.

اسکریپت نگهداری کوچک، مثل هشدار پر شدن دیسک، نباید به فصل اتوماسیون موکول شود تا وقتی اپراتور فرق خروج صفر و غیرصفر را ندیده. cron و تایمر به کد خروج نگاه می‌کنند. هدف ۱۰۵.۲ همین را می‌سنجد، به‌علاوهٔ `test` و `&&` و `||`.

## Architecture

ترتیب خواندن برای ورود SSH کاربر `ops` روی Ubuntu:

```text
login shell (ssh)
  │
  ├─ /etc/profile
  │     └─ /etc/profile.d/*.sh
  ├─ ~/.bash_profile   اگر باشد، زنجیرهٔ خانگی همین‌جا می‌ایستد
  ├─ ~/.bash_login     فقط اگر قبلی نباشد
  └─ ~/.profile        پیش‌فرض Ubuntu این را دارد
        └─ اگر پوسته bash باشد، ~/.bashrc را source می‌کند
              └─ /etc/bash.bashrc

interactive non-login (bash دوباره داخل نشست)
  └─ ~/.bashrc و /etc/bash.bashrc
     /etc/profile دوباره خوانده نمی‌شود

اسکریپت با #!/bin/bash
  └─ هیچ‌کدام، مگر خودش source کند
     PATH پیش‌فرض ممکن است کوتاه باشد
```

systemd برای سرویس، محیط را از واحد می‌گیرد نه از این فایل‌ها. کانفیگ سرویس در [systemd](/docs/01-linux/systemd) است.

`/etc/skel` قالبی است که `useradd -m` در خانهٔ کاربر نو کپی می‌کند. تغییر `~/.bashrc` کاربر موجود را عوض نمی‌کند. تغییر `/etc/skel` فقط کاربر بعدی را عوض می‌کند.

## Installation

bash از قبل پوستهٔ `ops` است. بررسی:

```bash
getent passwd ops
ls -l /bin/sh /bin/bash
```

خروجی سالم شبیه این است. شمارهٔ UID ممکن است ۱۰۰۰ باشد.

```text
ops:x:1000:1000:ops:/home/ops:/bin/bash
lrwxrwxrwx 1 root root 4 ... /bin/sh -> dash
-rwxr-xr-x 1 root root ... /bin/bash
```

اگر پوستهٔ `ops` ناگهان `/usr/sbin/nologin` شده، ورود SSH تعاملی عمداً بسته است. آن را برای راحتی تمرین برنگردانید تا وقتی دلیل تغییر را در تیکت ندیده‌اید. کاربر سرویس `deploy` حق دارد nologin باشد.

بستهٔ اضافه‌ای لازم نیست. ویرایشگر را طوری بگذارید که `crontab -e` ویرایشگر ناشناخته باز نکند:

```bash
printf '\nexport EDITOR=vim\nexport VISUAL=vim\n' >> ~/.bashrc
```

اگر `vim` ندارید، `nano` بگذارید. این خط را هر بار تکرار نکنید؛ یک‌بار کافی است.

## Configuration

فایل سراسری ورود را برای یک تنظیم آزمایشگاه دست نزنید. تکهٔ قابل حذف را در `/etc/profile.d` بگذارید. این فایل برای پوستهٔ ورود همهٔ کاربران خوانده می‌شود، پس فقط چیز بی‌خطر بگذارید، مثل یک مسیر سازمانی.

```bash
sudo tee /etc/profile.d/ops-lab.sh >/dev/null <<'EOF'
if [ -d /usr/local/sbin ]; then
  case ":$PATH:" in
    *:/usr/local/sbin:*) ;;
    *) PATH="/usr/local/sbin:$PATH" ;;
  esac
  export PATH
fi
EOF
```

نشست SSH فعلی این فایل را دوباره نمی‌خواند. یا خروج و ورود کنید یا یک‌بار `. /etc/profile.d/ops-lab.sh` بزنید. نقطه همان `source` در پوستهٔ POSIX است. `source` خودش کلمهٔ bash است و در dash نیست. آزمون هر دو را نام می‌برد.

فرق نقل‌قول را در نشست ببینید، نه در متن فارسی. نقل‌قول تکی تقریباً هیچ بسطی نمی‌دهد. نقل‌قول دوتایی متغیر و جایگزینی فرمان را بسط می‌دهد و فاصله را نگه می‌دارد. بدون نقل‌قول، فاصله کلمه را می‌شکند.

```bash
labname='app-1.example.internal'
printf '%s\n' '$labname' "$labname"
```

خروجی:

```text
$labname
app-1.example.internal
```

جایگزینی فرمان با `$()` است. آزمون بک‌تیک را هم نشان می‌دهد. در اسکریپت تازه از بک‌تیک استفاده نکنید چون تودرتو ناخوانا می‌شود.

تابع و alias برای کار تکراری تعاملی‌اند. alias در اسکریپت خاموش است. تابع را در `~/.bashrc` بگذارید اگر فقط تعامل است، و در فایل جدا source کنید اگر اسکریپت هم لازم دارد.

```bash
alias ll='ls -l --time-style=long-iso'
diskuse() { df -hT "$1"; }
```

`PATH` جاری را برای دیدن سایهٔ دستور بررسی کنید. یک `ls` در خانه نباید دستور سیستم را بپوشاند.

```bash
type ll diskuse ls
printf '%s\n' "$PATH"
```

## Production Example

اسکریپت نگهداری که اگر ریشه از ۸۵ درصد رد شد در journal بنویسد و با کد ۱ خارج شود. کد غیرصفر یعنی cron یا تایمر می‌تواند شکست را ببیند. جزئیات زمان‌بندی در [cron](/docs/13-automation/cron) است. اینجا خود اسکریپت هدف ۱۰۲ است.

```bash
sudo tee /usr/local/sbin/root-disk-watch >/dev/null <<'EOF'
#!/bin/bash
set -euo pipefail
PATH="/usr/sbin:/usr/bin:/sbin:/bin"
threshold=85
used=$(df -P / | awk 'NR==2 {print $5}' | tr -d '%')
if [ "$used" -ge "$threshold" ]; then
  logger -t root-disk-watch "root filesystem at ${used} percent on $(hostname)"
  exit 1
fi
logger -t root-disk-watch "root filesystem at ${used} percent"
exit 0
EOF
sudo chown root:root /usr/local/sbin/root-disk-watch
sudo chmod 755 /usr/local/sbin/root-disk-watch
```

بیت setuid روی این اسکریپت نگذارید. هدف ۱۰۵.۲ می‌پرسد که اسکریپت setuid را چطور مدیریت می‌کنید: پاسخ عملی این است که setuid روی اسکریپت پوسته را اصلاً به کار نبرید. پوسته فایل را دوباره می‌خواند و شرایط مسابقه دارد. کار ممتاز را با systemd یا sudo محدود انجام دهید. sudo در [امنیت ۱۰۲](/docs/02-lpic/lpic1-102-security) است.

اجرا و دیدن لاگ:

```bash
sudo /usr/local/sbin/root-disk-watch
echo "exit=$?"
journalctl -t root-disk-watch -n 3 --no-pager
```

اگر دیسک زیر آستانه باشد خروج صفر است. برای آزمودن شاخهٔ خطا، موقتاً آستانه را در یک کپی در `/tmp` روی صفر بگذارید، نه در فایلی که cron فردا می‌خواند.

نامه به مدیر، که آزمون با عبارت conditional mailing می‌آورد، وقتی بستهٔ نامه آماده است معنی دارد. تا صفحهٔ [پست](/docs/02-lpic/lpic2-202-mail) را نساخته‌اید، `logger` کانال درست است. اگر `mail` نصب شد، شکست اسکریپت می‌تواند یک نامه بفرستد. آن را به دامنهٔ واقعی سازمان نفرستید.

`set -euo pipefail` یعنی توقف در خطا، متغیر تعریف‌نشده ممنوع، و شکست داخل لوله پنهان نشود. فصل اتوماسیون همین را برای اسکریپت بلند اجباری کرده است. در آموزش عمدیِ یک خطا می‌توان برداشتش، ولی این فایل نگهداری است و باید بماند.

## Security Notes

دایرکتوری جاری را در `PATH` نگذارید، نه در اول و نه در آخر. فایلی به نام `ls` در `/tmp` نباید به‌جای `/usr/bin/ls` اجرا شود. اسکریپت بالا `PATH` را خودش به مسیرهای سیستم محدود کرده تا به محیط فراخواننده وابسته نباشد.

`~/.profile` و `~/.bashrc` را از روی وب کپی نکنید. همان فایل‌ها هنگام هر ورود SSH اجرا می‌شوند. یک خط مخرب آنجا یعنی پایداری بعد از reboot.

مجوز اسکریپت در `/usr/local/sbin` باید برای دیگران فقط اجرا و خواندن باشد، نه نوشتن. اگر گروه یا others نوشتن دارند، هر کسی که به میزبان رسیده می‌تواند اسکریپت را قبل از اجرای cron عوض کند.

رمز و توکن را در فایل پروفایل export نکنید. هر فرایند فرزند آن را در محیط می‌بیند و گاهی در `/proc` قابل خواندن است.

## Troubleshooting

علامت: در SSH متغیر هست، در `sudo /usr/local/sbin/root-disk-watch` نیست. طبیعی است اگر متغیر فقط در `~/.bashrc` باشد. sudo محیط را پاک می‌کند مگر سیاست `env_reset` را دستکاری کرده باشید. دستکاری نکنید. چیزی که اسکریپت لازم دارد باید داخل خودش یا در واحد systemd باشد.

علامت: `syntax error: "(" unexpected` هنگام `sh script`. فایل را با bash صدا زده‌اید در حالی که شِبنگ یا فراخوانی `sh` است و آرایه یا پرانتز bash داخلش است. `head -n 1` فایل را ببینید. یا شِبنگ را bash کنید و `bash script` بزنید، یا دستور را به POSIX برگردانید.

علامت: فرمان تازه در `/usr/local/sbin` پیدا نمی‌شود. نشست قدیمی `PATH` قدیمی دارد.

```bash
type root-disk-watch || true
. /etc/profile.d/ops-lab.sh
type root-disk-watch
```

اگر بعد از source هم نبود، مجوز دایرکتوری یا نام فایل غلط است. `ls -l /usr/local/sbin/root-disk-watch` باید فایل و بیت اجرا را نشان دهد.

علامت: اسکریپت با `set -u` روی متغیر خالی می‌میرد. متغیر را پیش‌فرض بدهید یا شرط وجودش را قبل از استفاده بگذارید. حذف `set -u` برای ساکت کردن خطا، اشکال را به خط بعدی موکول می‌کند.

## Best Practices

- شِبنگ را آگاه انتخاب کنید. نگهداری این دانشنامه `#!/bin/bash` است. اسکریپت قابل‌حمل POSIX فقط اگر واقعاً زیر `sh` آزمون شده باشد.
- تنظیم شخصی تعاملی در `~/.bashrc`. تنظیم ورود همهٔ کاربران، اگر واقعاً لازم است، در `/etc/profile.d` با نام مشخص.
- `PATH` اسکریپت cron را داخل اسکریپت ببندید. به `PATH` کاربر واردشده تکیه نکنید.
- alias را وارد اسکریپت نکنید. تابع یا دستور کامل بنویسید.
- اسکریپت پوسته را setuid نکنید. عمق بیشتر تابع و حلقه در [متغیر و شرط](/docs/13-automation/variables-conditions) و [حلقه و تابع](/docs/13-automation/loops-functions-arrays) است.

## تمرین

سناریو: همکارتان می‌گوید اسکریپت `root-disk-watch` در SSH دستی کار می‌کند و از یک نشست `sh` خطای پرانتز می‌دهد. علاوه بر این، یک کاربر نو باید همان `EDITOR` را داشته باشد.

1. شِبنگ فایل `/usr/local/sbin/root-disk-watch` را چاپ کنید و فایل را یک‌بار با bash و یک‌بار با `sh` صدا بزنید. خروجی دوم را توضیح دهید، نه این که شِبنگ را به `sh` تغییر دهید.
2. بررسی کنید `/etc/skel/.bashrc` وجود دارد یا نه. یک خط `EDITOR` را آنجا نگذارید اگر نمی‌دانید کاربر بعدی vim دارد یا nano. به‌جایش بگویید چرا تغییر skel کاربر `ops` فعلی را عوض نمی‌کند.
3. سؤال کوتاه: کدام فایل در ورود SSH خوانده می‌شود که در یک bash غیرورود دوباره خوانده نمی‌شود؟ `source` در dash چه معادلی دارد؟

```bash
head -n 1 /usr/local/sbin/root-disk-watch
bash /usr/local/sbin/root-disk-watch; echo "bash_exit=$?"
sh /usr/local/sbin/root-disk-watch; echo "sh_exit=$?"
ls -l /etc/skel/.bashrc /home/ops/.bashrc
```

## پاسخ تمرین

شِبنگ باید `#!/bin/bash` باشد. اجرای bash خروج ۰ یا ۱ می‌دهد بسته به درصد دیسک، و یک خط در journal. اجرای `sh` باید با خطای نحوی تمام شود، چون dash عملگر `pipefail` داخل `set` را نمی‌فهمد یا بسط bash را رد می‌کند. این خطا ثابت می‌کند اسکریپت عامدانه bash است. شِبنگ را برای ساکت کردن خطا به `sh` برنگردانید.

`/etc/skel/.bashrc` قالب کاربر آینده است. `ops` از قبل خانه دارد و فایل خانه‌اش جداست. ویرایش skel اثر عقب‌رو ندارد. برای `ops` همان `~/.bashrc` محل `EDITOR` است.

فایلی که ورود می‌خواند و bash غیرورود دوباره نمی‌خواند `/etc/profile` است، به‌همراه `/etc/profile.d`. `~/.profile` هم مال ورود است. `~/.bashrc` را Ubuntu از داخل `~/.profile` برای ورود هم صدا می‌زند، پس برای کاربر تعاملی Ubuntu اغلب هر دو بار دیده می‌شود؛ فرق را با یک `bash` بدون ورود از روی `bash --noprofile --norc` می‌توان ثابت کرد. معادل `source` در dash نقطه است: `. /path/file`.
