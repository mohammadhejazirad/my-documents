# پایش منبع سرور

## مقدمه

قبل از نصب هر عامل پایش باید بتوانید روی خود سرور بگویید CPU مشغول کار است یا منتظر دیسک، حافظه واقعاً کم است یا در کش فایل نشسته، و دیسک از نظر بایت پر شده یا از نظر inode. ابزار این صفحه از قبل روی Ubuntu Server 26.04 هست، به‌جز `sar` که بستهٔ `sysstat` است و تا وقتی نصب و فعالش نکرده‌اید وجود ندارد.

میزبان مثال `app-1.example.internal` روی `10.10.1.10` است. آستانه‌های پایین پیشنهاد عملیاتی همین دانشنامه برای اقدام انسان است، نه ثابت هسته و نه عدد Prometheus. قانون هشدار در [Prometheus](./prometheus) باید با همین حرف یکی باشد.

## مفهوم اصلی

CPU را با دو عدد جدا بخوانید. بار (load average) تعداد نخ‌هایی است که می‌خواهند اجرا شوند یا در وقفهٔ ناگسستنی دیسک‌اند. این عدد را با تعداد هسته مقایسه می‌کنید که `nproc` می‌گوید. بار ۴ روی ماشین ۲ هسته‌ای یعنی صف. بار ۴ روی ماشین ۱۶ هسته‌ای یعنی بیکاری نسبی. خود بار نمی‌گوید صف مال محاسبه است یا مال دیسک.

ستون‌های زمان CPU این را جدا می‌کنند. `us` کار کاربر است، `sy` کار هسته، `wa` انتظار برای ورودی/خروجی، `id` بیکار، `st` زمانی که هایپروایزر این ماشین را عقب انداخته. اگر `wa` بالاست و `us` پایین، خریدن CPU یا کشتن پروسهٔ پرمصرف پاسخ غلط است. باید دیسک و فراخوانی دیسک را ببینید.

حافظه در لینوکس کش فایل را «استفاده شده» نشان می‌دهد اگر فقط به ستون used نگاه کنید. ستون درست `available` در `free -h` است. این ستون تقریبی است از چیزی که برای برنامهٔ تازه بدون swap سخت در دسترس است و بخش بزرگ کش را هم شامل می‌شود. کش بالا با available بالا نشت حافظه نیست. available پایین به‌همراه swap در حال رشد، فشار واقعی است. فرق این دو در [نشت حافظه](/docs/14-troubleshooting/memory-leak) با حادثه آمده است.

دیسک دو منبع جدا دارد: بلوک و inode. `df -h` بایت را نشان می‌دهد و `df -i` تعداد فایل را. می‌شود بایت آزاد باشد و inode تمام، اگر میلیون‌ها فایل ریز ساخته باشید. برنامه همان خطا را می‌گیرد: `No space left on device`. کسی که فقط `df -h` دیده فکر می‌کند پیام دروغ است.

`vmstat` این‌ها را در یک نگاه یک‌ثانیه‌ای کنار هم می‌گذارد. `sar` همان جنس عدد را از نمونه‌های ذخیره‌شدهٔ بعد از نصب sysstat می‌دهد تا بپرسید ظهر چه شده، نه فقط الان.

## چرا استفاده می‌شود؟

عامل Prometheus ممکن است خودش به‌خاطر دیسک پر یا شبکه ننویسد. Netdata ممکن است نصب نباشد. در هر دو حال این دستورها از SSH یا از کنسول کار می‌کنند. عادت کردنشان باعث می‌شود عدد Grafana را بدون فهم ستون‌ها باور نکنید.

آستانهٔ مکتوب جلوی دو افراط را می‌گیرد: reboot شبانه چون load لحظه‌ای بالا رفته، و بی‌خیالی چون «هنوز که سایت باز است» در حالی که دیسک از ۹۰ درصد گذشته. پیشنهاد این دانشنامه برای اقدام انسان این است.

| منبع | چه را ببینید | کی انسان باید دست به کار شود |
| --- | --- | --- |
| CPU | `us+sy` و بار نسبت به `nproc` | بیش از حدود ۱۵ دقیقه `us+sy` بالای ۸۵ درصد، یا بار بالاتر از تعداد هسته در همان مدت، در حالی که `wa` پایین است |
| دیسک و CPU | ستون `wa` | `wa` پایدار بالای ۲۰ درصد: مسیر دیسک است، نه ارتقای CPU |
| RAM | `available` و روند swap | available زیر حدود ۱۰ درصد RAM کل، و swap نسبت به نیم‌ساعت قبل در حال رشد |
| دیسک بایت | `df -h` روی `/` و روی حجم داده | از ۸۰ درصد برنامه‌ریزی، از ۹۰ حادثهٔ همین هفته، از ۹۵ توقف کار غیرضروری و آزاد کردن جا |
| inode | `df -i` | از ۸۵ درصد همان فوریت دیسک بایت را دارد، حتی اگر بایت آزاد باشد |

این درصدها قرارداد تیم‌اند تا همه یک زبان حرف بزنند. سرویس خاص ممکن است زودتر به سقف خودش بخورد. اگر دیتابیس روی حجم جداست، آستانه را روی همان حجم بگیرید نه فقط روی `/`.

## Architecture

```text
شیفت
  │
  ├── uptime و nproc          بار در برابر تعداد هسته
  ├── vmstat 1 5              us sy id wa  در پنج نمونه
  ├── free -h                 available در برابر کش
  ├── df -h و df -i           بایت و inode
  └── sar                     فقط اگر sysstat فعال است
          │                      تاریخچهٔ محلی
          ▼
     تصمیم: دیسک، حافظه، CPU، یا هیچ‌کدام و باید لاگ را دید

عامل‌ها (صفحهٔ خودشان)
  node_exporter  →  Prometheus     برای وقتی انسان پای SSH نیست
  Netdata                          برای دیدن زندهٔ همان میزبان
```

این ابزارها هشدار نمی‌فرستند. اگر تنها پایش شما این صفحه باشد، شب کسی خبردار نمی‌شود. بعد از این‌که فهمیدید کدام منبع مهم است، همان را به قانون Prometheus وصل کنید.

## Installation

`uptime`، `free`، `df` و `vmstat` در نصب استاندارد سرور هستند. `vmstat` از بستهٔ `procps` می‌آید. اگر یک ایمیج خیلی تراشیده آن را ندارد:

```bash
vmstat 1 3
```

و در صورت نبود دستور:

```bash
sudo apt update
sudo apt install procps
```

`sar` را فقط وقتی نصب کنید که می‌خواهید تاریخچهٔ محلی داشته باشید. نصب کردنش به‌تنهایی کافی نیست. روی Ubuntu فایل `/etc/default/sysstat` اغلب جمع‌آوری را خاموش گذاشته.

```bash
sar -u 1 3
```

اگر پوسته گفت دستور نیست:

```bash
sudo apt install sysstat
grep ENABLED /etc/default/sysstat
```

اگر خط `ENABLED="false"` بود، آن را `true` کنید و سرویس را روشن کنید.

```bash
sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
sudo systemctl enable --now sysstat
systemctl is-active sysstat
```

چند دقیقه بعد `sar -u 1 3` باید عدد بدهد، نه خطای «can't open». اگر هنوز فایل روز را ندارد، یک بار `sudo systemctl restart sysstat` و چند دقیقه صبر. در حادثهٔ همین لحظه منتظر sar نمانید. `vmstat` همان حالا را می‌گوید. sar برای فردای حادثه است.

## Configuration

این ابزارها فایل کانفیگ سرویس ندارند. پیکربندی یعنی عادت خواندن و روشن کردن sysstat اگر تاریخچه می‌خواهید. فاصلهٔ نمونه‌گیری پیش‌فرض sysstat را همین ابتدا ریز نکنید. هر ده دقیقه یک نمونه برای جواب «ظهر چه خبر بود» کافی است. ریز کردن تا هر ثانیه، خودش دیسک لاگ sar را بزرگ می‌کند.

برای خواندن همین حالا، پنج نمونهٔ یک‌ثانیه‌ای بهتر از یک نمونه است. نمونهٔ اول `vmstat` از زمان بوت میانگین می‌گیرد و گمراه‌کننده است. همیشه حداقل دو خط بعد از خط میانگین را ببینید.

دستورهایی که در SSH حادثه می‌زنید:

```bash
nproc
uptime
free -h
df -hT
df -i
vmstat 1 5
```

`df -hT` نوع فایل‌سیستم را هم نشان می‌دهد تا tmpfs را با دیسک ریشه اشتباه نگیرید. tmpfs پر روی `/tmp` یا `/run` می‌تواند سرویس را بشکند در حالی که دیسک اصلی خالی است. آن سطر را جدا بخوانید.

## Production Example

کاربر می‌گوید سایت کند است. شما روی `app-1` هستید و هنوز نمی‌دانید کندی از CPU است یا دیسک یا حافظه.

### نشانه

درخواست‌ها دیر جواب می‌دهند. صفحه گاهی باز می‌شود. reboot نشده. همکار می‌گوید «حتماً CPU تمام شده».

### فرضیه

یا واقعاً پردازش اشباع شده، یا دیسک در `wa` است و CPU بیکار منتظر است، یا available تمام شده و ماشین swap می‌کند. هر سه در جملهٔ «کند است» جمع می‌شوند و اقدام‌شان یکی نیست.

### دستور مشاهده

```bash
nproc
uptime
vmstat 1 5
free -h
df -hT /
df -i /
```

نمونهٔ ماشینی که دو هسته دارد و ظاهر بارش ترسناک است ولی در واقع منتظر دیسک است:

```text
2
 10:15:01 up 12 days,  3:11,  1 user,  load average: 6.20, 4.10, 2.05
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 0  4      0 220000  80000 900000    0    0    12    80  300  700  4  2 40 54  0
 1  3      0 218000  80000 901000    0    0  2400   900  800 1600  6  3 30 61  0
```

`load average` بالای `nproc` است، پس صف واقعی است. در خط‌های vmstat ستون `us` تک‌رقمی است و `wa` بالای ۵۰ است. ستون `b` بیش از صفر است، یعنی پروسه در وقفهٔ دیسک خوابیده. این CPU اشباع نیست.

حافظه در همین نمونه هنوز آزاد است. اگر `si` و `so` غیرصفر و پایدار باشند، آن‌وقت فشار حافظه هم هست. یک نمونهٔ صفر در یک خط کافی نیست. پنج خط را ببینید.

دیسک:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/vda2      ext4   40G   30G   8.2G  79% /
```

۷۹ درصد هنوز زیر آستانهٔ برنامه‌ریزی این دانشنامه است. کندی این حادثه را با «دیسک پر است» توضیح ندهید. `wa` بالا با دیسک پر یکی نیست. می‌تواند دیسک کند یا I/O سنگین باشد در حالی که جا هست.

### تصمیم

`wa` بالا و `us` پایین: سراغ کشتن پروسهٔ بالای `top` به‌خاطر CPU نروید. ببینید کدام پروسه دیسک می‌خواند و آیا دیتابیس یا لاگ در همان حجم است. ادامه در [CPU بالا](/docs/14-troubleshooting/high-cpu) فقط اگر `us` واقعاً بالاست. اگر حجم داده بالای ۸۰ درصد بود، هم‌زمان جا را هم برنامه کنید، ولی آن را علت این کندی خاص اعلام نکنید مگر عددها جور باشند.

`us+sy` بالای ۸۵ برای چند دقیقه و `wa` نزدیک صفر: آن‌وقت فرض همکار درست است و باید پروسه را از `top` یا `ps` پیدا کنید.

available کم و `so` غیرصفر: فشار حافظه. مسیرش صفحهٔ نشت است، نه اضافه کردن CPU.

### اصلاح

در نمونهٔ بالا اصلاح، کم کردن I/O است نه reboot. مثلاً یک بکاپ یا `find` سنگین روی همان دیسک را متوقف کنید اگر واقعاً همان است، یا کندی دیسک مجازی را با مسئول زیرساخت ببرید اگر هیچ پروسهٔ محلی حجم نمی‌نویسد. شاهد اصلاح این است که `wa` در `vmstat 1 5` برگردد پایین و بار به نزدیکی یا زیر `nproc` بیاید.

اگر هم‌زمان `df` از ۹۰ درصد گذشت، آزاد کردن جا طبق صفحهٔ دیسک پر انجام می‌شود. این دو کار را در یادداشت حادثه جدا بنویسید تا فردا کسی فکر نکند truncate کردن لاگ، انتظار دیسک را درمان کرده است.

### جلوگیری از تکرار

برای میزبانی که یک بار `wa` غافلگیرتان کرد، sysstat را روشن کنید تا دفعهٔ بعد بپرسید مشکل از کی شروع شده.

```bash
sar -u -s 09:00:00 -e 10:30:00
```

ستون `%iowait` در خروجی sar همان جنس `wa` است. اگر دستور می‌گوید can't open `/var/log/sysstat/...` ، جمع‌آوری خاموش است و باید بخش نصب همین صفحه را انجام دهید. عدد نسازید.

آستانهٔ ۸۰ درصد دیسک را به قانون Prometheus وصل کنید تا لازم نباشد کسی SSH بزند و `df` بگیرد. تا آن روز، حداقل در گزارش شیفت `df -hT` میزبان‌های داده را داشته باشید.

## Security Notes

این دستورها وضعیت سیستم را به هر کسی که SSH دارد نشان می‌دهند. خروجی‌شان را در کانال عمومی مشتریان نفرستید. نام حجم، نام میزبان و اندازهٔ داده برای شناسایی کافی است.

`sysstat` تاریخچهٔ مصرف را روی دیسک محلی نگه می‌دارد. دسترسی `/var/log/sysstat` را بازتر از پیش‌فرض بسته نکنید.

برای «آزاد دیده شدن RAM» دستور نوشتن در `drop_caches` را عادت نکنید. این کار کش را دور می‌ریزد، بار دیسک را لحظه‌ای بدتر می‌کند، و تشخیص نشت را خراب می‌کند. در صفحهٔ حافظه هم به‌عنوان درمان نیامده است.

نصب sysstat روی میزبانی که دیسک ۹۵ درصد است اولویت نیست. اول جا آزاد کنید. نوشتن نمونهٔ sar خودش به دیسک نیاز دارد.

## Troubleshooting

`uptime` بار بالا نشان می‌دهد و سیستم روان است: تعداد هسته را نخوانده‌اید. `nproc` را کنار بار بگذارید. بار ۱ دقیقه‌ای تک‌جهشی هم به‌تنهایی حادثه نیست. ۱۵ دقیقه را ببینید.

`free` تقریباً همهٔ RAM را used نشان می‌دهد و available بزرگ است: طبیعی است. لینوکس RAM بیکار را صرف کش می‌کند. فقط available و swap را برای تصمیم استفاده کنید.

`df` می‌گوید جا هست و برنامه می‌گوید دیسک پر است: `df -i` بگیرید. اگر Use% اینود بالا است، فایل ریز زیاد شده، اغلب در `/tmp` یا یک پوشهٔ سشن. پاک کردن با الگو، نه فرمت کردن دیسک.

`vmstat` خط اول `wa` عجیب دارد و خط‌های بعد آرام‌اند: خط اول میانگین از بوت است. نادیده‌اش بگیرید.

`sar` عدد دیروز را ندارد: سرویس خاموش بوده یا `ENABLED` هنوز false است. گذشته را اختراع نمی‌کند. از لاگ برنامه و journal برای دیروز استفاده کنید و از امروز جمع‌آوری را روشن کنید.

`st` در vmstat پایدار و بالا است: هایپروایزر به این VM وقت نمی‌دهد. کشتن پروسه داخل مهمان مشکل همسایه یا سقف CPU ماشین را حل نمی‌کند. این را به مسئول مجازی‌سازی بدهید، با عدد `st` نه با حدس.

## Best Practices

- همیشه `nproc` را کنار load بگویید.
- خط اول vmstat را ملاک نگیرید. `vmstat 1 5` بزنید و خط‌های بعد را بخوانید.
- تصمیم حافظه با `available` است، نه با خالی بودن ستون free.
- `df -h` و `df -i` هر دو. خطای No space بدون اینود، تشخیص ناقص است.
- `wa` بالا را با ارتقای CPU درمان نکنید.
- sar را فقط با sysstat فعال بخواهید. اگر دستور نیست، همان لحظه vmstat کافی است.
- آستانهٔ ۸۰ و ۹۰ و ۹۵ دیسک و ۱۰ درصد available را در هشدار Prometheus تکرار کنید، نه یک درصد جدید.
- این دستورها جایگزین هشدار شبانه نیستند. بعد از فهمیدن منبع، همان را به [نقشهٔ پایش](/docs/12-monitoring) وصل کنید.
