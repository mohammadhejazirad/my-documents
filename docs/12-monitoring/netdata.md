# Netdata

## مقدمه

Netdata نمودار زندهٔ خود میزبان است: CPU، دیسک، شبکه، و اگر سوکت داکر را عمداً داده باشید کانتینرها. در این دانشنامه نسخهٔ عامل `v2.11.1` است، چه از ایمیج `netdata/netdata:v2.11.1` و چه از اسکریپت رسمی kickstart که همان شاخهٔ پایدار را نصب می‌کند به شرطی که موقع اجرا نسخه را در خروجی نصب بخوانید. میزبان نمونه `app-1.example.internal` روی `10.10.1.10` است. UI روی پورت 19999 است و فقط از شبکهٔ عملیات باز می‌شود.

این صفحه عامل را به Netdata Cloud وصل نمی‌کند. سرور داخلی لازم نیست برای دیدن CPU خودش به بیرون claim بزند. اگر فلگ دقیق خاموش کردن ابر را از روی حافظه بنویسیم، خطرش این است که اسکریپت آن را نفهمد یا رفتار دیگری بدهد. پس فلگ اختراعی این‌جا نیست. کار مشخص این است: توکن claim ندهید، در UI وارد فضای ابری نشوید، و پورت را با فایروال به شبکهٔ مدیریت محدود کنید.

Prometheus همچنان برای هشدار و نگهداری است. Netdata جای [نقشهٔ پایش](/docs/12-monitoring) را نمی‌گیرد.

## مفهوم اصلی

عامل Netdata روی همان ماشینی که می‌خواهید ببینید اجرا می‌شود و رابط وب محلی دارد. برخلاف Prometheus، لازم نیست جایی دیگر scrape شود تا شیفت همین حالا را ببیند. به همین دلیل برای «الان چه خبر است» سریع است و برای «سه هفته پیش چه خبر بود و به چه کسی زنگ بزن» ابزار غلطی است، مگر این‌که خودتان جای دیگری متریک را نگه دارید.

دو روش نصب هست و یکی را انتخاب کنید. داکر وقتی روی میزبان از قبل Docker Engine دارید و می‌خواهید عامل را مثل بقیهٔ کانتینرها بردارید. kickstart وقتی نمی‌خواهید برای پایش، داکر نصب کنید. هر دو به دسترسی گسترده به `/proc` و `/sys` نیاز دارند چون کارشان دیدن خود میزبان است. این دسترسی معادل یک عامل ممتاز است. آن را روی هر سرور اینترنتی بدون فایروال رها نکنید.

رابط محلی را بی‌رمز فرض کنید. نسخه‌های مختلف Netdata جلوی UI رفتار یکسان ندارند و این صفحه یک فلگ احراز هویت از خودش نمی‌سازد. کنترلی که به آن تکیه می‌کنیم فایروال است: فقط `10.10.0.0/16` ، و اگر سازمان یک زیرشبکهٔ مدیریت کوچک‌تر دارد همان، نه کل دنیا.

حالت شبکهٔ میزبان (`--network=host`) در روش داکر عمدی است. بدون آن، عامل شبکه و پروسهٔ میزبان را درست نمی‌بیند. Документаسیون رسمی همین حالت را برای پایش کامل می‌خواهد. هزینهٔ آن این است که پورت 19999 مستقیم روی میزبان گوش می‌دهد و mapping معمولی پورت داکر اعمال نمی‌شود. فایروال میزبان تنها در است.

## چرا استفاده می‌شود؟

در حادثه، `vmstat` پنج ثانیه را نشان می‌دهد و تمام. Netdata همان میزبان را بدون ساخت داشبورد به نمودار تبدیل می‌کند تا ببینید جهش از کی شروع شده، در حد حافظهٔ محلی عامل. برای شیفتی که هنوز Grafana را باز نکرده، این سریع‌ترین تصویر روی خود `app-1` است.

به درد این کارها نمی‌خورد: نامه زدن وقتی دیسک از ۸۰ درصد گذشت، مقایسهٔ ده میزبان در یک صفحهٔ واحد، و نگه داشتن عدد بعد از پاک شدن کانتینر. آن‌ها کار Prometheus و Grafana است. اگر فقط Netdata را نصب کنید و تصور کنید پایش تمام است، شب‌ها کور هستید.

## Architecture

```text
اپراتور، فقط از 10.10.0.0/16
        │
        │  TCP 19999
        ▼
عامل Netdata روی app-1
        │
        ├── /proc  /sys  /var/log     فقط‌خواندنی
        ├── docker.sock               اختیاری، معادل root روی داکر
        └── بدون claim token و بدون فضای ابری

Prometheus روی mon-1 این UI را scrape نمی‌کند
مگر بعداً خودتان صادرکننده را جدا پیکربندی کنید.
این صفحه آن کار را بخشی از نصب نمی‌داند.
```

سوکت داکر را فقط وقتی وصل کنید که می‌خواهید کانتینرهای همان میزبان در Netdata دیده شوند. هر کسی که به UI دسترسی پیدا کند، اگر عامل به سوکت وصل باشد، به اطلاعات داکر و در عمل به قدرت آن سوکت نزدیک است. روی `docker-1` این تصمیم آگاهانه است. روی پروکسی‌ای که داکر ندارد، آن volume را اصلاً نگذارید.

## Installation

روش اول، داکر. موتور داکر باید طبق [نصب داکر](/docs/05-docker/installation) باشد. برچسب را کامل بنویسید. `latest` و حتی `stable` شناورند. این دانشنامه `v2.11.1` را قفل کرده است.

دستور زیر همان فهرست mount و capability سند رسمی داکر Netdata است، با برچسب قفل‌شده. آن را یک‌جا اجرا کنید. حذف کردن `--pid=host` یا `--network=host` پایش میزبان را ناقص می‌کند. اگر pid میزبان را برمی‌دارید، سند رسمی می‌گوید باید `--init` بدهید. در این صفحه آن حالت را انتخاب نمی‌کنیم.

```bash
docker run -d --name=netdata \
  --pid=host \
  --network=host \
  -v netdataconfig:/etc/netdata \
  -v netdatalib:/var/lib/netdata \
  -v netdatacache:/var/cache/netdata \
  -v /:/host/root:ro,rslave \
  -v /etc/passwd:/host/etc/passwd:ro \
  -v /etc/group:/host/etc/group:ro \
  -v /etc/localtime:/etc/localtime:ro \
  -v /proc:/host/proc:ro \
  -v /sys:/host/sys:ro \
  -v /etc/os-release:/host/etc/os-release:ro \
  -v /var/log:/host/var/log:ro \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  -v /run/dbus:/run/dbus:ro \
  --restart unless-stopped \
  --cap-add SYS_PTRACE \
  --cap-add SYS_ADMIN \
  --security-opt apparmor=unconfined \
  netdata/netdata:v2.11.1
```

اگر داکر روی میزبان نیست و نمی‌خواهید به‌خاطر پایش نصبش کنید، روش دوم kickstart است. اسکریپت را از نشانی رسمی بردارید، قبل از اجرا بخوانید، و فقط بعد از خواندن اجرا کنید. لوله کردن مستقیم `curl` به پوسته ممنوع است، چون همان چیزی را اجرا می‌کنید که هنوز ندیده‌اید.

```bash
curl -fsSL -o /tmp/netdata-kickstart.sh https://get.netdata.cloud/kickstart.sh
less /tmp/netdata-kickstart.sh
sh /tmp/netdata-kickstart.sh
```

`less` را واقعاً باز کنید. دنبال این بگردید که اسکریپت از کجا بسته می‌گیرد و آیا در پایان از شما توکن می‌خواهد. اگر از شما claim token خواست، خالی بگذارید و رد کنید. توکن را از یک فضای ابری کپی نکنید «تا بعداً». سرور داخلی بدون توکن هم UI محلی دارد.

بعد از هر دو روش، نسخه و پورت را ببینید.

```bash
docker ps --filter name=netdata --format '{{.Image}} {{.Status}}'
ss -lnt | grep 19999
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 5 http://127.0.0.1:19999/
```

کد HTTP باید 200 باشد. ایمیج باید `netdata/netdata:v2.11.1` باشد. اگر kickstart زده‌اید و داکر در کار نیست، خط `docker ps` را نادیده بگیرید و به‌جایش سرویس را ببینید.

```bash
systemctl is-active netdata
```

اگر kickstart نسخهٔ دیگری غیر از 2.11.1 نصب کرد، در یادداشت تغییر بنویسید و تا وقتی دلیلش را نخوانده‌اید آن را «همان نسخهٔ دانشنامه» حساب نکنید. اسکریپت رسمی ممکن است داخل کانال پایدار، وصلهٔ جدیدتری بگذارد. نسخه را از خود عامل بخوانید، اختراع نکنید.

## Configuration

فایروال بخشی از پیکربندی است، نه کار بعدی. روی Ubuntu با UFW، فقط شبکهٔ آزمایشگاه. اگر شبکهٔ مدیریت سازمان کوچک‌تر از `10.10.0.0/16` است، همان را بگذارید.

```bash
sudo ufw allow from 10.10.0.0/16 to any port 19999 proto tcp comment 'netdata lab'
sudo ufw status verbose
```

جزئیات UFW در [صفحهٔ فایروال](/docs/10-security/ufw) است. اگر UFW خاموش است و فایروال دیگری دارید، معادل همین محدودیت را آنجا بنویسید. «فعلاً UFW خاموش است» مجوز باز ماندن 19999 روی کارت عمومی نیست.

هیچ متغیر claim در دستور داکر این صفحه نیست. هیچ آرگومان `--claim-token` در kickstart نیست. اگر بعداً کسی فایل کانفیگ را با یک token پر کرد، آن را پاک کنید و کانتینر را با همین دستور رسمیِ بدون توکن از نو بسازید. اختراع `--disable-cloud` یا مشابه آن را در واحد systemd ننویسید. اگر روزی سند رسمی نسخه‌ای که نصب کرده‌اید فلگ مشخصی برای نپیوستن داد، همان رشته را از سند کپی کنید و در یادداشت تغییر بیاورید.

ساعت کانتینر با mount شدن `/etc/localtime` با میزبان یکی می‌شود. میزبان باید `Asia/Tehran` باشد تا نمودار با journal قابل مقایسه باشد. اگر zone میزبان غلط است، اول همان را درست کنید، نه نمودار را.

سوکت داکر و گذرگاه D-Bus را روی میزبانی که لازم ندارید حذف کنید. بدون `docker.sock` همچنان CPU و دیسک میزبان را می‌بینید. بدون `/run/dbus` ممکن است بعضی متریک‌های systemd را از دست بدهید و بقیهٔ عامل کار می‌کند. حذف این دو از اضافه کردنشان روی سرور لبه امن‌تر است.

## Production Example

شیفت می‌گوید `app-1` کند است و Prometheus هنوز روی این میزبان scrape ندارد. می‌خواهید در چند دقیقه بفهمید کندی CPU است یا دیسک، بدون نصب کردن یک پشتهٔ کامل.

### نشانه

کاربران کندی را از ده دقیقه پیش می‌گویند. `ssh` به `app-1` برقرار است. روی `mon-1` هدفی برای `10.10.1.10:9100` نیست.

### فرضیه

یا یک پروسه CPU را برده، یا دیسک در انتظار است. Netdata این دو را روی یک میزبان نشان می‌دهد. فرض سوم این است که خود عامل بالا نمی‌آید و نباید وقت را صرف UI کنید.

### دستور مشاهده

اگر کانتینر همین صفحه را اجرا کرده‌اید:

```bash
docker ps --filter name=netdata
ss -lnt | grep 19999
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 5 http://127.0.0.1:19999/
```

از لپ‌تاپ داخل شبکه، نه از اینترنت:

```bash
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 5 http://10.10.1.10:19999/
```

اگر کد از خود میزبان 200 است و از لپ‌تاپ timeout است، فایروال یا مسیر است. UI را روی اینترنت با باز کردن پورت «موقت» درست نکنید.

وقتی 200 را دارید، در مرورگر همان آدرس داخلی را باز کنید و نمودار CPU و دیسک ده دقیقهٔ اخیر را ببینید. هم‌زمان در SSH همان چیزی را که صفحهٔ منبع می‌گوید بگیرید تا UI را کور باور نکرده باشید.

```bash
vmstat 1 5
```

### تصمیم

اگر UI و `vmstat` هر دو `wa` بالا و CPU کاربر پایین نشان می‌دهند، مسیر حادثه دیسک است. Netdata را به حال خود بگذارید و بروید سراغ I/O. اگر UI پروسهٔ مشخصی را نزدیک صددرصد یک هسته نشان می‌دهد و `vmstat` ستون `us` را بالا نشان می‌دهد، همان پروسه موضوع کار است. نام را از UI بردارید و با `ps` تأیید کنید قبل از هر stop.

اگر UI بالا نمی‌آید، با Netdata حادثه را معطل نکنید. `vmstat` و `top` همان لحظه کافی‌اند. عامل را بعد از آرام شدن میزبان درست کنید.

### اصلاح

اصلاح کندی، خاموش کردن Netdata نیست. اصلاح، اقدام روی پروسه یا دیسک است که صفحه‌های عیب‌یابی همان را دارند. شاهد این‌که عامل خودش سالم است، کد 200 روی `127.0.0.1:19999` و یک نمودار است که بعد از تمام شدن حادثه به سطح قبلی برگشته.

اگر فهمیدید سوکت داکر را بی‌دلیل داده‌اید، بعد از حادثه کانتینر را بدون آن volume از نو بسازید. وسط حادثهٔ CPU این کار را نکنید.

### جلوگیری از تکرار

میزبانی که یک بار به دید زنده نیاز پیدا کرد، Netdata را با فایروال نگه دارید، و همان هفته node_exporter را هم به Prometheus اضافه کنید. وگرنه دفعهٔ بعد باز فقط وقتی خبردار می‌شوید که کسی شکایت کند. چک خروج: از یک IP خارج از `10.10.0.0/16` پورت 19999 نباید باز باشد. از داخل شبکه باید 200 بگیرید.

## Security Notes

`--cap-add SYS_ADMIN` و `apparmor=unconfined` و pid میزبان، مجموعهٔ بسیار قدرتمندی است. آن را فقط برای عامل پایش و فقط با همین ایمیج قفل‌شده قبول کنید. یک کانتینر برنامهٔ معمولی این فلگ‌ها را لازم ندارد. اگر این دستور را به‌عنوان الگوی `docker run` جاهای دیگر کپی کنید، مدل تهدیدتان عوض می‌شود.

`/var/run/docker.sock` یعنی کنترل موتور داکر. UI بی‌رمز به‌علاوهٔ این سوکت به‌علاوهٔ پورت باز روی اینترنت یعنی واگذاری میزبان. اگر یکی از این سه را نمی‌توانید بردارید، سوکت را بردارید.

توکن claim را در تاریخچهٔ پوسته، در `docker inspect`، و در فایل‌های `/etc/netdata` جست‌وجو نکنید تا «ببینید خالی است» و همان لحظه یک توکن آزمایشی بگذارید. نگذارید. سرور داخلی به فضای ابری claim نمی‌شود.

اسکریپت kickstart را قبل از هر ارتقا دوباره بخوانید. نشانی رسمی `https://get.netdata.cloud/kickstart.sh` است. نشانی مشابه از ویکی یا چت را اجرا نکنید.

پورت 19999 را در گروه امنیتی ابری جدا از UFW هم ببندید اگر ماشین IP عمومی دارد. UFW داخل مهمان، گروه امنیتی را عوض نمی‌کند.

## Troubleshooting

کانتینر بلافاصله خارج می‌شود: `docker logs netdata` را بخوانید. خطای رایج، mount نبودن `/proc` یا `/sys` ، یا اجرای دوباره با همان نام است. برای ساخته شدن دوباره:

```bash
docker rm -f netdata
```

بعد همان `docker run` این صفحه را تکرار کنید. `rm -f` فقط وقتی است که نام قفل شده و کانتینر مال همین نصب است، نه یک کانتینر ناشناس هم‌نام.

UI از لوکال 200 است و از شبکه timeout: فایروال. `sudo ufw status verbose` باید اجازه از `10.10.0.0/16` را نشان بدهد و نباید `Anywhere` روی 19999 باشد.

نمودار CPU خالی است ولی کانتینر بالاست: احتمالاً `--pid=host` جا افتاده. `docker inspect netdata` را ببینید و اگر pid میزبان نیست، کانتینر را با دستور کامل از نو بسازید. وسط راه فلگ را با edit دستی نصف نکنید.

kickstart وسط کار از شما اتاق ابری خواست: لغو کنید. اگر قبلاً Enter زده‌اید و توکن داده‌اید، آن عامل را claim‌شده حساب کنید. توکن را بچرخانید در همان جایی که صادر شده، و عامل را بدون توکن دوباره نصب کنید. این صفحه فلگ حذف claim را از خودش نمی‌نویسد چون نباید رشتهٔ حدسی به اسکریپت بدهید.

نسخه در `docker ps` برابر `latest` است: کسی دستور را بدون برچسب اجرا کرده. کانتینر را حذف و با `v2.11.1` بسازید. دادهٔ نمودار محلی داخل volumeهای نام‌دار می‌ماند.

## Best Practices

- یک روش نصب، نه داکر و kickstart با هم روی یک میزبان.
- برچسب `netdata/netdata:v2.11.1` یا نسخه‌ای که kickstart واقعاً چاپ کرده و شما در یادداشت نوشته‌اید.
- اسکریپت را با `less` بخوانید، بعد `sh`. هرگز `curl | sh`.
- توکن claim ندهید و UI را با فایروال به شبکهٔ مدیریت محدود کنید.
- سوکت داکر را پیش‌فرض هر میزبان نکنید.
- Netdata را ابزار هشدار شبانه حساب نکنید. برای آن Prometheus هست.
