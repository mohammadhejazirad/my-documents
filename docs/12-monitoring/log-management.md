# مدیریت لاگ

## مقدمه

لاگ اگر سیاست نگهداری نداشته باشد خودش حادثه است. این صفحه روی Ubuntu Server 26.04 سه جا را مشخص می‌کند: journald که منبع اصلی سرویس‌های systemd است، rsyslog اگر هنوز روی ماشین نصب باشد و فایل‌های سنتی `/var/log` را پر کند، و logrotate برای فایلی که خود برنامه باز نگه می‌دارد، مثل access log در Nginx. خواندن روزمرهٔ journal در [journalctl](/docs/01-linux/journalctl) است. این‌جا تصمیم نگهداری و اشتباه خطرناک `rm` است.

میزبان نمونه وقتی مثال Nginx می‌زنیم پروکسی است: `proxy.example.internal` روی `10.10.1.5`. سیاست حجم journal برای هر میزبان آزمایشگاه یکی است تا شیفت مجبور نباشد هر سرور را از حفظ باشد.

## مفهوم اصلی

journald لاگ ساخت‌یافته را خودش می‌نویسد. اگر پایداری روشن باشد فایل‌ها زیر `/var/log/journal` هستند. اگر نباشند، زیر `/run/log/journal` می‌مانند و با reboot از بین می‌روند. برای سرور تولید، از دست رفتن لاگ بعد از reboot یعنی نفهمیدن این‌که قبل از خاموشی چه شده. `Storage=persistent` این را عوض می‌کند.

سقف را هم همان‌جا می‌گذارید. بدون سقف، journal تا پر شدن دیسک رشد می‌کند و بعد ابزارهایی که خودشان باید علت را بگویند دیگر اجرا نمی‌شوند. `SystemMaxUse` سقف حجم است. `MaxRetentionSec` سقف زمان است. هر کدام زودتر برسد همان اعمال می‌شود.

rsyslog یک دیمون جداست که هنوز روی خیلی از نصب‌های Ubuntu Server فایل متنی می‌سازد: معمولاً `/var/log/syslog` و `/var/log/auth.log`. systemd دیگر برای کارکردن به rsyslog نیاز ندارد. اگر بسته نصب است، آن فایل‌ها واقعی‌اند و logrotate توزیع معمولاً همان‌ها را می‌چرخاند. اگر بسته نصب نیست، نبودن `/var/log/syslog` خرابی نیست. دنبال کردنش به‌عنوان «لاگ پاک شده» وقت تلف کردن است. اول بپرسید سرویس هست یا نه.

Nginx به‌طور پیش‌فرض به journal نمی‌نویسد. فایل `/var/log/nginx/access.log` را باز می‌کند و همان توصیف‌گر فایل را نگه می‌دارد. logrotate باید فایل را عوض کند و بعد به Nginx بگوید توصیف‌گر را دوباره باز کند. سیگنال این کار در بستهٔ Ubuntu با `invoke-rc.d nginx rotate` است. اگر فایل را با `rm` پاک کنید، دایرکتوری خالی به نظر می‌رسد و دیسک آزاد نمی‌شود، چون پروسه هنوز inode حذف‌شده را باز دارد. `df` پر می‌ماند و `du` آن فایل را دیگر نمی‌بیند. این اختلاف علامت کلاسیک همان اشتباه است.

`truncate -s 0` روی فایلی که پروسه باز دارد inode را نگه می‌دارد و حجم را صفر می‌کند. این برای آزاد کردن فوری جا درست‌تر از `rm` است، به شرطی که بدانید کدام فایل است. بعدش باید logrotate درست شود تا فردا دوباره به همان جا نرسید.

## چرا استفاده می‌شود؟

پر شدن دیسک به‌خاطر لاگ، SSH را هم می‌کشد. ورود تعاملی گاهی به نوشتن روی دیسک نیاز دارد و وقتی `/` صددرصد است نشست تازه می‌میرد. مسیر نجات از کنسول هایپروایزر است و در [سرور از شبکه دیده نمی‌شود](/docs/14-troubleshooting/server-down) و [دیسک پر](/docs/14-troubleshooting/disk-full) آمده. این صفحه باید جلوی رسیدن به آن نقطه را بگیرد.

لاگ بی‌سقف هم در حادثه بی‌فایده است. اگر همه‌چیز را نگه دارید، جست‌وجو کند می‌شود و دیسک می‌میرد. اگر همه را پاک کنید، علت دیروز را ندارید. ۱۴ روز برای لاگ دسترسی Nginx در آزمایشگاه تعادل قابل دفاعی است. سازمان اگر ممیزی بلندتر می‌خواهد، باید دیسک و مقصد بایگانی جدا داشته باشد، نه این‌که rotate را بی‌نهایت کند.

## Architecture

```text
سرویس systemd (ssh، nginx اگر به journal برود، برنامهٔ unit)
        │
        ▼
systemd-journald
        ├── /run/log/journal     فقط تا reboot ، اگر persistent نباشد
        └── /var/log/journal     اگر Storage=persistent
                │
                │  اختیاری، اگر بسته نصب باشد
                ▼
            rsyslog
                ├── /var/log/syslog
                └── /var/log/auth.log
                        │
                        ▼
                    logrotate   روزانه، با فشرده‌سازی

Nginx (پروسهٔ master/worker)
        │  توصیف‌گر باز
        ▼
/var/log/nginx/access.log
        │
        ▼
logrotate  →  فایل تازه  →  nginx rotate  →  باز کردن دوبارهٔ توصیف‌گر
```

دو سیاست را روی یک فایل سوار نکنید. اگر هم rsyslog و هم یک قانون دست‌ساز logrotate یک مسیر را بچرخانند، رفتار حذف و فشرده‌سازی غافلگیرکننده می‌شود. قبل از نوشتن فایل تازه، ببینید همان glob در `/etc/logrotate.d` هست یا نه.

## Installation

journald با systemd هست. نصب نمی‌خواهد. rsyslog را فقط بررسی کنید. اگر نیست، برای «داشتن syslog کلاسیک» نصبش نکنید مگر برنامه‌ای دارید که فقط به سوکت syslog حرف می‌زند و نمی‌خواهید آن برنامه را عوض کنید.

```bash
systemctl is-active systemd-journald
systemctl is-active rsyslog || true
dpkg -l rsyslog || true
```

اگر rsyslog فعال باشد خروجی `is-active` برابر `active` است. اگر واحد وجود نداشته باشد، دستور با `|| true` اسکریپت را نمی‌ترکاند و شما می‌دانید فایل سنتی را نباید فرض کنید.

logrotate هم روی Ubuntu Server معمولاً از قبل نصب است، چون خود بسته‌ها فایل زیر `/etc/logrotate.d` می‌گذارند.

```bash
logrotate --version
ls -l /etc/logrotate.d/nginx
```

اگر فایل nginx از بسته وجود دارد، همان را ویرایش کنید. یک فایل دوم با همان glob نسازید.

## Configuration

سقف journal را در drop-in بگذارید تا ارتقای بسته، فایل اصلی `/etc/systemd/journald.conf` را با نظر شما قاطی نکند.

```ini
[Journal]
Storage=persistent
Compress=yes
SystemMaxUse=500M
MaxRetentionSec=14day
```

مسیر فایل: `/etc/systemd/journald.conf.d/size.conf`. پوشه را بسازید اگر نیست.

```bash
sudo install -d -m 0755 /etc/systemd/journald.conf.d
sudoedit /etc/systemd/journald.conf.d/size.conf
sudo systemctl restart systemd-journald
journalctl --disk-usage
```

restart کردن journald اتصال نوشتن را لحظه‌ای قطع می‌کند و سرویس‌های دیگر را reboot نمی‌کند. بعد از restart یک خط آزمایشی از یک واحد کم‌اهمیت بگیرید و مطمئن شوید `journalctl -n 5` هنوز می‌خواند. `SystemMaxUse=500M` سیاست این آزمایشگاه است، نه پیش‌فرض بالادست. اگر میزبان دیسک ۲۰ گیگابایتی دارد، ۵۰۰ مگابایت برای journal زیاد نیست. اگر چند سرویس پرگو دارید، حجم را با `--disk-usage` هفتگی دوباره ببینید.

برای Nginx، محتوای هدف فایل `/etc/logrotate.d/nginx` این است. اگر بسته همین مسیر را ساخته، `invoke-rc.d nginx rotate` را حفظ کنید. آن دستور همان reopen است.

```text
/var/log/nginx/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 www-data adm
    sharedscripts
    postrotate
        if [ -d /etc/logrotate.d/httpd-prerotate ]; then
            run-parts /etc/logrotate.d/httpd-prerotate
        fi
        invoke-rc.d nginx rotate >/dev/null 2>&1
    endscript
}
```

`delaycompress` یعنی فایل دیروز هنوز متن است و فایل‌های قدیمی‌تر فشرده‌اند. در حادثه، لاگ دیروز را بدون `zcat` می‌خوانید. `missingok` یعنی اگر یک روز فایل نبود، logrotate خطا نمی‌دهد. `notifempty` فایل خالی را نمی‌چرخاند. `create 0640 www-data adm` فایل تازه را با مالکی می‌سازد که workerهای Nginx بتوانند بنویسند. اگر کاربر Nginx روی این میزبان چیز دیگری است، همان را بگذارید. با `ps aux | grep nginx` کاربر worker را ببینید، حدس نزنید.

آزمون نحو بدون چرخاندن واقعی:

```bash
sudo logrotate -d /etc/logrotate.d/nginx
```

خروجی طولانی است. دنبال خط خطا بگردید. جملهٔ این‌که هنوز لازم نیست بچرخد، شکست نیست.

rsyslog را اگر فعال است دستکاری گسترده نکنید. فایل‌هایش را بشناسید.

```bash
systemctl is-active rsyslog
ls -l /var/log/syslog /var/log/auth.log
```

چرخش این دو معمولاً از `/etc/logrotate.d/rsyslog` خود بسته می‌آید. فقط وقتی آن فایل را عوض کنید که سیاست زمان سازمان با پیش‌فرض فرق دارد، و همان موقع `logrotate -d` بگیرید.

## Production Example

دیسک پروکسی پر شده و بزرگ‌ترین مصرف‌کننده `/var/log/nginx/access.log` است. کسی پیشنهاد می‌کند `rm` کنید تا سایت برگردد.

### نشانه

`df -h /` نزدیک صددرصد است. `du -sh /var/log/nginx` چند گیگابایت نشان می‌دهد. سایت هنوز بالا است یا تازه خطا می‌دهد. SSH کند است یا نشست تازه نمی‌سازد.

### فرضیه

یا logrotate نیست یا سیگنال reopen نمی‌رود و Nginx روی فایل قدیمی می‌نویسد، یا یک بار قبلاً فایل را پاک کرده‌اند و inode حذف‌شده هنوز باز است و `du` آن را نشان نمی‌دهد. در نشانهٔ بالا `du` فایل را می‌بیند، پس فرض اول محتمل‌تر است. فرض دوم را هم با یک دستور رد کنید تا دو مشکل روی هم نماند.

### دستور مشاهده

```bash
df -h /
sudo du -sh /var/log/nginx
sudo lsof +L1 | head
ls -l /etc/logrotate.d/nginx
sudo logrotate -d /etc/logrotate.d/nginx
```

اگر `lsof +L1` خطی برای nginx با ستون LINKCNT برابر 0 نشان بدهد، یک فایل حذف‌شده هنوز باز است. نمونه:

```text
nginx  912 www-data  6w  REG  8,1  2147483648  0  123456 /var/log/nginx/access.log (deleted)
```

عدد بایت همان جایی است که `df` اشغال می‌بیند و `du` دیگر به اسم قدیمی نشان نمی‌دهد. اگر چنین خطی نیست، فایل روی دیسک واقعاً بزرگ است و باید بچرخد یا موقت خالی شود.

### تصمیم

فایل حذف‌شدهٔ باز: `rm` دوباره هیچ اثری ندارد. باید پروسه توصیف‌گر را ببندد، یعنی reopen، یا در بدترین حالت سرویس reload شود. پاک کردن دوباره اتلاف وقت است.

فایل موجود خیلی بزرگ و logrotate سالم: یک بار چرخش اجباری کافی است، به شرطی که postrotate واقعاً Nginx را خبر کند.

logrotate خطا می‌دهد: اول نحو را درست کنید، بعد چرخش اجباری. `rm` را به‌عنوان میان‌بر انتخاب نکنید.

### اصلاح

اگر inode حذف‌شده باز است، reopen بدون پاک کردن مجدد:

```bash
sudo invoke-rc.d nginx rotate
sudo lsof +L1 | head
df -h /
```

بعد از reopen باید آن خط deleted از `lsof` برود و `df` جا را پس بگیرد.

اگر فایل سر جایش بزرگ است و باید همین حالا جا آزاد شود، صفر کردنش inode را حفظ می‌کند:

```bash
sudo truncate -s 0 /var/log/nginx/access.log
df -h /
```

این کار محتوای همان فایل را دور می‌ریزد. فقط وقتی مجاز است که جا برای برگشتن SSH یا سرویس لازم است و کپی کردنش روی دیسک ممکن نیست. بعد بلافاصله قانون rotate را درست کنید.

چرخش عادی، وقتی دیسک هنوز کمی جا دارد و می‌خواهید لاگ بماند:

```bash
sudo logrotate -f /etc/logrotate.d/nginx
ls -lh /var/log/nginx
```

`-f` حتی اگر امروز چرخیده باشد دوباره می‌چرخاند. در تولید فقط وقتی بزنید که دلیلش همین حادثه است، نه به‌عنوان آزمایش کنجکاوی روی تنها دیسک پر.

### جلوگیری از تکرار

`logrotate -d` را بعد از هر تغییر فایل nginx سبز کنید. یک بار فردا `ls -lh /var/log/nginx` را ببینید که `access.log` کوچک است و `access.log.1` ساخته شده. اگر فردا فایل اصلی همچنان چند گیگابایت است، Nginx توصیف‌گر را عوض نکرده. `postrotate` را دوباره بخوانید.

سقف journal را هم همان هفته چک کنید تا حادثهٔ بعدی به‌جای nginx از journal بیاید و غافلگیرتان کند.

```bash
journalctl --disk-usage
```

باید زیر سقفی باشد که در drop-in نوشته‌اید، با کمی اختلاف به‌خاطر فشرده‌سازی و زمان اعمال.

## Security Notes

`/var/log/auth.log` و journal واحد `ssh` حاوی نام کاربر و IP مبدأ هستند. `chmod 777` برای این‌که یک برنامه بتواند بخواند، آن را به هر کاربر محلی می‌دهد. گروه `adm` روی Ubuntu همان گروهی است که اجازهٔ خواندن لاگ را دارد. کاربر انسانی `ops` اگر باید لاگ بخواند عضو `adm` شود، نه این‌که فایل‌ها جهان‌خوان شوند.

لاگ دسترسی Nginx ممکن است URL با توکن یا مسیر حساس داشته باشد اگر برنامه اشتباه کرده باشد. چرخاندن و فشرده‌سازی این را پاک نمی‌کند. ۱۴ روز نگهداری یعنی ۱۴ روز از آن توکن روی دیسک است. درمان درست، ننوشتن توکن در URL است. تا آن روز، دسترسی فایل همان `0640` بماند.

لاگ را به تیکت عمومی کاربران نچسبانید. برای حادثه، بازهٔ زمانی و شناسهٔ درخواست را بردارید.

پاک کردن لاگ برای پنهان کردن یک ورود، کار این صفحه نیست و در عملیات عادی هم دستور پیشنهادی نیست. اگر به حذف به‌خاطر نشت یک راز نیاز شد، همان فایل را با اطلاع مسئول امنیت صفر کنید و واقعه را ثبت کنید. `rm` مخفیانه هم دیسک را لزوماً آزاد نمی‌کند و هم رد حادثه را خراب می‌کند.

## Troubleshooting

`journalctl` می‌گوید no persistent journal: drop-in خوانده نشده یا سرویس restart نشده. `systemd-analyze cat-config systemd/journald.conf` پیکربندی مؤثر را نشان می‌دهد. اگر `Storage=persistent` در خروجی هست و هنوز پوشه ساخته نشده، یک بار `sudo systemctl restart systemd-journald` و بعد `ls /var/log/journal`.

`logrotate -d` می‌گوید duplicate log entry: دو فایل در `/etc/logrotate.d` یک glob را دارند. یکی را بردارید. معمولاً فایل دست‌ساز اضافه است و فایل بسته باید بماند.

Nginx بعد از rotate دیگر نمی‌نویسد: فایل تازه مالک غلط دارد. worker با کاربر `www-data` باید بتواند بنویسد. `ls -l /var/log/nginx/access.log` را با کاربر worker مقایسه کنید. `create` را درست کنید و یک بار rotate اجباری بگیرید.

`du` و `df` اختلاف زیاد دارند: همان `lsof +L1`. اگر ابزار `lsof` نبود، بسته `lsof` را نصب کنید. تا آن موقع `/proc` را برای توصیف‌گرهای deleted بگردید فقط اگر با این روش آشنا هستید. نصب `lsof` در حادثهٔ دیسک پر ممکن است خودش به‌خاطر نبود جا شکست بخورد. اول با truncate یا reopen جا آزاد کنید، بعد بسته نصب کنید.

rsyslog فعال است ولی `/var/log/syslog` رشد وحشتناک دارد: یک سرویس در حلقه خطا می‌نویسد. چرخاندن به‌تنهایی علت را خاموش نمی‌کند. `journalctl -p err -n 50` را ببینید و سرویس پرسروصدا را آرام کنید. وگرنه فردا فایل چرخیده‌شده هم بزرگ است.

## Best Practices

- journal را persistent کنید و برایش سقف حجم و سقف زمان بگذارید.
- قبل از فرض کردن `/var/log/syslog` ، `systemctl is-active rsyslog` را بپرسید.
- فایل لاگی که پروسه باز نگه می‌دارد با logrotate و سیگنال reopen مدیریت می‌شود، نه با `rm`.
- اگر باید فوری جا آزاد شود، `truncate -s 0` روی همان فایل شناخته‌شده، بعد اصلاح rotate.
- دو قانون logrotate برای یک glob ننویسید.
- `logrotate -d` بعد از ویرایش، و یک نگاه روز بعد به اندازهٔ فایل.
- خواندن محتوا با `journalctl` است. این صفحه جای آن دستورها را تکرار نمی‌کند.
- لاگ جهان‌خوان نباشد. گروه `adm` برای انسان عملیات کافی است.
