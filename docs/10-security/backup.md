# بکاپ سرور

## مقدمه

بکاپ آخرین لایهٔ سخت‌سازی است، چون لایه‌های قبلی را اگر غلط اعمال کنید هنوز باید بتوانید برگردید، و چون خود بکاپ اگر راز را جهان‌خوانا کپی کند همان لایه‌ها را دور می‌زند. این صفحه می‌گوید چه چیزی از میزبان برداشته شود، با `rsync` به دیسک دوم یا به سرور پایش `10.10.1.40` برود، و بازیابی را همان هفته آزمایش کنید.

دیتابیس را از `/var/lib` در حال اجرا کپی نمی‌کنیم. فایل زندهٔ InnoDB یا PostgreSQL وسط نوشتن، روی مقصد ممکن است بالا نیاید. مسیر درست، ابزاری است که خود موتور دارد، مثل `mysqldump` یا `pg_dump`، و بعد `rsync` همان خروجی. اسکریپت آماده‌تر با قفل و لاگ در [اسکریپت بکاپ](/docs/13-automation/script-backup) است. این صفحه دستور دستی قابل اجرا را دارد تا قبل از آن اسکریپت هم بدانید چه چیزی باید داخلش باشد.

قانون ۳-۲-۱ را با زبان آزمایشگاه می‌گوییم، نه با شعار. سه نسخه، دو گونه رسانه، یک نسخه بیرون از خود سرور.

## مفهوم اصلی

نسخهٔ اول خود دادهٔ زنده است و بکاپ حساب نمی‌شود. نسخهٔ دوم باید روی رسانهٔ دیگر باشد تا سوختن یک دیسک هر دو را نبرد. نسخهٔ سوم باید از خود میزبان جدا باشد تا حذف و باج‌افزار و `rm` روی همان ماشین، همهٔ نسخه‌ها را با هم نبرد.

در این آزمایشگاه:

| نسخه | کجا | چه رسانه‌ای |
| --- | --- | --- |
| زنده | دیسک سیستم همان میزبان | دیسک اصلی، بکاپ نیست |
| دوم | دیسک دوم سوارشده روی `/mnt/backup-disk` | دیسک دیگر، همان اتاق و همان میزبان |
| سوم | `ops@10.10.1.40:/var/backups/hosts/...` | ماشین دیگر، `mon-1` |

این سه نسخه است، روی دو گونه رسانه (دیسک محلی دوم، و دیسک یک میزبان دیگر)، و یک نسخه بیرون از سرور اصلی. `mon-1` ساختمان دیگری نیست. اگر اتاق بسوخت، هم میزبان و هم احتمالاً دیسک دوم و شاید خود پایش می‌سوزد. قانون را در آزمایشگاه این‌طور صادقانه می‌خوانیم: از خود سرور جداست، از شهر جدا نیست. سازمان واقعی هنوز یک نسخه بیرون از این اتاق لازم دارد. تا آن روز، همین طرح از «هیچ بکاپ» بهتر است و شما را گول نمی‌زند که اتاق دوم دارید.

چه چیزی برداشته می‌شود:

- `/etc` پیکربندی، واحد systemd، کلید میزبان SSH، و drop-inهای همین فصل.
- `/opt/apps` برنامه، Compose، و `.env`. این درخت راز دارد.
- `/home` کلید و یادداشت `ops` و در صورت وجود `deploy`. راز دارد.
- خروجی دامپ دیتابیس زیر `/var/backups/db` که خودتان با ابزار موتور ساخته‌اید.

چه چیزی برداشته نمی‌شود:

- `/var/lib/mysql` و `/var/lib/postgresql` و `/var/lib/mongodb` و دادهٔ زندهٔ Redis، تا وقتی موتور در حال اجراست.
- `/proc` و `/sys` و `/dev` و `/run` و `/tmp`.
- کش بستهٔ apt و ایمیج داکر. ایمیج را رجیستری دوباره می‌دهد اگر شناسه را پاک نکرده باشید. رجیستری خودش بکاپ جدا می‌خواهد و این صفحه جای آن نیست.

اگر مجبورید خود دایرکتوری داده را بردارید، موتور را متوقف کنید، کپی کنید، بعد روشن کنید. این پنجرهٔ تعمیر است نه کار شبانه. کار شبانه دامپ است.

## چرا استفاده می‌شود؟

سخت‌سازی جلوی خیلی از حذف‌ها را نمی‌گیرد. یک `chmod -R` غلط، یک دیسک پر، یک به‌روزرسانی بد، و یک اسکریپت که `.env` را خالی می‌کند، همه فایل را از بین می‌برند در حالی که فایروال سبز است. بدون بکاپ، تنها راه ساختن دوباره از حافظه است. بدون آزمایش بازیابی، بکاپ یک پوشه است که شاید خالی یا ناقص باشد و روز حادثه این را می‌فهمید.

`rsync` اینجا ابزار کپی است چون اختلاف را می‌فرستد، مالک و مجوز را با پرچم درست نگه می‌دارد، و روی SSH به `mon-1` می‌رود. ابزار تصویر دیسک جای دیگری به درد می‌خورد. برای `/etc` و خانه و دامپ، `rsync` کافی و قابل فهم است.

## Architecture

```text
app-1 یا db-1 یا هر میزبان
    /etc
    /opt/apps
    /home
    /var/backups/db     ← فقط خروجی mysqldump یا pg_dump
            │
            ├── rsync  →  /mnt/backup-disk/app-1/
            │
            └── rsync روی SSH  →  ops@10.10.1.40:/var/backups/hosts/app-1/

عمداً خارج از کپی زنده:
    /var/lib/mysql
    /var/lib/postgresql

بازیابی آزمایشی، هر هفته یک فایل کوچک
بازیابی دامپ، داخل پایگاه موقتی نه روی پایگاه زنده
```

مقصد روی `mon-1` باید از قبل وجود داشته باشد و مجوزش محدود باشد. `mon-1` با این کار جعبهٔ راز همهٔ میزبان‌ها می‌شود. SSH به آن همان قدر مهم است که SSH به `db-1`. صفحهٔ SSH همان drop-in را آنجا هم می‌خواهد، با `AllowUsers ops`، بدون کاربر اضافه.

## Installation

`rsync` را روی مبدأ و روی `mon-1` نصب کنید:

```bash
sudo apt update
sudo apt install rsync
rsync --version
```

شماره را از خروجی همین دستور بردارید. دیسک دوم را سوار کنید. نام دستگاه را از `lsblk` بردارید نه از این صفحه. نمونهٔ نقطهٔ سوار شدن:

```bash
lsblk -o NAME,PATH,SERIAL,FSTYPE,UUID
ls -l /dev/disk/by-id
sudo mkdir -p /mnt/backup-disk
```

نام داخل `/dev/disk/by-id` که به دیسک دوم اشاره می‌کند را در `sudo mount` بگذارید. این صفحه آن نام را نمی‌نویسد چون به سریال دیسک شما بستگی دارد. از `/dev/sdb` در فایل دائمی استفاده نکنید چون بعد از بوت ممکن است اسم جابه‌جا شود. خط `/etc/fstab` را با UUID همان خروجی `lsblk` بگذارید، بعد از سوار کردن یک بار `sudo mount -a` را امتحان کنید. اگر دیسک دوم ندارید، همان نسخهٔ `mon-1` را همین هفته راه بیندازید و نبود دیسک دوم را در یادداشت میزبان بنویسید. آن وقت قانون دو رسانه ناقص است و باید بدانید.

روی `mon-1`:

```bash
sudo install -d -m 700 -o ops -g ops /var/backups/hosts
sudo install -d -m 700 -o ops -g ops /var/backups/hosts/app-1
```

کلید `ops` از مبدأ به `mon-1` باید از قبل کار کند. ورود با رمز را باز نکنید تا بکاپ راحت شود.

## Configuration

دامپ را روی خود `db-1` بگیرید، آنجا که سوکت محلی و کاربر سیستم دیتابیس هست. PostgreSQL 18 با کاربر `postgres`. این دستور فایل سفارشی فشرده می‌سازد و دادهٔ زنده را فایل‌به‌فایل کپی نمی‌کند:

```bash
sudo install -d -m 700 -o postgres -g postgres /var/backups/db
sudo -u postgres pg_dump -Fc -d app -f /var/backups/db/app.dump
sudo chown root:root /var/backups/db/app.dump
sudo chmod 600 /var/backups/db/app.dump
```

اگر نام پایگاه `app` نیست، نام واقعی را از `sudo -u postgres psql -c '\l'` بگذارید. MySQL 8.4 روی همین آزمایشگاه اگر با سوکت مدیر محلی وارد می‌شود:

```bash
sudo install -d -m 700 /var/backups/db
sudo mysqldump --single-transaction --routines --databases app | sudo tee /var/backups/db/app.sql >/dev/null
sudo chmod 600 /var/backups/db/app.sql
```

`--single-transaction` برای InnoDB یک دید پایدار می‌گیرد و جدول را برای مدت دامپ قفل سراسری نمی‌کند. این هنوز کپی فایل `/var/lib/mysql` نیست. اگر `sudo mysql` روی میزبان شما کار نمی‌کند، روش حساب محلی همان صفحهٔ MySQL فصل دیتابیس است. گذرواژه را در خط فرمان و در تاریخچه نگذارید.

کپی به دیسک دوم. مسیرها را جدا می‌زنیم تا قانون اسلش `rsync` غافلگیرتان نکند. `--delete` روی مقصد بکاپ یعنی فایلی که روی مبدأ پاک شده روی بکاپ هم پاک شود. برای دیسک دوم این رفتار را می‌خواهیم تا بکاپ آینهٔ امروز باشد، ولی بدانید حذف اشتباه هم آینه می‌شود. نسخهٔ `mon-1` در این صفحه بدون `--delete` است تا یک پاک‌سازی عجول، همان روز نسخهٔ بیرون را هم خالی نکند. این تفاوت عمدی است.

```bash
sudo mkdir -p /mnt/backup-disk/app-1
sudo rsync -aHAX --numeric-ids \
  /etc/ /mnt/backup-disk/app-1/etc/
sudo rsync -aHAX --numeric-ids \
  /opt/apps/ /mnt/backup-disk/app-1/opt/apps/
sudo rsync -aHAX --numeric-ids \
  /home/ /mnt/backup-disk/app-1/home/
sudo rsync -aHAX --numeric-ids \
  /var/backups/db/ /mnt/backup-disk/app-1/var/backups/db/
```

به `mon-1`، از خود مبدأ، با کلید `ops`. `--relative` نیست. هر درخت جدا است تا مقصد قاطی نشود:

```bash
rsync -aHAX --numeric-ids \
  -e "ssh -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes" \
  /etc/ ops@10.10.1.40:/var/backups/hosts/app-1/etc/
rsync -aHAX --numeric-ids \
  -e "ssh -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes" \
  /opt/apps/ ops@10.10.1.40:/var/backups/hosts/app-1/opt/apps/
rsync -aHAX --numeric-ids \
  -e "ssh -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes" \
  /home/ ops@10.10.1.40:/var/backups/hosts/app-1/home/
rsync -aHAX --numeric-ids \
  -e "ssh -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes" \
  /var/backups/db/ ops@10.10.1.40:/var/backups/hosts/app-1/var/backups/db/
```

این دستورها را با کاربر `ops` بزنید اگر آن کاربر آن مسیرها را می‌خواند، یا با `sudo` اگر باید. اگر با `sudo rsync` به SSH می‌روید، کلید root استفاده می‌شود نه کلید `ops`. ساده‌تر این است که `ops` با ACL یا گروه، خواندن بکاپ را داشته باشد و `sudo` فقط برای ساخت دامپ باشد. اگر `rsync` روی `/etc/shadow` به خطای مجوز خورد، همان فایل را جا نیندازید و بی‌خیب نشوید. `/etc/shadow` بخشی از برگرداندن حساب‌هاست و باید در بکاپ باشد. پس دستور مسیر `/etc` را با مجوزی بزنید که shadow را بخواند، و مقصد را `700` نگه دارید.

اسکریپت زمان‌بندی‌شده، قفل، و لاگ را در [اسکریپت بکاپ](/docs/13-automation/script-backup) بسازید. تا آن فایل در مخزن دانشنامه هست، منطق «چه چیز کپی شود» همین صفحه است و آن اسکریپت نباید `/var/lib` زنده را اضافه کند.

## Production Example

روی `app-1` دیسک دوم و `mon-1` هر دو امروز کپی گرفته‌اند. آزمایش بازیابی را روی یک فایل بی‌خطر انجام دهید، نه با برگرداندن کل `/etc` روی میزبان زنده.

روی `app-1`:

```bash
mkdir -p /tmp/restore-test
rsync -a \
  -e "ssh -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes" \
  ops@10.10.1.40:/var/backups/hosts/app-1/etc/hostname \
  /tmp/restore-test/hostname
cmp /etc/hostname /tmp/restore-test/hostname && printf '%s\n' "hostname matches"
rm -rf /tmp/restore-test
```

اگر `cmp` ساکت بماند و خط بعدی چاپ شود، این یک فایل از نسخهٔ سوم واقعاً خوانده می‌شود. این کل بازیابی نیست. هفتهٔ بعد یک فایل از `/etc/ssh/sshd_config.d/` را همین‌طور مقایسه کنید. ماهی یک بار، دامپ را در پایگاه موقتی بریزید.

برای PostgreSQL، پایگاه تمرین را روی `db-1` بسازید و بعد پاک کنید. این دستور دادهٔ زندهٔ `app` را بازنویسی نمی‌کند چون مقصد اسم دیگری است:

```bash
sudo -u postgres createdb app_restore_test
sudo -u postgres pg_restore -d app_restore_test /var/backups/db/app.dump
sudo -u postgres psql -d app_restore_test -c '\dt'
sudo -u postgres dropdb app_restore_test
```

اگر `pg_restore` خطا داد، بکاپ آن شب به‌درد نمی‌خورد حتی اگر حجم فایل بزرگ باشد. برای MySQL همان ایده با پایگاه جدا:

```bash
sudo mysql -e "CREATE DATABASE app_restore_test"
sudo mysql app_restore_test < /var/backups/db/app.sql
sudo mysql -e "DROP DATABASE app_restore_test"
```

این را روی سرور تولید فقط وقتی بزنید که جا و I/O دارید. ساعت اوج را انتخاب نکنید. اگر دامپ بزرگ است، تمرین را روی یک نسخهٔ همان موتور در آزمایشگاه بزنید، نه روی `db-1` شلوغ. مهم این است که یک بار واقعاً restore شده باشد، نه اینکه فایل `.sql` فقط وجود داشته باشد.

برگرداندن فاجعه، وقتی میزبان مرده، یعنی نصب تازه، بعد `rsync` از `mon-1` به `/etc` و `/opt/apps` و `/home`، بعد دامپ در موتور، بعد باز کردن SSH فقط وقتی `sshd -t` سبز است. آن روز روز خواندن این صفحه است. اگر تمرین `cmp` را نکرده باشید، آن روز می‌فهمید کلید SSH به `mon-1` فقط روی همان میزبان مرده بوده است. کلید خواندن بکاپ را یک جای دوم، در اختیار `ops`، نگه دارید.

## Security Notes

`/etc` و `/home` و `.env` راز دارند: کلید میزبان، `shadow`، کلید خصوصی، توکن رجیستری داخل `config.json`. مقصد `700` و مالک `ops` حداقل است. یک اشتراک NFS با `no_root_squash` و مجوز `777` بکاپ را به همهٔ آزمایشگاه نشان می‌دهد. چنین مقصدی نسازید.

`mon-1` را مثل میزبان دیتابیس سخت کنید: SSH فقط کلید، UFW فقط از شبکهٔ مدیریت به پورت `22`، و هیچ سرویس وب عمومی برای «دانلود راحت بکاپ». راحت، یعنی راز روی HTTP.

`--delete` را روی تنها نسخهٔ بیرون روشن نکنید. دیسک دوم می‌تواند آینه باشد چون نسخهٔ سوم هنوز هست. اگر فقط یک مقصد دارید، `--delete` را نگذارید تا حذف مبدأ، آخرین نسخه را هم نبرد.

دامپ را در `/tmp` نگذارید. `/tmp` اغلب پاک می‌شود و گاهی برای همه قابل فهرست است. مسیر `/var/backups/db` با `700` جای دامپ است.

کپی زندهٔ `/var/lib/mysql` را حتی «کنار دامپ، احتیاط اضافه» نگیرید و بعد از آن برای بازیابی استفاده نکنید. یک فایل ناسازگار که کسی فکر می‌کند سالم است، از نبود فایل بدتر است، چون بازیابی را با دادهٔ خراب تمام می‌کنید و نسخهٔ سالم دامپ را دیرتر نگاه می‌کنید.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| `rsync: mkdir ... failed: Permission denied` | روی `mon-1` پوشه را `ops` نساخته یا مجوز `700` مال کس دیگری است |
| `shadow: Permission denied` و بقیهٔ `/etc` رفته | دستور را با مجوزی بزنید که فایل محدود را بخواند، و مقصد را بازتر نکنید |
| `pg_dump: database "app" does not exist` | نام را از `\l` بردارید. نام صفحه را به زور نسازید |
| حجم دامپ صفر است | دستور خطا داده و `tee` فایل خالی ساخته. کد خروج را ببینید. `set -o pipefail` در اسکریپت لازم است. دستی، خروجی خطا را نادیده نگیرید |
| `cmp` فرق نشان می‌دهد | یا فایل بعد از بکاپ عوض شده، که طبیعی است اگر hostname را بعداً عوض کرده‌اید، یا مقصد کهنه است. زمان فایل روی `mon-1` را با `ls -l` ببینید |
| دیسک دوم پر شده و `rsync` نیمه مانده | مقصد ناقص است. جا خالی کنید و همان دستور را دوباره بزنید. نیمه‌کاره را بکاپ سالم حساب نکنید |
| بازیابی MySQL خطای جداول نیمه‌کاره می‌دهد | از دامپ `mysqldump` برنگشته‌اید. احتمالاً کسی `/var/lib/mysql` را کپی کرده. همان را دور بریزید و دامپ را دوباره بگیرید |
| از میزبان مرده به `mon-1` نمی‌رسید | کلید فقط آنجا بوده. کلید دوم را قبل از فاجعه جایی بیرون از آن میزبان بگذارید |

لاگ خود `rsync` را با `-v` یک بار در تمرین ببینید. در کار شبانه، خروجی را به فایل لاگ زیر `/var/log` بفرستید نه به ایمیل جهان‌خوانا. اسکریپت فصل اتوماسیون این را با قفل انجام می‌دهد.

## Best Practices

- سه نسخه را واقعاً بشمارید. زنده را جزو سه تا نیاورید. دیسک دوم و `mon-1` دو تای اضافه‌اند و سومی واقعی سازمان باید روزی بیرون این اتاق باشد.
- دیتابیس فقط از ابزار خودش. `/var/lib` زنده ممنوع.
- یک بار در هفته یک فایل را `cmp` کنید. یک بار در ماه دامپ را در پایگاه موقتی باز کنید.
- `--delete` فقط روی نسخه‌ای که تنها نسخه نیست.
- مجوز مقصد را مثل مبدأ راز نگه دارید. بکاپ جهان‌خوانا، سخت‌سازی را باطل می‌کند.
- وقتی این دستورها تکراری شدند، آن‌ها را به [اسکریپت بکاپ](/docs/13-automation/script-backup) ببرید، با `set -euo pipefail` و قفل. منطق حذف و شمول را آنجا شل نکنید.
