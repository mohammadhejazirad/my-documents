# Fail2ban

## مقدمه

Fail2ban لاگ شکست را می‌خواند و برای مدتی آدرس منبع را در فایروال می‌گذارد. در این آزمایشگاه فقط زندان `sshd` را روشن می‌کنیم، با backend برابر `systemd`، چون لاگ احراز روی Ubuntu 26.04 در journal است نه لزوماً در یک فایل متنی. آدرس‌های شبکهٔ مدیریت `10.10.0.0/16` در `ignoreip` هستند تا یک اشتباه از داخل آزمایشگاه، مدیر را از SSH بند نکند.

فیلتر را ساده نگه می‌داریم. فیلتر آمادهٔ بسته به نام `sshd` کافی است. فیلتر دست‌ساز با عبارت منظم طولانی، خودش را با یک تغییر کوچک در متن لاگ OpenSSH کور می‌کند و شما فکر می‌کنید حفاظت روشن است.

رمز SSH در [صفحهٔ SSH](/docs/10-security/ssh-hardening) بسته است. پایین توضیح داده شده چرا زندان هنوز برای کسی که کلید غلط می‌فرستد فایده دارد. UFW باید قبل از این صفحه روشن باشد، چون عمل ban در این پیکربندی با UFW انجام می‌شود.

## مفهوم اصلی

زندان (jail) سه چیز را به هم وصل می‌کند: کجا را نگاه کند، چه الگویی شکست است، و بعد از چند بار شکست چه کند. `maxretry` تعداد شکست در پنجرهٔ `findtime` است. اگر از آن بگذرد، آدرس برای مدت `bantime` بسته می‌شود. `ignoreip` هرگز بسته نمی‌شود.

backend برابر `systemd` یعنی Fail2ban از journalctl می‌خواند، نه از `/var/log/auth.log`. روی سروری که rsyslog ندارد همان journal منبع حقیقت است. اگر هر دو را نصف‌نیمه تنظیم کنید، زندان فایل خالی را نگاه می‌کند و journal پر از شکست است.

فیلتر `sshd` که با بسته می‌آید، خط‌های شکست احراز را می‌شناسد. شکل لاگ OpenSSH برای کلید غلط شبیه «Failed publickey» است و برای رمز غلط شبیه «Failed password». فیلتر آماده هر دو خانواده را، در حالت معمولی خودش، شکست حساب می‌کند. ما حالت عجیب و فیلتر دوم نمی‌سازیم.

`banaction = ufw` یعنی قانون موقت از همان UFW می‌آید که مدیر در `ufw status` می‌بیند. action پیش‌فرض iptables کنار UFW دو جای حقیقت می‌سازد. یکی را انتخاب کرده‌ایم: UFW.

`PerSourcePenalties` داخل خود `sshd` هم منبع بد را برای مدتی رد می‌کند. Fail2ban جای آن را نمی‌گیرد و برعکس. جریمهٔ OpenSSH داخل خود دمون است و به فایروال میزبان کاری ندارد. Fail2ban قانون فایروال می‌سازد و برای سرویس‌های دیگر هم قابل استفاده است. هر دو روشن می‌مانند. معافیت جریمهٔ OpenSSH فقط آدرس پایش است. `ignoreip` این صفحه کل شبکهٔ مدیریت است، چون قفل شدن مدیر از داخل آزمایشگاه گران‌تر از این است که یک میزبان داخلی اسکنر SSH را Fail2ban بند کند. این یک معاملهٔ آگاهانه است، نه فراموشی.

## چرا استفاده می‌شود؟

بستن رمز، حدس رمز را بی‌فایده می‌کند. این کارها را بی‌فایده نمی‌کند:

- کلاینت قدیمی یا اسکریپت غلط هنوز رمز می‌فرستد و لاگ را پر می‌کند.
- کسی کلید خصوصی لو رفته یا کلید آزمایشی را پشت سر هم امتحان می‌کند. سرور هر بار `Failed publickey` می‌نویسد.
- یک میزبان آلوده در اینترنت به پورت `22` که UFW هنوز از دنیا قبول می‌کند می‌کوبد.

بدون Fail2ban این تلاش‌ها فقط لاگ‌اند، به‌اضافهٔ جریمهٔ کوتاه `PerSourcePenalties`. با زندان `sshd`، بعد از چند شکست، UFW همان منبع را برای یک ساعت کنار می‌گذارد و بقیهٔ پورت‌های مجاز میزبان را هم از آن منبع می‌بندد. این برای اسکنر بیرون از `10.10.0.0/16` مفید است. برای داخل شبکه، `ignoreip` عمداً این اثر را خاموش کرده تا CI و مدیر گرفتار نشوند. پس فایدهٔ اصلی این صفحه جلوی سر و صدای بیرون است، نه جلوی همکار داخل آزمایشگاه.

اگر روزی SSH فقط از شبکهٔ مدیریت قابل دسترسی شود و از اینترنت به پورت `22` هیچ بسته‌ای نرسد، فایدهٔ Fail2ban کمتر می‌شود ولی صفر نمی‌شود: یک میزبان اشتباه‌پیکربندی‌شده در لبه هنوز ممکن است پورت را ببیند. هزینهٔ زندان `sshd` کم است. خاموش کردنش را به بعد از آنکه `ufw status` واقعاً پورت `22` را از اینترنت بسته نشان داد موکول کنید.

## Architecture

```text
تلاش SSH
    │
    ▼
sshd  ── journal ──►  fail2ban  زندان sshd
                         │  فیلتر آمادهٔ بسته
                         │  backend systemd
                         │  ignoreip 10.10.0.0/16 و loopback
                         ▼
                       ufw  قانون موقت روی همان منبع
                         │
                         ▼
                       بستهٔ بعدی از آن منبع، تا پایان bantime

جدا از این مسیر:
sshd خودش PerSourcePenalties دارد
معافیت آن فقط 10.10.1.40 است
```

Fail2ban به بستهٔ سالم کاری ندارد. اگر کلید `ops` درست باشد، اصلاً شکست حساب نمی‌شود. اگر از آدرس داخل `ignoreip` صد بار کلید غلط بزنید، زندان شما را نمی‌بندد. جریمهٔ خود OpenSSH هنوز ممکن است همان آدرس را برای مدت کوتاه رد کند، مگر آدرس `10.10.1.40` باشد.

## Installation

```bash
sudo apt update
sudo apt install fail2ban
sudo systemctl enable --now fail2ban
systemctl status fail2ban --no-pager
```

فایل توزیع `/etc/fail2ban/jail.conf` را ویرایش نکنید. به‌روزرسانی بسته آن را عوض می‌کند. تنظیم محلی در `/etc/fail2ban/jail.local` است و بر فایل توزیع غلبه می‌کند.

قبل از نوشتن زندان، ببینید journal واقعاً خط SSH دارد:

```bash
sudo journalctl -u ssh -n 20 --no-pager
```

اگر این دستور خالی است و SSH کار می‌کند، واحد سرویس چیز دیگری است. روی 26.04 باید `ssh` باشد. زندان را به فایل `/var/log/auth.log` برنگردانید فقط چون یک آموزش قدیمی این مسیر را دارد. اگر آن فایل نیست، زندان فایل‌محور همیشه خاموش می‌ماند.

## Configuration

`/etc/fail2ban/jail.local` را با `sudoedit` بسازید:

```ini
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 4
backend = systemd
ignoreip = 127.0.0.1/8 ::1 10.10.0.0/16
banaction = ufw

[sshd]
enabled = true
port = ssh
filter = sshd
backend = systemd
maxretry = 4
```

`port = ssh` یعنی همان پورتی که در `/etc/services` برای ssh هست، یعنی `22`. اگر پورت SSH را عوض نکرده‌اید همین درست است. `filter = sshd` فیلتر بسته است. فایل تازه‌ای در `filter.d` نسازید.

`ignoreip` شامل loopback است تا اسکریپت محلی که کلید را اشتباه می‌فرستد میزبان را از خودش جدا نکند، و شامل کل `10.10.0.0/16` است چون مدیر، runner، و پرش بین `app-1` و `docker-1` از همین محدوده می‌آیند. پایش `10.10.1.40` هم داخل همین محدوده است. این از معافیت `PerSourcePenaltyExemptList` گسترده‌تر است و عمدی است: Fail2ban مدیر را از راه دور داخل آزمایشگاه ban نمی‌کند. هزینه این است که یک ماشین آلوده داخل `10.10.0.0/16` را هم با این زندان ban نمی‌کنید. برای آن تهدید، بخش‌بندی UFW و کلید SSH مهم‌تر از این زندان است.

اعمال:

```bash
sudo fail2ban-client -t
sudo systemctl restart fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

`fail2ban-client -t` نحو را چک می‌کند. `status sshd` باید زندان را روشن نشان دهد و فهرست ban معمولاً اول کار خالی است. خالی بودن فهرست یعنی خراب بودن نیست. یک خط وضعیت که باید ببینید شبیه این است. نام زندان و عددها مهم‌اند، نه زمان دقیق:

```text
Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed:     0
|  `- File list:        systemd
`- Actions
   |- Currently banned: 0
   |- Total banned:     0
   `- Banned IP list:
```

اگر به‌جای `systemd` یک مسیر `/var/log/auth.log` دیدید، backend فایل است و روی میزبانی که آن فایل را ندارد زندان کور می‌ماند.

یک آزمایش کنترل‌شده، نه از آدرس خودتان اگر راه بازگشت ندارید. از یک میزبان بیرون از `10.10.0.0/16` که اگر قفل شد مهم نیست، چند بار با کلید غلط به SSH بزنید. بعد از چهار شکست در ده دقیقه، `status sshd` آن آدرس را نشان می‌دهد و `ufw status` یک قانون موقت دارد. آزمایش را از لپ‌تاپ روزمرهٔ داخل شبکه نکنید. `ignoreip` شما را حفظ می‌کند، ولی عادت آزمایش از تنها راه ورود عادت بدی است.

اگر آدرس آزمایشی ماند و می‌خواهید آزادش کنید:

```bash
sudo fail2ban-client set sshd unbanip 203.0.113.10
```

`203.0.113.10` آدرس مستندسازی است. آدرس واقعی آزمایش خودتان را بگذارید. آن را در فایل پیکربندی ذخیره نکنید.

## Production Example

روی `app-1` رمز SSH بسته است و CI با کلید `deploy` می‌آید. یک runner خراب که کلید را اشتباه بفرستد، از `10.10.1.30` است و داخل `ignoreip` است. Fail2ban آن را ban نمی‌کند. لاگ را هنوز می‌توانید ببینید:

```bash
sudo journalctl -u ssh --since "15 min ago" --no-pager
```

خط `Failed publickey` یعنی کسی کلید را فرستاده و سرور نپذیرفته. این همان چیزی است که فیلتر `sshd` بیرون از `ignoreip` روی آن ban می‌سازد. داخل شبکه فقط می‌بینید و خودتان تصمیم می‌گیرید آن میزبان را اصلاح کنید، نه اینکه امیدوار باشید Fail2ban همکارتان را بیرون بیندازد.

روی میزبانی که به اینترنت آدرس عمومی دارد، همان فایل کافی است. `bantime` یک ساعت است تا یک اسکنر کند شود، نه تا یک اشتباه تایپی تا فردا بماند. اگر لاگ نشان داد یک منبع بعد از آزاد شدن بلافاصله برمی‌گردد، `bantime` را در `jail.local` به `1d` ببرید و restart کنید. این را همان روز اول روی همهٔ میزبان‌ها `1d` نکنید. اول ببینید مثبت کاذب ندارید.

زندان‌های `nginx` و `recidive` را در این صفحه روشن نمی‌کنیم. هر کدام فیلتر و مثبت کاذب خودشان را دارند. وقتی زندان `sshd` یک هفته بی‌دردسر `status` می‌دهد، اگر هنوز لازم بود زندان بعدی را جدا طراحی کنید. اضافه کردن همهٔ زندان‌های فایل نمونه، صفحه را از «ساده» خارج می‌کند و اولین خطای فیلتر، اعتماد به کل Fail2ban را از بین می‌برد.

## Security Notes

`ignoreip` یک فهرست اعتماد است. هر چه بزرگ‌تر باشد، Fail2ban کم‌اثرتر است. `10.10.0.0/16` کل آزمایشگاه این دانشنامه است. آن را به `0.0.0.0/0` نرسانید. آن را به یک آدرس تکی هم کوچک نکنید اگر مدیر از چند آدرس داخل همین شبکه می‌آید، مگر اینکه همه آن آدرس‌ها را واقعاً نوشته باشید. حذف کامل `ignoreip` در شب حادثه یعنی یک اسکریپت مانیتورینگ با کلید غلط می‌تواند `ops` را هم، اگر از همان مبدأ بیاید، قفل کند. مبدأ پایش و مبدأ انسان معمولاً فرق دارند. اینجا هر دو داخل یک /16 هستند و ما آگاهانه هر دو را معاف کرده‌ایم.

`banaction = ufw` فرض می‌کند UFW فعال است. اگر کسی `ufw disable` کند، banهای بعدی جایی برای نشستن درست ندارند. فایروال را با اسکریپت خاموش نکنید.

Fail2ban رمز و کلید را قوی نمی‌کند. اگر کلید خصوصی `ops` لو برود، اتصال موفق است و زندان بیکار می‌ماند. چرخش کلید هنوز کار انسان است.

فیلتر را با کپی از یک gist عوض نکنید. فیلتر آماده با نسخهٔ بسته جلو می‌رود. فیلتر کپی‌شده همان روزی می‌شکند که متن لاگ OpenSSH یک کلمه عوض شود، و `status` هنوز زندان را روشن نشان می‌دهد.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| `status` زندان `sshd` ندارد | `jail.local` بخش `[sshd]` یا `enabled = true` را ندارد، یا `fail2ban-client -t` خطا داده و سرویس بالا نیامده |
| سرویس بالا نمی‌آید | `journalctl -u fail2ban -n 50 --no-pager` و خروجی `fail2ban-client -t` |
| شکست SSH در journal هست و ban ساخته نمی‌شود و مبدأ بیرون از آزمایشگاه است | backend هنوز فایل است. `backend = systemd` را در هر دو بخش بگذارید و restart کنید |
| خودتان ban شده‌اید | از کنسول `fail2ban-client set sshd unbanip` با آدرس خودتان. بعد آن آدرس را اگر واقعاً مدیریتی است داخل `ignoreip` بگذارید |
| UFW قانون عجیب با شمارهٔ زیاد دارد | banهای فعال. `fail2ban-client status sshd` را با `ufw status` مقایسه کنید. قانون را با دست پاک نکنید و بگذارید خود Fail2ban unban کند، وگرنه پایگاه خودش گم می‌شود |
| داخل شبکه عمداً ban نمی‌شوید | این همان `ignoreip` است، خرابی نیست |
| فکر می‌کنید کلید غلط لاگ نمی‌شود | یک بار از بیرون با `ssh -i` یک کلید بی‌ربط بزنید و `journalctl -u ssh` را ببینید. باید شکست publickey باشد |

اگر `filter = sshd` را به نام فیلتری که وجود ندارد عوض کرده باشید، زندان بالا نمی‌آید. به نام آماده برگردید. عبارت منظم تازه ننویسید.

خروجی سالم `fail2ban-client status sshd` بعد از راه‌اندازی، زندان را روشن نشان می‌دهد و فهرست بن‌شده می‌تواند خالی باشد. وقتی یک آزمایش از بیرون شبکه انجام شد، همان فهرست یک آدرس و زمان بن را نشان می‌دهد. اگر عدد شکست‌ها بالا می‌رود و فهرست بن خالی می‌ماند، یا مبدأ داخل `ignoreip` است یا فیلتر خط لاگ را نمی‌بیند. این دو را با `journalctl -u ssh` از هم جدا کنید، نه با عوض کردن `maxretry` به ۱. `maxretry` خیلی کوچک، اسکنر را زودتر می‌گیرد و اشتباه تایپی از یک آدرس بیرون شبکه را هم زودتر می‌گیرد. مقدار ۴ در ده دقیقه برای شروع کافی است.

## Best Practices

- فقط `jail.local`، فقط زندان `sshd`، فقط فیلتر بسته، فقط backend برابر systemd.
- `ignoreip` را مساوی کل اینترنت نکنید و آن را خالی نگذارید.
- ban را از روی UFW با دست پاک نکنید. از `fail2ban-client` خارج کنید تا شمارنده و قانون با هم جلو بروند.
- هفته‌ای یک بار `fail2ban-client status sshd` را ببینید. اگر همیشه خالی است، یا کسی نمی‌زند یا backend جای اشتباه را می‌خواند. یک آزمایش کنترل‌شده از بیرون شبکه این دو را از هم جدا می‌کند.
- Fail2ban را بهانهٔ باز کردن `PasswordAuthentication` نکنید. ترتیب فصل برعکس است: اول کلید، بعد فایروال، بعد این زندان.
- قدم بعدی بعد از پایدار شدن ورود و فایروال، [مجوز فایل](/docs/10-security/users-and-files) است. زندان جلوی فایل `777` را نمی‌گیرد.
