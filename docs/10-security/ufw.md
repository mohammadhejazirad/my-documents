# UFW

## مقدمه

UFW فایروال میزبان روی Ubuntu است. در این آزمایشگاه سیاست یکی است و قانون‌ها به نقش میزبان بستگی دارند: ورودی پیش‌فرض بسته، خروجی پیش‌فرض باز، و قبل از `ufw enable` حتماً اجازهٔ OpenSSH. اگر این ترتیب را عوض کنید، نشست فعلی شاید بماند و نشست بعدی دیگر ساخته نشود.

پورت `80` و `443` فقط روی پروکسی `10.10.1.5` باز می‌شوند. روی سرور دیتابیس `db-1.example.internal` (`10.10.1.20`) پورت `3306` و `5432` فقط از برنامهٔ `10.10.1.10` قبول می‌شوند. این دو جمله را روی میزبان اشتباه اجرا نکنید. کپی کردن همهٔ قانون‌ها روی همهٔ سرورها یعنی دیتابیس را روی پروکسی باز کرده‌اید و وب را روی دیتابیس.

بعد از هر تغییر، `ufw status verbose` را بخوانید. خروجی کوتاه `status` مبدأ قانون را پنهان می‌کند و همان پنهان شدن است که قانون غلط را سالم نشان می‌دهد.

## مفهوم اصلی

UFW روی خودش قانون نمی‌سازد. به netfilter می‌گوید چه بسته‌ای وارد شود. پیش‌فرض `deny incoming` یعنی هر پورتی که صریحاً اجازه ندارد از شبکه دور ریخته می‌شود. پیش‌فرض `allow outgoing` یعنی خود سرور هنوز می‌تواند به‌روزرسانی و رجیستری و DNS را بزند. بستن خروجی یک پروژهٔ جداست و اینجا انجام نمی‌شود، چون با یک قانون ناقص، DNS و NTP و apt با هم می‌خوابند.

`ufw allow OpenSSH` از پروفایل برنامه استفاده می‌کند که بستهٔ `openssh-server` می‌گذارد. پورت همان `22` است مگر شما پورت SSH را عوض کرده باشید. اگر پورت را عوض کرده‌اید، اجازه باید همان پورت باشد نه اسم پروفایل. این آزمایشگاه پورت SSH را عوض نمی‌کند. عوض کردن پورت امنیت نیست و فقط لاگ اسکن را خلوت‌تر نشان می‌دهد.

ترتیب قانون در UFW مهم است. اولین قانونی که جور شود برنده است. برای همین قانون خاص «از این مبدأ به این پورت» را می‌نویسیم و یک `allow 3306` کلی کنارش نمی‌گذاریم. قانون کلی، قانون خاص را بی‌معنی می‌کند اگر زودتر جور شود.

IPv6 را خاموش نکنید تا «فقط IPv4 را مدیریت کنیم». اگر `IPV6=yes` در `/etc/default/ufw` باشد، UFW همان سیاست را روی نسخهٔ ۶ هم می‌گذارد. خاموش کردنش در حالی که آدرس ۶ روی کارت مانده، یک در پشتی است.

## چرا استفاده می‌شود؟

سرویس‌ها گاهی روی `0.0.0.0` گوش می‌دهند چون فایل پیکربندی پیش‌فرض همین است. فایروال آخرین جایی است که آن گوش‌دادن را از اینترنت و از بقیهٔ آزمایشگاه جدا می‌کند. سخت‌سازی SSH جلوی رمز را می‌گیرد. جلوی رسیدن بسته به پورت دیتابیس را نمی‌گیرد. اگر MySQL روی `db-1` به همهٔ رابط‌ها گوش دهد و فایروال باز باشد، هر میزبان `10.10.0.0/16` می‌تواند در را بزند. قانون این صفحه آن را به `10.10.1.10` محدود می‌کند.

خطر قفل شدن واقعی است. `enable` سیاست را همان لحظه اعمال می‌کند. اتصال SSH فعلی اغلب به‌خاطر حالت اتصال برقرار می‌ماند. این شما را گول می‌زند. پنجره را که ببندید، پنجرهٔ تازه تایم‌اوت می‌شود. برای همین اجازهٔ OpenSSH قبل از enable است و یک نشست دوم بعد از enable اجباری است.

## Architecture

```text
اینترنت یا بقیهٔ شبکه
        │
        ▼
   UFW  default deny incoming
        │
        ├─ همهٔ میزبان‌ها: tcp/22 از آزمایشگاه (پروفایل OpenSSH)
        │
        ├─ proxy 10.10.1.5
        │     tcp/80 و tcp/443 از بیرون
        │
        ├─ db-1 10.10.1.20
        │     tcp/3306 و tcp/5432 فقط از 10.10.1.10
        │
        ├─ docker-1 10.10.1.30
        │     tcp/8080 فقط از 10.10.1.5
        │     (UI جنکینز اگر هست روی 127.0.0.1 است و قانون جدا نمی‌خواهد)
        │
        └─ app-1 10.10.1.10
              SSH، و بس، مگر سرویسی که واقعاً از پروکسی می‌آید
```

خروجی میزبان‌ها باز می‌ماند تا `apt`، رجیستری، و DNS کار کنند. این نمودار مجوز خروج آزاد به هر مقصد است. اگر سازمان خروج را هم می‌بندد، آن طرح را جدا بنویسید و اول DNS و NTP و مخزن بسته را اجازه دهید، بعد deny کنید. آن کار را با عجله به ته این صفحه نچسبانید.

## Installation

```bash
sudo apt update
sudo apt install ufw
sudo ufw version
```

قبل از روشن کردن، ببینید چه چیزی گوش می‌دهد تا قانونی که می‌نویسید با واقعیت `ss` یکی باشد:

```bash
sudo ss -lntup
```

اگر SSH روی پورت `22` نیست، همین‌جا بایستید. پروفایل OpenSSH به درد شما نمی‌خورد.

سیاست و اجازهٔ مدیریت، هنوز بدون enable:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH comment 'admin'
sudo ufw show added
```

`show added` باید قانون OpenSSH را نشان دهد قبل از اینکه `enable` دیده شود. اگر نمی‌بینید، جلو نروید.

IPv6:

```bash
grep -E '^IPV6=' /etc/default/ufw
```

مقدار `yes` را نگه دارید. اگر `no` است، دلیل میزبان را بدانید. در آزمایشگاه آن را `yes` می‌کنیم تا سیاست روی هر دو خانواده یکی باشد.

نشست فعلی را نبندید. بعد:

```bash
sudo ufw enable
sudo ufw status verbose
```

از یک پنجرهٔ دیگر SSH بزنید. اگر بالا آمد، پنجرهٔ اول را می‌شود بست. اگر نه، در پنجرهٔ اول:

```bash
sudo ufw disable
```

و قانون را اصلاح کنید. `disable` سیاست را برمی‌دارد. این دستور اضطراری است، نه وضعیت تولید.

## Configuration

قانون‌های نقش را فقط روی همان میزبان بزنید.

پروکسی `proxy.example.internal`:

```bash
sudo ufw allow 80/tcp comment 'http'
sudo ufw allow 443/tcp comment 'https'
sudo ufw status verbose
```

سرور دیتابیس `db-1.example.internal`. این دستورها را روی `app-1` نزنید. آنجا مبدأ و مقصد برعکس می‌شود:

```bash
sudo ufw allow from 10.10.1.10 to any port 3306 proto tcp comment 'mysql from app-1'
sudo ufw allow from 10.10.1.10 to any port 5432 proto tcp comment 'postgres from app-1'
sudo ufw status verbose
```

اگر فقط یکی از دو موتور را دارید، قانون موتور دیگر را نگذارید. پورت بسته بهتر از پورت آماده برای سرویسی است که ماه بعد کسی نصب می‌کند.

میزبان Docker، برای سرویس `app` که Compose آن را روی `10.10.1.30:8080` منتشر می‌کند:

```bash
sudo ufw allow from 10.10.1.5 to any port 8080 proto tcp comment 'app from proxy'
sudo ufw status verbose
```

اگر پورت منتشرشده در Compose چیز دیگری است، عدد قانون را با همان یکی کنید. عدد را از حافظهٔ این صفحه برندارید وقتی `ss` چیز دیگری نشان می‌دهد. UI جنکینز اگر طبق صفحهٔ Jenkins به `127.0.0.1:8080` چسبیده، از شبکه به آن نمی‌رسند و نباید برایش `allow 8080` از کل آزمایشگاه نوشت. آن قانون، در کنار انتشار برنامه، UI را هم اگر روزی به `0.0.0.0` لغزید باز می‌کند. قانون بالا مبدأ را به پروکسی محدود می‌کند.

`app-1` در این آزمایشگاه وب عمومی ندارد. SSH کافی است. اگر یک سرویس مدیریتی روی خودش گوش می‌دهد، مبدأ را پروکسی یا یک آدرس تکی بگذارید، نه `allow` بدون `from`.

حذف قانون غلط با شماره امن‌تر از پاک کردن همه است. اول شمارهٔ زنده را ببینید:

```bash
sudo ufw status numbered
```

ستون چپ همان شماره است. اگر قانون غلط در خروجی شما ردیف ۴ بود، حذف این است و بلافاصله فهرست را دوباره بگیرید، چون شماره‌ها بعد از حذف جابه‌جا می‌شوند:

```bash
sudo ufw delete 4
sudo ufw status numbered
```

اگر ردیف ۴ قانون OpenSSH بود، آن را حذف نکنید. شماره را از خروجی همین میزبان بردارید، نه از حافظهٔ دیروز.

Docker و UFW با هم معروف‌اند که قواعد را دور می‌زنند، چون Docker زنجیرهٔ خودش را در netfilter دست‌کاری می‌کند و پورت منتشرشدهٔ `0.0.0.0` ممکن است قبل از قانون UFW پذیرفته شود. برای همین Compose این آزمایشگاه پورت را به `10.10.1.30:8080` می‌چسباند نه به همهٔ رابط‌ها، و باز هم `ufw status` را کافی ندانید. از یک میزبان دیگر که نباید راه داشته باشد، واقعاً `nc -vz 10.10.1.30 8080` بزنید. اگر از `db-1` این پورت باز شد، انتشار Compose یا فایروال هنوز غلط است.

## Production Example

یک عصر روی هر شش میزبان، فقط قانون همان نقش را دارید. بررسی از `app-1`:

```bash
nc -vz -w 3 10.10.1.20 5432
nc -vz -w 3 10.10.1.5 443
nc -vz -w 3 10.10.1.30 8080
```

انتظار: به `5432` روی دیتابیس وصل می‌شود چون مبدأ `10.10.1.10` است. به `443` پروکسی وصل می‌شود. به `8080` داکر از `app-1` نباید وصل شود، چون قانون فقط پروکسی را اجازه داده. اگر وصل شد، یا قانون `from` را فراموش کرده‌اید یا Docker آن را دور زده.

از لپ‌تاپی که فقط باید SSH داشته باشد، `nc` به `10.10.1.20` پورت `3306` باید شکست بخورد. از خود `db-1` به `127.0.0.1:5432` هنوز موفق است. فایروال میزبان جلوی loopback را به شکل پیش‌فرض UFW نمی‌گیرد و این برای مدیر محلی درست است. معنایش این نیست که برنامه حق دارد از میزبان دیگر بیاید.

`ufw status verbose` روی `db-1` باید چیزی با این شکل نشان دهد. شماره و شمارنده فرق می‌کنند. مبدأ و پورت نباید فرق کنند:

```text
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), deny (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
22/tcp (OpenSSH)           ALLOW IN    Anywhere
3306/tcp                   ALLOW IN    10.10.1.10
5432/tcp                   ALLOW IN    10.10.1.10
22/tcp (OpenSSH (v6))      ALLOW IN    Anywhere (v6)
```

اگر کنار `3306` مبدأ `Anywhere` بود، قانون کلی اضافه دارید. حذفش کنید و دوباره از یک میزبان غیر از `app-1` آزمایش کنید.

بستن خروجی را در این مثال انجام نمی‌دهیم. پروکسی باید به بالادست گواهی و به مخزن بسته برسد. دیتابیس باید به هیچ میزبان دیگری جز پاسخ همان اتصال‌ها نیاز نداشته باشد، ولی بستن خروجی DNS روی `db-1` بدون اینکه بدانید resolv از کجا می‌آید، همان شب شما را به کنسول می‌کشاند.

## Security Notes

`ufw allow OpenSSH` از همه‌جا به پورت `22` است. آزمایشگاه پشت شبکهٔ مدیریت است. اگر میزبان یک آدرس عمومی هم دارد، این قانون پورت مدیریت را روی همان آدرس عمومی باز می‌کند. در آن حالت به‌جای پروفایل کلی، `allow from 10.10.0.0/16 to any port 22 proto tcp` بگذارید و قبل از enable از داخل همان شبکه یک نشست دوم بگیرید. این صفحه چون آزمایشگاه آدرس عمومی برای مدیریت ندارد، پروفایل OpenSSH را نگه می‌دارد. روزی که آدرس عمومی اضافه شد، این جمله را دوباره بخوانید.

قانون را با `comment` بنویسید. ماه بعد کسی نمی‌داند `8080` مال برنامه بوده یا مال یک آزمایش رها شده. قانون بدون شرح، کاندیدای ماندن برای همیشه است.

`ufw disable` را در اسکریپت استقرار نگذارید. یک خط لولهٔ عجول کل فایروال را برمی‌دارد. تغییر قانون باید یک دستور مشخص `allow` یا `delete` باشد و بعد `status verbose`.

لاگ UFW روی `low` برای شروع کافی است. اگر در حال تعقیب یک پورت مشکوک هستید موقتاً `sudo ufw logging medium` و بعد برگرداندن به `low`، تا دیسک پر از لاگ رد شدن نشود. پر شدن دیسک هم نوعی قطعی است.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| SSH بعد از enable تایم‌اوت می‌شود و نشست قدیمی هنوز زنده است | در نشست قدیمی `ufw disable`، بعد `allow OpenSSH`، بعد enable، بعد نشست دوم |
| هر دو نشست مرده‌اند | کنسول هایپروایزر، `ufw disable`، بعد اصلاح. از بیرون بسته نفرستید و امیدوار نباشید |
| برنامه از پروکسی `502` می‌دهد ولی روی خود میزبان سالم است | قانون مبدأ یا پورت با Compose یکی نیست. `ss -lntup` و `ufw status verbose` را کنار هم بگذارید |
| از `db-1` به پورت برنامه وصل می‌شوید | قانون بدون `from` است، یا Docker پورت را روی `0.0.0.0` منتشر کرده |
| `ufw` می‌گوید پروفایل OpenSSH نیست | `openssh-server` نصب نیست یا پورت را عوض کرده‌اید. پورت واقعی را اجازه دهید |
| IPv6 هنوز باز است و `status` فقط v4 را نشان نمی‌دهد | `status verbose` را ببینید. اگر قانون v6 نیست، `IPV6` در `/etc/default/ufw` را چک کنید و `ufw reload` |
| قانون را حذف کردید و شمارهٔ بعدی را هم حذف کردید | `status numbered` را بعد از هر حذف دوباره بگیرید |

`sudo ufw reload` بعد از تغییر `/etc/default/ufw` لازم است. خود `allow` معمولاً فوری است. اگر شک دارید، نشست دوم را ملاک بگیرید نه پیام `Rule added`.

## Best Practices

- enable آخرین دستورِ بلوک اول است، نه اولین دستور.
- هر نقش یک فهرست کوتاه. پروکسی وب دارد، دیتابیس فقط از `app-1`، داکر فقط از پروکسی، بقیه فقط SSH.
- بعد از قانون تازه، از مبدأ مجاز و از یک مبدأ غیرمجاز هر دو آزمایش کنید. آزمایش فقط از مبدأ مجاز، قانون `Anywhere` را هم سبز نشان می‌دهد.
- پورت را «موقتاً از همه‌جا» باز نگذارید. موقت‌ها در `status verbose` می‌مانند و کسی پاکشان نمی‌کند.
- وقتی Docker در کار است، به UFW تنها اعتماد نکنید. آدرس گوش‌دادن در Compose را محدود کنید و از میزبان غریبه `nc` بزنید.
- قدم بعدی، وقتی SSH و UFW هر دو با نشست دوم ثابت شدند، [Fail2ban](/docs/10-security/fail2ban) است. فایروال تلاش ناموفق را کند نمی‌کند. فقط در را کم می‌کند.
