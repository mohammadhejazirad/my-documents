# امنیت کاربر و فایل

## مقدمه

دو جور حساب روی سرور آزمایشگاه هست و قاطی کردنشان بیشتر از یک پورت باز دردسر می‌سازد. حساب شخصی مال انسان است: `ops`، با کلید، با `sudo`، و با خانهٔ واقعی. حساب سرویس مال یک برنامه است: `deploy` یا `clamav` یا `jenkins`، بدون ورود روزمره، بدون عضویت در `sudo`، و با دسترسی فقط به همان مسیرهایی که برنامه می‌نویسد.

این صفحه بعد از پایدار شدن SSH و فایروال خوانده می‌شود. اگر `ops` هنوز کلید ندارد، اول [سی دقیقهٔ اول](/docs/04-server-management/initial-bootstrap) و [SSH](/docs/10-security/ssh-hardening) را تمام کنید. اینجا فرض این است که می‌توانید وارد شوید و حالا می‌خواهید حساب اضافه و فایل شل را جمع کنید.

مجوز پیش‌فرض درست برای راز `600` است و برای پوشه‌ای که راز را نگه می‌دارد `700`. پیدا کردن `777` و setuid کار بازرسی است، نه دستور پاک‌سازی کور. خیلی از setuidهای سیستم، مثل `sudo` و `passwd`، باید بمانند.

## مفهوم اصلی

انسان پاسخگو است و سرویس نه. اگر برنامه با حساب `ops` اجرا شود، باگ برنامه همان دسترسی مدیر را دارد، کلیدهای خانهٔ `ops` را می‌خواند، و در لاگ معلوم نیست کار از انسان بوده یا از فرایند. کاربر سرویس را بسته یا خود شما با `adduser --system` می‌سازد، پوستهٔ آن وقتی فقط سرویس است `/usr/sbin/nologin` است، و در `AllowUsers` نمی‌آید.

استثنای آزمایشگاه کاربر `deploy` روی `app-1` و `docker-1` است. آنجا پوسته `/bin/bash` است چون خط لوله باید یک اسکریپت ثابت را اجرا کند. این کاربر هنوز عضو `sudo` نیست. محدودیت کلید در صفحهٔ SSH و در [سناریوی خط لوله](/docs/09-cicd/pipeline-scenario) است. استثنا را به بقیهٔ میزبان‌ها کپی نکنید.

مجوز یونیکس سه رقم آشنا دارد. برای فایل راز، مالک خواندن و نوشتن دارد و گروه و دیگران هیچ: `600`. برای پوشهٔ راز، مالک می‌تواند وارد شود و دیگران نه: `700`. پوشه بدون بیت اجرا شدن، حتی اگر خواندنی باشد، قابل ورود نیست. برای همین پوشه را `600` نکنید و انتظار داشته باشید `cd` کار کند.

`777` یعنی هر حساب محلی می‌تواند فایل را عوض کند. روی اسکریپت استقرار یا فایل unit این یعنی هر کاربر می‌تواند کار مدیر را عوض کند. setuid یعنی فرایند با صاحب فایل اجرا می‌شود نه با کسی که آن را صدا زده. setuid روی اسکریپت خانه یا روی یک باینری که شما نساخته‌اید و در `/opt` است، تقریباً همیشه اشتباه است. setuid روی `/usr/bin/sudo` طبیعی است.

ACL وقتی لازم است که گروه و دیگران کافی نیستند، مثلاً `clamav` باید آپلود را بخواند و دیگران نه. مدلش در [ACL](/docs/01-linux/acl) است. دادن `sudo` به حساب سرویس راه‌حل این مشکل نیست. مدل sudo در [sudo](/docs/01-linux/sudo) است.

## چرا استفاده می‌شود؟

حساب مشترک `ops` که هم انسان با آن SSH می‌زند و هم سرویس با آن فایل می‌نویسد، بعد از ترک یک همکار غیرقابل جمع شدن است. شما یا رمز و کلید او را باطل می‌کنید و سرویس می‌خوابد، یا سرویس را زنده نگه می‌دارید و کلید انسان قبلی معتبر می‌ماند. حساب جدا این گره را باز می‌کند.

فایل `777` اغلب از یک `chmod -R` عجول یا از یک کپی پشتیبان آمده. تا وقتی دنبالش نگردید، فرض می‌کنید مجوزها مرتب‌اند. setuid اضافه اغلب از یک بستهٔ قدیمی یا یک آزمایش مانده. هر دو را با `find` می‌شود دید. پاک کردن را با چشم انجام می‌دهید، نه با یک لوله به `chmod`.

## Architecture

```text
انسان
  ops
    گروه sudo
    پوسته bash
    ~/.ssh  مجوز 700
    authorized_keys  مجوز 600
    ورود SSH طبق AllowUsers

سرویس
  deploy / clamav / jenkins / ghrunner
    نه در گروه sudo
    پوسته nologin، مگر استثنای مستند deploy روی app-1 و docker-1
    فقط مسیر کار خودش
    رازها 600، پوشه 700

بازرسی
  find  برای 777 و بیت setuid/setgid
  مقایسه با فهرست مورد انتظار سیستم
  بدون chmod گروهی
```

خانه‌ها زیر `/home` برای انسان است. خانهٔ سرویس اگر لازم باشد زیر `/var/lib` است، مثل کاری که صفحهٔ Chromium با کاربر `chrome` می‌کند، یا همان `/home/deploy` وقتی اسکریپت باید کلید SSH نگه دارد. کلید سرویس را در خانهٔ `ops` نگذارید.

## Installation

ابزار این صفحه همان `adduser`، `deluser`، `find`، `stat` و `chmod` است و از بستهٔ پایه می‌آید. ACL اگر به دستور `setfacl` رسیدید بستهٔ `acl` است و توضیحش در صفحهٔ ACL است، نه اینجا.

فهرست حساب‌های انسانی را ببینید. حساب با شناسهٔ عددی هزار به بالا انسان یا سرویس دست‌ساز است. حساب‌های زیر هزار را به‌عنوان «اضافه» حذف نکنید. `nobody` و `systemd-network` و بقیهٔ سیستم باید بمانند:

```bash
getent passwd | awk -F: '$3 >= 1000 && $3 < 65534 { print $1, $3, $6, $7 }'
```

خروجی سالم روی یک میزبان برنامهٔ تمیز تقریباً این است: `ops` با پوستهٔ bash، و شاید `deploy` با bash فقط روی `app-1` و `docker-1`. نامی که نمی‌شناسید اضافه است تا وقتی ثابت شود مال یک بسته است.

گروه‌های حساس را هم ببینید:

```bash
getent group sudo
getent group docker
```

`sudo` باید فقط `ops` را نشان دهد. `docker` اگر روی این میزبان اصلاً هست، فقط حسابی که واقعاً موتور را اجرا می‌کند. روی `db-1` گروه `docker` نباید وجود داشته باشد. روی `docker-1` عضویت این گروه معادل root است و فهرستش باید کوتاه باشد.

## Configuration

ساخت حساب سرویس که فقط فایل محلی می‌نویسد و SSH ندارد:

```bash
sudo adduser --system --group --home /var/lib/app --shell /usr/sbin/nologin app
sudo install -d -m 750 -o app -g app /var/lib/app
```

نام `app` اینجا کاربر سیستم است، جدا از نام سرویس. اگر همان کار را `deploy` انجام می‌دهد، کاربر دوم نسازید. دو حساب برای یک فرایند یعنی دو مجموعه راز.

راز و پوشه:

```bash
sudo install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
sudo install -m 600 -o deploy -g deploy /dev/null /home/deploy/.ssh/authorized_keys
sudo chmod 600 /opt/apps/app/.env
sudo chown deploy:deploy /opt/apps/app/.env
```

`install -m 600` حتی وقتی فایل از قبل با مجوز شل ساخته شده، مجوز را درست می‌کند. `chmod 777` را در هیچ اسکریپت استقرار نگذارید، حتی موقت.

حذف کاربر اضافه، بعد از اینکه مطمئن شدید فرایندی ندارد و داده‌اش را برداشته‌اید:

```bash
ps -u unwanted -o pid,cmd
sudo crontab -u unwanted -l
sudo deluser --remove-home unwanted
```

`--remove-home` خانه را پاک می‌کند. اگر در خانه کلیدی هست که هنوز روی سرور دیگری مجاز است، اول آن کلید را از `authorized_keys` سرورهای دیگر بردارید، بعد خانه را پاک کنید. `deluser` بدون `--remove-home` خانهٔ یتیم می‌گذارد و همان خانه اغلب مجوز شل دارد.

بایت setuid و مجوز جهان‌نوشتنی را پیدا کنید. جستجو را به مسیر خودتان محدود کنید تا کل `/usr` را با چیزهای طبیعی قاطی نکنید. یک بار هم کل سیستم را برای بازرسی ببینید، نه برای پاک‌سازی خودکار:

```bash
sudo find /opt/apps /etc /home /var/lib -xdev \( -perm -0002 -o -perm -0001 \) -type f -print
sudo find /opt /home /var/lib /usr/local -xdev \( -perm -4000 -o -perm -2000 \) -type f -print
sudo find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -print
```

دستور سوم طولانی است و روی `/usr` نتیجه‌های سالم دارد: `/usr/bin/sudo`، `/usr/bin/passwd`، و چند باینری دیگر بسته. آن‌ها را حذف نکنید. چیزی که زیر `/opt` یا `/home` یا `/tmp` بیت setuid دارد مشکوک است. `/tmp` را جدا نگاه کنید چون فایل زودگذر است. اگر چیزی آنجا setuid بود، قبل از پاک کردن صاحب و زمان را یادداشت کنید.

برای یک فایل مشکوک، قبل از تغییر:

```bash
stat /opt/apps/app/bin/deploy.sh
```

`deploy.sh` باید مالک `deploy` و مجوز `700` باشد، نه setuid. اگر setuid است، آن بیت را بردارید:

```bash
sudo chmod 700 /opt/apps/app/bin/deploy.sh
```

این را به `chmod -R` روی `/opt` گسترش ندهید. یک درخت را با یک رقم واحد خراب می‌کنید و سرویس دیگر نمی‌تواند پوشه‌های داده‌اش را بخواند.

## Production Example

روی `app-1` بعد از راه‌اندازی خط لوله این وضعیت قابل دفاع است:

| مسیر | مالک | مجوز | چرا |
| --- | --- | --- | --- |
| `/home/ops` | `ops` | `755` یا `750` | خانهٔ انسان. `755` پیش‌فرض Ubuntu است. اگر راز بیرون از `.ssh` دارید، `750` |
| `/home/ops/.ssh` | `ops` | `700` | وگرنه `sshd` کلید را نادیده می‌گیرد |
| `/home/ops/.ssh/authorized_keys` | `ops` | `600` | همین‌طور |
| `/home/deploy/.ssh` | `deploy` | `700` | کلید پرش به `docker-1` |
| `/opt/apps/app/.env` | `deploy` | `600` | فقط برچسب، ولی همان عادت راز |
| `/opt/apps/app/bin/deploy.sh` | `deploy` | `700` | قابل نوشتن برای دیگران نیست |

یک همکار رفته و حساب `tempadmin` با پوستهٔ bash هنوز در `getent` هست. فرایند ندارد، crontab ندارد، و کلیدش را از میزبان‌های دیگر برداشته‌اید. بعد `deluser --remove-home`. اگر او در گروه `sudo` بوده، `getent group sudo` دیگر نامش را نشان نمی‌دهد. `deluser` عضویت گروه را هم برمی‌دارد. دوباره گروه را ببینید تا مطمئن شوید.

روی `db-1` کاربر `deploy` نباید SSH داشته باشد و نباید مالک `/var/lib/mysql` یا `/var/lib/postgresql` شود. آن مسیرها مال کاربر سیستم خود موتور دیتابیس است. برنامه از شبکه با حساب SQL وصل می‌شود، نه با حساب یونیکس `deploy`.

اگر `find` روی `/opt/apps` یک فایل `666` نشان داد، آن را `640` یا `600` کنید و ببینید کدام فرایند آن را ساخته. معمولاً `umask` سرویس `000` یا `022` است و باید در unit سرویس اصلاح شود، وگرنه فایل بعدی دوباره شل ساخته می‌شود. `chmod` تنها، فردا فراموش می‌شود.

## Security Notes

حساب سرویس را در گروه `sudo` نگذارید تا اسکریپت «راحت» شود. اگر یک دستور مدیر لازم است، یک خط مشخص در sudoers برای همان مسیر بگذارید، با `visudo`. توضیح مدل در [sudo](/docs/01-linux/sudo) است. `NOPASSWD: ALL` برای `gitlab-runner` یا `deploy` همان root بی‌رمز است.

کلید خصوصی مجوز `600` و پوشه‌اش `700` است. بکاپ این فایل‌ها را با همان محدودیت ببرید. `rsync` به مقصد جهان‌خوانا، سخت‌سازی مبدأ را دور می‌زند. صفحهٔ [بکاپ](/docs/10-security/backup) این را تکرار می‌کند چون مقصد معمولاً فراموش می‌شود.

`chmod 777` روی سوکت یا روی پوشهٔ آپلود «تا برنامه بالا بیاید» را همان روز جمع کنید. اگر برنامه به گروه نیاز دارد، گروه بسازید یا ACL بدهید. [ACL](/docs/01-linux/acl) برای همین است که رقم «دیگران» را باز نکنید.

setuid را روی اسکریپت shell نگذارید. هستهٔ لینوکس سال‌هاست setuid اسکریپت را نادیده می‌گیرد یا رفتارش گمراه‌کننده است، و بعضی فایل‌سیستم‌ها آن را جور دیگری نشان می‌دهند. اگر واقعاً باید کاری با امتیاز بالاتر انجام شود، همان یک دستور در sudoers شفاف‌تر است.

کاربر را با `userdel` خشن پاک نکنید وقتی هنوز فرایند دارد. اول سرویس را متوقف کنید. پاک کردن حساب مالک فایل‌های `/opt`، فایل را با شناسهٔ عددی یتیم می‌گذارد و نفر بعدی ممکن است همان شماره را دوباره بگیرد.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| SSH کلید درست را رد می‌کند | `ls -ld` روی خانه، روی `.ssh`، و روی `authorized_keys`. مالک باید خود کاربر باشد. گروه نوشتنی روی خانه گاهی کافی است که `sshd` کلید را رد کند |
| سرویس بعد از `chmod -R 600` بالا نمی‌آید | پوشه‌ها بیت اجرا را از دست داده‌اند. از بکاپ یا از بسته برگردانید. این دستور را دوباره نزنید |
| `find` پر از setuid زیر `/usr` است | طبیعی است. فقط مسیرهایی را که خودتان ساخته‌اید با فهرست بالا مقایسه کنید |
| `deluser` می‌گوید فرایند هنوز هست | `ps -u` و `systemctl cat` را برای `User=` همان حساب ببینید. سرویس را متوقف کنید |
| برنامه نمی‌تواند فایل `600` را بخواند | برنامه با کاربر دیگری اجرا می‌شود. `ps` کاربر واقعی را نشان می‌دهد. یا کاربر unit را درست کنید یا گروه و مجوز `640`، نه `666` |
| دو نفر با یک کلید وارد `ops` می‌شوند | کلید شخصی نیست. برای هر انسان یک کلید بسازید و خط قدیمی را بعد از آزمایش حذف کنید |

برای دیدن مجوز به‌شکل عددی:

```bash
stat -c '%U %G %a %n' /opt/apps/app/.env /home/ops/.ssh /home/ops/.ssh/authorized_keys
```

خروجی مورد انتظار چیزی شبیه `deploy deploy 600` برای `.env` و `ops ops 700` برای پوشهٔ کلید است.

## Best Practices

- یک انسان، یک حساب، یک کلید. یک سرویس، یک حساب، بدون sudo کلی.
- `ops` را به برنامه قرض ندهید. `deploy` را به انسان قرض ندهید.
- راز `600`، پوشهٔ راز `700`، اسکریپت اجرایی `700` اگر لازم نیست دیگران آن را بخوانند.
- `find` بازرسی است. خروجی را بخوانید. هیچ لوله‌ای از `find` به `chmod` یا `rm` نسازید.
- کاربر ناشناس با uid بالای هزار یا حذف می‌شود یا در همین صفحه دلیل ماندنش نوشته می‌شود. حساب بی‌صاحب نگه ندارید.
- جایی که سه رقم یونیکس کم می‌آورد، به [ACL](/docs/01-linux/acl) بروید. جایی که دستور مدیر لازم است، به [sudo](/docs/01-linux/sudo). رقم `777` و گروه `sudo` میانبر هیچ‌کدام نیستند.
