# استقرار دستی

## مقدمه

این صفحه یک برنامهٔ Node کوچک را با دست روی `10.10.1.10` می‌گذارد: ورود با SSH، کلون از GitLab داخلی، نصب از قفل وابستگی، بیلد، و یک اجرای پیش‌زمینه تا ثابت شود فرایند به `127.0.0.1:3000` جواب می‌دهد. نگه داشتن آن بعد از قطع SSH کار این صفحه نیست. آن کار [PM2 یا systemd](/docs/08-deployment/nodejs-pm2-systemd) است. اگر اینجا `nohup` بگذارید، صفحهٔ بعد دو فرایند روی یک پورت پیدا می‌کند.

باینری Node باید شاخهٔ 24 باشد و در `/usr/local/bin/node` باشد. روش نصب بدون اختراع شمارهٔ patch در صفحهٔ بعد است. اگر `node -v` این را نشان نمی‌دهد، اول همان صفحه را انجام دهید و برگردید. Nginx جلوی این پورت در [پروکسی Node](/docs/06-nginx/nodejs) است.

## مفهوم اصلی

انسان با کاربر `ops` وارد می‌شود. سرویس با کاربر `deploy` اجرا می‌شود و شل ورود ندارد. مخزن روی سرور در `/opt/apps/app` است نه در خانهٔ `ops`. نصب با `npm ci` است چون `package-lock.json` را محترم می‌شمارد و اگر قفل نباشد اصلاً نصب نمی‌کند. `npm install` روی سرور قفل را جلو می‌برد و دو میزبان را از هم جدا می‌کند.

بیلد این برنامهٔ کوچک `node --check` است، یعنی فقط نحو فایل را می‌خواند و خروجی جدا نمی‌سازد. برنامهٔ واقعی ممکن است قبل از اجرا به کامپایلر نیاز داشته باشد. ترتیب آن حالت این است: نصب با وابستگی توسعه، بیلد، بعد حذف وابستگی توسعه. این نمونه وابستگی توسعه ندارد و همان اول `npm ci --omit=dev` کافی است.

اجرای این صفحه پیش‌زمینه است تا لاگ را ببینید و با Ctrl+C تمامش کنید. تا وقتی آن را تمام نکرده‌اید، پورت ۳۰۰۰ اشغال است و واحد systemd صفحهٔ بعد بالا نمی‌آید.

## چرا استفاده می‌شود؟

قبل از نوشتن واحد سرویس باید بدانید فرمان اجرا اصلاً کار می‌کند. واحدی که برنامهٔ خراب را هر پنج ثانیه restart می‌کند فقط journal را پر می‌کند. مسیر دستی این شک را از شک به systemd جدا می‌کند.

کلون روی سرور همچنین ثابت می‌کند کلید خواندن GitLab از خود میزبان کار می‌کند، نه فقط از لپ‌تاپ. اگر این را رد کنید و فایل را با `scp` بریزید، فردا کسی که باید `git pull` کند هنوز کلید ندارد.

## Architecture

```text
ایستگاه کاری ops
  کلید ed25519
        │  SSH به ops@10.10.1.10
        ▼
/opt/apps/app          مالک deploy
  package.json
  package-lock.json
  server.js
        │
        ▼
node  127.0.0.1:3000   پیش‌زمینه، تا Ctrl+C
        ▲
        └── بعداً Nginx همان میزبان، نه در این صفحه
```

GitLab آزمایشگاه `gitlab.example.internal` روی `10.10.1.50` است. نشانی مخزن نمونه `git@gitlab.example.internal:team/app.git` است. کلید خصوصی را در سند نمی‌آوریم. کلید خواندن‌فقط را تیم در حساب `deploy` می‌گذارد.

## Installation

کاربر و پوشه، یک بار:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 ops@10.10.1.10
sudo adduser --disabled-password --gecos "" --home /home/deploy deploy
sudo usermod -s /usr/sbin/nologin deploy
sudo mkdir -p /opt/apps /home/deploy/.ssh
sudo chown deploy:deploy /opt/apps /home/deploy /home/deploy/.ssh
sudo chmod 755 /opt/apps
sudo chmod 700 /home/deploy /home/deploy/.ssh
```

کلید عمومی متناظر را در GitLab به عنوان Deploy key فقط‌خواندنی روی همان مخزن ثبت کنید. فایل خصوصی را با حالت `600` و مالک `deploy` در `/home/deploy/.ssh/id_ed25519` بگذارید. بررسی host key گیت‌لب را با `StrictHostKeyChecking=no` دور نزنید. یک بار با `sudo -u deploy ssh -o IdentitiesOnly=yes -i /home/deploy/.ssh/id_ed25519 git@gitlab.example.internal` اثر انگشت را ببینید و اگر با کانال معرفی تیم یکی است، بپذیرید.

Node را جداگانه لازم دارید:

```bash
/usr/local/bin/node -v
```

خروجی باید با `v24.` شروع شود. اگر فرمان نیست، [صفحهٔ Node](/docs/08-deployment/nodejs-pm2-systemd) را تا پایان نصب باینری انجام دهید. بقیهٔ این صفحه را با بستهٔ تصادفی `nodejs` از آرشیو جایگزین نکنید؛ آن بسته را این دانشنامه برای شاخهٔ 24 تضمین نکرده است.

## Configuration

شکل مخزن بعد از کلون. این سه فایل باید در گیت باشند، نه اینکه روی سرور اختراع شوند و فراموش شوند.

`package.json`:

```bash
sudo tee /opt/apps/app/package.json >/dev/null <<'EOF'
{
  "name": "app",
  "private": true,
  "scripts": {
    "start": "node server.js",
    "build": "node --check server.js"
  }
}
EOF
```

این بلوک فقط نشان می‌دهد بیلد و شروع چه نامی دارند. منبع حقیقت گیت است. اگر روی سرور فایل را با دست بسازید و پوش نکنید، استقرار بعدی آن را دور می‌ریزد.

`server.js` باید به میزبان و پورت از محیط گوش بدهد و پیش‌فرضش حلقهٔ محلی و پورت ۳۰۰۰ باشد:

```bash
sudo tee /opt/apps/app/server.js >/dev/null <<'EOF'
const http = require('http');
const host = process.env.HOST || '127.0.0.1';
const port = Number(process.env.PORT || 3000);
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'content-type': 'text/plain; charset=utf-8' });
  res.end('ok\n');
});
server.listen(port, host, () => {
  console.log('listening ' + host + ':' + port);
});
EOF
```

قفل وابستگی حتی برای این برنامهٔ بدون کتابخانه باید در مخزن باشد تا `npm ci` تعریف شده باشد. روی ایستگاه توسعه یک بار `npm install` بزنید، `package-lock.json` را commit کنید، و روی سرور دیگر `npm install` نزنید.

## Production Example

```bash
sudo -u deploy git clone git@gitlab.example.internal:team/app.git /opt/apps/app
cd /opt/apps/app
sudo -u deploy npm ci --omit=dev
sudo -u deploy npm run build
sudo -u deploy env HOME=/opt/apps/app NODE_ENV=production HOST=127.0.0.1 PORT=3000 /usr/local/bin/node /opt/apps/app/server.js
```

اگر برنامه بیلد واقعی با ابزار توسعه دارد، به‌جای خط `npm ci --omit=dev` این ترتیب را بزنید: `npm ci`، سپس `npm run build`، سپس `npm prune --omit=dev`.

در یک نشست SSH دیگر:

```bash
curl -fsS http://127.0.0.1:3000/
sudo ss -lptn 'sport = :3000'
```

بدنه باید `ok` باشد. `ss` باید `127.0.0.1:3000` و یک pid از `node` را نشان بدهد، نه `0.0.0.0:3000`. از `10.10.1.5` همین `curl` به پورت ۳۰۰۰ باید شکست اتصال باشد. بعد از دیدن `ok`، در نشست اول Ctrl+C بزنید تا پورت آزاد شود. تا وقتی آزاد نشده، واحد صفحهٔ بعد را شروع نکنید.

مالکیت اگر کلون را با کاربر دیگری زدید:

```bash
sudo chown -R deploy:deploy /opt/apps/app
```

فایل محیط اگر بعداً اضافه شد حالت `600` و مالک `deploy` است. این برنامهٔ نمونه رمز ندارد.

## Security Notes

`IdentitiesOnly` جلوی پیشنهاد شدن کلیدهای دیگر عامل SSH را می‌گیرد. بررسی host key را خاموش نکنید. اگر هشدار عوض شدن کلید میزبان دیدید، استقرار را قطع کنید و از کانال دیگر بپرسید چرا کلید عوض شده است.

`deploy` را در گروه `sudo` نگذارید تا «ساخت سرویس راحت شود». `ops` دستور ممتاز را می‌زند. شل `nologin` یعنی این حساب از SSH وارد نمی‌شود حتی اگر کسی کلید را به `authorized_keys` اضافه کند. `sudo -u deploy` همچنان فرمان را اجرا می‌کند و به شل ورود نیاز ندارد.

برنامه به `127.0.0.1` چسبیده چون پیش‌فرض کد همین است. متغیر `HOST=0.0.0.0` را در شل آزمایشی export نکنید و همان نشست را رها نکنید. Nginx تنها ورودی است.

کلید Deploy روی GitLab نباید اجازهٔ نوشتن داشته باشد. سرور تولید نباید بتواند به مخزن push کند.

## Troubleshooting

`Permission denied (publickey)` از گیت، در حالی که SSH به خود سرور درست است: کلید `deploy` به آن مخزن وصل نیست یا فایل حالت `644` دارد و SSH آن را نادیده می‌گیرد. `ls -l /home/deploy/.ssh` باید `600` برای کلید خصوصی و `700` برای پوشه را نشان بدهد.

`npm ci` با پیام نبودن `package-lock.json` یعنی مخزن ناقص است. روی سرور `npm install` نزنید تا قفل ساخته شود. قفل را در ایستگاه توسعه بسازید و commit کنید.

`EADDRINUSE` روی ۳۰۰۰ یعنی اجرای قبلی هنوز زنده است یا واحد systemd را زودتر روشن کرده‌اید. `ss` pid را می‌گوید. پیش‌زمینهٔ فراموش‌شده را Ctrl+C کنید یا اگر pid مال واحد است، واحد را stop کنید و فقط یکی را نگه دارید.

`node: not found` زیر `sudo -u deploy` یعنی PATH امن sudo باینری را نمی‌بیند. مسیر کامل `/usr/local/bin/node` همان است که در فرمان بالا هست. از `sudo` بدون مسیر تکیه نکنید.

اگر `curl` روی سرور `ok` می‌دهد و از مرورگر نه، هنوز Nginx یا لبه را ننوشته‌اید. این صفحه عمداً پورت را عمومی نمی‌کند. ادامه در فصل Nginx است.

`git clone` در پوشهٔ نای خالی نیست: یک تلاش قبلی نیمه‌کاره مانده. پوشه را فقط اگر خودتان همین الان ساخته‌اید و فایلی ندارید پاک کنید. `/opt/apps/app` دارای `.env` تولید را با `rm -rf` برای «شروع تمیز» برندارید.

اگر `npm ci` با خطای شبکه به رجیستری عمومی می‌میرد، میزبان به آینهٔ تیم نیاز دارد. آدرس آینه را در فصل Docker برای بستهٔ npm گذاشته‌اند؛ اینجا رجیستری را با یک URL شانسی در `.npmrc` عوض نکنید. تا وقتی `npm ci` غیرصفر است، `node server.js` را روی درخت نصفه اجرا نکنید. فرایند بالا می‌آید و اولین `require` جا مانده را با خطای ماژول نشان می‌دهد و شما فکر می‌کنید کد برنامه غلط است.

خروجی سالم `ss` شبیه این است، با pid متفاوت روی میزبان شما:

```text
LISTEN 0 511 127.0.0.1:3000 0.0.0.0:* users:(("node",pid=1842,fd=18))
```

اگر به‌جای `127.0.0.1` ستاره یا `0.0.0.0` دیدید، متغیر `HOST` در همان شل خالی نیست. نشست را ببندید و فرمان `env` صفحهٔ مثال را بدون صادرات قبلی دوباره بزنید.

## Best Practices

- SSH فقط `ops` و فقط کلید `ed25519`. host key را نادیده نگیرید.
- کلون و `npm ci` و اجرا با `deploy`. قفل وابستگی در گیت.
- بیلد را روی سرور همان‌طور که مخزن تعریف کرده اجرا کنید. اگر بیلد ابزار توسعه می‌خواهد، اول نصب کامل، بعد prune.
- اجرا پیش‌زمینه است تا اثبات شود، بعد قطع، بعد ناظر صفحهٔ بعد.
- پیش‌فرض گوش دادن `127.0.0.1:3000`. آن را برای آزمون از لپ‌تاپ به همهٔ رابط‌ها باز نکنید.
- فایل را روی سرور ویرایش نکنید مگر برای اثبات کوتاه، و همان را به مخزن برگردانید یا دور بریزید.
