# نقشهٔ استقرار

## مقدمه

فصل Nginx درِ HTTP را می‌سازد. این فصل خود فرایند را روی دیسک و زیر یک ناظر می‌گذارد تا با بستن SSH نمیرَد. میزبان برنامه `app-1.example.internal` روی `10.10.1.10` است و کاربر انسانی `ops` است. فرایندی که به درخواست جواب می‌دهد با کاربر `deploy` اجرا می‌شود، نه با `ops` و نه با `root`. ریشهٔ برنامه زیر `/opt/apps/` به‌علاوهٔ نام برنامه است: برای Node نام `app` و برای Laravel نام `laravel`.

لبهٔ TLS هنوز `proxy.example.internal` روی `10.10.1.5` است و نام عمومی `app.example.com` است. میزبان Docker جداست: `docker-1.example.internal` روی `10.10.1.30`. استقرار کانتینری را روی `10.10.1.10` با systemd قاطی نکنید. یک برنامه یا فرایند روی میزبان است یا کانتینر روی `10.10.1.30`، نه هر دو روی یک پورت.

منطقهٔ زمانی آزمایشگاه `Asia/Tehran` است. لاگ systemd با ساعت میزبان خوانده می‌شود. ساعت داخل خود Laravel را صفحهٔ صف جداگانه می‌گوید، چون با ساعت کرنل یکی فرض نمی‌شود.

## مفهوم اصلی

استقرار تولید چهار چیز را همزمان دارد. کد همان است که در گیت است، نه ویرایش روی سرور. وابستگی از قفل نسخه نصب می‌شود، نه از «هر چه امروز در رجیستری بود». فرایند یک ناظر دارد که بعد از reboot و بعد از crash آن را برمی‌گرداند. برگشت به نسخهٔ قبلی ممکن است، چون نسخهٔ قبلی هنوز روی دیسک یا در رجیستری با تگ مشخص هست.

ناظر دوم روی همان پورت ناظر نیست؛ مسابقه است. systemd و PM2 هر کدام فکر می‌کنند صاحب Node هستند. Apache و Nginx هر کدام فکر می‌کنند صاحب پورت ۸۰ هستند. کانتینر و فرایند میزبان هر دو فکر می‌کنند صاحب ۳۰۰۰ هستند. هر صفحهٔ این فصل جایی که این انتخاب پیش می‌آید، یکی را روشن می‌کند و دیگری را خاموش.

دستی بودن صفحهٔ اول یعنی بدون pipeline. فصل CI جای خودش را دارد. تا وقتی pipeline نیست، انسان با SSH همان مرحله‌ها را می‌زند و خروجی را می‌خواند. عجلهٔ `nohup` و `&` در این فصل پذیرفته نیست، چون فردا معلوم نیست کدام pid مال کدام نسخه است.

## چرا استفاده می‌شود؟

بدون مسیر نوشته‌شده، هر نفر فایل را در خانهٔ خودش کلون می‌کند، `npm install` را بدون قفل می‌زند، و با شل خودِ `ops` برنامه را بالا می‌گذارد. آن برنامه تا خروج از SSH زنده است و فایل‌هایی که ساخته مال `ops` است. نفر بعدی یا دسترسی ندارد یا سرویس را دوباره روی همان پورت شروع می‌کند.

این فصل همان کار را خسته‌کننده و تکراری می‌کند تا حادثه خسته‌کننده نباشد. مسیر `/opt/apps`، کاربر `deploy`، و یک واحد سرویس، چیزهایی هستند که در لاگ و در `ps` دیده می‌شوند. اگر در سند نباشند، در حادثه هم پیدا نمی‌شوند.

## Architecture

```text
ops  از ایستگاه کاری با کلید ed25519
        │  SSH
        ▼
10.10.1.10  app-1
  /opt/apps/app       Node، یک ناظر: systemd یا PM2
  /opt/apps/laravel   php-fpm + صف با supervisor + زمان‌بند
        ▲
        │  فقط 10.10.1.5 به پورت داخلی
10.10.1.5   لبه، فصل Nginx

10.10.1.30  docker-1
  /opt/apps/web       compose، فقط Nginx پورت 80 و 443
```

ترتیب خواندن:

| صفحه | کار |
| --- | --- |
| [استقرار دستی](/docs/08-deployment/manual-ssh) | SSH، کلون، نصب، بیلد، اجرای پیش‌زمینه |
| [Node با PM2 و systemd](/docs/08-deployment/nodejs-pm2-systemd) | باینری Node 24، بعد یکی از دو ناظر |
| [PHP با Apache و Nginx](/docs/08-deployment/php-apache-nginx) | هر دو وب‌سرور، و انتخاب یکی در تولید |
| [صف Laravel](/docs/08-deployment/laravel) | Supervisor، cron یا تایمر، worker |
| [Docker تولید](/docs/08-deployment/docker-production) | یک میزبان، تگ گیت، برگشت |

کانفیگ خود Nginx را اینجا بازنویسی نمی‌کنیم. برای Node به [پروکسی Node](/docs/06-nginx/nodejs)، برای PHP به [PHP-FPM](/docs/06-nginx/php-fpm)، برای Laravel به [Laravel پشت Nginx](/docs/06-nginx/laravel)، و برای کانتینر به [Nginx جلوی کانتینر](/docs/06-nginx/docker) برگردید.

## Installation

این صفحه بستهٔ تازه‌ای نصب نمی‌کند. پیش‌نیاز میزبان برنامه این است که `ops` بتواند با کلید وارد شود و `sudo` داشته باشد، و ساعت میزبان را بتوان دید:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 ops@10.10.1.10
timedatectl
id
sudo -n true && echo sudo-ok
```

`timedatectl` باید `Time zone: Asia/Tehran` را نشان بدهد. اگر میزبان تازه است و هنوز UTC است، قبل از اینکه زمان‌بند Laravel را معنی کنید:

```bash
sudo timedatectl set-timezone Asia/Tehran
```

این را روی میزبانی که سرویس دیگری عمداً UTC می‌خواهد نزنید. آزمایشگاه ما تهران است تا لاگ شیفت با ساعت تیم یکی باشد.

`sudo-ok` یعنی پرسش رمز وسط اسکریپت غافلگیرتان نمی‌کند. اگر `sudo -n` شکست، اول دسترسی را درست کنید. استقرار را با ورود ریشه انجام ندهید. ورود ریشه با رمز در این آزمایشگاه بسته است.

ساعت و کاربر را با خروجی واقعی تمام کنید، نه با فرض. شکل سالم `timedatectl` منطقهٔ `Asia/Tehran` و NTP فعال را نشان می‌دهد. اگر NTP خاموش است و ساعت چند دقیقه عقب است، گواهی و لاگ شیفت هر دو دروغ می‌گویند. `chronyc` یا `timedatectl timesync-status` را ببینید قبل از اینکه واحد سرویس را برای «تاخیر عجیب» باز کنید.

کاربر `deploy` را این‌جا اگر نیست نسازید با گزینه‌های سلیقه‌ای. صفحهٔ دستی خانه، شل `nologin` و مالک `/opt/apps` را یک‌جا می‌سازد. ساختن دوبارهٔ کاربر وسط صفحهٔ Docker روی `10.10.1.30` اشکالی ندارد به شرطی که همان نام بماند. دو کاربر `deploy` و `app` برای یک نقش، مجوز فایل را بین صفحه‌ها ناسازگار می‌کند.

## Configuration

قرارداد پوشه را قبل از صفحهٔ بعد بسازید تا هر کس مسیر خودش را اختراع نکند:

```bash
sudo mkdir -p /opt/apps /var/backups
sudo chown deploy:deploy /opt/apps
sudo chmod 755 /opt/apps /var/backups
```

اگر کاربر `deploy` هنوز نیست، صفحهٔ [دستی](/docs/08-deployment/manual-ssh) آن را می‌سازد. `chown` قبل از وجود کاربر شکست می‌خورد؛ در آن صورت اول کاربر، بعد پوشه.

نسخهٔ زبان را این صفحه ثابت نمی‌کند. Node شاخهٔ 24 است و شمارهٔ patch را از فهرست رسمی همان روز برمی‌دارید، در صفحهٔ PM2. PHP شاخهٔ 8.5 است و سوکت را با `ls /run/php` می‌بینید، نه با حدس. ایمیج برنامه تگ گیت می‌گیرد و `latest` نیست.

یک برنامه یک پرونده در `/opt/apps` دارد. ریپازیتوری را در `/home/ops` کلون نکنید و بعد با پیوند عجیب به سرویس نشان ندهید. خانهٔ انسان با خانهٔ سرویس فرق دارد. `deploy` شل ورود ندارد وقتی فقط سرویس است؛ کار تعاملی با `ops` است و اجرا با `sudo -u deploy`.

## Production Example

نشانه‌ای که یک استقرار را تمام‌شده حساب می‌کنیم، این چهار مشاهده روی `10.10.1.10` است. برای برنامه‌ای که هنوز نساخته‌اید، این فهرست معیار صفحه‌های بعد است نه فرمان امروز:

```bash
sudo ss -lptn 'sport = :3000'
systemctl is-active nginx
sudo -u deploy test -r /opt/apps/app/server.js && echo tree-ok
systemctl is-enabled app.service || systemctl is-enabled pm2-deploy
```

پورت ۳۰۰۰ باید `127.0.0.1` باشد و فقط یک شنونده داشته باشد. Nginx باید فعال باشد. درخت باید برای `deploy` خوانا باشد. دقیقاً یکی از دو واحد `app.service` یا `pm2-deploy` باید enabled باشد، نه هر دو. اگر هر دو enabled هستند، استقرار تمام نشده حتی اگر سایت همین حالا باز شود.

برای Laravel به‌جای پورت ۳۰۰۰ سوکت php-fpm و واحد `supervisor` و تایمر یا cron را می‌شمارید. برای Docker این فرمان‌ها روی `10.10.1.30` هستند و به‌جای systemd برنامه، `docker compose ps` است. معیار مشترک این است: یک راه ورود، یک ناظر، یک مسیر دیسک.

بعد از reboot میزبان، بدون SSH مجدد به داخل شل برنامه، `curl` از لبه باید همان پاسخ را بدهد. اگر فقط تا قبل از reboot کار می‌کند، ناظر enable نشده است. این آزمون را بعد از هر صفحهٔ این فصل یک بار انجام دهید.

نشانه‌های تمام شدن را با نوع برنامه عوض کنید، ولی شکل سؤال یکی بماند: چه کسی فرایند را بعد از قطع SSH برمی‌گرداند، روی کدام نشانی گوش می‌دهد، و نسخهٔ روی دیسک کدام تگ یا کدام commit است.

| نوع | ناظر | آزمون شنودن |
| --- | --- | --- |
| Node | فقط `app.service` یا فقط `pm2-deploy` | `127.0.0.1:3000` |
| PHP | `php8.5-fpm` و یک وب‌سرور | سوکت زیر `/run/php` بعد از `ls` |
| Laravel | همان PHP به‌علاوهٔ Supervisor و یک زمان‌بند | دو worker در `supervisorctl status` |
| Docker | `restart` در compose، نه systemd برنامه | فقط پورت ۸۰ و ۴۴۳ روی `10.10.1.30` |

اگر ردیف Node هر دو ناظر را دارد، استقرار را تمام‌شده حساب نکنید حتی اگر `curl` همین لحظه `ok` برگرداند. ردیف Docker را روی `10.10.1.10` اجرا نکنید. آن میزبان مال فرایند است. قاطی کردن حجم دیتابیس کانتینر با دادهٔ MySQL میزبان `10.10.1.20` دو منبع داده می‌سازد و بکاپ معلوم نیست مال کدام است.

ترتیب پیشنهادی وقتی همه‌چیز از صفر است: صفحهٔ دستی تا `curl` محلی جواب بدهد، بعد ناظر Node یا مسیر PHP، بعد کانفیگ Nginx همان برنامه، بعد یک reboot آزمایشی. Docker را به‌جای این زنجیره بردارید نه به‌علاوهٔ آن، مگر برنامهٔ کانتینری واقعاً برنامهٔ دیگری باشد با نام دیگری زیر `/opt/apps`.

## Security Notes

کلید SSH فقط `ed25519` است. گذرواژهٔ ریشه و ورود کاربر `deploy` از شبکه هدف این فصل نیستند. `deploy` اگر شل `nologin` دارد هنوز می‌تواند فرایند سرویس باشد؛ systemd برای این کار به شل تعاملی نیاز ندارد.

کد و `.env` را با `chmod 777` «تا سرویس بالا بیاید» باز نکنید. الگوی مجوز هر صفحه جدا نوشته شده است. بکاپ زیر `/var/backups` است و نباید از وب‌سرور قابل خواندن باشد. آن مسیر را `root` یک سایت Nginx نکنید.

رمز نمونه اگر در صفحه‌ای هست، مال آزمایشگاه است و فایلش باید حالت `0600` باشد. رمز تولید را در گیت و در خروجی `docker compose config` که به تیکت می‌چسبد نگذارید.

## Troubleshooting

اگر SSH همان اول رد شد، استقرار را شروع نکنید. نام کاربر `ops` است نه `root`، میزبان `10.10.1.10` است نه لبه، و کلید باید `ed25519` باشد. بررسی سمت کلاینت: `ssh -v` فقط برای دیدن اینکه کدام کلید پیشنهاد می‌شود، نه برای خاموش کردن بررسی host key.

اگر برنامه روی لپ‌تاپ شما کار می‌کند و روی سرور نه، فرق معمولاً مسیر، کاربر، یا متغیر محیط است نه «Nginx خراب است». اول `sudo -u deploy` همان دستوری را بزنید که واحد سرویس می‌زند. اگر آنجا شکست، واحد را دست نزنید.

اگر بعد از reboot هیچ‌چیز بالا نیست، `systemctl is-enabled` را برای همان واحد ببینید. `start` بدون `enable` فقط تا خاموشی بعدی زنده است. برای Docker معادل این اشتباه، `docker compose up` بدون `-d` است که با بستن SSH کانتینر را از جلسه جدا نمی‌کند ولی اگر کسی Ctrl+C بزند پشته می‌خوابد. تولید `docker compose up -d` است و سیاست `restart: unless-stopped` داخل فایل است، نه یک `docker start` دستی بعد از هر بوت.

وقتی کد روی دیسک جدید است و فرایند هنوز کهنه است، علامت معمولاً این است که `git rev-parse HEAD` یک commit را نشان می‌دهد و لاگ برنامه هنوز رشتهٔ نسخهٔ قبلی را چاپ می‌کند. برای Node ری‌استارت همان یک ناظر کافی است. برای PHP، php-fpm کد را هر درخواست می‌خواند مگر `opcache` فایل را نگه داشته باشد؛ بعد از استقرار `systemctl reload php8.5-fpm` ارزان و بی‌خطر است. برای صف Laravel، reload وب کافی نیست و Supervisor باید worker را از نو بسازد، وگرنه job با کد قبلی اجرا می‌شود در حالی که صفحهٔ سایت کد جدید است.

دو پاسخ متفاوت پشت سر هم از یک URL، با یک گره، اغلب یعنی دو فرایند و یکی کهنه. `ss` باید یک شنونده نشان بدهد. اگر دو pid می‌بینید، یکی را متوقف کنید و کانفیگ ناظر را با صفحهٔ همان برنامه یکی کنید.

یک استقرار را برنگردانید با پاک کردن درخت. برای Node، commit قبلی را کلون یا checkout کنید و همان یک ناظر را ری‌استارت کنید. برای Laravel همین کار به‌علاوهٔ `config:cache` و ری‌استارت گروه worker است، و مهاجرت دیتابیس را فقط اگر آن نسخه اسکیما را هم برمی‌گرداند جدا بررسی کنید. برای Docker تگ قبلی در compose است و حجم دیتابیس نباید پاک شود. اگر تنها راه «برگشت» شما `rm -rf /opt/apps` است، نسخهٔ قبلی را جایی نگه نداشته‌اید و این فصل را تمام‌شده حساب نکنید.

قبل از اعلام تمام، این سه خروجی را در یادداشت تغییر همان روز بگذارید: `git rev-parse --short HEAD` داخل درخت برنامه، نام واحد یا تگ ایمیجی که واقعاً بالا است، و کد وضعیت `curl` از `https://app.example.com/`. بدون این سه تا، نفر شیفت بعدی نمی‌داند چه چیزی در تولید است.

چک‌لیست همان شب، روی میزبانی که برنامه را گرفته، این است:

```bash
hostname -f
git -C /opt/apps/app rev-parse --short HEAD
systemctl is-active nginx
sudo ss -lptn 'sport = :3000' || true
curl -fsS -o /dev/null -w "%{http_code}\n" -H "Host: app.example.com" http://127.0.0.1:3000/ || true
```

برای Laravel مسیر گیت `/opt/apps/laravel` است و به‌جای پورت ۳۰۰۰ باید `ls /run/php` سوکت استخر `app` را نشان بدهد و `supervisorctl status` دو worker را `RUNNING` بگوید. برای Docker همین منطق روی `10.10.1.30` با `docker compose ps` است و `hostname -f` باید `docker-1.example.internal` باشد. اگر hostname چیز دیگری است، یا روی میزبان غلط هستید یا نام میزبان در بوت‌استرپ فصل مدیریت سرور جا مانده. استقرار را روی ماشین بی‌نام ادامه ندهید، چون گواهی و لاگ و فایروال بعداً به نام گره می‌خورند.

اگر `git rev-parse` گفت این مسیر مخزن نیست، فایل‌ها با کپی دستی آمده‌اند. برای آزمون دود قابل قبول است و برای تولید نه، چون برگشت به commit قبلی دستور ندارد. همان روز مخزن را جایگزین کپی کنید، نه هفتهٔ بعد وسط حادثه.

## Best Practices

- یک میزبان، یک مسیر زیر `/opt/apps/` با نام همان برنامه، یک کاربر `deploy`، یک ناظر.
- نسخه را از منبع همان روز بخوانید جایی که سند گفته patch نسازید. جایی که نسخهٔ توزیع معلوم است، همان را بنویسید: Nginx 1.28.x و PHP 8.5.
- قبل از بستن SSH، یک بار از لبه `curl` بزنید و یک بار برنامه‌ریزی reboot آزمایشی داشته باشید.
- کانفیگ لبه را در این فصل کپی نکنید؛ به صفحهٔ Nginx همان برنامه پیوند بدهید و همان را اعمال کنید.
- `latest` و `nohup` تولید نیستند.
- صفحهٔ بعد را وقتی بردارید که صفحهٔ قبل واقعاً روی `10.10.1.10` جواب داده، نه فقط خوانده شده.
- یادداشت تغییر را با سه خروجی همان شب پر کنید: commit، نام ناظر یا تگ ایمیج، و کد `curl` از نام عمومی. حافظهٔ شفاهی فردا با reboot پاک نمی‌شود ولی آدم عوض می‌شود.
- اگر مجبورید بین سرعت و برگشت‌پذیری یکی را انتخاب کنید، برگشت را نگه دارید. استقرار سریع بدون تگ یا بدون commit قبلی، حادثهٔ فردا را طولانی‌تر از همین شب می‌کند.
- پورت برنامه را برای «فقط یک تست از خانه» روی فایروال باز نکنید. تست از `10.10.1.5` یا از خود میزبان با `curl` به حلقهٔ محلی کافی است و قاعدهٔ موقت معمولاً دائمی می‌ماند.
- نام‌ها را از جدول آزمایشگاه برندارید. `app.example.com`، `10.10.1.5` و `10.10.1.10` در همهٔ صفحه‌های این فصل همان‌اند.
