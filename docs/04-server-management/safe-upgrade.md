# به‌روزرسانی سرور بدون از دست رفتن داده

## مقدمه

به‌روزرسانی بسته روی Ubuntu دادهٔ شما را فرمت نمی‌کند. `apt upgrade` فایل‌های `/home`، `/opt/apps`، `/var/lib/mysql`، `/var/lib/postgresql` و `/var/lib/minio` را به عنوان «زباله» پاک نمی‌کند. ترسی که از این جمله می‌آید معمولاً از سه دستور دیگر است: پاک کردن دستی یک پوشه، `purge` بدون خواندن فهرست، و پرش بین نسخه‌های LTS با `do-release-upgrade` بدون بکاپ.

این صفحه روش به‌روزرسانی همان میزبان زنده است، با داده سر جایش. نمونه `app-1.example.internal` روی `10.10.1.10` است. سی دقیقهٔ اول سرور تازه در [بوت‌استرپ](./initial-bootstrap) است. اینجا میزبان از قبل سرویس دارد.

## مفهوم اصلی

سه سطح به‌روزرسانی با سه خطر متفاوت وجود دارد.

سطح اول، به‌روزرسانی امنیتی و جزئی داخل همان انتشار است. `apt update` فقط فهرست را تازه می‌کند. `apt upgrade` بسته‌های قابل به‌روزرسانی را عوض می‌کند و بسته‌ای را که لازم باشد حذف کند عقب می‌اندازد. `apt full-upgrade` اگر برای حل وابستگی لازم باشد بسته را برمی‌دارد. روی 26.04 هر دو داخل همان Resolute می‌مانند. دادهٔ پایگاه معمولاً سر جایش می‌ماند، ولی سرویس ممکن است یک بار restart شود و اگر فایل پیکربندی را شما دست زده باشید، apt بپرسد فایل شما بماند یا فایل بسته بیاید.

سطح دوم، `apt autoremove` است. بسته‌هایی را برمی‌دارد که دیگر هیچ بسته‌ای به آن‌ها وابسته نیست. این دادهٔ `/var/lib` نیست، ولی اگر تنها دلیل نصب یک ابزار همین وابستگی بوده، خود ابزار می‌رود. فهرست را قبل از تأیید بخوانید. پرچم `-y` این خواندن را حذف می‌کند.

سطح سوم، `do-release-upgrade` است. این پرش LTS است، مثلاً از 24.04 به 26.04. دیسک را فرمت نمی‌کند، ولی نسخهٔ اصلی MySQL و PostgreSQL و OpenSSH عوض می‌شود. فایل‌های داده روی دیسک می‌مانند، اما PostgreSQL نسخهٔ اصلی جدید، کلاستر قدیمی را خودش باز نمی‌کند تا `pg_upgradecluster` را اجرا کنید. تا آن لحظه داده هست و سرویس نیست. این همان جایی است که بدون بکاپ، «داده پاک نشده» با «سرویس بالا نمی‌آید» قاطی می‌شود.

دستورهایی که داده را واقعاً نابود می‌کنند و جزء به‌روزرسانی نیستند: `mkfs`، حذف پارتیشن و ساختن دوباره با شروعِ سکتور متفاوت، `rm -rf` روی `/var/lib`، و نصب دوبارهٔ سیستم‌عامل روی همان دیسک بدون نگه داشتن پارتیشن. هیچ‌کدام را برای «آپدیت» اجرا نکنید.

## چرا استفاده می‌شود؟

میزبانِ عقب‌مانده آسیب‌پذیری شناخته‌شده دارد. میزبانی که بی‌برنامه `full-upgrade` و reboot شبانه می‌گیرد، وسط ترافیک Nginx یا پایگاه را یک بار قطع می‌کند و گاهی فایل پیکربندی محلی را با فایل بسته عوض می‌کند. هر دو سر این طیف در تولید دیده می‌شود. این صفحه وسطش است: بکاپ یا اسنپ‌شات، فهرست بسته‌ها، ارتقای کنترل‌شده، و reboot وقتی واقعاً لازم است نه از روی عادت هر شب.

سیاست دانشنامه برای شب‌ها همان است که در بوت‌استرپ آمده: `unattended-upgrades` فقط جیب امنیت. به‌روزرسانی معمولی Nginx، PHP، هستهٔ غیرامنیتی، و پایگاه در ساعت خلوت و با همین صفحه انجام می‌شود.

## Architecture

```text
قبل از دست زدن
    اسنپ‌شات هایپروایزر  یا  بکاپ فصل امنیت
    df -h  فضای خالی برای دانلود بسته
    فهرست بستهٔ قابل ارتقا
            │
            ▼
apt update && apt upgrade
    بسته‌ها در /var/cache/apt
    پیکربندی در /etc  با پرسش conffile
    داده در /var/lib دست نمی‌خورد
            │
            ▼
reboot-required ؟
    بله → پنجرهٔ reboot، بعد healthcheck
    نه → checkrestart برای سرویس‌هایی که کتابخانهٔ کهنه در حافظه دارند
```

اسنپ‌شات دیسکِ ماشین مجازی، اگر هایپروایزر دارید، سریع‌ترین راه برگشت است. بکاپ منطقی پایگاه (`mysqldump` یا `pg_dump`) هنوز لازم است، چون اسنپ‌شاتِ یک پایگاه در حال نوشتن ممکن است به بازیابی نقطه‌ای نیاز داشته باشد. هر دو را با هم برای پرش LTS انجام دهید. برای یک `apt upgrade` کوچک امنیتی روی میزبانی که دیشب بکاپ سالم داشته، اسنپ‌شات همان روز کافی است.

## Installation

ابزار دیدن «چه کسی هنوز فایل پاک‌شده را در حافظه دارد» بستهٔ `debian-goodies` است. اگر در بوت‌استرپ نصب نشده:

```bash
sudo apt update
sudo apt install -y debian-goodies
```

خود `apt` از قبل روی سرور هست. چیز دیگری برای به‌روزرسانی معمولی نصب نکنید.

## Configuration

قبل از ارتقا این‌ها را ثبت کنید. خروجی را در یادداشت تغییر همان روز بگذارید، نه فقط روی ترمینال.

```bash
hostnamectl --static
df -hT /
df -hi /
apt-get -s upgrade | tail -n 30
```

خط `Inst` در شبیه‌سازی یعنی بسته‌ای عوض می‌شود. اگر اسم `mysql-server`، `postgresql`، `nginx`، `docker-ce` یا هسته (`linux-image`) را دیدید، پنجره را خلوت کنید و بکاپ همان روز را چک کنید که قابل خواندن است، نه اینکه فقط فایل dump وجود دارد.

ارتقای معمولی:

```bash
sudo apt update
sudo apt upgrade
```

اگر apt پرسید فایل پیکربندی را نگه دارد یا نسخهٔ بسته را بنویسد، پیش‌فرض امن برای فایلی که خودتان تنظیم کرده‌اید «نگه داشتن نسخهٔ محلی» است. نسخهٔ بسته را فقط وقتی بپذیرید که می‌دانید تغییر بالادست را می‌خواهید و diff را خوانده‌اید. انتخاب کورِ «نسخهٔ نگهدارنده» میانبر از دست دادن `server_name` و قانون فایروال است. apt کپی فایل را معمولاً با پسوند `.dpkg-dist` یا `.dpkg-old` کنار همان مسیر می‌گذارد. بعد از تمام شدن ارتقا این‌ها را پیدا کنید:

```bash
sudo find /etc -name '*.dpkg-dist' -o -name '*.dpkg-old'
```

`full-upgrade` را وقتی بزنید که `apt upgrade` بسته‌ای را عقب انداخته و شما فهرست حذف‌شونده را خوانده‌اید:

```bash
sudo apt full-upgrade
```

`autoremove` را جدا و بدون `-y` بزنید:

```bash
sudo apt autoremove
```

اگر در فهرست `mysql-server` یا `nginx` یا `docker-ce` را دیدید، تأیید نکنید. وابستگی شکسته است و باید دلیلش را بفهمید.

بسته‌ای را که نباید این هفته جلو برود نگه دارید. این قفل دائمی نیست. تاریخ برداشتنش را بنویسید.

```bash
sudo apt-mark hold nginx
apt-mark showhold
sudo apt-mark unhold nginx
```

reboot را apt خودش نمی‌زند. بعد از ارتقا:

```bash
if [ -f /var/run/reboot-required ]; then
  cat /var/run/reboot-required
  cat /var/run/reboot-required.pkgs
fi
sudo checkrestart
```

اگر فایل reboot هست، هسته یا کتابخانه‌ای عوض شده که تا restart کل ماشین در حافظه نمی‌آید. `uptime` و `uname -r` را قبل و بعد مقایسه کنید. بعد از بالا آمدن، SSH و سرویس اصلی را چک کنید:

```bash
systemctl is-active ssh nginx
systemctl --failed
```

پرش LTS جداست. فقط با بکاپ تست‌شده و در پنجرهٔ اعلام‌شده:

```bash
sudo apt update
sudo apt full-upgrade
sudo do-release-upgrade
```

اگر ابزار گفت انتشار جدید پیدا نشده، `do-release-upgrade -c` را بخوانید. پرش را با عوض کردن دستی `ubuntu.sources` از `noble` به `resolute` تقلید نکنید. آن مسیر پرسش‌های `do-release-upgrade` را دور می‌زند و مخزن شخص ثالث را نصفه جا می‌گذارد.

بعد از پرش به 26.04، PostgreSQL 16 کنار 18 ممکن است هر دو بسته نصب باشند و فقط کلاستر جدید خالی بالا باشد. دادهٔ قدیمی هنوز زیر `/var/lib/postgresql/16` است. انتقال با `pg_upgradecluster` است و در فصل پایگاه آمده. تا آن دستور را نزده‌اید داده پاک نشده، فقط سرویس قدیمی ممکن است خاموش باشد. MySQL از 8.0 به 8.4 معمولاً در جا مهاجرت می‌کند و باز هم dump قبلی را نگه دارید تا اولین سلامت بودن کوئری را ببینید.

## Production Example

سه‌شنبه ۱۰ صبح، `app-1` حدود چهل بسته امنیتی عقب است و یک هستهٔ نو در فهرست است. دیسک ریشه ۲۰ گیگابایت خالی دارد. اسنپ‌شات ماشین در پنل مجازی‌سازی گرفته می‌شود و تا پایان سلامت بودن پاک نمی‌شود.

`apt upgrade` را در `tmux` اجرا می‌کنید تا قطع SSH کار را نصفه نگذارد. پرسش conffile برای `/etc/ssh/sshd_config` پیش نمی‌آید چون تنظیم شما در `sshd_config.d` است. برای یک فایل Nginx که محلی است، نسخهٔ خودتان را نگه می‌دارید.

`reboot-required` هست. در همان `tmux` به کاربر برنامه می‌گویید دو دقیقه قطع می‌شوند، بعد `sudo reboot`. بعد از بازگشت، `uname -r` هستهٔ نو را نشان می‌دهد، `systemctl --failed` خالی است، و صفحهٔ سلامت برنامه کد ۲۰۰ می‌دهد. اسنپ‌شات را همان روز پاک نمی‌کنید. فردا اگر کسی گزارش بازگشت باگ داد، هنوز نقطهٔ برگشت هست.

پایگاه را در این سناریو dump جدا نمی‌گیرید چون نسخهٔ اصلی MySQL عوض نشده و بکاپ شب قبل در `/var/backups` قابل خواندن است. اگر در فهرست `mysql-server` با پرش نسخهٔ اصلی بود، dump همان صبح اجباری بود.

## Security Notes

به‌روزرسانی را با کاربر `ops` و `sudo` انجام دهید، نه با ورود root. نشست دوم SSH را قبل از reboot باز نگه دارید تا اگر `sshd` بعد از ارتقا دیر بالا آمد، از نشست فعلی هنوز داخل باشید. این جادو نیست. اگر ماشین واقعاً reboot شود هر دو نشست می‌روند. کنسول هایپروایزر راه برگشت است.

مخزن شخص ثالث را وسط ارتقا اضافه نکنید. یک منبع خراب، بستهٔ هم‌نام را از جای دیگری می‌آورد. `apt-cache policy nginx` باید هنوز از آرشیو Ubuntu باشد مگر خودتان مخزن nginx.org را عمداً اضافه کرده باشید.

`unattended-upgrades` را در این صفحه وسیع‌تر نکنید. شب جمعه جای `full-upgrade` خودکار نیست.

اسنپ‌شات را روی همان دیسکی که فقط یک کپی از داده دارد به عنوان تنها بکاپ حساب نکنید. خراب شدن آن دیسک، هم داده و هم اسنپ‌شات را می‌برد. قانون بکاپ در [بکاپ سرور](/docs/10-security/backup) است.

## Troubleshooting

| نشانه | معنی | کار |
| --- | --- | --- |
| `No space left on device` وسط apt | کش یا دیسک ریشه پر است | ارتقا را تکرار نکنید. [دیسک پر](/docs/14-troubleshooting/disk-full) را خلوت کنید، بعد `sudo dpkg --configure -a` و دوباره `apt upgrade` |
| `dpkg was interrupted` | ارتقای قبلی نصفه مانده | `sudo dpkg --configure -a` سپس `sudo apt -f install` |
| پرسش conffile را اشتباه جواب داده‌اید | فایل شما با `.dpkg-old` مانده | diff بگیرید و دستی ادغام کنید. بسته را purge نکنید |
| بعد از reboot سایت بالا نیست | سرویس enable نبوده یا پیکربندی شکسته | `systemctl --failed` و `nginx -t`. اسنپ‌شات را فقط وقتی برگردانید که ادغام پیکربندی بیشتر از پنجره طول می‌کشد |
| PostgreSQL بعد از پرش LTS بالا نمی‌آید | کلاستر قدیمی با دودویی جدید باز نمی‌شود | داده را پاک نکنید. `pg_lsclusters` را ببینید و مسیر ارتقای فصل پایگاه را بروید |
| `autoremove` می‌خواهد docker را بردارد | مخزن یا وابستگی قاطی شده | رد کنید. `apt-cache policy docker-ce` |

اگر `apt` قفل است، فرایند دیگر apt را با `ps` پیدا کنید. قفل `/var/lib/dpkg/lock` را با `rm` برندارید مگر مطمئن باشید هیچ aptای در حال اجرا نیست. حذف قفلِ زنده، پایگاه dpkg را نصفه می‌کند و آن وقت تعمیرش از خود ارتقا سخت‌تر است.

## Best Practices

- ارتقا را در `tmux` یا `screen` شروع کنید.
- قبل از پرش LTS، بکاپ را یک بار واقعاً برگردانید یا حداقل `gzip -t` و یک restore آزمایشی روی ماشین دیگر بگیرید.
- داده‌های پایگاه و فایل کاربر را جزء «چیزی که apt ممکن است پاک کند» فرض نکنید و برای همین هم دست به `rm` نزنید. فرض درست این است که apt داده را پاک نمی‌کند و انسان با دستور اضافه پاک می‌کند.
- بعد از هستهٔ نو، reboot را به هفتهٔ بعد موکول نکنید. تا reboot، وصله در دیسک است نه در هسته‌ای که حمله می‌بیند.
- فهرست `apt-mark showhold` را ماهانه بخوانید. بستهٔ نگه‌داشته‌شدهٔ فراموش‌شده همان سوراخی است که به‌روزرسانی باید می‌بست.
