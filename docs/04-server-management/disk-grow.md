# بزرگ کردن دیسک بدون پاک شدن داده

## مقدمه

وقتی دیسک پر می‌شود، راه امن اضافه کردن فضاست نه پاک کردن دادهٔ برنامه. اگر دیسک را در پنل ماشین مجازی بزرگ کنید و داخل Ubuntu کاری نکنید، `df` همان عدد قدیمی را نشان می‌دهد. هسته دیسک بزرگ‌تر را می‌بیند، ولی پارتیشن و حجم منطقی و فایل‌سیستم هنوز به انتهای قدیمی ختم می‌شوند.

این صفحه همان سه لایه را، به ترتیب و بدون حذف فایل، جلو می‌برد. فرض آزمایشگاه دیسکی است که در نصب اولیه LVM شده: پارتیشن روی `/dev/sda`، گروه حجمی، و حجم منطقی ریشه با ext4 یا xfs. نام دقیق را از `lsblk` همان میزبان بگیرید. اگر نام را از این صفحه کپی کنید و دیسک شما `vda` یا `nvme0n1` باشد، دستور را به دیسک اشتباه می‌زنید.

## مفهوم اصلی

فضای خالیِ تازه‌ای که هایپروایزر به انتهای دیسک چسبانده، هنوز مال هیچ پارتیشنی نیست. `growpart` انتهای پارتیشن را جلو می‌برد بدون اینکه سکتور شروع را عوض کند. عوض شدن سکتور شروع یعنی فایل‌سیستم از جای غلط خوانده می‌شود و این همان پاک شدن عملی داده است. برای همین پارتیشن را پاک نکنید و با `fdisk` از نو نسازید مگر اینکه دقیقاً همان سکتور شروع را دوباره وارد کنید و این صفحه را کنار بگذارید و آهسته بروید. `growpart` همین کار را امن‌تر می‌کند.

اگر حجم ریشه روی LVM است، بعد از پارتیشن باید `pvresize` فضای جدید را به گروه حجمی بدهد و `lvextend` حجم منطقی را بکشد. فلگ `-r` فایل‌سیستم را هم همراه حجم بزرگ می‌کند: برای ext4 معادل `resize2fs` و برای xfs معادل `xfs_growfs`. هر دو روی فایل‌سیستمِ وصل‌شده کار می‌کنند. لازم نیست `umount` کنید و لازم نیست داده را جابه‌جا کنید.

کوچک کردن برعکس این صفحه است. ext4 را برای کوچک کردن باید جدا کنید. xfs را اصلاً نمی‌شود کوچک کرد. این صفحه فقط بزرگ کردن است.

## چرا استفاده می‌شود؟

پاک کردن لاگ و بکاپ کهنه وقتی دیسک واقعاً از فایل مرده پر شده درست است و در فصل عیب‌یابی آمده. وقتی دادهٔ زنده بزرگ شده، پاک کردن `/var/lib` برای جا باز کردن حادثه است. بزرگ کردن دیسکِ مجازی معمولاً چند دقیقه است و فایل‌ها سر جایشان می‌مانند.

بدون ترتیب لایه‌ها، آدم پارتیشن را بزرگ می‌کند و فکر می‌کند تمام شده، در حالی که `df` هنوز ۱۰۰ درصد است. یا فقط `lvextend` می‌زند و فایل‌سیستم را فراموش می‌کند و `df` باز هم قدیمی است.

## Architecture

```text
پنل مجازی‌سازی
    دیسک ۴۰G به ۸۰G
            │
            ▼
هسته   lsblk دیسک را ۸۰G می‌بیند
            │
            ▼
growpart   انتهای پارتیشن LVM جلو می‌رود
            │  سکتور شروع ثابت
            ▼
pvresize   گروه حجمی فضای تازه را می‌بیند
            │
            ▼
lvextend -r
    حجم منطقی ریشه
    و فایل‌سیستم ext4 یا xfs
            │
            ▼
df -hT   همان عدد تازه، بدون reboot اجباری
```

reboot بعد از بزرگ کردن معمولاً لازم نیست. اگر هسته دیسک جدید را ندید، یک بار `echo 1 | sudo tee /sys/class/block/sda/device/rescan` برای SCSI، یا reboot اگر هایپروایزر دیسک را تا restart مهمان نشان نمی‌دهد. داده در این reboot جابه‌جا نمی‌شود.

## Installation

بستهٔ `cloud-guest-utils` دستور `growpart` را می‌آورد. `lvm2` اگر از اول LVM نصب کرده باشید هست. `xfsprogs` فقط اگر فایل‌سیستم xfs است.

```bash
sudo apt update
sudo apt install -y cloud-guest-utils lvm2
```

قبل از هر دستور نوشتنی، تصویر وضعیت را بردارید:

```bash
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT
sudo pvs
sudo vgs
sudo lvs
findmnt -no SOURCE,FSTYPE,TARGET /
df -hT /
```

نمونهٔ سالم روی ریشهٔ LVM شبیه این است. نام‌ها مال میزبان شما ممکن است فرق کند.

```text
sda                         80G
└─sda3                      40G
  └─ubuntu--vg-ubuntu--lv   40G   ext4   /
```

اینجا دیسک ۸۰ شده و حجم منطقی هنوز ۴۰ است. کار همین فاصله است. اگر `lsblk` هنوز دیسک را ۴۰ نشان می‌دهد، هایپروایزر را دوباره چک کنید و rescan را بزنید. `growpart` را روی دیسک کوچک نزنید.

## Configuration

شمارهٔ پارتیشنی را بزرگ کنید که LVM روی آن است، نه پارتیشن EFI. در نمونهٔ بالا پارتیشن ۳ است.

```bash
sudo growpart /dev/sda 3
sudo pvresize /dev/sda3
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
df -hT /
```

`+100%FREE` همهٔ فضای تازهٔ گروه حجمی را به همان حجم منطقی می‌دهد. اگر می‌خواهید برای حجم دیگر جا بماند، به‌جای آن اندازهٔ مشخص بدهید، مثلاً `-L +20G`. یک بار `-L` و یک بار `-l` را با هم نزنید.

اگر `findmnt` نوع را `xfs` نشان داد، همان `-r` کافی است. اگر خواستید جدا اجرا کنید، xfs را با مسیر نقطهٔ اتصال بزرگ می‌کنند نه با دستگاه:

```bash
sudo xfs_growfs /
```

ext4:

```bash
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

دوبار اجرا کردن `resize2fs` وقتی فایل‌سیستم از قبل هم‌اندازهٔ حجم است، داده را خراب نمی‌کند. می‌گوید کاری نمانده.

اگر ریشه LVM نیست و پارتیشن مستقیم ext4 است، بعد از `growpart` فقط `resize2fs` روی همان پارتیشن است. `pvresize` را به دیسکی که LVM ندارد نزنید.

پارتیشن EFI و `/boot` را با این روش «برای جا باز کردن» بزرگ نکنید مگر واقعاً خودشان پر شده باشند. فضای داده مال حجم ریشه یا مال حجم جداگانه‌ای است که `/var` روی آن است.

## Production Example

`app-1` دیسک ریشه را ۹۴ درصد پر کرده. بکاپ شب در `/var/backups` مانده و دادهٔ برنامه زیر `/opt/apps` است. در پنل، دیسک از ۴۰ به ۸۰ گیگابایت می‌رسد. داخل مهمان `lsblk` عدد ۸۰ را روی `sda` نشان می‌دهد و حجم منطقی هنوز ۴۰ است.

`growpart` و `pvresize` و `lvextend -r` را می‌زنید. `df -hT /` حدود ۷۵ گیگابایت با درصد پایین‌تر نشان می‌دهد. `du -sh /opt/apps /var/lib/mysql` همان اندازه‌های قبل از کار است. هیچ سرویسی restart نشده. اگر MySQL وسط کار خطا نداده، لازم نیست برای بزرگ شدن دیسک restart شود.

یک ساعت بعد دوباره `df` می‌گیرید. اگر درصد دوباره بالا رفت، رشد داده واقعی است و بزرگ کردن فقط وقت خریده. آن وقت یا دیسک را باز هم زیاد می‌کنید یا دادهٔ کهنه را با روش صفحهٔ دیسک پر جابه‌جا می‌کنید، نه با حذف کور.

## Security Notes

دستورهای این صفحه دستگاه بلوک را هدف می‌گیرند. یک شماره پارتیشن اشتباه، پارتیشن EFI را دفرمه نمی‌کند اگر `growpart` فقط انتها را بکشد، ولی `mkfs` روی هر دستگاهی جدول فایل را از نو می‌سازد و داده را غیرقابل استفاده می‌کند. در این صفحه `mkfs` نیست. اگر آموزشی جای دیگر `mkfs` را وسط بزرگ کردن آورده، همان را اجرا نکنید.

`lvextend` بدون `-r` داده را پاک نمی‌کند. فقط `df` را دیر به‌روز می‌کند. عجله برای «تمام شدن» را با دستور تخریبی عوض نکنید.

اسنپ‌شات قبل از اولین باری که این کار را روی میزبان تولید می‌کنید ارزان است. بعد از اینکه یک بار روی همان الگوی دیسک جواب گرفتید، تکرارش کم‌خطر است، به شرطی که باز هم `lsblk` را بخوانید و نام دستگاه را از روی آن کپی کنید.

## Troubleshooting

| نشانه | کار |
| --- | --- |
| `growpart` می‌گوید NOCHANGE | پارتیشن از قبل تا انتهای دیسک آمده، یا هسته دیسک نو را ندیده. `lsblk` و rescan |
| `pvresize` فضا اضافه نمی‌کند | پارتیشن هنوز کوچک است یا روی دستگاه اشتباه زده‌اید. `sudo pvs` باید `PSize` بزرگ‌تر را نشان دهد |
| `df` بعد از `lvextend` عوض نشده | `-r` نبوده. `resize2fs` یا `xfs_growfs` را جدا بزنید. نوع را از `findmnt` بگیرید |
| `xfs_growfs` می‌گوید not mounted | مسیر نقطهٔ اتصال را بدهید، نه `/dev/mapper/...` را اگر آن را جدا کرده‌اید |
| سیستم بعد از reboot بالا نمی‌آید | سکتور شروع پارتیشن عوض شده. از اسنپ‌شات برگردید. با `fdisk` خلاقیت به خرج ندهید |
| فقط `/var` پر است و `/` خالی است | حجم جداست. همان LV که `findmnt /var` نشان می‌دهد را بکشد، نه حتماً ریشه را |

اگر `lsblk` نام `nvme0n1p3` نشان داد، دستگاه `growpart` می‌شود `/dev/nvme0n1` و شمارهٔ پارتیشن `3`. فاصله را برندارید و به `sda` برنگردانید.

## Best Practices

- همیشه قبل از دستور نوشتنی، `lsblk` و `df` و `pvs` را در همان نشست ببینید.
- سکتور شروع پارتیشن را عوض نکنید.
- فایل‌سیستم را همراه حجم بزرگ کنید و با `df` تمام شدن را ثابت کنید، نه با پیام «تمام شد» هایپروایزر.
- این کار جای بکاپ نیست. دیسک بزرگ‌تر، خراب شدن را دیرتر می‌کند نه بی‌اثر.
- روی پایگاه شلوغ، بزرگ کردن آنلاین مجاز است. کوچک کردن و `mkfs` مجاز نیست.
