# برچسب و انتشار

## مقدمه

شاخه حرکت می‌کند. برچسب (tag) باید ثابت بماند. انتشاری که فردا روی `app-1.example.internal` اجرا می‌شود با نام شاخهٔ `main` مشخص نمی‌شود، چون `main` تا شب چند کامیت جلو رفته است. نام ثابت این فصل `v1.4.2` است و به کامیت ادغام `0ab77e1` وصل است. همان عدد، بدون پیشوند `v`، نام ایمیج است: `app:1.4.2`.

اگر این دو نام از هم جدا شوند، لاگ مانیتورینگ یک نسخه می‌گوید و کانتینر نسخهٔ دیگری اجرا می‌کند. این صفحه همان گره را می‌بندد. ادغامی که زیر برچسب می‌نشیند در [ادغام و بازنویسی](./merge-rebase.md) است و ترتیب انسانی انتشار در [گردش‌کار](./workflows.md).

## مفهوم اصلی

برچسب سبک (lightweight) فقط یک نام در `refs/tags` است که به یک کامیت اشاره می‌کند. نویسنده، تاریخ، و پیام ندارد. برای نشانه‌گذاری محلیِ گذرا بد نیست. برای انتشار بد است، چون از یک شاخه قابل تشخیص نیست و `git push --follow-tags` آن را با شاخه نمی‌فرستد.

برچسب annotated یک شیء از نوع tag در پایگاه است. فیلدهایش این‌هاست: شیء هدف، نوع هدف، نام برچسب، tagger، تاریخ، و پیام. هدف معمولاً یک کامیت است. `git show v1.4.2` اول شیء برچسب را نشان می‌دهد و بعد کامیتی که زیر آن است. `git tag -a v1.4.2 -m "پیام"` این شیء را می‌سازد.

حرکت دادن برچسبی که یک‌بار push شده، در عمل یعنی یک انتشار را دو معنی کردن. Git به‌صورت پیش‌فرض به‌روزرسانی برچسب روی ریموت را رد می‌کند. اگر کسی با اجبار آن را عوض کند، کش CI و سرورهایی که آن نام را دارند با هم فرق می‌کنند. در این تیم برچسب انتشار حرکت نمی‌کند. اصلاح بعدی `v1.4.3` است، نه جابه‌جا کردن `v1.4.2`.

`git push --follow-tags` همان push معمولی شاخه است، به‌علاوهٔ برچسب‌های annotated که از کامیت‌های در حال ارسال قابل رسیدن هستند و روی ریموت نیستند. برچسب سبک با این پرچم نمی‌رود. `git push --tags` همهٔ برچسب‌ها را می‌فرستد، از جمله نشانهٔ محلی که نباید به سرور برسد. در اسکریپت انتشار از `--tags` استفاده نمی‌کنیم.

رابطه با Docker عمدی و ساده است. Git عدد را با `v` نگه می‌دارد تا در `git describe` و در گفتگوی نسخه معلوم باشد. رجیستری ایمیج، طبق قرارداد همین آزمایشگاه، همان عدد را بدون `v` می‌گیرد. `latest` نام انتشار نیست. `latest` یعنی «آخرین چیزی که یک نفر push کرده» و برای برگشت به عقب اسم ندارد.

## چرا استفاده می‌شود؟

pipeline به یک نام متحرک اعتماد نکند. اگر Job روی نوک `main` بیلد شود، تکرار همان Job در روز بعد شیء دیگری است، حتی اگر پیام کامیت شبیه باشد. برچسب annotated این تکرار را به یک هش قفل می‌کند.

استقرار هم به همان قفل نیاز دارد. چه مسیر، checkout در `/opt/apps/app` باشد و چه اجرای کانتینر، باید بتوان پرسید «الان v1.4.2 است یا نه». شاخه این سؤال را فردا غلط جواب می‌دهد.

پیام برچسب جای یادداشت انتشار کوتاه است: چه چیزی برای عملیات مهم است، نه فهرست همهٔ diff. جزئیات داخل کامیت‌ها مانده است. پیام `v1.4.2` می‌گوید مهلت کلاینت صورتحساب ۸ ثانیه شده و ایمیج متناظر چیست، تا شیفت شب مجبور نباشد تاریخ را از نو تفسیر کند.

## Architecture

```text
refs/heads/main  ----------------------->  0ab77e1
refs/tags/v1.4.2  -->  شیء tag
                         object 0ab77e1
                         type   commit
                         tag    v1.4.2
                         tagger Ops

سبک، اگر اشتباهی ساخته شود:
refs/tags/wip-local  -->  0ab77e1     مستقیم، بدون شیء tag

انتشار

  v1.4.2
     │
     ├── git push --follow-tags     برچسب annotated همراه main
     │
     ├── Runner
     │     docker build
     │     نام ایمیج app:1.4.2
     │
     └── app-1.example.internal
           همان ایمیج، یا checkout همان کامیت
           هرگز latest به‌تنهایی
```

رجیستری‌ای که ایمیج تیم را نگه می‌دارد با آینهٔ کش ایمیج‌های عمومی یکی نیست. آینهٔ `mirror.example.internal` برای کشیدن ایمیج پایه است. ایمیج خود `app` را pipeline به رجیستری‌ای که سازمان انتخاب کرده می‌فرستد. در آزمایشگاه، اگر GitLab رجیستری را روشن کرده باشد، میزبان همان `gitlab.example.internal` است. عدد نسخه عوض نمی‌شود، هر کدام میزبان باشد.

`git describe` نزدیک‌ترین برچسب annotated قابل رسیدن از HEAD را پیدا می‌کند. اگر HEAD خودش همان برچسب باشد، فقط نام برچسب را برمی‌گرداند. اگر جلوتر باشد، پسوند تعداد کامیت و هش کوتاه می‌چسباند. آن پسوند یعنی «این دقیقاً انتشار نیست». استقرار باید `--exact-match` بخواهد تا این پسوند مخفی نماند.

## Installation

برچسب جزء خود Git است. بستهٔ جدا برای tag وجود ندارد.

```bash
sudo apt update
sudo apt install -y git
git --version
```

```text
git version 2.53.0
```

امضای GPG برچسب با `-s` وقتی کلید سازمانی و `gpg` نصب باشد ممکن است. این صفحه امضا را اجباری نمی‌کند، چون ساختن کلید خصوصی نمونه کار خطرناکی است و کلید واقعی نباید در دانشنامه بیاید. اگر تیم امضا را روشن کرد، نبودن کلید باید `git tag -s` را با خطا متوقف کند.

هویت tagger از همان `user.name` و `user.email` می‌آید. روی لپ‌تاپ شخصی می‌تواند در `~/.gitconfig` باشد. داخل مخزن کاری، برای اینکه معلوم باشد این انتشار را کدام پیکربندی زده، محلی هم تنظیم کنید:

```bash
cd /home/ops/src/app
git config user.name "Ops"
git config user.email "ops@example.internal"
```

روی `app-1` برچسب نسازید. سرور مصرف‌کننده است. ساخت برچسب روی checkout استقرار، برچسبی می‌سازد که در `origin` نیست و شیفت بعد آن را با انتشار واقعی اشتباه می‌گیرد.

## Configuration

این مخزن برچسب annotated را همراه push شاخه بفرستد. تنظیم را محلی مخزن بگذارید تا روی لپ‌تاپ، مخزن‌های آزمایشی دیگر را غافلگیر نکند.

```bash
cd /home/ops/src/app
git config push.followTags true
git config --get push.followTags
```

با این مقدار، `git push` همان اثر `--follow-tags` را دارد. هنوز فقط annotated و فقط آن‌هایی که از کامیت‌های همین push قابل رسیدن‌اند. اگر یک‌بار خواستید این رفتار خاموش باشد، `--no-follow-tags` همان دفعه کافی است. تنظیم سراسری `push.followTags` روی حساب مشترک سرور لازم نیست و نباید باشد.

نام‌گذاری را در یادداشت تیم ثابت کنید، نه با یک قلاب Git که نسخه را حدس بزند:

- پیشوند `v`
- سه عدد: ناسازگار، ویژگی، اصلاح
- `v1.4.2` اصلاح روی خط `1.4` است
- ویژگی بعدی `v1.5.0` است
- هیچ برچسبی `latest` یا `stable` نام ندارد

قیچی کردن `v` برای Docker کار pipeline است، نه کار دستی روی سرور. یک خط پوسته در Job کافی است و باید همان برچسب Git باشد، نه یک متغیر که کسی در رابط وب تایپ کرده.

```bash
tag="$(git describe --tags --exact-match HEAD)"
version="${tag#v}"
printf '%s\n' "$version"
```

خروجی روی کامیت انتشار:

```text
1.4.2
```

اگر `describe` شکست بخورد، Job باید همان‌جا بمیرد. ساختن `app:latest` به‌عنوان جایگزین، شکست را مخفی می‌کند.

## Production Example

بعد از اینکه `main` به کامیت ادغام `0ab77e1` رسید و تست همان کامیت سبز بود، برچسب را روی همان کامیت بزنید، نه روی نوک یک شاخهٔ feature.

```bash
cd /home/ops/src/app
git switch main
git pull --ff-only origin main
git log -1 --oneline --decorate
git tag -a v1.4.2 -m "release: billing timeout 8s

Image app:1.4.2 is built from this commit.
Rollback target remains v1.4.1."
git show v1.4.2
```

`git show` هم شیء برچسب را نشان می‌دهد و هم خلاصهٔ کامیت را. شکل سالم، با هش نمونهٔ همین فصل:

```text
tag v1.4.2
Tagger: Ops <ops@example.internal>
Date:   Wed Sep 23 16:10:02 2026 +0330

release: billing timeout 8s

Image app:1.4.2 is built from this commit.
Rollback target remains v1.4.1.

commit 0ab77e14c5d6e7f8091a2b3c4d5e6f708192a3b4 (HEAD -> main, tag: v1.4.2)
Merge: d09aa31 f52cc07
Author: Ops <ops@example.internal>
Date:   Wed Sep 23 16:05:41 2026 +0330

    Merge branch 'feature/billing-timeout'
```

اگر `git show` بخش `Tagger` نداشت، برچسب سبک ساخته‌اید. آن را برای انتشار استفاده نکنید. تا وقتی push نشده، می‌شود نام محلی را برداشت و annotated را از نو ساخت. بعد از push، نام سوخته است و باید شمارهٔ بعدی بگیرید.

فرستادن شاخه و برچسب با هم:

```bash
git push --follow-tags origin main
```

```text
To gitlab.example.internal:ops/app.git
   d09aa31..0ab77e1  main -> main
 * [new tag]         v1.4.2 -> v1.4.2
```

اگر `push.followTags` را قبلاً در همین مخزن true کرده باشید، پرچم تکراری است و ضرر ندارد. صریح بودنش در دستور انتشار بهتر است، چون خوانندهٔ لاگ Job می‌بیند برچسب عمداً رفته است.

کنترل نوع شیء:

```bash
git cat-file -t v1.4.2
git rev-parse v1.4.2^{commit}
```

خط اول باید `tag` باشد نه `commit`. خط دوم کامیت زیر برچسب است و باید با `git rev-parse HEAD` روی همان انتشار یکی باشد. این دو را داخل پوسته بگذارید. در نثر، «باز کردن برچسب تا کامیت» همان کار خط دوم است.

از اینجا به بعد Git تمام شده و استقرار شروع شده است. Runner که به برچسب واکنش نشان می‌دهد در [GitLab Runner](/docs/09-cicd/gitlab-runner) ثبت می‌شود. Job باید ایمیج را `app:1.4.2` بسازد، نه `app:latest`. اجرای آن ایمیج روی میزبان در [Docker در Production](/docs/08-deployment/docker-production) است. اگر هنوز کانتینر ندارید و درخت را روی دیسک می‌گذارید، checkout همان برچسب در [استقرار دستی](/docs/08-deployment/manual-ssh) است و مسیرش `/opt/apps/app` است. هر دو مسیر باید بتوانند بگویند نسخه `1.4.2` است. داشتن دو نسخهٔ همزمان روی `app-1` بدون اسم، بازگشت به عقب را غیرممکن می‌کند.

برگشت به عقب یعنی اجرای دوبارهٔ `app:1.4.1` یا checkout برچسب `v1.4.1`، نه rebase کردن `v1.4.2` تا «اصلاح داخل همان شماره جا شود». شمارهٔ قبلی باید برای همیشه همان بایت‌ها را معنی بدهد.

## Security Notes

برچسب را روی مخزن عمومیِ تصادفی نگذارید اگر سورس خصوصی است. نام برچسب خودش معمولاً راز نیست، ولی `git show` پیام و بعداً با clone کل درخت را هم می‌دهد. خصوصی بودن پروژهٔ GitLab مرز اصلی است.

هر کسی که می‌تواند برچسب را روی `main` بزند در عمل می‌تواند انتشار اعلام کند. در GitLab این را به Maintainer محدود کنید. Developer که شاخهٔ feature را push می‌کند لازم نیست بتواند `v1.4.2` بسازد.

جابه‌جا کردن برچسب منتشرشده یک حادثه است، حتی اگر «فقط پیام را درست می‌کردیم». کسی که `v1.4.2` را به کامیت دیگری برده، ایمیج `app:1.4.2` را دروغگو کرده است. رجیستری هم اگر همان نام را دوباره push کند، لایه‌ها عوض می‌شوند و سروری که ایمیج را کش کرده با سروری که تازه pull کرده فرق دارد. پاسخ حادثه: آن نام را نسوزانید با یک overwrite سوم. شمارهٔ جدید بدهید، ایمیج جدید بسازید، و در یادداشت بگویید `v1.4.2` دیگر قابل اعتماد نیست. پاک کردن برچسب از ریموت با force در این دانشنامه دستور کار نیست.

`latest` علاوه بر ابهام، یک مشکل امنیتی عملی دارد. اگر pipeline خراب چیزی را با `latest` منتشر کند، استقرار بعدی که کورکورانه `latest` می‌کشد همان خرابی را به Production می‌برد. قفل بودن به `1.4.2` یعنی خراب شدن Job جدید، نسخهٔ در حال اجرا را عوض نمی‌کند.

پیام برچسب را جای رمز و توکن استفاده نکنید. پیام داخل شیء tag است و با clone می‌آید.

## Troubleshooting

| نشانه | معنی |
| --- | --- |
| `tag 'v1.4.2' already exists` | محلی این نام را دارید. `git show v1.4.2` بگوید annotated است یا نه. اگر غلط است و push نشده، حذف محلی و ساخت دوباره. اگر push شده، شمارهٔ جدید |
| push شاخه رفت ولی برچسب نه | برچسب سبک بوده، یا از کامیت‌های همین push قابل رسیدن نیست، یا `--follow-tags` را نزده‌اید و `push.followTags` هم خاموش است |
| `would clobber existing tag` | ریموت این نام را دارد و مال شما فرق دارد. نام را عوض نکنید با اجبار. ببینید کدام کامیت واقعی انتشار است |
| `git describe --exact-match` خطا می‌دهد | HEAD برچسب ندارد. برای Job انتشار این شکست درست است |
| سرور `1.4.2` است ولی رفتار `1.4.1` است | یا ایمیج کش شده، یا checkout با درخت کثیف است، یا فرآیند ری‌استارت نشده. هش داخل کانتینر یا `git rev-parse HEAD` روی سرور را با `git rev-parse v1.4.2` مقایسه کنید |
| `cat-file -t` می‌گوید `commit` | این نام سبک است. برای `app:1.4.2` به آن تکیه نکنید |

اگر دو نفر هم‌زمان برچسب را ساختند و هش‌ها فرق دارد، زودتر push شده برنده نیست از نظر معنی. برنده کسی است که pipeline سبز و یادداشت انتشار دارد. نفر دوم شمارهٔ بعدی را می‌گیرد، حتی اگر کارش کوچک‌تر باشد.

## Best Practices

- انتشار فقط annotated است. سبک را برای یادداشت شخصی روی لپ‌تاپ نگه دارید و push نکنید.
- `git push --follow-tags` را به `--tags` ترجیح دهید.
- `v1.4.2` و `app:1.4.2` یک عدد باشند. پیشوند `v` فقط مال Git است.
- برچسب را بعد از سبز شدن تست روی همان کامیت بزنید، نه قبل از merge.
- برچسب منتشرشده را جابه‌جا نکنید. اصلاح، شمارهٔ تازه است.
- استقرار و بازگشت به عقب هر دو با شمارهٔ صریح انجام می‌شوند، نه با `latest` و نه با نوک `main`.
