# معماری Git

## مقدمه

بیشتر خطای روزمرهٔ Git از قاطی کردن سه جا می‌آید: فایلی که در ویرایشگر است، چیزی که `git add` به کامیت بعدی سپرده، و چیزی که واقعاً داخل تاریخ ثبت شده. این صفحه همان مدل را روی دیسک نشان می‌دهد تا دستورهای فصل بعد معنی داشته باشند.

مثال‌ها روی مخزن سرویس `app` هستند. اگر هنوز مخزن نساخته‌اید، نصب و هویت در [نقشهٔ فصل](./index.md) است و ساخت مخزن در [مخزن](./repository.md). برای دیدن مدل، یک مخزن محلی کوچک کافی است و لازم نیست به `gitlab.example.internal` وصل باشید. Git برای ساخت شیء به شبکه نیاز ندارد.

## مفهوم اصلی

Git محتوا را سه بار، با سه نقش متفاوت، نگه می‌دارد.

درخت کاری (working tree) همان پوشهٔ پروژه است، منهای `.git`. این فایل‌ها معمولی‌اند. می‌شود با ویرایشگر عوضشان کرد و می‌شود پاکشان کرد. Git تا وقتی دستور نزنید این تغییر را ثبت نمی‌کند.

فهرست (index) یک فایل باینری به نام `.git/index` است. نام دیگرش ناحیهٔ آماده‌سازی (staging area) است. index می‌گوید کامیت بعدی، اگر همین حالا ساخته شود، چه درختی خواهد بود. `git add` درخت کاری را به تاریخ وصل نمی‌کند. فقط محتوای فعلی فایل را به شکل یک شیء blob در پایگاه می‌نویسد و مسیر را در index به آن blob وصل می‌کند.

پایگاه شیء (object database) زیر `.git/objects` است. هر شیء با درهم‌ساز (hash) محتوایش نام‌گذاری می‌شود. تا وقتی `git gc` اشیاء را بسته‌بندی نکرده، فایل شل (loose object) در مسیری مثل `.git/objects/6f/8a1c2d...` است. دو حرف اول هش نام پوشه است و بقیه نام فایل. محتوای فایل قبل از ذخیره‌سازی با zlib فشرده می‌شود. شیء تکراری دوباره ذخیره نمی‌شود، چون نامش از محتوا می‌آید.

چهار نوع شیء کافی است:

| نوع | چه چیزی است |
| --- | --- |
| blob | محتوای یک فایل، بدون نام. نام فایل داخل blob نیست |
| tree | یک پوشه: حالت فایل، نام، و هش blob یا tree فرزند |
| commit | هش یک tree ریشه، والد یا والدها، نویسنده، committer، پیام |
| tag | شیء برچسب annotated: به کدام شیء اشاره می‌کند، چه کسی، چه پیامی |

کامیت یک تصویر لحظه‌ای (snapshot) است. وصله (diff) را Git موقع `git show` و `git log -p` از مقایسهٔ دو tree حساب می‌کند. داخل بسته (pack) ممکن است برای صرفه‌جویی دلتا ذخیره شود، ولی مدل ذهنی شما باید تصویر باشد نه زنجیرهٔ وصله. به همین دلیل دو کامیت که فایل عوض‌نشده دارند به یک blob مشترک اشاره می‌کنند و مخزن به اندازهٔ «یک کپی کامل از هر نسخهٔ هر فایل» بزرگ نمی‌شود.

هش پیش‌فرض در Git 2.53 هنوز SHA-1 است و ۴۰ رقم hexadecimal دیده می‌شود. مخزن SHA-256 با `git init --object-format=sha256` ممکن است، ولی مخزن Production را بی‌برنامه عوض نکنید. ابزار، آینه، و GitLab باید همان قالب را بفهمند. SHA-1 امروز برای امضای کور کافی نیست. Git سال‌هاست تشخیص برخورد (collision) را موقع ایندکس کردن شیء دارد. این دلیل نمی‌شود مخزن را روی یک قالب آزمایشی ببرید. قالب را با دستور ببینید، حدس نزنید.

سه حالت فایل در مدل کلاسیک Git این‌هاست:

1. committed یعنی نسخهٔ داخل آخرین کامیت، که HEAD می‌بیند.
2. staged یعنی index با HEAD فرق دارد و این فرق سوار کامیت بعدی است.
3. modified یعنی درخت کاری با index فرق دارد و هنوز برای کامیت بعدی انتخاب نشده.

فایل untracked حالت چهارم عملی است: Git هنوز هیچ blob برایش در این مخزن ندارد. تا `git add` نشود نه modified است و نه staged.

## چرا استفاده می‌شود؟

اگر Git فقط «آخرین نسخهٔ فایل» را نگه می‌داشت، نمی‌شد پرسید این خط سه‌شنبه از کجا آمده. مدل شیء این سؤال را ارزان می‌کند: هر کامیت به یک tree کامل اشاره می‌کند، tree به blobها، و blob تکراری فضای دوباره نمی‌گیرد.

جدا بودن index از درخت کاری هم عمدی است. می‌شود در یک فایل دو جور تغییر داشت و فقط یکی را در کامیت آورد. بدون index، یا همهٔ ویرایش‌های ذخیره‌نشده وارد تاریخ می‌شد یا مجبور بودید تغییر را قایم کنید. index همان انتخاب است.

روی `app-1` این مدل یک آزمون مشخص می‌دهد. اگر فایل روی دیسک با blob داخل برچسب `v1.4.2` یکی نیست، سرور همان انتشاری را اجرا نمی‌کند که فکر می‌کنید. مقایسهٔ هش این را در یک دقیقه معلوم می‌کند، بدون اعتماد به تاریخ ویرایش فایل.

## Architecture

```text
/home/ops/src/app/                  درخت کاری
├── src/billing-client.js
├── README.md
└── .git/
    ├── HEAD                        معمولاً: ref: refs/heads/main
    ├── config                      پیکربندی همین مخزن
    ├── index                       فهرست مسیرها و هش blobها
    ├── objects/
    │   ├── 6f/8a1c2d...            blob شل
    │   └── pack/                   بعد از git gc
    ├── refs/heads/main             هش کامیت نوک شاخه
    ├── refs/remotes/origin/main    نوک main آن‌طور که آخرین fetch دیده
    ├── refs/tags/v1.4.2            برچسب
    └── logs/                       reflog، تاریخ حرکت اشاره‌گرها

کامیت
  tree    9b2e1c4a...     ریشهٔ درخت همان لحظه
  parent  d09aa31b...     کامیت قبلی، ادغام دو parent دارد
  author  Ops
  message متن انسانی
```

جریان یک تغییر سالم این است. فلش برگشت یعنی دور ریختن، نه مسیر عادی انتشار.

```text
ویرایش در درخت کاری
        │
        │  حالت modified
        ▼
   git add مسیر
        │
        │  blob در objects، ردیف تازه در index
        │  حالت staged
        ▼
   git commit
        │
        │  tree تازه + شیء commit
        │  refs/heads/BRANCH جلو می‌رود
        │  حالت committed
        ▼
   git push origin
        │
        ▼
   origin همان شیءها را دارد

برگشت، فقط وقتی عمداً می‌خواهید کار ذخیره‌نشده از بین برود:
  درخت کاری  <--  git restore          از index
  درخت کاری  <--  git restore --source از یک کامیت
  index      <--  git restore --staged بیرون آوردن از کامیت بعدی
```

`HEAD` یک فایل متنی است. در کار عادی محتوایش `ref: refs/heads/main` است، یعنی «شاخهٔ فعلی main است». خود main یک فایل متنی دیگر است که فقط هش کامیت نوک را دارد. شاخه شیء جداگانه‌ای نیست. اگر `HEAD` مستقیم هش کامیت را داشته باشد، حالت detached است. این حالت برای استقرار روی یک برچسب مفید است و برای کار روزمره خطرناک، چون کامیت جدید به هیچ شاخه‌ای آویزان نیست.

ردیف index علاوه بر مسیر و هش، حالت فایل (مثلاً فایل معمولی یا اجرایی) و شمارهٔ stage را دارد. stage صفر یعنی مسیر حل شده است. موقع تداخل ادغام، همان مسیر در stageهای ۱ و ۲ و ۳ هم دیده می‌شود: پایه، مال ما، مال شاخهٔ دیگر. تا این ردیف‌ها جمع نشوند کامیت ساخته نمی‌شود.

## Installation

مدل بالا به بستهٔ اضافه نیاز ندارد. همان بستهٔ `git` روی Ubuntu 26.04 کافی است. اگر این ماشین هنوز Git ندارد:

```bash
sudo apt update
sudo apt install -y git
git --version
```

```text
git version 2.53.0
```

برای آزمایش مدل، یک مخزن دور از سرویس واقعی بسازید. شاخه را صریح `main` بنامید. در Git 2.53 پیش‌فرض بالادست هنوز `master` است مگر `init.defaultBranch` ست شده باشد.

```bash
mkdir -p /home/ops/src/app
cd /home/ops/src/app
git init -b main
git config user.name "Ops"
git config user.email "ops@example.internal"
mkdir -p src
printf '%s\n' 'const timeoutMs = 3000;' > src/billing-client.js
git add src/billing-client.js
git commit -m "chore: initial service layout"
git rev-parse --show-object-format
git var GIT_DEFAULT_BRANCH
```

`git rev-parse --show-object-format` باید `sha1` چاپ کند، مگر خودتان موقع init قالب دیگری خواسته باشید. هویت این‌جا داخل `.git/config` همین مخزن است، نه سراسری روی یک سرور مشترک.

## Configuration

چیزی که مدل شیء را عوض می‌کند باید آگاهانه باشد. این سه را بشناسید و بقیه را به حال خود بگذارید.

```bash
git config --show-origin --get init.defaultBranch
git config --show-origin --get core.repositoryFormatVersion
git rev-parse --git-path objects
git rev-parse --git-path index
```

`core.repositoryFormatVersion` در مخزن معمولی `0` است. اگر کسی مخزن را با افزونهٔ قالب ناشناخته ساخته باشد، Git قدیمی‌تر از باز کردنش امتناع می‌کند. این یک محافظ است، نه خطا. فشرده‌سازی و آستانهٔ pack را دست نزنید. هویت را در سطح همین مخزن بگذارید و روی `app-1` با حساب مشترک، `user.name` سراسری نسازید.

## Production Example

سه حالت را با یک وضعیت واقعی ببینید. فرض کنید روی شاخهٔ `feature/billing-timeout` زمان انتظار را در درخت کاری به ۸ ثانیه رسانده‌اید، توضیح README را هم عوض کرده‌اید ولی هنوز add نکرده‌اید، و اسکریپت سلامت هنوز ناشناخته است. یک‌بار فقط فایل برنامه را به index بسپارید.

```bash
cd /home/ops/src/app
git add src/billing-client.js
git status
```

```text
On branch feature/billing-timeout
Your branch is up to date with 'origin/feature/billing-timeout'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   src/billing-client.js

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	deploy/healthcheck.sh
```

خواندن همین خروجی، سه حالت به‌علاوهٔ untracked است. `src/billing-client.js` استیج شده. `README.md` اصلاح شده ولی هنوز مال کامیت بعدی نیست. `deploy/healthcheck.sh` را Git اصلاً نمی‌شناسد. اگر همین حالا کامیت بگیرید، فقط تغییر کلاینت صورتحساب وارد تاریخ می‌شود.

اثبات با هش، نه با حدس. هش درخت کاری باید با blob داخل index یکی باشد، چون همین فایل را add کرده‌اید. هش HEAD هنوز blob قدیمی است.

```bash
git hash-object src/billing-client.js
git rev-parse :src/billing-client.js
git rev-parse HEAD:src/billing-client.js
```

دو خط اول یکی‌اند. خط سوم فرق دارد تا وقتی کامیت نسازید. علامت `:` یعنی «این مسیر را از index بخوان». پیشوند `HEAD:` یعنی «این مسیر را از درخت همان کامیت بخوان».

بعد از کامیت، خود شیء را باز کنید. هش‌ها نمونهٔ آموزشی همین فصل‌اند. روی مخزن شما ۴۰ رقم متفاوت است و ساختار باید همین باشد.

```bash
git cat-file -t HEAD
git cat-file -p HEAD
```

```text
commit
tree 9b2e1c4a8f0d55e6a7b3c1d2e4f60718293a4b10
parent d09aa31b2c4d6e8f0a1b3c5d7e9f1234567890ab
author Ops <ops@example.internal> 1790160728 +0330
committer Ops <ops@example.internal> 1790160728 +0330

fix: raise billing client timeout to 8s

The invoice API p99 is about 5s after the tax-service change.
A 3s client budget aborted valid checkouts on app-1.
```

عدد `1790160728` زمان یونیکس همان `Wed Sep 23 14:22:08 2026 +0330` است. نویسنده (author) و ثبت‌کننده (committer) اینجا یکی‌اند. اگر بعدها کسی کامیت را rebase کند، committer عوض می‌شود و author می‌ماند. این فرق موقع حسابرسی حادثه به درد می‌خورد.

روی سرور، آزمون «آیا دیسک همان برچسب است» این است:

```bash
git -C /opt/apps/app rev-parse HEAD
git -C /opt/apps/app rev-parse v1.4.2^{commit}
```

اگر این دو هش یکی نباشد، checkout سرور آن انتشار نیست. دستور دوم برچسب annotated را تا کامیت زیرش باز می‌کند و فقط داخل پوسته معنی دارد. اگر `git status` روی سرور خالی نیست، درخت را با ویرایشگر «حل» نکنید. یا ایمیج همان برچسب اجرا می‌شود، یا checkout دوباره از همان برچسب ساخته می‌شود.

## Security Notes

پایگاه شیء، سطح دسترسی فایل معمولی لینوکس را دارد. اگر `.git` برای گروه یا دیگران نوشتنی باشد، هر کسی که به آن حساب برسد می‌تواند تاریخ را عوض کند. مخزن روی سرور باید مالک مشخص داشته باشد و برای جهان نوشتنی نباشد. جزئیات مجوز در [کاربر و فایل](/docs/10-security/users-and-files) است.

شیءهای Git رمزنگاری‌شده نیستند. کلون یعنی کپی تمام blobها، از جمله رازی که اشتباهاً کامیت شده. پاک کردن فایل در کامیت جدید، blob قدیمی را حذف نمی‌کند. فرض کنید هر چیزی که یک‌بار push شد، برای همهٔ کسانی که نقش Reporter به بالا دارند قابل خواندن است.

حالت detached روی سرور فقط وقتی قابل قبول است که فرآیند استقرار خودش HEAD را روی برچسب سنجاق کرده باشد و کسی آنجا ویرایش و کامیت نکند. کامیت روی سرور، بدون شاخه، کار را گم می‌کند.

حادثهٔ بازنویسی `main`: اگر کسی اشیاء نوک `main` را عوض کند و ریموت را با force جلو ببرد، هش‌هایی که pipeline و سرور به آن‌ها تکیه کرده‌اند دیگر نوک شاخه نیستند. شیء قدیمی تا وقتی reflog یا یک کلون دیگر آن را نگه داشته از بین نرفته است. این حادثه است. محافظ شاخه باید جلوی این push را بگیرد. دستور انجامش در این دانشنامه رویه نیست.

`safe.directory *` را در پیکربندی سراسری سرور نگذارید. آن ستاره هر مخزنی را که این کاربر ببیند قابل اعتماد می‌کند، از جمله مخزن داخل آرشیوی که یک نفر در `/tmp` باز کرده است.

## Troubleshooting

`git status` تمیز است ولی برنامهٔ در حال اجرا رفتار قدیمی دارد. فرآیند را از درخت کاری جدا ببینید. systemd یا Docker ممکن است باینری یا ایمیج قبلی را نگه داشته باشد. هش HEAD فقط می‌گوید منبع Git چیست، نه اینکه فرآیند همان را بار کرده باشد.

`git hash-object` با `git rev-parse :path` فرق دارد. فایل بعد از `git add` دوباره ویرایش شده و index هنوز blob قبلی را نشان می‌دهد. یک‌بار دیگر add کنید، یا اگر تغییر دوم نباید در کامیت باشد آن را کنار بگذارید. کامیت، index را ثبت می‌کند نه لزوماً آخرین بایت روی دیسک را، اگر بعد از add دوباره ذخیره کرده باشید.

`fatal: path 'src/billing-client.js' exists on disk, but not in 'HEAD'` یعنی فایل در درخت کاری هست و در آن کامیت نبوده. این خطا نیست که با force حل شود. یا مسیر را غلط نوشته‌اید یا آن فایل هنوز کامیت نشده.

پوشهٔ خالی در Git نمی‌ماند، چون tree خالی شیء ماندگار ندارد. اگر برنامه به پوشهٔ خالی نیاز دارد، یک فایل نگهبان عمدی بگذارید و دلیلش را در همان کامیت بنویسید، نه اینکه بعد از clone روی سرور mkdir دستی فراموش شود.

اگر `git cat-file -t HEAD` بگوید `commit` ولی `git status` از مخزن دیگری حرف بزند، متغیر `GIT_DIR` در محیط پوسته مانده است. با `env | grep GIT` ببینید و نشست را تازه کنید. این متغیر روی اسکریپت استقرار اگر اشتباه ست شود، Git را به مخزن مخزن دیگری وصل می‌کند.

## Best Practices

- قبل از هر کامیت `git status` را به سه بخش تقسیم کنید: استیج، تغییر استیج‌نشده، untracked. فقط بخش اول وارد کامیت می‌شود.
- هش را کوتاه‌شده در گفتگو استفاده کنید، ولی در اسکریپت `git rev-parse` کامل را بگیرید تا ابهام پیش نیاید.
- diff را نتیجهٔ مقایسه بدانید، نه چیزی که Git ذخیره کرده است.
- روی سرور درخت کاری را با دست جلو نبرید. یا HEAD همان برچسب است یا استقرار غلط است.
- قالب شیء را وسط عمر مخزن عوض نکنید. `sha1` پیش‌فرض Git 2.53 است و برای این آزمایشگاه کافی است.
- index را با کپی کردن فایل `.git/index` بین ماشین‌ها «منتقل» نکنید. index مال همان درخت کاری است.
