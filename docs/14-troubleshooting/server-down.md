# سرور از شبکه دیده نمی‌شود

## مقدمه

این صفحه وقتی است که به میزبان SSH نمی‌رسد یا اصلاً از شبکه دیده نمی‌شود. میزبان نمونه `app-1.example.internal` روی `10.10.1.10` است. شما هنوز یک نشست روی آن ندارید. ابزار اول کنسول هایپروایزر است، نه یک SSH دیگر با فلگ بیشتر.

سه علتی که این صفحه تا اقدام مشخص پیش می‌برد: دیسک پر که حتی ورود SSH را می‌کشد، فایروال که بسته را دور می‌ریزد، و سرویس `ssh` که گوش نمی‌دهد. اگر کنسول نشان داد ماشین خاموش است، بقیهٔ دستورها را روی هوا نزنید. اول برق و وضعیت VM.

## مفهوم اصلی

دیده نشدن از شبکه یک علامت است با چند مکانیزم. timeout یعنی پاسخ نرسیده. ممکن است میزبان خاموش باشد، مسیر نباشد، یا فایروال بسته را بی‌صدا بیندازد. `Connection refused` یعنی یک میزبان زنده RST داده و روی آن پورت شنونده نیست. این دو را با یک reboot درمان نکنید.

SSH روی Ubuntu واحدی به نام `ssh` دارد، نه لزوماً `sshd`. باینری `sshd` است و واحد `ssh.service` است. `systemctl status ssh` دستور درست این توزیع است.

دیسک صددرصد روی `/` ورود را هم می‌شکند. `sshd` ممکن است TCP را قبول کند و هنگام ساخت نشست، نوشتن روی دیسک شکست بخورد. از بیرون این را timeout یا قطع ناگهانی بعد از احراز هویت می‌بینید. از کنسول گاهی همان ورود هم با `No space left on device` می‌میرد. درمان از کنسول است: جا آزاد کردن، نه reboot. reboot ماشینی که دیسکش پر است ممکن است در بوت هم گیر کند چون سرویس‌ها نمی‌توانند بنویسند.

فایروال ممکن است مال خود میزبان (UFW) باشد یا جلوی آن. اگر از یک میزبان همسایه در `10.10.0.0/16` پورت 22 باز است و از لپ‌تاپ شما نه، قانون میانی است. اگر از خود کنسول `ss` پورت 22 را نشان می‌دهد و از همسایه timeout است، فایروال میزبان یا مسیر است. اگر `ss` خالی است، فایروال مقصر اول نیست. سرویس است.

## چرا استفاده می‌شود؟

reboot از پنل هایپروایزر عادت خطرناکی است. اگر دیسک پر باشد، بوت دوم بدتر می‌شود. اگر فایروال بعد از یک `ufw enable` بی‌دقت SSH را بسته باشد، reboot هیچ چیز را باز نمی‌کند. اگر فقط `ssh.service` مرده باشد، reboot بقیهٔ سرویس‌ها را هم می‌برد در حالی که `systemctl start ssh` کافی بود.

کنسول را کسانی دیر باز می‌کنند که امید دارند SSH «لحظه‌ای» برگردد. اگر دو تلاش با `ssh -v` علت را نگفت، کنسول را باز کنید. هزینهٔ کنسول از هزینهٔ یک reboot کور کمتر است.

## Architecture

```text
لپ‌تاپ شما
    │  ssh -v ops@10.10.1.10
    │
    ├── timeout ─────────── میزبان خاموش، مسیر، یا فیلتر
    ├── refused ─────────── میزبان زنده، sshd گوش نمی‌دهد
    └── قطع بعد از auth ─── اغلب دیسک، مجوز خانه، یا PAM

وقتی SSH نیست:
    کنسول هایپروایزر (virsh console ، noVNC ، سریال ارائه‌دهنده)
        │
        ├── ورود نشد و No space left  →  دیسک
        ├── ورود شد و ss پورت 22 ندارد →  سرویس ssh
        └── ss دارد و از شبکه timeout است →  فایروال یا مسیر
```

همسایهٔ داخل آزمایشگاه، مثلاً `mon-1` روی `10.10.1.40` ، برای آزمون «از داخل شبکهٔ 10.10.0.0/16» به کار می‌آید. اگر به هیچ میزبانی SSH ندارید، فقط کنسول می‌ماند.

## Installation

روی ماشینی که هنوز SSH دارد چیزی نصب نمی‌کنید. `ssh` کلاینت روی لپ‌تاپ هست. روی میزبان خراب، از کنسول، ابزارها از قبل باید باشند: `df` ، `ss` ، `systemctl`. اگر دیسک آن‌قدر پر است که حتی `apt` ممکن نیست، نصب نکنید. جا آزاد کنید.

اگر کنسول می‌گوید دستور `ss` نیست، `netstat` را هم فرض نکنید. `systemctl status ssh` و `cat /proc/net/tcp` برای امشب زیاد است. فردا بستهٔ `iproute2` را برگردانید.

## Configuration

قبل از حادثه این‌ها را روشن کرده باشید وگرنه شب در را به روی خودتان می‌بندید.

ورود کنسول را یک بار در آرامش امتحان کنید. رمز یا کلید کنسول را جایی بگذارید که به SSH همان سرور وابسته نباشد. اگر تنها راه ادمین SSH است و SSH مرد، دیگر راهی نیست جز پنل میزبان ابری.

`sshd` را طوری پیکربندی نکنید که فقط از یک آدرس گوش کند و آن آدرس را بعداً از netplan بردارید. پیکربندی امن SSH در [سخت‌سازی SSH](/docs/10-security/ssh-hardening) است. این صفحه همان را در حادثه باز نمی‌نویسد. فقط واحد و پورت را زنده می‌کند.

UFW باید اجازهٔ SSH را قبل از `enable` داشته باشد. اگر نمی‌دانید دارد یا نه، از کنسول `ufw status` را بخوانید قبل از هر تغییری. جزئیات قانون در [UFW](/docs/10-security/ufw) است.

## Production Example

از لپ‌تاپ به `app-1` وصل نمی‌شوید. پینگ را هم قطع کرده‌اید چون یادتان است پینگ منفی اثبات مرگ نیست، ولی این‌جا پینگ هم جواب نمی‌دهد. همکار می‌گوید شاید خاموش است.

### نشانه

```bash
ssh -v -o ConnectTimeout=5 ops@10.10.1.10
```

خروجی، بعد از چند خط دیباگ، به این می‌رسد:

```text
debug1: Connecting to 10.10.1.10 [10.10.1.10] port 22.
debug1: connect to address 10.10.1.10 port 22: Connection timed out
ssh: connect to host 10.10.1.10 port 22: Connection timed out
```

timeout است، نه refused. پس هنوز نمی‌دانید شنونده نیست یا بسته فیلتر شده یا میزبان پایین است.

### فرضیه

اول خاموش بودن VM. دوم دیسک پر که میزبان آن‌قدر مریض است که جواب نمی‌دهد. سوم فایروال. چهارم مسیر شبکه. سرویس ssh به‌تنهایی معمولاً refused می‌دهد نه timeout. پس فرض چهارم سرویس را پشت سر این‌ها می‌گذاریم، مگر کنسول چیز دیگری بگوید.

### دستور مشاهده

وضعیت برق را فقط از هایپروایزر ببینید. در libvirt، از میزبان میزبان‌ها اگر دسترسی دارید:

```bash
virsh domstate app-1
```

نمونهٔ خاموش:

```text
shut off
```

نمونهٔ روشن:

```text
running
```

اگر `running` است، کنسول را باز کنید. `virsh console app-1` یا noVNC در پنل. اگر پنل ابری است، همان دکمهٔ کنسول، نه دکمهٔ reboot.

روی کنسول، اگر پوسته گرفتید:

```bash
df -hT /
df -i /
ss -lnt | grep ':22'
systemctl is-active ssh
sudo ufw status verbose
```

نمونهٔ دیسک پر:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/vda2      ext4   40G   40G      0 100% /
```

و `systemctl is-active ssh` ممکن است `active` باشد در حالی که نشست تازه می‌میرد. یا خود کنسول هم با پیام `No space left on device` ورود را نصفه رها کند.

نمونهٔ فایروال که SSH را بسته:

```text
Status: active
Default: deny (incoming)
```

و در فهرست قانون‌ها هیچ `22/tcp` از شبکهٔ عملیات نیست. هم‌زمان `ss` خط `10.10.1.10:22` را نشان می‌دهد. یعنی سرویس سالم است و سیاست ورودی نه.

### تصمیم

`domstate` برابر `shut off`: سرویس و فایروال را از راه دور حدس نزنید. VM را روشن کنید و بعد SSH را امتحان کنید. اگر خاموش شدن غیرمنتظره بود، بعد از بالا آمدن `journalctl -b -1 -p err` را بخوانید تا بفهمید بوت قبلی چرا تمام شده. این کار بعد از برگشتن دسترسی است.

دیسک ۱۰۰ درصد: reboot نکنید. جا آزاد کنید. اگر لاگ مشخص است، صفر کردن همان فایل. روش امن‌تر و شرح inode حذف‌شده در [دیسک پر](./disk-full) است. امشب اگر باید یک اقدام فوری بزنید و فایل غول را شناخته‌اید:

```bash
sudo truncate -s 0 /var/log/nginx/access.log
df -hT /
```

فقط همان فایلی که `du` نشان داده بزرگ است. `truncate` روی یک مسیر حدسی، دادهٔ سالم را هم می‌برد.

فایروال بدون اجازهٔ 22، در حالی که `ss` شنونده دارد: یک قانون برای شبکهٔ آزمایشگاه اضافه کنید. جهان را باز نکنید.

سرویس inactive و دیسک جا دارد: فقط همان واحد را روشن کنید.

### اصلاح

برای فایروال، از خود کنسول:

```bash
sudo ufw allow from 10.10.0.0/16 to any port 22 proto tcp comment 'ssh lab'
sudo ufw status verbose
```

از لپ‌تاپ، نه از کنسول:

```bash
ssh -o ConnectTimeout=5 ops@10.10.1.10 'hostname'
```

باید نام `app-1` را برگرداند. اگر برنگرداند، قانون را گسترده‌تر نکنید تا وقتی از یک همسایهٔ داخل `10.10.0.0/16` هم امتحان نکرده‌اید. اگر همسایه وصل می‌شود و لپ‌تاپ نه، مشکل مسیر لپ‌تاپ است و UFW میزبان دیگر مقصر نیست.

برای سرویس:

```bash
sudo systemctl start ssh
systemctl is-active ssh
ss -lnt | grep ':22'
```

اگر start شکست خورد، `journalctl -u ssh -n 40 --no-pager` را روی کنسول بخوانید. خطای پورت اشغال یا کانفیگ `sshd_config` را با reboot عوض نکنید.

برای دیسک، بعد از `truncate` یا rotate، دوباره `df` باید زیر ۱۰۰ باشد و SSH از بیرون برگردد. بعد بروید صفحهٔ دیسک تا علت پر شدن بماند.

### جلوگیری از تکرار

یک بار در ماه ورود کنسول را آزمایش کنید. هشدار دیسک Prometheus باید قبل از ۱۰۰ درصد خبر بدهد. قانونش در [Prometheus](/docs/12-monitoring/prometheus) است. UFW را بدون قانون SSH فعال نکنید. تغییر `sshd` را در یک نشست باز دوم تست کنید و نشست اول را نبندید تا وقتی دومی وارد شده است.

## Security Notes

برای برگرداندن SSH، `PermitRootLogin yes` نگذارید و رمز عبور را روی اینترنت باز نکنید. حادثه مجوز شل کردن سخت‌سازی نیست. اگر کلیدتان کار نمی‌کند، از کنسول با کاربر `ops` وارد شوید و کلید را درست کنید. جزئیات کلید در صفحهٔ سخت‌سازی SSH است.

`ufw allow 22` بدون محدودیت مبدأ، اگر میزبان IP عمومی دارد، SSH را به دنیا نشان می‌دهد. از `10.10.0.0/16` اجازه بدهید، یا از محدودهٔ VPN سازمان. قانون `Anywhere` را به‌عنوان درمان timeout قبول نکنید.

کنسول noVNC را در مرورگر روی سیستم عمومی باز نگذارید. نشست کنسول یعنی root عملیاتی.

خروجی `journalctl` ممکن است نام کاربر ناموفق را داشته باشد. آن را در کانال حادثهٔ عمومی نفرستید.

## Troubleshooting

`Connection refused` روی 22: میزبان و مسیر تا حد TCP سالم‌اند. کنسول را برای دیدن `systemctl is-active ssh` باز کنید، نه برای reboot. اگر واحد active است و `ss` خالی است، واحد به آدرس دیگری چسبیده یا بلافاصله خارج می‌شود. `journalctl -u ssh -n 40` را بخوانید.

پینگ جواب می‌دهد و SSH timeout است: ICMP باز است و 22 فیلتر شده، یا sshd روی آدرس دیگری گوش می‌دهد. از کنسول `ss -lnt` ستون آدرس را ببینید. `127.0.0.1:22` یعنی فقط محلی. آن را با پیکربندی `ListenAddress` در صفحهٔ SSH یکی کنید، نه با خاموش کردن فایروال کل.

پینگ و SSH هر دو timeout و کنسول نشان می‌دهد سیستم بالا است و `ss` روی `10.10.1.10:22` گوش می‌دهد: بسته به میزبان نمی‌رسد یا قبل از پاسخ دور ریخته می‌شود. `ip -br addr` را با چیزی که در DNS داخلی برای `app-1` ثبت شده مقایسه کنید. اگر آدرس افتاده، [مبانی شبکه](/docs/11-networking/fundamentals) را برای netplan دنبال کنید. فایروال را شل نکنید تا وقتی آدرس درست نشده.

ورود کنسول با `No space left on device` حتی برای root: باید از محیط نجات دیسک را mount کنید و فایل را از بیرون کوچک کنید. reboot پیاپی این وضعیت را بهتر نمی‌کند. اگر هایپروایزر دیسک را به یک VM نجات وصل می‌کند، همان کار رسمی شماست. فایل را از آنجا truncate کنید، نه فرمت.

`virsh domstate` می‌گوید `paused`: ادامهٔ CPU متوقف است. `virsh resume` تصمیم هایپروایزر است و فقط اگر می‌دانید چرا pause شده. اگر به‌خاطر دیسک میزبانِ میزبان‌ها pause شده، resume فوری دوباره pause می‌شود. اول با مسئول زیرساخت حرف بزنید.

## Best Practices

- timeout را از refused جدا بنویسید. اقدامشان یکی نیست.
- کنسول قبل از reboot.
- دیسک ۱۰۰ درصد را با آزاد کردن فایل مشخص درمان کنید، نه با بوت دوباره.
- واحد Ubuntu نامش `ssh` است. وضعیت را از همان بخوانید.
- قانون فایروال را به شبکهٔ عملیات محدود کنید.
- نشست SSH فعلی را هنگام دستکاری sshd نبندید تا نشست آزمایشی دوم موفق نشده.
- بعد از برگشتن دسترسی، علت خاموشی یا پر شدن دیسک را در یادداشت حادثه بنویسید و هشدار غایب را فردا اضافه کنید.
