# دیسک پر

## مقدمه

وقتی `/` پر است، برنامه خطا می‌دهد و گاهی SSH هم نمی‌آید. این صفحه فرض می‌کند یا هنوز SSH دارید یا از کنسول هایپروایزر پوسته گرفته‌اید. هدف، آزاد کردن جا بدون پاک کردن دادهٔ سالم، و فهمیدن این است که چرا `du` و `df` با هم نمی‌خوانند.

میزبان نمونه هم می‌تواند پروکسی باشد، چون لاگ Nginx معمول‌ترین پرکننده است، و هم `app-1`. دستورها یکی است. سیاست نگهداری لاگ در [مدیریت لاگ](/docs/12-monitoring/log-management) است. این‌جا حادثه است. آستانهٔ تیم: از ۸۰ درصد برنامه، از ۹۰ حادثه، از ۹۵ فقط کار لازم برای آزاد کردن جا. inode جداست و همان فوریت را دارد.

## مفهوم اصلی

`df` از سوپربلوک می‌گوید چند بلوک آزاد است. `du` درخت دایرکتوری را جمع می‌زند. اگر فایلی را `rm` کنید ولی یک پروسه هنوز آن را باز داشته باشد، نام از درخت حذف می‌شود و `du` آن را نمی‌بیند، ولی بلوک‌ها تا بسته شدن توصیف‌گر آزاد نمی‌شوند. `df` همچنان پر است. این اختلاف کلاسیک است. درمان، بستن توصیف‌گر است نه `rm` دوباره.

`truncate -s 0` روی فایلی که هنوز نام دارد، همان inode را صفر می‌کند و پروسه می‌تواند به نوشتن ادامه دهد. برای لاگی که باید فوری جا آزاد کند و محتوایش را می‌توانید از دست بدهید، این از `rm` امن‌تر است. بعدش باید چرخش درست شود وگرنه فردا همان فایل دوباره بزرگ می‌شود.

journald اگر سقف نداشته باشد زیر `/var/log/journal` رشد می‌کند. `journalctl --vacuum-size` قدیمی‌ترین آرشیو را تا رسیدن به سقف پاک می‌کند. این با `rm -rf /var/log/journal` یکی نیست. حذف پوشهٔ journal، سرویس را گیج می‌کند و رد بوت قبلی را بی‌دلیل می‌سوزاند.

inode تمام با بایت آزاد، همان خطای `No space left on device` را می‌دهد. `df -i` تنها دستوری است که این را از «دیسک واقعاً پر» جدا می‌کند. درمان، پاک کردن تعداد زیاد فایل ریز است، نه اضافه کردن دیسک، مگر این‌که واقعاً به آن تعداد فایل نیاز دارید.

## چرا استفاده می‌شود؟

`rm -rf /var/log` هم دادهٔ لازم حادثه را می‌برد و هم اگر فایل باز باشد جا آزاد نمی‌کند. `reboot` ممکن است جا را پس بگیرد، چون پروسه بسته می‌شود، ولی اگر لاگ در استارت دوباره پر شود، بوت بعدی همان‌جا گیر می‌کند. دیدن علت قبل از reboot، فرق این صفحه است.

پاک کردن دادهٔ کاربر یا حجم دیتابیس برای جا باز کردن، حادثه را به فاجعه تبدیل می‌کند. ترتیب آزاد کردن این است: لاگ قابل‌بازسازی، کش بسته که دوباره دانلود می‌شود، بعد با تصمیم انسان هر چیز دیگر. هیچ‌وقت فایل داخل `/var/lib/mysql` یا `/var/lib/postgresql` را با `rm` کوچک نکنید.

## Architecture

```text
df -hT و df -i
    │
    ├── inode پر، بایت آزاد  →  فایل ریز، نه لاگ غول
    └── بایت پر
         │
         ▼
      du -xhd1 از /  و پایین رفتن در پوشهٔ بزرگ
         │
         ├── du خیلی کوچک‌تر از df  →  lsof +L1  فایل deleted
         └── du همان را توضیح می‌دهد
                ├── /var/log/nginx یا journal
                ├── /var/log/journal
                └── جای دیگر، با چشم باز
```

`du -x` از یک فایل‌سیستم بیرون نمی‌رود تا `/proc` و حجم‌های دیگر عدد را دروغ نکنند.

## Installation

`df` و `du` هستند. `lsof` گاهی نیست. اگر دیسک صددرصد است، `apt install lsof` خودش شکست می‌خورد. اول کمی جا آزاد کنید، بعد اگر هنوز لازم است بسته را نصب کنید.

```bash
lsof +L1
```

اگر دستور نبود، از `/proc` می‌شود توصیف‌گر deleted را دید ولی کند است. برای حادثه، `truncate` روی فایلی که `du` هنوز به اسم نشان می‌دهد نیازی به `lsof` ندارد. `lsof` را برای وقتی بگذارید که اسمی در کار نیست.

## Configuration

پیشگیری پیکربندی است و درمان حادثه نیست، ولی اگر همین حالا می‌بینید logrotate نیست، بعد از آزاد کردن جا همان روز باید باشد. فایل Nginx و سقف journal در صفحهٔ لاگ است. این‌جا فقط چک می‌کنید وجود دارند.

```bash
ls /etc/logrotate.d/nginx
systemd-analyze cat-config systemd/journald.conf | grep -E 'SystemMaxUse|Storage'
```

اگر grep خالی است، سقف ندارید. بعد از حادثه drop-in را بگذارید. وسط دیسک صددرصد، اول جا، بعد ویرایش کانفیگ. نوشتن فایل کانفیگ خودش به چند بلوک نیاز دارد.

## Production Example

پروکسی هشدار دیسک داده یا SSH قطع و وصل می‌شود. از کنسول یا از یک SSH نیمه‌جان وارد شده‌اید.

### نشانه

برنامه یا Nginx خطای نوشتن می‌دهد، یا اصلاً وارد نمی‌شوید. `df` اگر بتوانید بزنید نزدیک ۱۰۰ است.

### فرضیه

یا لاگ Nginx یا journal بزرگ شده، یا کسی قبلاً `rm` زده و فایل هنوز باز است، یا inode تمام است و بایت باقی است. فرض «باید دیسک بزرگ کنیم» را تا بعد از `du` قبول نکنید. اغلب جا هست، در فایل غلط.

### دستور مشاهده

```bash
df -hT
df -i
sudo du -xhd1 / | sort -h
```

نمونهٔ بایت پر روی ریشه:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/vda2      ext4   40G   38G  180M 100% /
```

و `du` نشان می‌دهد `/var` بزرگ است. یک سطح پایین‌تر:

```bash
sudo du -xhd1 /var | sort -h
sudo du -xhd1 /var/log | sort -h
```

نمونه:

```text
8.0G    /var/log/nginx
1.2G    /var/log/journal
```

اگر `df` می‌گوید ۳۸ گیگ پر است و جمع `du -xhd1 /` خیلی کمتر است، مثلاً ۱۰ گیگ، اختلاف مال فایل حذف‌شدهٔ باز است.

```bash
sudo lsof +L1
```

نمونه:

```text
nginx  912 www-data  6w  REG  253,0  21474836480  0  184212 /var/log/nginx/access.log (deleted)
```

ستون SIZE حدود ۲۰ گیگ است و انتهای خط `(deleted)` است. این همان بلوک‌هایی است که `du` نمی‌بیند.

inode را در خروجی `df -i` جدا بخوانید. اگر Use% بالای ۸۵ است و بایت آزاد دارید، سراغ لاگ غول نروید. پوشه‌ای را پیدا کنید که تعداد فایلش زیاد است.

```bash
sudo du -x --inodes -d 1 /var | sort -n
```

### تصمیم

فایل deleted باز است: reopen همان پروسه. `rm` دوباره بی‌اثر است. محتوا از نظر نام قبلاً رفته. هدف فقط پس گرفتن بلوک است.

فایل nginx هنوز به اسم وجود دارد و چند گیگ است: اگر باید سرویس همین لحظه زنده بماند، `truncate` روی همان فایل، بعد چرخش. اگر کمی جا هست و می‌خواهید لاگ بماند، `logrotate -f` بهتر است.

journal بخش اصلی مصرف است: vacuum با سقف، نه حذف پوشه.

مسیر زیر `/var/lib` دیتابیس است: متوقف شوید. جا را از لاگ بگیرید. کوچک کردن داده کار صفحهٔ دیتابیس و بکاپ است، نه این حادثه.

inode پر است: فایل‌های ریز مشخص را پاک کنید، مثلاً نشست‌های کهنهٔ یک پوشهٔ cache که سیاستش مشخص است. `rm -rf /tmp` را نزنید اگر نمی‌دانید چه کسی آنجا قفل دارد. محتویات شناخته‌شده را پاک کنید.

### اصلاح

برای inode حذف‌شدهٔ Nginx:

```bash
sudo invoke-rc.d nginx rotate
sudo lsof +L1
df -hT /
```

خط deleted باید برود و Avail باید برگردد. اگر `invoke-rc.d` نبود، `sudo systemctl kill -s USR1 nginx` همان reopen را می‌فرستد. سرویس را restart نکنید مگر سیگنال اثر نکرد.

برای فایل خیلی بزرگ که هنوز نام دارد و جا برای خود دستورها کم است:

```bash
sudo truncate -s 0 /var/log/nginx/access.log
df -hT /
```

برای journal، وقتی چند صد مگابایت لازم دارید و لاگ هفتهٔ قبل را می‌توانید فدا کنید:

```bash
journalctl --disk-usage
sudo journalctl --vacuum-size=200M
journalctl --disk-usage
df -hT /
```

۲۰۰ مگابایت سقف موقت حادثه است تا دستورها کار کنند، نه سیاست دائمی. سیاست دائمی صفحهٔ لاگ، ۵۰۰ مگابایت و ۱۴ روز است. بعد از حادثه drop-in را با همان سیاست برگردانید تا vacuum دستی هر شب تکرار نشود.

شاهد اصلاح: `df` زیر آستانهٔ ۹۵، و SSH تازه از بیرون برقرار می‌شود. یک فایل را که پاک کرده‌اید در یادداشت بنویسید تا کسی فکر نکند دادهٔ برنامه رفته.

### جلوگیری از تکرار

همان روز، نه هفتهٔ بعد:

```bash
sudo logrotate -d /etc/logrotate.d/nginx
systemd-analyze cat-config systemd/journald.conf | grep SystemMaxUse
```

اگر قانون nginx نیست، از صفحهٔ لاگ بنویسیدش. اگر `SystemMaxUse` نیست، drop-in را بگذارید و journald را restart کنید وقتی دیسک دیگر بحرانی نیست.

هشدار `RootFilesystemLow` باید قبل از ۱۰۰ درصد آمده باشد. اگر نیامده، [Prometheus](/docs/12-monitoring/prometheus) را برای این میزبان چک کنید. دیسک پرِ بی‌خبر یعنی scrape یا قانون یا گیرنده غایب است.

فردا یک بار `sudo du -xhd1 /var` را ببینید تا مصرف‌کنندهٔ بعدی را بشناسید، نه این‌که فقط خوشحال باشید جا آزاد شده.

## Security Notes

لاگ را در عجله به یک پوشهٔ جهان‌خوان کپی نکنید «تا بعداً بررسی شود». اگر باید نگه دارید و دیسک جای کپی ندارد، نگه نمی‌دارید. تظاهر به بکاپ روی همان دیسک پر، هر دو را از دست می‌دهد.

`truncate` برگشت‌پذیر نیست. فقط روی فایلی بزنید که `du` و نام سرویس آن را لاگ دانسته. روی فایل دیتابیس، روی فایل کاربر در `/home` ، و روی باینری هرگز.

اگر پر شدن دیسک مال یک برنامهٔ مشکوک در `/tmp` است، قبل از پاک کردن نام و زمان و کاربر مالک را یادداشت کنید. پاک کردن برای جا، با نابود کردن شاهد نفوذ یکی نیست. اگر هر دو لازم است، اول چند خط شاهد، بعد پاک کردن فقط به اندازهٔ برگشتن سرویس.

دستور vacuum و truncate را با `sudo` بزنید. برای این‌که راحت شوید `chmod 777 /var/log` نکنید.

## Troubleshooting

`df` صد است و `du -xhd1 /` جمع را توضیح می‌دهد ولی شما پوشه را نمی‌شناسید: یک سطح پایین‌تر بروید، نه `rm -rf` روی `/var`. هر سطح را `sort -h` کنید. وقتی به فایل رسیدید `ls -lh` بگیرید.

`truncate` کردید و `df` تکان نخورد: یا فایل دیگری پر است، یا آن مسیر روی فایل‌سیستم دیگری است، یا شما یک نام تازه ساختید و نام بازِ پروسه چیز دیگری است. `lsof +L1` را ببینید. `df -hT` را بدون محدود کردن به `/` بگیرید. شاید `/var` اصلاً پارتیشن جدا نباشد و شاید حجم پر، `/var/lib/docker` باشد. آن‌وقت صفحهٔ داکر را هم ببینید، ولی باز هم دادهٔ کانتینر را با `docker system prune` کور پاک نکنید مگر بدانید ایمیج و حجم قابل‌بازسازی است و در حال استفاده نیست.

vacuum می‌گوید هیچ کاری نکرد: journal روی دیسک پایدار نیست و مصرف مال `/run` است که tmpfs است. `df -h /run` را ببینید. پر بودن tmpfs را با vacuum دیسک درمان نمی‌کنید. پروسهٔ پرسروصدا را آرام کنید.

بعد از جا خالی کردن، سرویس هنوز خطا می‌دهد: ممکن است یک بار شکست خورده باشد و نیاز به restart همان واحد داشته باشد، نه همهٔ سرور. لاگ واحد را بخوانید. اگر خطای دیسک دیگر نیست، علت دیگری مانده و باید برگردید به [روش عمومی](/docs/14-troubleshooting).

inode پر از فایل‌های session: برنامه را پیدا کنید که پوشه را خالی نمی‌کند. پاک کردن یک‌بار جا می‌دهد. بدون اصلاح برنامه یا cron، هفتهٔ بعد برمی‌گردد. cron پاک‌سازی باید فایل کهنه‌تر از یک سیاست مشخص را حذف کند، نه کل پوشه را هر دقیقه.

## Best Practices

- اول `df -h` و `df -i` با هم.
- اگر `du` و `df` نمی‌خوانند، `lsof +L1` قبل از هر `rm`.
- لاگ باز را truncate یا rotate کنید. `rm` روی فایل باز جا نمی‌دهد.
- journal را vacuum کنید، پوشه‌اش را با دست پاک نکنید.
- به `/var/lib` دیتابیس دست نزنید.
- بعد از حادثه سقف و logrotate را درست کنید. درمان بدون پیشگیری یعنی شیفت بعدی.
- هشدار دیسک باید قبل از صددرصد باشد. اگر نبود، فردا قانون را اضافه کنید نه این‌که فقط دیسک را بزرگ کنید.
