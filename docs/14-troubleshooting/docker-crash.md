# سقوط کانتینر

## مقدمه

کانتینر «خوابیده» یک تشخیص نیست. یا هرگز بالا نیامده، یا با کد مشخص خارج شده، یا هسته به‌خاطر حافظه کشته‌اش، یا در حلقهٔ restart است، یا پروسه زنده است و healthcheck آن را ناسالم می‌داند. این صفحه روی `docker-1.example.internal` با آدرس `10.10.1.30` این‌ها را از هم جدا می‌کند.

نام کانتینر در مثال `app` است. ایمیج را از خروجی خود داکر بخوانید، نه از حافظه. دستورها با `docker compose` هستند اگر سرویس از یک فایل compose آمده، و با `docker` اگر کانتینر تکی است. باینری قدیمی `docker-compose` را استفاده نکنید.

اگر کل میزبان SSH نمی‌دهد، این صفحه زود است. اول [سرور دیده نمی‌شود](./server-down). اگر میزبان بالا است و فقط کانتینر نیست، همین‌جا بمانید.

## مفهوم اصلی

`docker ps` فقط در حال اجرا را نشان می‌دهد. حادثه اغلب در `docker ps -a` است، در ستونی که وضعیت و کد خروج دارد. کد 0 یعنی پروسه تمام شده و خودش را موفق دانسته. برای یک سرویس دائمی، خروج 0 هم خرابی است چون نباید تمام می‌شد. کد 1 خطای خود برنامه است. کد 137 یعنی 128 به‌علاوهٔ سیگنال 9. اغلب OOM killer یا یک `kill -9` است. `OOMKilled` در `docker inspect` این دو را جدا می‌کند. اگر true باشد، حافظه تمام شده. اگر false باشد و کد 137 است، کسی یا چیزی سیگنال 9 فرستاده.

حلقهٔ restart یعنی سیاست `restart` کانتینر را برمی‌گرداند و همان علت دوباره می‌کشد. شمارنده در `RestartCount` بالا می‌رود. ری‌استارت دستی شما این حلقه را درمان نمی‌کند. باید علت خروج را از لاگ همان اجرای قبلی بخوانید. `docker logs` به‌طور پیش‌فرض اجرای فعلی را نشان می‌دهد. اگر کانتینر هر چند ثانیه می‌میرد، لاگ کوتاه است. همان را بردارید قبل از این‌که `docker rm` تاریخ را پاک کند.

healthcheck مال خود Docker است و با «پورت باز است» یکی نیست. کانتینر می‌تواند `Up` باشد و `unhealthy`. آن‌وقت وابستهٔ compose ممکن است ترافیک نگیرد. درمان unhealthy، دیدن دستور healthcheck و خروجی همان دستور داخل کانتینر است، نه بالا بردن بی‌دلیل حافظه.

OOM داخل کانتینر لزوماً OOM کل میزبان نیست. سقف `mem_limit` کانتینر می‌تواند کوچک‌تر از RAM میزبان باشد. بالا بردن سقف بدون دیدن مصرف، نشت را به کل میزبان منتقل می‌کند. اگر میزبان خودش در فشار است، صفحهٔ [حافظه](./memory-leak) را روی میزبان بخوانید. اگر فقط همین کانتینر سقف خورده، تصمیم این‌جاست.

## چرا استفاده می‌شود؟

`docker restart` در حلقه، شمارنده را صفر نمی‌کند و علت را پاک نمی‌کند. `docker rm -f` بدون خواندن لاگ، تنها شاهد را حذف می‌کند اگر لاگ راننده را جای دیگری نفرستاده باشید. `docker system prune` وسط حادثه ایمیج و شبکهٔ لازم را هم می‌برد. این صفحه هیچ‌کدام را قدم اول نمی‌گذارد.

تیم گاهی کد 137 را «باگ داکر» می‌خواند و موتور را ارتقا می‌دهد. در حالی که برنامه از سقف حافظه گذشته. ارتقا موتور آن سقف را عوض نمی‌کند.

## Architecture

```text
علامت: سایت 502 یا کانتینر در ps نیست
        │
        ▼
docker ps -a          وضعیت و کد خروج
        │
        ├── Exited (137)  →  inspect OOMKilled
        ├── Exited (1)    →  logs برنامه
        ├── Restarting    →  logs و RestartCount
        └── Up (unhealthy)→  healthcheck، نه حافظه
                │
                ▼
        docker logs --tail
        docker inspect برای OOMKilled و Error و Health
                │
                ▼
        یک اصلاح: سقف، باگ، یا وابستگی
        بعد دوباره ps و یک درخواست واقعی
```

## Installation

Docker Engine باید از قبل طبق [نصب داکر](/docs/05-docker/installation) باشد. وسط حادثه موتور را از نو نصب نکنید. اگر خود دستور `docker` خطا می‌دهد، ببینید واحد موتور بالا است یا دیسک پر است.

```bash
systemctl is-active docker
df -hT /var/lib/docker
docker ps -a
```

اگر دیسک داکر صد است، اول [دیسک پر](./disk-full) را برای جا دادن دستورها انجام دهید. prune را همان اول نزنید.

## Configuration

فایل compose باید سیاست restart و سقف حافظه و healthcheck را عمدی داشته باشد، نه ارثی از یک نمونهٔ وبلاگ. نمونهٔ سلامت برای سرویسی که روی 8080 داخل کانتینر `/health` دارد. اگر برنامهٔ شما چنین مسیری ندارد، این بلوک را کپی نکنید. یک دستور دروغین unhealthy دائمی می‌سازد.

```yaml
services:
  app:
    image: example/app:1.4.2
    restart: unless-stopped
    mem_limit: 512m
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://127.0.0.1:8080/health"]
      interval: 15s
      timeout: 3s
      retries: 3
      start_period: 20s
```

`unless-stopped` یعنی بعد از reboot میزبان برمی‌گردد، مگر کسی `docker stop` زده باشد. `always` حتی بعد از stop دستی هم در بعضی سناریوها برمی‌گردد و در حادثه دست‌وپاگیر است. عدد `512m` مثال است نه توصیهٔ جهانی. عدد درست از مصرف نسخهٔ سالم می‌آید. اگر نمی‌دانید، سقف را در حادثه از روی خیال عوض نکنید. اول بفهمید OOM شده یا نه.

`start_period` یعنی اوایل بالا آمدن، شکست سلامت کانتینر را unhealthy حساب نکند. اگر برنامه کند بالا می‌آید و این عدد کوتاه است، حلقهٔ ناسالم دروغین می‌گیرید.

## Production Example

کاربر 502 می‌بیند. Nginx سالم است. روی `docker-1` باید بفهمید کانتینر `app` چرا ترافیک نمی‌دهد.

### نشانه

از پروکسی، `curl` به `10.10.1.30:8080` رد می‌شود یا refused است. خود میزبان داکر SSH دارد.

### فرضیه

کانتینر خارج شده، یا در حلقه است، یا بالا است ولی به پورت میزبان وصل نیست، یا OOM شده. فرض «ایمیج خراب است و باید دوباره pull کنیم» را تا دیدن کد خروج نگه دارید. pull بدون تشخیص، همان باگ را برمی‌گرداند.

### دستور مشاهده

```bash
docker ps -a --filter name=app
docker inspect --format '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' app
docker logs --tail 80 app
```

نمونهٔ OOM:

```text
CONTAINER ID   IMAGE               STATUS
a1b2c3d4e5f6   example/app:1.4.2   Exited (137) 2 minutes ago
```

و inspect:

```text
exited 137 true 4
```

یعنی خارج شده، کد 137، OOMKilled برابر true ، چهار بار restart شده. لاگ برنامه ممکن است آخرین خط را نصفه قطع کرده باشد. این با یک exception معمولی فرق دارد. exception کد 1 می‌دهد و OOMKilled false است.

نمونهٔ حلقه، اگر درست وقتی نگاه می‌کنید بالا باشد:

```text
Restarting (1) 3 seconds ago
```

و RestartCount هر بار که دستور را تکرار کنید بیشتر می‌شود. لاگ هر بار همان خطای برنامه را نشان می‌دهد. آن خط را کپی کنید.

نمونهٔ ناسالم ولی زنده:

```text
Up 10 minutes (unhealthy)
```

ExitCode در این حالت ملاک نیست چون پروسه نمرده. سلامت را ببینید.

```bash
docker inspect --format '{{json .State.Health}}' app
```

خروجی JSON است. فیلد `Status` و آخرین `Log` را بخوانید. اگر خروجی خالی است، این کانتینر healthcheck ندارد و unhealthy از جای دیگری آمده، مثلاً از orchestrator. به JSON خالی سلامت اضافه نکنید.

### تصمیم

OOMKilled true: حافظه. یا سقف کانتینر کوچک است نسبت به کارکرد سالم، یا نشت است. یک بار مصرف را از میزبان ببینید تا بدانید سقف را به قیمت کشتن بقیه بالا می‌برید یا نه.

```bash
free -h
```

اگر available میزبان راحت است و فقط کانتینر سقف خورده، می‌شود سقف را با عدد دیده‌شده از نسخهٔ سالم بالا برد. اگر نمی‌دانید مصرف سالم چند است، کانتینر را بالا نیاورید در حلقه. متوقفش کنید تا میزبان پایدار بماند و نویسنده را با لاگ صدا کنید.

کد 1 و OOMKilled false: باگ یا پیکربندی یا وابستگی. لاگ را بخوانید. اگر لاگ می‌گوید به `10.10.1.20` وصل نمی‌شود، کانتینر سالم است و دیتابیس یا مسیر نیست. بروید [شبکه](./network-problem) یا [دیتابیس کند](./database-slow). ری‌استارت حلقه را غلیظ‌تر نمی‌کند.

unhealthy و پروسه Up: دستور healthcheck داخل کانتینر را همان‌طور که هست اجرا کنید.

```bash
docker exec app curl -fsS --max-time 3 http://127.0.0.1:8080/health
```

اگر این 200 داد و Docker هنوز unhealthy می‌گوید، دستور داخل ایمیج با دستوری که شما زدید یکی نیست. `inspect` همان دستور را نشان می‌دهد. اگر `exec` هم شکست خورد، برنامهٔ داخل جواب نمی‌دهد. لاگ برنامه را بخوانید، نه لاگ موتور داکر را تنها.

### اصلاح

برای حلقهٔ کد 1 که علتش را در لاگ دیده‌اید و اصلاح کانفیگ مشخص است، کانفیگ را عوض کنید و یک بار بالا بیاورید. اگر از compose است:

```bash
docker compose up -d app
docker ps --filter name=app
docker logs --tail 30 app
```

شاهد: وضعیت `Up` بماند، RestartCount در یک دقیقه بالا نرود، و از میزبان:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 5 http://127.0.0.1:8080/
```

برای OOM، اگر تصمیم گرفتید سقف را عوض کنید، در compose `mem_limit` را به عددی که از مصرف سالم می‌دانید تغییر دهید و `up -d` کنید. اگر تصمیم گرفتید نشت است، همان ری‌استارت کنترل‌شدهٔ صفحهٔ حافظه است، با این فرق که واحد، کانتینر است. قبلش RestartCount و زمان را بنویسید. اگر در ده دقیقه دوباره OOMKilled شد، `docker compose stop app` تا میزبان را نکشد، و نسخه را برگردانید.

کانتینر را `rm` نکنید تا وقتی لاگ را جایی کپی کرده‌اید، مگر درایور لاگ جای دیگری می‌فرستد و شما همان‌جا خط را دیده‌اید.

### جلوگیری از تکرار

healthcheck باید مسیری را بزند که واقعاً کار برنامه را ثابت کند، نه فقط این را که پورت باز است. `start_period` را از زمان بالا آمدن واقعی بگیرید، از یک استقرار سالم، نه از صفر خیالی.

سیاست restart بدون سقف حافظه یعنی یک نشت می‌تواند میزبان را ببرد. سقف را بعد از دیدن عدد بگذارید. هشدار را هم روی restart پشت‌سرهم بگذارید اگر پایش دارید. خود Docker نامه نمی‌فرستد.

ایمیج را با برچسب مشخص بالا بیاورید. `latest` بعد از حادثه نمی‌گوید چه چیزی در حال اجرا بوده. برچسب را از `docker ps` در یادداشت حادثه بنویسید.

## Security Notes

`docker logs` ممکن است متغیر و رمز چاپ‌شدهٔ برنامه را داشته باشد. قبل از فرستادن به تیکت، خط‌های دارای گذرواژه را حذف کنید. برای پیدا کردن علت معمولاً نوع استثنا کافی است.

`docker exec` را با تصویر ناشناس و دستور طولانی که از چت کپی کرده‌اید باز نکنید. فقط همان healthcheck یا یک دستور خواندنی.

سوکت داکر معادل root است. حادثه مجوز این را نمی‌دهد که کاربر تازه‌وارد را به گروه `docker` اضافه کنید «تا خودش لاگ بگیرد». با `sudo` برای همان دستورها کار کنید و عضویت گروه را در آرامش تصمیم بگیرید.

`docker compose` فایل `.env` را می‌خواند. آن فایل را برای دیباگ در کانال نگذارید.

## Troubleshooting

`docker ps` می‌گوید daemon نیست: `systemctl status docker --no-pager` و دیسک `/var/lib/docker`. اگر دیسک پر است، موتور ممکن است بعد از جا خالی کردن بالا بیاید. prune اولین دستور نباشد.

کد 127: دستور داخل کانتینر پیدا نشده، اغلب healthcheck با `curl` در ایمیجی که curl ندارد. یا ایمیج را با همان ابزار بسازید یا healthcheck را به برنامه‌ای که واقعاً در ایمیج هست عوض کنید. این خطای حافظه نیست.

کد 139: سیگنال 11، معمولاً خطای حافظهٔ خود برنامه. مثل OOM با بالا بردن mem_limit درمان نمی‌شود. لاگ و نسخهٔ ایمیج را به نویسنده بدهید.

پورت میزبان خالی است ولی کانتینر Up است: mapping اشتباه است. `docker port app` را با چیزی که Nginx هدف گرفته مقایسه کنید. 8080 داخل کانتینر به‌خودی‌خود روی میزبان نیست مگر منتشر شده باشد.

`compose up` خطا می‌دهد که نام مشغول است: یک کانتینر دستی با همان نام مانده. `docker ps -a` را ببینید. فقط اگر همان سرویس خراب شماست و لاگ را برداشته‌اید، حذف و بالا آوردن از compose درست است. نام غریبه را حذف نکنید.

## Best Practices

- همیشه `docker ps -a` ، نه `ps` تنها.
- کد خروج و `OOMKilled` را با هم بنویسید. 137 بدون OOM یک داستان دیگر است.
- در حلقه، لاگ را بردارید و شمارنده را نگاه کنید. restart دستی درمان نیست.
- unhealthy را با اجرای همان دستور healthcheck بفهمید.
- سقف حافظه را بدون عدد سالم زیاد نکنید. نشت را به میزبان منتقل نکنید.
- `prune` و `rm` بعد از برداشتن شاهد، نه قبل از آن.
- برچسب ایمیج را در یادداشت حادثه بیاورید.
