# معرفی دانشنامه

## مقدمه

این دانشنامه مرجع داخلی تیم فنی است. قرار است سال‌ها بماند و آدم جدید، بدون شفاهی‌گویی، بتواند یک سرور Ubuntu را بالا بیاورد، سرویس را پشت Nginx بگذارد، دیتابیس را بکاپ بگیرد و وقتی سرویس خوابید مسیر عیب‌یابی را از همین‌جا شروع کند.

لحن صفحات لحن گزارش کار یک مهندس شیفت است: چه چیزی روی دیسک وجود دارد، کدام دستور را می‌زنیم، خروجی سالم چه شکلی است، و کدام اشتباه فردا صبح حادثه می‌سازد. اگر صفحه‌ای فقط تعریف یک ابزار باشد و دستور قابل اجرا نداشته باشد، آن صفحه کارش را نکرده است.

مخاطب کسی است که به SSH دسترسی دارد و مسئول بالا ماندن سرویس است. برای خواندن لازم نیست همه فصل‌ها را از اول تا آخر طی کنید. از فصلی شروع کنید که همین هفته به آن نیاز دارید، و وقتی یک مفهوم را در صفحهٔ دیگری تمام کرده‌ایم به همان صفحه لینک شده است.

## مفهوم اصلی

دانشنامه یک کتاب مرجع عملیاتی است، نه دورهٔ ویدیویی و نه ترجمهٔ صفحهٔ اول یک محصول. هر ابزار در بستری که واقعاً کنار ابزارهای دیگر کار می‌کند توضیح داده می‌شود. Nginx تنها نیست؛ جلوی Node یا PHP-FPM است. Docker تنها نیست؛ ایمیج باید از آینهٔ داخلی هم قابل کشیدن باشد. Git تنها نیست؛ شاخه باید به یک pipeline برسد.

اصطلاح انگلیسی حذف نمی‌شود. در Production لاگ و فایل کانفیگ انگلیسی است و اگر اینجا فقط معادل فارسی را ببینید، شب حادثه آن رشته را در `journalctl` پیدا نمی‌کنید. رسم صفحه این است که بار اول هر دو را بیاورد: سرویس (service)، واحد (unit)، ایمیج (image). خود دستور، بدون ترجمه، داخل بلوک کد می‌ماند.

محیط مرجع این متن‌ها Ubuntu Server 26.04 LTS با نام رمز Resolute Raccoon است. پایهٔ بسته همان Debian است و هرجا Debian 13 Trixie رفتار متفاوتی دارد، همان‌جا گفته می‌شود. Ubuntu 24.04 LTS هنوز در خیلی از رک‌ها زنده است؛ اگر دستوری بین 26.04 و 24.04 فرق کند، هر دو نوشته شده است.

## چرا استفاده می‌شود؟

دانش شفاهی با عوض شدن آدم‌ها از بین می‌رود. این پورتال سه کار را ثابت نگه می‌دارد:

- مسیر ساخت یک سرویس، از ماشین خام تا دامنه و گواهی، یک‌جا و به ترتیب قابل اجرا باشد.
- تصمیم‌های خطرناک یک‌بار با دلیل نوشته شوند. مثلاً چرا ورود با رمز به SSH بسته است، یا چرا دیتابیس را به `0.0.0.0` وصل نمی‌کنیم.
- عیب‌یابی نیمهٔ شب از صفر شروع نشود. فصل آخر سناریوهای پرتکرار را با ترتیب مشاهده، فرضیه و اصلاح نوشته است.

صفحه را وقتی تمام‌شده حساب می‌کنیم که یک همکار بتواند آن را روی یک VM تازه اجرا کند و به خروجی نوشته‌شده برسد. نمونهٔ رمز عبور، نمونه است. در فایل واقعی باید عوض شود و این هشدار کنار همان نمونه آمده است.

## Architecture

فصل‌ها به ترتیب کار یک تیم عملیات چیده شده‌اند. عدد پوشه ترتیب سایدبار است.

```text
معرفی
  │
  ├─ 01 لینوکس ──────── پایهٔ همهٔ فصل‌های بعدی
  ├─ 02 LPIC ─────────── همان مهارت‌ها از زاویهٔ آزمون و سناریو
  ├─ 03 Git
  ├─ 04 ابزار سرور ───── سی دقیقهٔ اول، FFmpeg، Chromium، ClamAV
  ├─ 05 Docker ───────── به‌علاوهٔ آینه وقتی اینترنت محدود است
  ├─ 06 Nginx
  ├─ 07 دیتابیس ──────── MySQL، PostgreSQL، MongoDB، Redis
  ├─ 08 استقرار
  ├─ 09 CI/CD
  ├─ 10 امنیت
  ├─ 11 شبکه، DNS، SSL
  ├─ 12 پایش
  ├─ 13 Bash
  └─ 14 عیب‌یابی
```

آزمایشگاه همهٔ فصل‌ها یکی است تا مثال‌ها به هم لینک شوند.

| نقش | آدرس | نام |
| --- | --- | --- |
| پروکسی | `10.10.1.5` | `proxy.example.internal` |
| برنامه | `10.10.1.10` | `app-1.example.internal` |
| دیتابیس | `10.10.1.20` | `db-1.example.internal` |
| Docker | `10.10.1.30` | `docker-1.example.internal` |
| پایش | `10.10.1.40` | `mon-1.example.internal` |
| GitLab | `10.10.1.50` | `gitlab.example.internal` |
| آینه | `10.10.1.60` | `mirror.example.internal` |

دامنهٔ عمومی نمونه‌ها `app.example.com` است. این نام طبق RFC 2606 رزرو شده و مال هیچ سازمانی نیست. کاربر مدیر انسانی `ops` است و کاربر اجرای سرویس `deploy`. برنامه زیر `/opt/apps` و بکاپ زیر `/var/backups` می‌نشیند. منطقهٔ زمانی `Asia/Tehran` است.

ساختار هر صفحه ثابت است: مقدمه، مفهوم، دلیل استفاده، معماری، نصب، کانفیگ، مثال Production، یادداشت امنیتی، عیب‌یابی، و رویهٔ درست. صفحهٔ مرجع دستور به‌جای این فهرست، برای هر دستور توضیح و مثال و کاربرد Production دارد.

## Installation

برای خواندن روی کاغذ یا از طریق سرور مستندات، به نصب چیزی روی لپ‌تاپ نیاز ندارید. برای بالا آوردن خود همین پورتال در شبکهٔ داخلی:

```bash
git clone <آدرس مخزن تیم> devops-docs
cd devops-docs
npm install
npm start
```

Node.js 22 یا جدیدتر کافی است. اجرای کانتینری، بدون نصب Node روی سرور مقصد:

```bash
docker compose up --build
```

بعد از بیلد، مرورگر را به `http://127.0.0.1:8080` باز کنید. جزئیات Nginx جلوی این کانتینر، عوض کردن آدرس canonical، و محدودیت جستجو در [استقرار پورتال](/docs/15-portal/deployment) است.

اگر فقط می‌خواهید یک سرور Ubuntu بسازید، این بخش را رها کنید و از [نصب Ubuntu Server](/docs/01-linux/ubuntu-server-installation) شروع کنید.

## Configuration

سه قراری که اگر نادیده بگیرید مثال‌ها را غلط اجرا می‌کنید:

1. دستور را همان‌طور که در بلوک کد است بزنید. متن فارسی دور بلوک، توضیح است و نباید داخل ترمینال paste شود.
2. بلوک کد چپ‌چین است، حتی وقتی صفحه راست‌چین است. اگر یک خط شکسته به‌نظر رسید، اسکرول افقی همان بلوک را ببینید؛ خط را از وسط برندارید.
3. مقدارهایی مثل `change-me`، `10.10.1.10` و `app.example.com` متعلق به آزمایشگاه این کتاب‌اند. قبل از اجرا روی سرور سازمان، آدرس، نام دامنه و رمز را با مقدار واقعی عوض کنید.

پیکربندی خود سایت در `docusaurus.config.ts` است. زبان پیش‌فرض `fa` و جهت `rtl` است. فونت Vazirmatn همراه خود سایت بسته‌بندی شده تا بدون دسترسی به اینترنت خارجی هم حروف درست باشد. حالت تیره از تنظیم سیستم پیروی می‌کند و از نوار بالا قابل عوض کردن است. جستجو محلی است و ایندکسش موقع `npm run build` ساخته می‌شود؛ در حالت `npm start` هم فعال است، ولی نتیجهٔ فارسی به دلیل محدودیت Lunr کاملِ یک موتور فارسی نیست. واژه‌های انگلیسی دستورها را مطمئن جستجو کنید و برای عنوان فارسی اگر نتیجه کم بود، کلمه را کوتاه‌تر کنید.

سایدبار از پوشهٔ `docs` ساخته می‌شود. برای اضافه کردن صفحه، فایل Markdown را در پوشهٔ همان فصل بگذارید و `sidebar_position` بدهید. لازم نیست `sidebars.ts` را برای هر صفحه ویرایش کنید.

## Production Example

ساعت ۰۲:۱۰ مانیتورینگ می‌گوید `app.example.com` از بیرون کد ۵۰۲ می‌دهد. کسی که این دانشنامه را دارد لازم نیست از جستجوی پراکنده شروع کند.

ترتیب واقعی همان شب این است:

1. از [سرور بالا نمی‌آید](/docs/14-troubleshooting/server-down) و [مشکل شبکه](/docs/14-troubleshooting/network-problem) مشخص کنید اصلاً به `10.10.1.5` و `10.10.1.10` SSH می‌شود یا نه.
2. اگر پروکسی زنده است، [عیب‌یابی Nginx](/docs/06-nginx/configuration) و لاگ `error.log` را ببینید. ۵۰۲ معمولاً یعنی Nginx هست و برنامهٔ پشت آن نیست.
3. اگر برنامه روی Docker است، [سقوط کانتینر](/docs/14-troubleshooting/docker-crash) را دنبال کنید: `docker ps`، کد خروج، و `docker logs`.
4. اگر برنامه زنده است و فقط کند است، [دیتابیس کند](/docs/14-troubleshooting/database-slow) را باز کنید.

این ترتیب ارزش دانشنامه است. هر صفحه باید جایی در چنین زنجیره‌ای قابل استفاده باشد، نه اینکه فقط تعریف ابزار را تکرار کند.

## Security Notes

این مخزن مثال عملیاتی دارد و مثال عملیاتی خطرناک است اگر بی‌فکر کپی شود.

- رمزهای نمونه، توکن و کلید خصوصی واقعی نیستند و نباید به سرور سازمانی منتقل شوند. هر جا رمزی آمده، فایل باید مجوز `0600` داشته باشد و مالک آن کاربر سرویس باشد.
- باز کردن پورت دیتابیس روی اینترفیس عمومی در مثال‌ها ممنوع نوشته شده است. اگر صفحه‌ای `bind 0.0.0.0` را نشان می‌دهد، همان صفحه باید بگوید چرا در Production این کار را نمی‌کنیم و به‌جایش چه می‌گذاریم.
- سخت‌سازی SSH در [فصل امنیت](/docs/10-security/ssh-hardening) است. تا آن صفحه را اعمال نکرده‌اید، سرور تازه را به اینترنت وصل نکنید.
- آینهٔ داخلی در فصل Docker مکانیزم را یاد می‌دهد. آدرس `mirror.example.internal` را با آینهٔ سازمان عوض کنید. مخزن تصادفی اینترنت را به‌عنوان آینهٔ مورد اعتماد وارد `daemon.json` نکنید.

## Troubleshooting

اگر دستوری در یک صفحه خطا داد، قبل از اینکه صفحه را غلط فرض کنید این چهار مورد را تطبیق دهید:

| نشانه | بررسی |
| --- | --- |
| `command not found` | بسته نصب نشده یا مسیرش در `PATH` این کاربر نیست. `dpkg -l` و `command -v` را ببینید |
| فایل کانفیگ پیدا نمی‌شود | نسخهٔ توزیع فرق دارد. `lsb_release -a` باید Ubuntu 26.04 یا Debian 13 را نشان دهد، مگر صفحه نسخهٔ دیگری را گفته باشد |
| `Permission denied` | دستور به `sudo` نیاز دارد، یا کاربر `deploy` عمداً shell تعاملی ندارد |
| سرویس بالا نمی‌آید | `systemctl status نام-سرویس` و `journalctl -u نام-سرویس -n 50 --no-pager` را همان‌طور که در فصل لینوکس آمده اجرا کنید |

اگر خروجی شما با خروجی نمونه فرق کوچک در شمارهٔ نسخهٔ patch داشت، صفحه هنوز معتبر است. اگر نام یونیت، مسیر فایل، یا زیر‌دستور عوض شده بود، صفحه را با واقعیت همان سرور اصلاح کنید و در کنارش نسخه را بنویسید.

## Best Practices

- صفحه‌ای که اضافه می‌کنید همان ده بخش را داشته باشد. حذف یک بخش فقط وقتی قابل دفاع است که واقعاً برای آن موضوع مصداق ندارد، و در این صورت یک جمله بگویید چرا.
- دستور را روی یک VM تمیز بزنید و خروجی را از روی همان اجرا خلاصه کنید، نه از حافظه.
- لینک داخلی بدهید تا یک موضوع دو بار با دو عدد متفاوت توضیح داده نشود. آزمایشگاه `10.10.1.0/24` را به‌هم نزنید.
- کانفیگ را کامل بگذارید. تکه‌ای که بدون خطوط قبل و بعد قابل reload نیست، در Production به‌درد نمی‌خورد.
- راز سازمان، آدرس عمومی واقعی مشتری، و دادهٔ کاربر را داخل این مخزن ننویسید. مثال با `example.com` و شبکهٔ `10.10.0.0/16` ساخته شده تا قابل کپی به گیت داخلی بماند.
