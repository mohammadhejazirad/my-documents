# توازن بار

## مقدمه

یک گرهٔ `10.10.1.10` برای آزمون و برای بار کم کافی است. وقتی دو نسخه از برنامه همزمان بالا هستند، لبه روی `10.10.1.5` باید بین آن‌ها یکی را برای هر درخواست انتخاب کند و گرهٔ مرده را برای مدتی کنار بگذارد. این صفحه همان کار را با بستهٔ `nginx` اوبونتو 1.28.x می‌کند، بدون ماژول تجاری.

گرهٔ اول همان `app-1.example.internal` با نشانی `10.10.1.10` است. گرهٔ دوم را فقط همین صفحه اضافه می‌کند: `app-2.example.internal` روی `10.10.1.11`، در همان شبکهٔ `10.10.0.0/16`. بقیهٔ دانشنامه وقتی یک برنامه کافی است فقط از `10.10.1.10` حرف می‌زند. هر گره Nginx محلی خودش را روی پورت ۸۰۸۰ دارد و Node همان گره به `127.0.0.1:3000` وصل است. توازن بار جلوی پورت ۳۰۰۰ نیست.

## مفهوم اصلی

بلوک `upstream` یک نام می‌سازد که `proxy_pass` به آن می‌دهد. روش پیش‌فرض، اگر هیچ دستوری نگذارید، نوبتی وزن‌دار است. `least_conn` درخواست را به گره‌ای می‌دهد که همین الان اتصال فعال کمتری دارد. برای API که بعضی درخواست‌هایش طولانی است این از نوبتی ساده عادلانه‌تر است. `ip_hash` از نشانی کاربر یک گرهٔ ثابت درمی‌آورد تا نشستی که در حافظهٔ همان فرایند مانده از دست نرود.

این دو دستور روش توزیع هستند و در یک upstream با هم جمع نمی‌شوند. دومی که در بلوک باشد `nginx -t` را با دستور تکراری می‌شکند. در این صفحه دو بلوک جدا هستند. تولید روی `least_conn` است. `ip_hash` آماده است تا فقط وقتی برنامه نشست را محلی نگه داشته، نام upstream در `proxy_pass` عوض شود.

سلامت پیش‌فرض این بسته منفعل است. `max_fails` تعداد تلاش ناموفق در پنجرهٔ `fail_timeout` است و بعد از آن گره برای همان مدت کنار می‌رود. پیش‌فرض خود Nginx یک شکست و ده ثانیه است. ما سه شکست در سی ثانیه می‌گذاریم تا یک خطای گذرا گره را خارج نکند. تلاش ناموفق یعنی خطای اتصال یا تایم‌اوت، مگر `proxy_next_upstream` کد HTTP دیگری را هم ناموفق حساب کند. پیش‌فرض آن دستور فقط `error timeout` است. پاسخ ۵۰۰ برنامه، گره را بیمار نمی‌کند.

دستور `health_check` که دوره‌ای و بی‌توجه به درخواست کاربر گره را می‌زند، مال اشتراک تجاری Nginx Plus است و در بستهٔ Ubuntu نیست. `least_time` و `sticky` و `slow_start` هم همین‌طورند. اگر آن‌ها را در فایل بگذارید، خطا `unknown directive` است. این صفحه آن دستورها را در کانفیگ نمی‌گذارد.

## چرا استفاده می‌شود؟

بدون upstream، لبه یک نشانی ثابت دارد و با خاموش شدن `10.10.1.10` کل `app.example.com` می‌خوابد. با دو گره و سلامت منفعل، درخواست بعدی بعد از چند شکست اتصال به گرهٔ دیگر می‌رود. این جایگزین سلامت فعال نیست: اگر هر دو گره بالا باشند و هر دو پاسخ ۵۰۰ بدهند، Nginx هر دو را سالم می‌بیند. برای این بسته، ۵۰۰ یعنی باگ برنامه، نه مرگ گره. ۵۰۲ و ۵۰۳ و ۵۰۴ معمولاً یعنی خود گره یا پروکسی جلوی آن خراب است و ارزش یک تلاش روی گرهٔ دیگر را دارد.

`ip_hash` وقتی وسوسه‌کننده است که برنامه فایل نشست را روی دیسک محلی همان میزبان گذاشته باشد. سه اکتت اول IPv4 کلید است، پس یک دفتر که پشت یک NAT است همه به یک گره می‌چسبند و عدالت از بین می‌رود. درمان درست، بردن نشست به یک انبار مشترک است نه چسباندن کاربر به میزبان. تا آن روز، بلوک `ip_hash` اینجاست تا آگاهانه روشن شود، نه به عنوان پیش‌فرض.

اگر توازن را به‌جای لبه روی Nginx محلی برنامه بگذارید، تنها نشانی که آن Nginx از کاربر می‌بیند `10.10.1.5` است و `ip_hash` همهٔ دنیا را به یک گره می‌فرستد. برای همین upstream فقط در کانفیگ `10.10.1.5` است.

## Architecture

```text
کاربر
  │
  ▼
10.10.1.5
  upstream app_nodes   least_conn
  zone مشترک بین workerها
        │
        ├─ 10.10.1.10:8080  app-1  →  127.0.0.1:3000
        └─ 10.10.1.11:8080  app-2  →  127.0.0.1:3000
```

حافظهٔ اشتراکی `zone` از نسخهٔ 1.9 در خود Nginx آزاد هست و در 1.28 هم هست. بدون آن، شمارندهٔ شکست هر worker جداست و یک گره ممکن است پیش یک worker مرده و پیش دیگری زنده باشد. این `zone` همان API تجاری برای عوض کردن عضو گروه بدون reload نیست. عضو جدید هنوز یعنی ویرایش فایل و `nginx -t` و reload.

اگر فقط یک `server` داخل گروه بماند، Nginx پارامتر `max_fails` را نادیده می‌گیرد و همان یک گره را هرگز کنار نمی‌گذارد. گروه تک‌عضوی سلامت منفعل ندارد.

## Installation

هر دو گره باید همان چیزی را گوش بدهند که لبه انتظار دارد. از خود `10.10.1.5`:

```bash
curl -fsS -o /dev/null -w "%{http_code}\n" --connect-timeout 3 http://10.10.1.10:8080/ -H "Host: app.example.com"
curl -fsS -o /dev/null -w "%{http_code}\n" --connect-timeout 3 http://10.10.1.11:8080/ -H "Host: app.example.com"
```

هر دو باید کد برنامه را بدهند، نه خطای اتصال. فایروال هر گره فقط مبدأ `10.10.1.5` را به پورت ۸۰۸۰ راه می‌دهد. بستهٔ Nginx لبه همان 1.28.x است که [نصب](/docs/06-nginx/installation) گذاشت. چیز دیگری برای توازن بار نصب نمی‌شود.

## Configuration

فایل `/etc/nginx/sites-available/app.conf` روی لبه. بلوک ۴۴۳ و هدرها همان قرارداد [پروکسی معکوس](/docs/06-nginx/reverse-proxy) است. تفاوت اینجاست که `proxy_pass` به نام گروه می‌رود و گروه قبل از `server` تعریف شده است.

```nginx
upstream app_nodes {
    zone app_nodes 64k;
    least_conn;
    server 10.10.1.10:8080 max_fails=3 fail_timeout=30s;
    server 10.10.1.11:8080 max_fails=3 fail_timeout=30s;
    keepalive 16;
}

upstream app_nodes_iphash {
    zone app_nodes_iphash 64k;
    ip_hash;
    server 10.10.1.10:8080 max_fails=3 fail_timeout=30s;
    server 10.10.1.11:8080 max_fails=3 fail_timeout=30s;
}

server {
    listen 80;
    listen [::]:80;
    server_name app.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    access_log /var/log/nginx/app.example.com.access.log;
    error_log  /var/log/nginx/app.example.com.error.log warn;
    client_max_body_size 20m;

    location / {
        proxy_pass http://app_nodes;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
        proxy_connect_timeout 3s;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_timeout 5s;
        proxy_next_upstream_tries 2;
    }
}
```

`keepalive` با `ip_hash` در بلوک دوم نیامده چون آن بلوک خاموش است و چسباندن نشست با استخر اتصال، اشکال جداگانه‌ای در شمارش `max_conns` می‌سازد که این صفحه لازم ندارد. برای روشن کردن چسبندگی، فقط خط `proxy_pass` را به `http://app_nodes_iphash` عوض کنید. هر دو نام را همزمان در دو location مختلف یک سایت به کار نبرید مگر بدانید کاربر بین دو روش پرت می‌شود.

`proxy_next_upstream_tries 2` یعنی یک تلاش دوباره، نه چرخیدن بی‌پایان. تایم‌اوت پنج ثانیه جلوی جمع شدن تأخیر دو گرهٔ کند را می‌گیرد. کد ۵۰۰ عمداً در فهرست نیست. اگر ۵۰۰ را اضافه کنید، یک باگ که هر دو گره یکسان دارند درخواست را دو بار اجرا می‌کند و اگر آن درخواست POST باشد، اثر جانبی دو بار اتفاق می‌افتد.

روی Ubuntu 24.04 به‌جای `http2 on` بنویسید `listen 443 ssl http2` و معادل IPv6.

## Production Example

یکی از گره‌ها را موقتاً متوقف کنید و از بیرون فقط لبه را بزنید:

```bash
sudo nginx -t && sudo systemctl reload nginx
curl -fsS -o /dev/null -w "%{http_code}\n" https://app.example.com/
```

سپس روی `10.10.1.11` سرویس Nginx محلی را `systemctl stop nginx` کنید. درخواست بعدی به `https://app.example.com/` باید هنوز ۲۰۰ باشد، شاید بعد از یک یا چند ۵۰۲ کوتاه. در error log لبه باید `connect() failed` برای `10.10.1.11` بیاید و `upstream` درخواست موفق `10.10.1.10` باشد. بعد از برگرداندن سرویس گرهٔ دوم، لازم نیست حتماً reload کنید؛ بعد از `fail_timeout` همان گره دوباره امتحان می‌شود. برای برگرداندن فوری، reload بی‌ضرر است.

در لاگ، اگر هر درخواست موفق پشت سر هم به یک نشانی بالادست می‌رود در حالی که `least_conn` روشن است، احتمالاً فقط یک گره از دید لبه باز است. `curl` مستقیم به هر دو پورت ۸۰۸۰ را تکرار کنید.

این آزمون را با POST که در برنامه چیزی می‌سازد انجام ندهید. توقف گره وسط یک نوشتن، با `proxy_next_upstream` ممکن است همان نوشتن را به گرهٔ دوم هم بفرستد اگر خطا بعد از رسیدن درخواست به گرهٔ اول باشد. فهرست ما خطای اتصال و ۵۰۲ و ۵۰۳ و ۵۰۴ است. باز هم آزمون را با GET انجام دهید.

## Security Notes

هر دو گره باید کانفیگ و نسخهٔ یکسان ببینند. توازن بار بین یک نسخهٔ سالم و یک نسخهٔ قدیمی یعنی گاهی کاربر باگ را می‌بیند و گاهی نه، و عیب‌یابی دروغ می‌گوید. استقرار را روی هر دو تمام کنید، بعد لبه را reload کنید.

پورت ۸۰۸۰ را به `0.0.0.0` روی اینترنت باز نکنید تا «توازن بار از بیرون هم کار کند». تنها مشتری مجاز این پورت `10.10.1.5` است. اگر گره دوم در شبکهٔ دیگری است، قبل از اضافه کردن به upstream باید همان قاعدهٔ فایروال را داشته باشد، نه اینکه برای آزمون سریع فایروال را خاموش کنید.

حافظهٔ `zone` محتوای درخواست را نگه نمی‌دارد. ۶۴ کیلوبایت برای دو نشانی زیاد هم هست. آن را به ده‌ها مگابایت نبرید.

## Troubleshooting

دستور تجاری روی این بسته:

```text
nginx: [emerg] unknown directive "health_check" in /etc/nginx/sites-enabled/app.conf:48
```

خط را بردارید. سلامت فعال با این باینری ساخته نمی‌شود. جایگزین عملی همین `max_fails` است، با محدودیت‌هایی که بالا گفته شد.

اگر هر دو گره را در گروه گذاشته‌اید و یکی از اول مرده است، کاربرها به نسبت شکست‌ها ۵۰۲ می‌بینند تا شمارنده پر شود. برای بیرون کشیدن معلوم یک گره، در خط `server` پارامتر `down` بگذارید و reload کنید. `down` یعنی دیگر به آن وصل نشو، تا وقتی خط را برمی‌دارید. این با سلامت منفعل فرق دارد چون تصمیم انسان است.

گروه با یک عضو، حتی اگر آن عضو بسته باشد، گره را کنار نمی‌گذارد و هر درخواست همان خطای اتصال را می‌گیرد. اگر در حادثه موقتاً یک خط `server` را کامنت می‌کنید، انتظار eject نداشته باشید.

`no live upstreams` یعنی هر دو گره در پنجرهٔ شکست هستند. سی ثانیه صبر کنید یا reload کنید. اگر بلافاصله برگشت، هر دو پورت ۸۰۸۰ واقعاً بسته‌اند و توازن بار کاری برای انجام ندارد.

`ip_hash` و پارامتر `backup` با هم مجاز نیستند. این صفحه گرهٔ پشتیبان تعریف نکرده تا بلوک دوم معتبر بماند. اگر بعداً `backup` اضافه کردید، فقط روی گروه `least_conn`.

اشتباه گذاشتن هر دو روش در یک بلوک:

```text
nginx: [emerg] invalid parameter "ip_hash" in /etc/nginx/sites-enabled/app.conf:4
```

متن دقیق خطا به ترتیب دستورها بستگی دارد، ولی `-t` رد می‌شود. یکی را حذف کنید.

## Best Practices

- توازن را روی لبه بگذارید، جایی که نشانی واقعی کاربر دیده می‌شود.
- تولید با `least_conn` و `max_fails=3` و `fail_timeout=30s`. `ip_hash` را فقط با دلیل نشست محلی روشن کنید.
- `zone` را بگذارید تا workerها یک وضعیت مشترک داشته باشند.
- ۵۰۰ را وارد `proxy_next_upstream` نکنید. POST را با آزمون قطع گره امتحان نکنید.
- `health_check` را به امید اینکه بستهٔ Ubuntu بفهمد ننویسید.
- گره را `down` کنید وقتی می‌دانید خراب است؛ منتظر سلامت منفعل نمانید وقتی خودتان در حال استقرارید و هنوز ترافیک می‌فرستید.
