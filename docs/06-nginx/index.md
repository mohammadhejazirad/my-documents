# نقشهٔ Nginx

## مقدمه

این فصل وب‌سرور لبهٔ آزمایشگاه است. بستهٔ `nginx` از مخزن خود Ubuntu 26.04 می‌آید و شاخهٔ آن 1.28.x است. مخزن nginx.org و کامپایل دستی در این دانشنامه پیش‌فرض نیستند، چون بقیهٔ صفحه‌ها با همان بسته‌ای نوشته شده‌اند که `apt upgrade` امنیتش را می‌رساند. Ubuntu 24.04 هنوز Nginx 1.24 می‌دهد؛ هر جا دستوری بین این دو فرق کند، همان صفحه گفته است.

نام عمومی `app.example.com` است. پروکسی `proxy.example.internal` روی `10.10.1.5` به پورت ۸۰ و ۴۴۳ گوش می‌دهد. برنامه `app-1.example.internal` روی `10.10.1.10` است. Node فقط به `127.0.0.1:3000` وصل می‌شود. اگر نقش‌ها را عوض کنید، بقیهٔ فصل‌ها با هم نمی‌خوانند. جدول میزبان‌ها در [معرفی دانشنامه](/docs/intro) همان جدول این فصل است.

## مفهوم اصلی

Nginx اینجا برنامه را اجرا نمی‌کند. یک فرایند master کانفیگ را می‌خواند و چند worker اتصال‌ها را می‌گیرند. کار worker در این دانشنامه چهارتاست: فایل ثابت، تمام کردن TLS، پروکسی به فرایندی که خودش سوکت را باز کرده، و محدود کردن درخواست بد. کد PHP داخل php-fpm است و کد Node یک فرایند جدا روی حلقهٔ محلی است. اگر این مرز بشکند، یا پورت ۳۰۰۰ را به اینترنت باز کرده‌اید یا PHP را داخل خود Nginx جا داده‌اید. هیچ‌کدام الگوی این فصل نیست.

هر درخواست با `server_name` به یک بلوک server می‌رسد و بعد location انتخاب می‌شود. اولویت location در صفحهٔ ساختار کانفیگ است. تا آن را نخوانده، `try_files` و عبارت باقاعده را کنار هم نگذارید؛ اولین حدس معمولاً همان بلاکی نیست که Nginx واقعاً انتخاب می‌کند.

## چرا استفاده می‌شود؟

تیم یک لبه می‌خواهد، نه یک کانفیگ جدا برای هر زبان. Node، PHP و کانتینر هر سه پشت همین worker می‌نشینند تا هدر امنیتی، محدودیت نرخ، لاگ و گواهی یک‌جا باشند. برنامه به `0.0.0.0:3000` یا سوکت عمومی php-fpm وصل نمی‌شود. شب حادثه هم به‌جای سه مدل لاگ، `error.log` همان میزبان را باز می‌کنید.

جایگزین، چسباندن خود برنامه به پورت ۸۰ است. آن الگو گواهی را داخل کد می‌برد، فایل ثابت را با همان فرایندی سرو می‌کند که درخواست سنگین را جواب می‌دهد، و با ری‌استارت برنامه اتصال‌های سالم را هم می‌برد. Nginx با `reload` کانفیگ را عوض می‌کند و اتصال جاری را قطع نمی‌کند. به همین دلیل لبه ثابت می‌ماند و برنامه پشت آن عوض می‌شود.

## Architecture

مسیر درخواست در استقرار معمولی، بدون Docker:

```text
کاربر
  │  HTTPS  app.example.com
  ▼
10.10.1.5   proxy.example.internal
  Nginx لبه، پورت 80 و 443
  │  HTTP فقط از همین میزبان به 10.10.1.10:8080
  ▼
10.10.1.10  app-1.example.internal
  Nginx محلی روی 10.10.1.10:8080
  ├─ Node   127.0.0.1:3000
  └─ php-fpm  سوکت /run/php/php8.5-fpm-app.sock
```

پورت ۳۰۰۰ از شبکه دیده نمی‌شود. پورت ۸۰۸۰ فقط از `10.10.1.5` قابل وصل است. دیتابیس `10.10.1.20` در این فصل سوکت عمومی نمی‌گیرد. میزبان Docker `10.10.1.30` معماری جدا دارد و فقط صفحهٔ کانتینر و فصل استقرار آن را وصف می‌کنند.

## Installation

نصب خط‌به‌خط در صفحهٔ بعد است. این صفحه فقط قراردادی را ثابت می‌کند که صفحه‌های بعدی فرض کرده‌اند: بستهٔ Ubuntu به نام `nginx`، کاربر worker برابر `www-data`، و چیدمان Debian با `sites-available` و `sites-enabled`. روی خود پروکسی، قبل از هر ویرایش:

```bash
nginx -v
apt-cache policy nginx
grep -n include /etc/nginx/nginx.conf
ls -l /etc/nginx/sites-enabled
```

خروجی `nginx -v` باید رشتهٔ `nginx/1.28` داشته باشد. شمارهٔ patch را این صفحه ثابت نمی‌نویسد؛ هر به‌روزرسانی امنیتی آرشیو آن را جلو می‌برد. `apt-cache policy` باید مخزن Ubuntu را نشان بدهد، نه `nginx.org`. اگر `sites-enabled` یک پیوند به `default` دارد، سایت پیش‌فرض هنوز روشن است و صفحهٔ ساختار آن را خاموش می‌کند.

## Configuration

فایل اصلی `/etc/nginx/nginx.conf` است. داخل بلوک http این includeها را دارد و صفحه‌های ما فایل جدیدشان را در همین مسیرها می‌گذارند، نه با بازنویسی فایل اصلی:

```nginx
include /etc/nginx/mime.types;
include /etc/nginx/conf.d/*.conf;
include /etc/nginx/sites-enabled/*;
```

`conf.d` برای دستوری است که باید هم‌سطح http باشد: `map`، `limit_req_zone`، `proxy_cache_path`. `sites-available` برای بلوک server است و فقط از راه پیوند در `sites-enabled` بارگذاری می‌شود. هر دو پوشه در زمینهٔ http include می‌شوند. گذاشتن `events` داخل یک فایل سایت، `nginx -t` را می‌شکند چون `events` هم‌سطح http نیست.

هر صفحه یک فایل کامل برای همان موضوع می‌دهد. آن‌ها را پشت سر هم در `sites-enabled` کپی نکنید. دو `server` با یک `server_name` و یک `listen` رفتار را مبهم می‌کند و zone هم‌نام خطای emergent می‌دهد. وقتی صفحهٔ بعدی را کار می‌کنید، همان فایل سایت را گسترش دهید.

## Production Example

این آزمون دود روی پروکسی `10.10.1.5` است تا مطمئن شوید نام `app.example.com` به فایل شما می‌رسد، نه به صفحهٔ خوش‌آمد بسته. فایل `/etc/nginx/sites-available/app.conf`:

```nginx
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;
    return 444;
    access_log off;
}

server {
    listen 80;
    listen [::]:80;
    server_name app.example.com;
    default_type text/plain;
    return 200 "ok app.example.com\n";
    access_log /var/log/nginx/app.example.com.access.log;
    error_log /var/log/nginx/app.example.com.error.log warn;
}
```

فعال‌سازی فقط با پیوند است. سایت پیش‌فرض بسته باید برداشته شود وگرنه دو `default_server` دارید:

```bash
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -s /etc/nginx/sites-available/app.conf /etc/nginx/sites-enabled/app.conf
sudo nginx -t && sudo systemctl reload nginx
curl -fsS -H "Host: app.example.com" http://127.0.0.1/
```

پاسخ سالم دقیقاً `ok app.example.com` است. این `return` تولید نیست. صفحه‌های پروکسی و Node همان بلوک را با `proxy_pass` عوض می‌کنند. اگر این پاسخ را در محیط واقعی جا بگذارید، کاربران به‌جای برنامه یک خط متن می‌بینند و سلامت‌سنج شما دروغ سبز می‌شود.

اگر میزبان IPv6 را در کرنل خاموش کرده، خط `listen [::]:80` را بردارید. علامت آن در لاگ این است: `Address family not supported by protocol`.

## Security Notes

سایت پیش‌فرض ریشهٔ `/var/www/html` را روی هر نام و روی خود نشانی IP نشان می‌دهد. تا وقتی آن پیوند در `sites-enabled` هست، یک درخواست بدون نام درست ممکن است صفحهٔ نسخهٔ بسته را نشان بدهد. `return 444` برای نام ناشناس اتصال را می‌بندد و بدنه‌ای برنمی‌گرداند.

پورت برنامه را در فایروال لبه باز نکنید. روی `10.10.1.5` فقط ۲۲ از شبکهٔ مدیر، به‌علاوهٔ ۸۰ و ۴۴۳ از بیرون، کافی است. روی `10.10.1.10` پورت ۸۰۸۰ فقط از `10.10.1.5` مجاز است و ۳۰۰۰ از شبکه بسته است. جزئیات سخت‌سازی SSH در فصل امنیت است؛ اینجا فقط پورت وب را با برنامه قاطی نمی‌کنیم.

`server_tokens off` و هدرها در صفحهٔ امنیت هستند. در آزمون دود بالا عمداً نیستند تا این فایل کوتاه بماند. قبل از ترافیک واقعی آن صفحه را اعمال کنید.

## Troubleshooting

سه فرمان اول وقتی نام بالا نمی‌آید:

```bash
sudo nginx -t
systemctl status nginx --no-pager
sudo journalctl -u nginx -n 50 --no-pager
```

اگر `-t` شکست بخورد، `reload` نزنید. reload کانفیگ خراب را بارگذاری نمی‌کند ولی عادت کردنتان به رد کردن خطا، روزی سرویس را با `restart` زمین می‌زند. خطای پرتکرار بعد از آزمون دود:

```text
nginx: [emerg] a duplicate default server for 0.0.0.0:80 in /etc/nginx/sites-enabled/app.conf:2
nginx: configuration file /etc/nginx/nginx.conf test failed
```

یعنی هم `default` بسته مانده و هم فایل شما `default_server` دارد. پیوند `/etc/nginx/sites-enabled/default` را بردارید و دوباره `-t` بگیرید.

اگر `curl` به IP بدون هدر Host وصل شد و جواب آزمون دود را ندید، طبیعی است؛ آن درخواست به بلوک `return 444` می‌رود. بدون `-H "Host: app.example.com"` در حال آزمون سایت خودتان نیستید. اگر با هدر درست هنوز صفحهٔ پیش‌فرض Debian را می‌بینید، `sudo nginx -T` را بگردید و ببینید کدام فایل `root /var/www/html` هنوز include شده است.

وقتی `curl` روی خود پروکسی درست است و از بیرون نه، مشکل Nginx نیست. `ss -lptn 'sport = :80'` باید `nginx` را نشان بدهد و فایروال نباید ۸۰ را بسته باشد.

اگر `nginx -t` موفق است و `reload` هم خطا نمی‌دهد ولی هنوز پاسخ قبلی را می‌بینید، به میزبان دیگری وصل شده‌اید یا هدر Host را نفرستاده‌اید. از خود `10.10.1.5` این را بزنید و کد را بخوانید، نه بدنهٔ کش‌شدهٔ مرورگر را:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: app.example.com" http://127.0.0.1/health
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/health
```

اولی باید ۲۰۰ باشد. دومی به پیش‌فرض `444` می‌خورد و اغلب از `curl` خطای پاسخ خالی می‌گیرید. اگر هر دو ۲۰۰ و بدنهٔ یکی هستند، `server_name` شما با `default_server` یکی شده یا هنوز سایت بسته در کار است.

صفحهٔ خطای `duplicate default server` را با پاک کردن پیوند حل کنید، نه با پاک کردن بسته. `apt purge nginx` کانفیگ `/etc/nginx` را هم، اگر تأیید کنید، دور می‌ریزد و آزمون دود را از صفر می‌سازید بی‌آنکه به علت رسیده باشید.

## Best Practices

- فایل اصلی را بازنویسی نکنید. سایت را در `sites-available` بگذارید و با پیوند روشن کنید.
- بعد از هر ویرایش `sudo nginx -t && sudo systemctl reload nginx`. ری‌استارت برای تغییر کانفیگ لازم نیست.
- یک `server_name` در یک فایل. ادغام صفحه‌های این فصل یعنی ویرایش همان فایل، نه انباشتن چند کپی.
- نسخه را از `nginx -v` بخوانید. شمارهٔ patch را در مستند داخلی تیم هم ثابت نکنید مگر روی یک میزبان مشخص pin کرده باشید.
- لاگ جدا برای `app.example.com` بسازید تا لاگ سایت پیش‌فرض و سایت شما قاطی نشود.
- وقتی آزمون دود تمام شد، `return 200` را برندارید و فراموش نکنید؛ صفحهٔ [پروکسی](/docs/06-nginx/reverse-proxy) جایگزین آن است.
- روی `10.10.1.10` هم سایت پیش‌فرض را بردارید، حتی اگر آن Nginx فقط به `10.10.1.10:8080` گوش بدهد. یک `default` فراموش‌شده روی پورت ۸۰ همان میزبان، صفحهٔ خوش‌آمد را به شبکهٔ داخلی نشان می‌دهد.
- شمارهٔ worker و `worker_connections` بسته را تا وقتی صف listen پر نشده عوض نکنید. اول `ss -lnt` و لاگ خطا، بعد عدد.
- نام میزبان‌ها را بین صفحه‌ها عوض نکنید. اگر لبه را روی `10.10.1.10` بالا آوردید، بقیهٔ مثال‌های `10.10.1.5` را هم همان‌جا نگذارید وگرنه دو سرویس روی یک پورت با هم دعوا می‌کنند.
