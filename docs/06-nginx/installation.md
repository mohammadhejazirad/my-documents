# نصب Nginx

## مقدمه

این صفحه Nginx را روی Ubuntu 26.04 از همان آرشیوی نصب می‌کند که بقیهٔ سیستم را به‌روز می‌کند. نام بسته `nginx` است و نسخهٔ آن در این دانشنامه 1.28.x است. شمارهٔ patch را از خروجی خود میزبان می‌خوانیم، چون آرشیو بین دو نقطهٔ به‌روزرسانی آن را عوض می‌کند و نوشتن یک patch ثابت در سند، فردا دروغ می‌شود.

میزبان این دستورها پروکسی آزمایشگاه است: `proxy.example.internal` با نشانی `10.10.1.5`. همان بسته را روی `app-1.example.internal` (`10.10.1.10`) هم نصب می‌کنیم، چون Nginx محلی برنامه به `127.0.0.1:3000` پروکسی می‌کند. نقشهٔ نقش‌ها در [نقشهٔ فصل](/docs/06-nginx) است. بعد از نصب، ساختار فایل و خاموش کردن سایت پیش‌فرض در [ساختار کانفیگ](/docs/06-nginx/configuration) است.

## مفهوم اصلی

بستهٔ Ubuntu یک metapackage است که باینری، واحد systemd، فایل اصلی `/etc/nginx/nginx.conf`، پوشهٔ `sites-available` و `sites-enabled`، و صفحهٔ پیش‌فرض را با هم می‌آورد. worker با کاربر `www-data` اجرا می‌شود. لاگ در `/var/log/nginx` است و pid در `/run/nginx.pid`.

این چیدمان مال Debian و Ubuntu است. فایل اصلی، `conf.d` و `sites-enabled` را داخل بلوک http با include می‌خواند. تا وقتی آن خط‌ها کامنت نشده باشند، فایلی که بعداً در این پوشه‌ها می‌گذاریم بدون دست زدن به `nginx.conf` بارگذاری می‌شود. سرویس را با systemd بالا نگه می‌داریم، نه با اجرای دستی `nginx` در یک شل.

شاخهٔ 1.28 دستور `http2 on` را جدا از خط `listen` می‌فهمد. روی Ubuntu 24.04 بسته هنوز 1.24 است و آن دستور جدا را ندارد؛ آنجا باید بنویسید `listen 443 ssl http2`. بقیهٔ دستورهای این فصل روی هر دو شاخه هستند. Debian 13 همان الگوی پوشه را دارد و نصبش همین `apt install nginx` است.

## چرا استفاده می‌شود؟

مخزن رسمی nginx.org بستهٔ تازه‌تر می‌دهد و کلید و فایل source جدا می‌خواهد. قاطی کردن آن با بستهٔ Ubuntu دو مبدأ برای یک باینری می‌سازد و ارتقای امنیتی را به کسی گره می‌زند که یادش بماند کدام مخزن برنده است. برای لبهٔ این آزمایشگاه، پنجرهٔ پشتیبانی توزیع کافی است. ماژول تجاری Nginx Plus اصلاً داخل این بسته نیست؛ صفحه‌ای که سلامت فعال یا `health_check` می‌خواهد باید صریح بگوید که این بسته آن را ندارد، نه اینکه مخزن را عوض کند.

کامپایل از منبع هم رد می‌شود. یک باینری دست‌ساز ماژول gzip و TLS را هر طور که آن روز پیکربندی شده باشد دارد، واحد systemd ندارد، و نفر بعدی نمی‌داند باید دوباره `make install` کند یا نه. `apt` هر سه را یک‌جا حل می‌کند.

## Architecture

```text
apt archive Ubuntu 26.04
        │
        ▼
بستهٔ nginx 1.28.x
        │
        ├─ /usr/sbin/nginx
        ├─ /etc/nginx/nginx.conf
        │     include conf.d/*.conf
        │     include sites-enabled/*
        ├─ /etc/nginx/sites-available/default
        ├─ /etc/nginx/sites-enabled/default -> ../sites-available/default
        ├─ /var/log/nginx/access.log
        ├─ /var/log/nginx/error.log
        └─ systemd: nginx.service
```

سایت پیش‌فرض هنوز به پورت ۸۰ و نام `_` جواب می‌دهد و ریشهٔ `/var/www/html` را نشان می‌دهد. نصب تمام‌شده یعنی سرویس بالا باشد، نه یعنی ترافیک `app.example.com` درست باشد. آن کار صفحهٔ بعد است.

روی `10.10.1.10` همین بسته یک Nginx دوم است که فقط روی نشانی خصوصی و پورت ۸۰۸۰ گوش خواهد داد. هر دو میزبان بستهٔ یکسان دارند تا کانفیگ را با تفاوت باینری اشتباه نگیریم.

## Installation

اگر پورت ۸۰ را فرایند دیگری گرفته، نصب سرویس بالا می‌آید ولی سوکت را نمی‌گیرد. قبل از نصب نگاه کنید:

```bash
sudo ss -lptn 'sport = :80' || true
sudo apt update
sudo apt install nginx
apt-cache policy nginx
nginx -v
sudo systemctl enable --now nginx
systemctl status nginx --no-pager
sudo nginx -t
sudo ss -lptn 'sport = :80'
```

`apt-cache policy nginx` باید خطی از آرشیو Ubuntu نشان بدهد، مثلاً pocket به‌روزرسانی `resolute-updates` یا خود `resolute`. اگر Origin چیز دیگری است، یک source اضافه قبلاً روی میزبان بوده و باید قبل از ادامه پاک شود. `nginx -v` را با چشم بخوانید و مطمئن شوید شاخه `1.28` است. نمونهٔ شکل خروجی، با patch همان روز آرشیو:

```text
nginx version: nginx/1.28.x
```

به‌جای `x` عدد واقعی می‌نشیند. آن عدد را در اسکریپت تیم سخت ننویسید. `systemctl status` باید `active (running)` و `enabled` باشد. `nginx -t` روی بستهٔ تازه باید `syntax is ok` و `test is successful` بدهد، حتی پیش از ویرایش ما، چون فایل پیش‌فرض خودش معتبر است.

واحد را از بسته بردارید و مسیرش را حدس نزنید:

```bash
systemctl cat nginx
```

Debian 13 همین دستور `apt install nginx` را دارد. فرق عملی این صفحه با Debian در نام رمز آرشیو است، نه در نام سرویس. روی Ubuntu 24.04 نصب همین است و فقط خروجی نسخه `nginx/1.24` خواهد بود. آنجا کانفیگ‌های این فصل را با همان قاعدهٔ `listen ... http2` که بالاتر گفته شد بنویسید.

## Configuration

بعد از نصب، includeهای فایل اصلی را تأیید کنید. اگر کسی قبلاً آن‌ها را کامنت کرده باشد، سایت‌هایی که در صفحه‌های بعد می‌سازیم بی‌صدا بارگذاری نمی‌شوند:

```bash
grep -nE 'include ' /etc/nginx/nginx.conf
ls -l /etc/nginx/sites-enabled /etc/nginx/conf.d
```

باید این مسیرها را ببینید، داخل بلوک http و بدون `#` در ابتدای خط:

```nginx
include /etc/nginx/mime.types;
include /etc/nginx/conf.d/*.conf;
include /etc/nginx/sites-enabled/*;
```

ممکن است خط `include /etc/nginx/modules-enabled/*.conf;` هم باشد. به آن دست نزنید. ماژول‌های بسته‌بندی‌شده از آنجا می‌آیند.

کاربر و مسیرهایی که صفحه‌های بعد فرض می‌کنند:

| مورد | مقدار بعد از نصب |
| --- | --- |
| کاربر worker | `www-data` |
| فایل اصلی | `/etc/nginx/nginx.conf` |
| سایت خاموش‌کردنی | پیوند `sites-enabled/default` |
| لاگ | `/var/log/nginx/error.log` و `access.log` |
| آزمون نحو | `sudo nginx -t` |
| اعمال بدون قطع اتصال | `sudo systemctl reload nginx` |

صفحهٔ خوش‌آمد را با `curl` ببینید تا بدانید سرویس واقعاً جواب می‌دهد. این پاسخ را با پاسخ برنامه اشتباه نگیرید:

```bash
curl -fsS -D- http://127.0.0.1/ -o /tmp/nginx-default-body.txt
head -n 5 /tmp/nginx-default-body.txt
```

بدنه صفحهٔ پیش‌فرض بسته است، نه `app.example.com`. تا وقتی [ساختار کانفیگ](/docs/06-nginx/configuration) سایت پیش‌فرض را برنمی‌دارد، هر نامی که بلوک خودش را ندارد همین صفحه را می‌بیند.

## Production Example

روی هر دو میزبان آزمایشگاه بسته را نصب کنید و نسخه را در یادداشت تغییر همان روز بنویسید. از پروکسی:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 ops@10.10.1.5
nginx -v
systemctl is-enabled nginx
systemctl is-active nginx
```

سپس همین سه فرمان را روی `ops@10.10.1.10` تکرار کنید. هر دو باید `enabled` و `active` باشند و هر دو باید `nginx/1.28` را نشان بدهند. اگر یکی 1.24 است، آن میزبان 26.04 نیست و کانفیگ `http2 on` را نباید بی‌ملاحظه به آن کپی کنید.

بعد از نصب، فایروال را هنوز باز نکنید تا سایت پیش‌فرض به اینترنت نرسد. روی پروکسی، اجازهٔ ۸۰ و ۴۴۳ مال وقتی است که بلوک `app.example.com` جایگزین صفحهٔ پیش‌فرض شده باشد. آزمون دود آن جایگزینی در [نقشهٔ فصل](/docs/06-nginx) است و جزئیات پیوندها در صفحهٔ ساختار.

به‌روزرسانی بعدی بسته کار جداگانه‌ای نیست. `apt upgrade` باینری را عوض می‌کند و اسکریپت بسته معمولاً سرویس را reload می‌کند. بعد از هر ارتقا این دو فرمان را بزنید و خروجی را نگه دارید:

```bash
nginx -v
sudo nginx -t && sudo systemctl reload nginx
```

اگر `-t` بعد از ارتقا شکست، کانفیگ شما از دستوری استفاده کرده که بستهٔ جدید برمی‌دارد یا فایل شما از قبل خراب بوده و reload قبلی هرگز اتفاق نیفتاده است. سرویس قدیمی ممکن است هنوز در حافظه باشد. کانفیگ را با صفحهٔ مربوط درست کنید؛ بسته را hold نکنید.

## Security Notes

بسته را از یک `.deb` دانلود‌شدهٔ بی‌نام نصب نکنید. `apt` امضای آرشیو را چک می‌کند. کپی کردن باینری از لپ‌تاپ این بررسی را دور می‌زند.

سایت پیش‌فرض اطلاعات کم اما واقعی لو می‌دهد: نرم‌افزار لبه Nginx است و میزبان زنده است. تا خاموش شدنش، پورت ۸۰ را در لبهٔ شبکه باز نگذارید. `server_tokens` هنوز پیش‌فرض بسته است و نسخه را در صفحهٔ خطا می‌گذارد. خاموش کردنش در [امنیت و نرخ](/docs/06-nginx/security-rate-limit) است و جای نصب نیست، چون قبل از داشتن TLS و نام درست، هدر امنیتی نیمه‌کاره گمراه‌کننده است.

کاربر `www-data` نباید مالک کد برنامه باشد. Nginx فقط فایل ثابتی را می‌خواند که برایش خوانا گذاشته‌اید، یا به سوکت محلی وصل می‌شود. مالک `/opt/apps` کاربر `deploy` است. این جداسازی را موقع نصب با اضافه کردن `www-data` به گروه `deploy` خراب نکنید.

## Troubleshooting

اگر `apt install` تمام شد ولی `status` می‌گوید `failed`:

```bash
sudo journalctl -u nginx -n 40 --no-pager
sudo nginx -t
sudo ss -lptn 'sport = :80'
```

پرتکرارترین علت روی میزبان شلوغ این است که چیز دیگری پورت ۸۰ را گرفته است. `ss` نام فرایند را نشان می‌دهد. تا آن فرایند را به پورت دیگری نبرید یا خاموش نکنید، Nginx بالا نمی‌ماند. بسته را purge نکنید؛ مشکل از سوکت است نه از فایل‌های `/etc/nginx`.

اگر `nginx -t` می‌گوید `open() "/etc/nginx/sites-enabled/..." failed`، یک پیوند شکسته در آن پوشه مانده است. `ls -l` هدف پیوند را نشان می‌دهد. پیوند را بردارید و دوباره `-t` بگیرید. خود پوشهٔ `sites-available` را پاک نکنید.

اگر `nginx -v` فرمان را پیدا نمی‌کند ولی بسته نصب است، PATH نشست شما `/usr/sbin` را ندارد. مسیر کامل `/usr/sbin/nginx -v` را بزنید. واحد systemd به PATH شما وابسته نیست.

اگر بعد از نصب `curl http://127.0.0.1/` رد می‌شود و `ss` خالی است، سرویس `active` نیست. `sudo systemctl enable --now nginx` را دوباره بزنید و اگر واحد ماسک شده، `systemctl unmask nginx` لازم است. ماسک را فقط وقتی بردارید که خودتان قبلاً عمداً ماسک نکرده باشید؛ روی یک میزبان تازهٔ Ubuntu این وضعیت عادی نیست.

خطای `Address already in use` در journal یعنی همان برخورد پورت. یک Nginx دستی که کسی با شل بالا آورده هم همین علامت را می‌دهد. `ps -C nginx` را ببینید. اگر pid زیر نظر systemd نیست، همان فرایند یتیم را متوقف کنید و بعد `systemctl start nginx`.

## Best Practices

- فقط بستهٔ `nginx` از آرشیو Ubuntu. مخزن nginx.org را کنار این بسته اضافه نکنید.
- نسخه را با `nginx -v` و مبدأ را با `apt-cache policy nginx` ثابت کنید. patch را در سند کپی نکنید.
- `enable --now` تا بعد از reboot لبه خودش بالا بیاید. اجرای دستی `nginx` در ssh نشست را به عمر شل گره می‌زند.
- سایت پیش‌فرض را در همین صفحه به عنوان تمام‌شده قبول نکنید. صفحهٔ [ساختار](/docs/06-nginx/configuration) آن را برمی‌دارد.
- بعد از هر `apt upgrade` یک بار `nginx -t` و در صورت نیاز reload.
- روی 24.04 فرض نکنید دستور `http2 on` وجود دارد. آنجا پارامتر `http2` روی خط `listen` است.
