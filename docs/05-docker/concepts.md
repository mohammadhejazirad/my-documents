# کانتینر، ایمیج، رجیستری، ولوم، شبکه، لایه

## مقدمه

قبل از نوشتن Dockerfile یا Compose باید بتوانید بگویید داده کجا می‌ماند، اسم سرویس از کجا حل می‌شود، و چرا پاک کردن کانتینر دیتابیس را پاک نمی‌کند ولی پاک کردن ولوم می‌کند. این صفحه همان مدل است. دستورهای روزمره در [مرجع دستورها](./commands.md) هستند و اینجا تکرار فهرست فلگ نیستند.

مثال‌ها روی `docker-1.example.internal` یعنی `10.10.1.30` فرض شده‌اند. اگر هنوز `docker info` خروجی Server ندارد، اول [نصب](./installation.md) را تمام کنید.

## مفهوم اصلی

شش واژه در لاگ و در حادثه مدام قاطی می‌شوند.

| واژه | چیست | با حذف چه چیزی از بین می‌رود |
| --- | --- | --- |
| لایه (layer) | تفاوت فایل‌سیستم که ایمیج را می‌سازد | با حذف ایمیج، اگر لایه جای دیگر استفاده نشده باشد |
| ایمیج (image) | مجموعهٔ لایه‌های فقط-خواندنی به‌علاوهٔ پیکربندی پیش‌فرض فرایند | با `docker rmi`، نه با توقف کانتینر |
| کانتینر (container) | فرایند در حال اجرا به‌علاوهٔ لایهٔ قابل نوشتن روی ایمیج | لایهٔ قابل نوشتن با حذف کانتینر |
| رجیستری (registry) | مخزن ایمیج روی شبکه | محلی نیست؛ قطع شبکه‌اش pull را می‌خواباند |
| ولوم (volume) | دایرکتوری مدیریت‌شده توسط Engine، جدا از لایهٔ قابل نوشتن | فقط با حذف صریح ولوم |
| شبکه (network) | دامنهٔ ارتباطی کانتینرها و جدول DNS داخلی | با حذف شبکه، نه با ریبوت کانتینر |

ایمیج برنامه نیست. ایمیج قالب است. کانتینر هم ماشین مجازی کوچک نیست. کرنل میزبان یکی است و جداسازی با namespace و cgroup انجام می‌شود. به همین دلیل نسخهٔ کرنل را ایمیج تعیین نمی‌کند، ولی کاربران فضای کاربر داخل ایمیج مال توزیع پایهٔ همان ایمیج است. `node:24-bookworm-slim` یعنی کاربران Debian 12 داخل کانتینر، حتی اگر میزبان Ubuntu 26.04 Resolute باشد. این تفاوت عادی است.

تگ (tag) اسم متحرک یک ایمیج است. `nginx:1.28-alpine` برای انسان خواناست و در این دانشنامه از آن استفاده می‌شود. digest شناسهٔ محتوایی است و بعد از pull در `RepoDigests` دیده می‌شود. `latest` تگ است، نسخه نیست، و در Production این فصل ممنوع است. دلیل اجرایی در [Dockerfile](./dockerfile.md) است.

اسم کوتاه را Engine قبل از pull کامل می‌کند. `nginx` یعنی `docker.io/library/nginx` و تگ نانوشته یعنی `latest`، همان چیزی که این فصل در فایل سرویس نمی‌پذیرد. `mysql:8.4` یعنی رجیستری پیش‌فرض، مسیر رسمی `library/mysql`، و تگ `8.4`. اگر در نام، میزبان دیگری ببینید، مثلاً یک رجیستری خصوصی، کلید `registry-mirrors` در آن کشیدن دخالت نمی‌کند. این را موقع خواندن خطای pull از روی خود نام ایمیج تشخیص دهید، نه از حدس.

رجیستری پیش‌فرض Docker Hub است. اسم کوتاه `nginx` در واقع `docker.io/library/nginx` است. رجیستری‌های دیگر مثل یک رجیستری خصوصی سازمان با همین مکانیزم کار می‌کنند، ولی کلید `registry-mirrors` فقط کشیدن از Hub را به آینه می‌فرستد. این محدودیت در [آینهٔ رجیستری](./registry-mirror.md) باز شده است.

## چرا استفاده می‌شود؟

اگر این شش واژه را عوضی به کار ببرید، تعمیر حادثه بدتر از خود حادثه می‌شود. نمونهٔ پرتکرار: کانتینر MySQL رمز را از env جدید برنمی‌دارد، اپراتور ولوم را پاک می‌کند تا «از اول بسازد»، و داده می‌رود. رمز اولیه فقط وقتی اعمال می‌شود که دایرکتوری داده خالی باشد. ولوم خالی نیست. مفهوم، جلوی این تصمیم را می‌گیرد.

نمونهٔ دوم: دو کانتینر را روی شبکهٔ پیش‌فرض `bridge` با اسم به هم وصل می‌کنید و DNS جواب نمی‌دهد. روی شبکهٔ پیش‌فرض، Engine اسم کانتینر را بین کانتینرها حل نمی‌کند. روی شبکهٔ تعریف‌شده توسط کاربر حل می‌کند. Compose برای همین برای هر پروژه شبکه می‌سازد.

نمونهٔ سوم: `docker commit` از یک کانتینر در حال اجرا ایمیج می‌سازد تا «سریع به Production برسد». لایهٔ قابل نوشتن شامل لاگ، فایل موقت، و شاید رمز است. ایمیج قابل بازتولید نیست. مسیر این فصل Dockerfile و Compose است، نه commit از کانتینر زنده.

## Architecture

یک کانتینر در حال اجرا از این قطعه‌ها ساخته شده است.

```text
docker pull nginx:1.28-alpine
        │
        ▼
رجیستری Hub  یا  mirror.example.internal
        │  لایه‌های فقط-خواندنی
        ▼
ذخیرهٔ ایمیج روی دیسک میزبان
        │
        ▼
docker run ──► لایهٔ قابل نوشتن کانتینر   (با حذف کانتینر می‌رود)
        │
        ├─► ولوم سوارشده                  (می‌ماند)
        └─► کارت شبکه داخل شبکهٔ shop     (DNS اسم سرویس)
```

لایه‌ها روی هم سوار می‌شوند و کپی هنگام نوشتن (copy-on-write) دارند. تا وقتی فرایندی یک فایل را ننویسد، همان فایل لایهٔ پایین دیده می‌شود. اولین نوشتن، یک کپی در لایهٔ قابل نوشتن کانتینر می‌سازد. به همین دلیل نوشتن سنگین دیتابیس روی لایهٔ قابل نوشتن هم کند است هم با حذف کانتینر نابود می‌شود. دادهٔ ماندگار باید روی ولوم باشد.

هر دستور Dockerfile که فایل‌سیستم را عوض کند لایهٔ جدید می‌سازد. ترتیب دستورها روی کش بیلد اثر دارد. اگر اول سورس برنامه را کپی کنید و بعد وابستگی را نصب کنید، هر تغییر یک خطی سورس نصب وابستگی را باطل می‌کند. در [Dockerfile](./dockerfile.md) اول فایل قفل وابستگی کپی می‌شود.

دو مسیر دیسک را با هم قاطی نکنید. ولوم‌ها و متادیتای Engine زیر `/var/lib/docker` می‌مانند. روی نصب تازهٔ Engine که فروشگاه ایمیج containerd را پیش‌فرض دارد، محتوای ایمیج و اسنپ‌شات کانتینر زیر `/var/lib/containerd` است. ارتقای یک Engine قدیمی این مسیر را خودش عوض نمی‌کند و دستورهای `docker images` و `docker pull` و `docker build` در هر دو حالت همان دستورها هستند. پر شدن هر کدام از این دو مسیر pull و شروع کانتینر را با خطای دیسک خراب می‌کند.

شبکهٔ داخل Compose یک بریج است. هر سرویس یک آدرس از زیرشبکهٔ همان بریج می‌گیرد. انتشار پورت روی میزبان کار جداگانه‌ای است: `127.0.0.1:3306:3306` یعنی پورت `3306` میزبان فقط روی loopback به پورت `3306` کانتینر وصل شود. بدون این انتشار، سرویس فقط از داخل همان شبکهٔ Docker دیده می‌شود و این برای دیتابیس نمونهٔ مطلوب ماست، به شرطی که کلاینت یا تونل هم همان‌جا باشد.

## Installation

مفهوم به بسته نیاز ندارد، ولی برای دیدن همین مدل روی میزبان باید Engine نصب باشد. بعد از [نصب](./installation.md) این فرمان‌ها مدل را روی دیسک نشان می‌دهند، بدون اینکه سرویس دائمی بسازند.

```bash
docker info
docker network ls
docker volume ls
docker images
```

`docker network ls` همیشه سه شبکهٔ پیش‌فرض را نشان می‌دهد: `bridge` و `host` و `none`. این سه را حذف نمی‌کنید. `host` یعنی کانتینر پشتهٔ شبکهٔ میزبان را شریک می‌شود و ایزولاسیون پورت از بین می‌رود. در نمونه‌های این فصل از شبکهٔ `host` استفاده نشده است. `none` یعنی کانتینر رابط شبکه‌ای جز loopback ندارد.

یک ولوم آزمایشی و یک شبکهٔ آزمایشی بسازید و بعد پاک کنید تا اسم‌ها در ذهن بماند. اگر نام را در Production همین‌جا رها کنید، ماه بعد کسی نمی‌داند مال کدام سرویس است.

```bash
docker volume create lab-concepts-data
docker volume inspect lab-concepts-data
docker network create lab-concepts
docker network inspect lab-concepts
docker volume rm lab-concepts-data
docker network rm lab-concepts
```

`inspect` مسیر واقعی ولوم روی میزبان را در `Mountpoint` نشان می‌دهد. آن مسیر را با ابزار عادی میزبان ویرایش نکنید. مالکیت فایل‌های داخلش مال کاربر داخل کانتینر است و یک `chown` عجولانه دیتابیس را از بالا آمدن می‌اندازد.

## Configuration

چیزهایی که ظاهر پیکربندی دارند ولی در واقع انتخاب مدل‌اند:

- تگ ایمیج در فایل Compose ثابت است. عوض کردن تگ یعنی عوض کردن لایه‌ها، نه یک رفرش بی‌خطر.
- `restart: unless-stopped` سیاست میزبان است برای وقتی فرایند می‌میرد یا daemon بعد از ریبوت بالا می‌آید. این سیاست داده را نگه نمی‌دارد.
- ولوم نام‌دار در Compose اسم صریح دارد تا با اسم پروژه قاطی نشود. ولوم بی‌نامی که فقط به خاطر دستور `VOLUME` داخل Dockerfile ساخته می‌شود، اسم هگز طولانی می‌گیرد و در بکاپ فراموش می‌شود.
- شبکهٔ هر Compose اسم صریح دارد. دو پروژه که هر دو شبکه را `default` رها کنند، به اسم دایرکتوری وابسته‌اند و اپراتور در `docker network ls` گم می‌شود.
- متغیر محیطی داخل کانتینر با فایل env روی میزبان یکی نیست، مگر Compose آن را تزریق کند. فایل `.env` کنار `compose.yaml` به‌طور پیش‌فرض برای جایگذاری داخل فایل Compose خوانده می‌شود. رسیدن همان متغیر به داخل کانتینر نیاز به `environment` یا `env_file` دارد. این فرق در صفحه‌های دیتابیس مهم است.

فروشگاه ایمیج را برای «مرتب شدن» عوض نکنید. نصب تازهٔ Engine 29 و جدیدتر فروشگاه ایمیج containerd را خودش روشن می‌کند و بستهٔ `containerd.io` این مخزن، containerd 2 است. میزبانی که از Engine قدیمی‌تر ارتقا شده روی درایور قبلی می‌ماند. سوییچ دستی وسط شیفت، ایمیج‌های ذخیره‌شده با درایور قبلی را از `docker images` پنهان می‌کند در حالی که هنوز روی دیسک هستند. دستورها نمی‌شکنند، ولی ظاهر امر این است که ایمیج‌ها پاک شده‌اند. این سوییچ کار این صفحه نیست.

## Production Example

یک سرویس ایستا را یک بار با ولوم و یک بار بدون ولوم تصور کنید. Nginx که فقط فایل ایمیج را سرو می‌کند به ولوم نیاز ندارد. MySQL بدون ولوم بعد از `docker rm` پایگاه خالی است، حتی اگر کانتینر را با همان اسم دوباره بسازید.

شکل درست برای داده:

```text
ایمیج mysql:8.4          فقط-خواندنی، قابل تعویض با تگ جدید
لایهٔ قابل نوشتن         لاگ موقت و فایل فرایند، بی‌ارزش
ولوم shop-mysql-data     /var/lib/mysql داخل کانتینر
شبکهٔ shop-mysql         فقط همین سرویس، پورت میزبان 127.0.0.1:3306
```

شکل درست برای ارتباط دو سرویس، در [مدل Compose](./compose.md) فایل کامل دارد. اینجا فقط قرارداد اسم است: سرویس `web` به اسم `api` وصل می‌شود، نه به آدرس IP که بعد از هر بالا آمدن ممکن است عوض شود. IP داخل شبکهٔ Docker قرارداد Production نیست.

برای رجیستری، قرارداد این است که `docker pull nginx:1.28-alpine` روی `docker-1` در حالت عادی از آینهٔ سازمان رد شود. آینه باید همان ایمیج رسمی را کش کند، نه اینکه تگ را به ایمیج دیگری گره بزند. اگر آینه در کار نیست، Engine به Hub برمی‌گردد. اگر هر دو بسته باشند، pull تمام نمی‌شود و مسیر [کار آفلاین](./offline-operations.md) با `docker save` و `docker load` است. save ایمیج را می‌برد، نه ولوم را و نه لایهٔ قابل نوشتن یک کانتینر در حال اجرا را.

## Security Notes

لایهٔ قابل نوشتن و تاریخچهٔ ایمیج جای رمز نیست. `docker diff` فایل‌هایی را نشان می‌دهد که کانتینر نسبت به ایمیج نوشته است. اگر کسی داخل کانتینر در حال اجرا یک فایل env ساخته باشد، آن فایل در لایهٔ قابل نوشتن است و با یک ایمیج commit‌شده به رجیستری نشت می‌کند.

شبکهٔ `bridge` پیش‌فرض فیلتر هویت نیست. هر کانتینری که به یک شبکهٔ کاربر وصل باشد، پورت‌های شنوده‌شده روی آن شبکه را می‌بیند، حتی اگر آن پورت روی میزبان منتشر نشده باشد. جدا کردن شبکهٔ دیتابیس از شبکهٔ وب در Compose برای همین است، نه برای زیبایی فایل.

mount کردن `/` یا `/var/run/docker.sock` داخل کانتینر یعنی آن کانتینر اختیار میزبان را دارد. نمونه‌های این فصل این کار را نمی‌کنند. اگر روزی یک ابزار مانیتورینگ به سوکت نیاز داشت، آن استثنا باید جداگانه بررسی شود و پیش‌فرض این صفحه نیست.

digest را وقتی ثبت کنید که باید ثابت کنید چه بایتی اجرا شده است. تگ خوانا برای انسان می‌ماند و digest را خروجی واقعی `docker image inspect` همان روز تعیین می‌کند. digest ساختگی در مستند ننویسید.

## Troubleshooting

| باور غلط | واقعیت |
| --- | --- |
| با توقف کانتینر دادهٔ ولوم پاک می‌شود | ولوم می‌ماند. `down` بدون پرچم ولوم هم ولوم را نگه می‌دارد |
| با حذف کانتینر ایمیج پاک می‌شود | ایمیج می‌ماند تا خودتان حذفش کنید |
| اسم کانتینر از میزبان همیشه قابل ping است | DNS مال شبکهٔ تعریف‌شده است، نه مال میزبان |
| پورت منتشرنشده از LAN بسته است، پس از کانتینر کناری هم بسته است | کانتینر هم‌شبکه پورت را می‌بیند |
| عوض کردن `.env` رمز دیتابیس زنده را عوض می‌کند | اسکریپت ورود ایمیج فقط ولوم خالی را مقداردهی می‌کند |
| دیسک Docker فقط `/var/lib/docker` است | روی نصب تازه ایمیج‌ها زیر `/var/lib/containerd` هم هستند |
| `latest` یعنی جدیدترین نسخهٔ امن | یعنی آخرین چیزی که آن اسم به آن اشاره کرده، هر چه باشد |

اگر `docker pull` اسم را پیدا نمی‌کند، اول تگ را با [دستور images](./commands.md) محلی چک کنید. `manifest unknown` یعنی رجیستری آن تگ را ندارد. این با قطع شبکه فرق دارد. قطع شبکه معمولاً timeout یا خطای TLS است. این دو را در گزارش حادثه یکی ننویسید.

یک تمرین ذهنی را روی میزبان خالی از سرویس واقعی انجام دهید تا شش واژه از هم جدا بمانند. چیزی نسازید که اسمش شبیه سرویس Production باشد.

```bash
docker network create lab-concepts
docker volume create lab-concepts-data
docker run -d --name lab-concepts-web --network lab-concepts \
  -v lab-concepts-data:/usr/share/nginx/html \
  nginx:1.28-alpine
docker ps --filter name=lab-concepts-web
docker volume ls
docker network inspect lab-concepts
```

`docker ps` کانتینر را نشان می‌دهد، `docker images` ایمیج `nginx:1.28-alpine` را، و `docker volume ls` ولوم را. این‌ها سه فهرست جدا هستند. حالا کانتینر را حذف کنید و دوباره نگاه کنید.

```bash
docker rm -f lab-concepts-web
docker ps -a --filter name=lab-concepts-web
docker volume inspect lab-concepts-data
docker images nginx
```

فهرست کانتینر خالی است. ولوم و ایمیج مانده‌اند. این همان دلیلی است که حذف کانتینر دیتابیس، به‌خودی خود، داده را نمی‌برد و حذف ولوم می‌برد. بعد از دیدن خروجی، آزمایش را جمع کنید.

```bash
docker volume rm lab-concepts-data
docker network rm lab-concepts
```

اگر `network rm` گفت شبکه هنوز استفاده می‌شود، یک کانتینر را جا گذاشته‌اید. `docker network inspect lab-concepts` اسمش را نشان می‌دهد. شبکهٔ پیش‌فرض `bridge` را با این نام اشتباه نگیرید و حذف نکنید.

`EXPOSE` داخل Dockerfile و ستون `PORTS` در `docker ps` هم یکی نیستند. `EXPOSE` فقط سند است و پورتی روی میزبان باز نمی‌کند. تا وقتی `-p` یا کلید `ports` در Compose نباشد، از `10.10.1.10` به آن پورت نمی‌رسید، ولی از کانتینر دیگری در `lab-concepts` می‌رسید. این تفاوت را در طراحی «دیتابیس را به LAN باز نکنیم» استفاده می‌کنیم، نه به‌عنوان جایگزین رمز.

## Best Practices

- برای هر دادهٔ ماندگار ولوم نام‌دار تعریف کنید و اسمش را در مستند سرویس بیاورید.
- شبکهٔ پیش‌فرض `bridge` را برای سرویس چندبخشی استفاده نکنید.
- تگ را تا حد major و واریانت سیستم‌عامل پایه مشخص کنید. `node:24-bookworm-slim` قبول است. `node:latest` قبول نیست.
- IP داخلی کانتینر را در کانفیگ برنامه سخت ننویسید. اسم سرویس Compose کافی است.
- قبل از حذف ولوم، اسم را با `docker volume inspect` و با لیست کانتینرهای متصل تطبیق دهید.
- ایمیج را با `docker commit` از محیط زنده نسازید.
- راز را در لایه نگذارید. فایل env روی میزبان با مجوز `0600` بماند.
- وقتی دیسک را چک می‌کنید هر دو مسیر `/var/lib/docker` و `/var/lib/containerd` را ببینید.
- سوییچ فروشگاه ایمیج را وسط حادثه انجام ندهید. نصب تازه رفتار خودش را دارد و دستورها را عوض نمی‌کند.
- اگر مفهومی در لاگ بود و این جدول پوشش‌اش نداد، همان اسم انگلیسی لاگ را در مرجع دستور جستجو کنید، ترجمه‌اش را نه.
- قبل از پاک کردن هر چیزی بپرسید کدام فهرست باید خالی شود: `docker ps -a`، `docker images`، یا `docker volume ls`. این سه را با یک فرمان یکی نکنید.
- انتشار پورت را با `EXPOSE` اشتباه نگیرید. اولی را در Compose می‌نویسید، دومی فقط توضیح داخل Dockerfile است.
