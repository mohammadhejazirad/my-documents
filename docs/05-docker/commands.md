# مرجع دستورهای Docker

## مقدمه

این صفحه مرجع شیفت است، نه معرفی مفهوم. اگر فرق ولوم و لایه هنوز روشن نیست، اول [مفهوم‌ها](./concepts.md) را بخوانید. نصب موتور در [نصب](./installation.md) است. اینجا فرض این است که کاربر `ops` روی `docker-1.example.internal` یعنی `10.10.1.30` عضو گروه `docker` است و `docker ps` بدون `sudo` به سوکت وصل می‌شود.

دستورها همان چیزی هستند که در لاگ و در تیکت دیده می‌شوند: `docker ps`، `docker images`، `docker build`، `docker run`، `docker exec`، `docker logs`، `docker volume`، `docker network`. زیر‌دستورهای نزدیک، مثل `ps -a` و `logs -f` و `volume ls` و `network ls`، داخل همان بخش آمده‌اند. Compose با فاصله نوشته می‌شود و در [مدل Compose](./compose.md) است. این صفحه باینری `docker-compose` را صدا نمی‌زند.

خروجی‌های نمونه شکل واقعی جدول Engine هستند. شناسهٔ دوازده‌حرفی مال میزبان شما نیست. ستون `STATUS` و اسم و پورت را با میزبان خودتان تطبیق دهید.

## docker ps

### توضیح

`docker ps` کانتینرهای در حال اجرا را نشان می‌دهد. یک ردیف یعنی یک کانتینر، نه یک ایمیج. ستون‌هایی که موقع حادثه به کار می‌آیند: `STATUS`، `PORTS`، `NAMES`.

| پرچم | اثر |
| --- | --- |
| `-a` | اجرا و توقف‌خورده را با هم نشان می‌دهد |
| `-q` | فقط شناسه، مناسب لوله‌کردن به دستور دیگر |
| `--filter` | محدود کردن بر اساس وضعیت، اسم، یا برچسب |
| `--format` | ستون‌های انتخابی برای گزارش |
| `-n` | تعداد آخرین کانتینرهایی که ساخته شده‌اند، همراه با `-a` |

`STATUS` اگر `Up` باشد فرایند اصلی هنوز خارج نشده است. `Up ... (healthy)` یعنی healthcheck تعریف شده و آخرین بار موفق بوده. `Up ... (unhealthy)` یعنی کانتینر زنده است ولی آزمون سلامت شکست خورده. `Exited` فقط با `-a` دیده می‌شود. کد خروج داخل پرانتز است. `137` معمولاً یعنی SIGKILL، اغلب به‌خاطر سقف حافظه. `0` یعنی فرایند خودش تمام شده و از نظر سیستم‌عامل خطا نبوده، حتی اگر از نظر شما سرویس نباید می‌خوابید.

`PORTS` انتشار روی میزبان است. `127.0.0.1:3306->3306/tcp` یعنی فقط loopback میزبان. اگر این ستون خالی است، سرویس فقط از شبکهٔ Docker در دسترس است.

### مثال واقعی

```bash
docker ps
docker ps -a
docker ps -a --filter status=exited
docker ps --filter name=edge
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

شکل خروجی `docker ps` وقتی نمونهٔ Nginx این فصل بالا باشد:

```text
CONTAINER ID   IMAGE               COMMAND                  CREATED       STATUS                 PORTS                        NAMES
9c1e0a44b7d2   nginx:1.28-alpine   "/docker-entrypoint.…"   3 hours ago   Up 3 hours (healthy)   10.10.1.30:8080->80/tcp      edge-web
```

کانتینر خارج‌شده فقط با `-a` می‌آید:

```text
CONTAINER ID   IMAGE        COMMAND    CREATED     STATUS                      PORTS    NAMES
51ab90c2e11d   hello-world  "/hello"   5 days ago  Exited (0) 5 days ago                hello-test
```

### کاربرد Production

اول حادثه `docker ps -a --filter name=shop` است، نه ریبوت میزبان. اسم را از `compose.yaml` بردارید. اگر ردیف نیست، Compose اصلاً کانتینر را نساخته یا کسی حذفش کرده. اگر `Exited` است، دستور بعدی `docker logs` همان اسم است، نه `docker start` بی‌خبر.

برای گزارش شیفت، قالب کوتاه کافی است.

```bash
docker ps -a --filter name=shop-mysql --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

`-q` را در اسکریپت فقط وقتی به کار ببرید که فیلتر دقیق است. `docker ps -aq` بدون فیلتر همهٔ شناسه‌ها را می‌دهد و اگر به `docker rm` لوله شود همه‌چیز پاک می‌شود. در فرمان تعاملی Production از این ترکیب استفاده نکنید.

سلامت را از همین جدول بخوانید. `unhealthy` یعنی باید لاگ و دستور healthcheck را ببینید، نه اینکه کانتینر را حذف کنید. حذف، لایهٔ قابل نوشتن را می‌برد و اگر ولوم درست وصل نشده باشد داده را هم با خودش می‌برد.

### وقتی خراب می‌شود

`Cannot connect to the Docker daemon at unix:///var/run/docker.sock` یعنی کلاینت به دیمون نرسیده. `systemctl is-active docker.service` و عضویت گروه را ببینید. نشست قدیمی بعد از `usermod` هنوز گروه `docker` را ندارد. یک بار از SSH خارج شوید.

اگر جدول خالی است و شما مطمئنید سرویس دیشب بالا بوده، `docker ps -a` بزنید. بدون `-a` خروج‌خورده‌ها را نشان نمی‌دهد و اپراتور فکر می‌کند «همه‌چیز پاک شده».

اگر ستون `PORTS` پورتی را نشان می‌دهد که `ss` روی میزبان نمی‌بیند، یا به آدرس کارت دیگری bind شده یا قانون iptables Docker را جدا از انتظارتان نوشته. آدرس سمت چپ `->` را بخوانید. `0.0.0.0:8080` با `10.10.1.30:8080` یکی نیست.

`permission denied` هنگام اجرای خود `docker ps` مسئلهٔ سوکت است، نه مسئلهٔ کانتینر.

## docker images

### توضیح

`docker images` ایمیج‌های محلی را فهرست می‌کند. این فهرست با کانتینر یکی نیست. ایمیج می‌تواند هیچ کانتینر زنده‌ای نداشته باشد و هنوز دیسک بگیرد. ستون `TAG` اگر مقدار `none` باشد یعنی ایمیج بی‌تگ است، اغلب لایهٔ میانی یک بیلد یا حاصل یک تگ که جایش را به بیلد جدید داده.

| پرچم | اثر |
| --- | --- |
| `-a` | لایه‌های میانی را هم نشان می‌دهد. خروجی شلوغ می‌شود |
| `--digests` | ستون digest برای تطبیق با رجیستری |
| `--filter dangling=true` | فقط ایمیج بی‌تگ |
| `--no-trunc` | شناسهٔ کامل |

`docker image inspect` پیکربندی ایمیج را نشان می‌دهد: دستور پیش‌فرض، متغیرها، و `RepoDigests`. راز نباید این‌جا باشد. اگر بود، ایمیج را نجات ندهید. بیلد را اصلاح کنید.

حذف با `docker rmi` است. اگر یک کانتینر، حتی توقف‌خورده، به ایمیج ارجاع دهد، حذف بدون `-f` شکست می‌خورد. `-f` را برای «جا باز کردن» عادت نکنید. اول کانتینر را با `docker ps -a` پیدا کنید.

### مثال واقعی

```bash
docker images
docker images --digests nginx
docker image inspect nginx:1.28-alpine
docker images -f dangling=true
```

شکل فهرست:

```text
REPOSITORY   TAG            IMAGE ID       CREATED        SIZE
nginx        1.28-alpine    4c1b5c1d8e01   2 weeks ago    22MB
mysql        8.4            91aa00c11de4   3 weeks ago    590MB
node         24-bookworm-slim  b7e19aa00c31  10 days ago  220MB
```

اندازهٔ دقیق را از میزبان بخوانید. عددهای این جدول فقط شکل ستون‌اند.

### کاربرد Production

قبل از هر پنجرهٔ تغییر، تگی را که قرار است اجرا شود محلی ببینید.

```bash
docker images --digests 'mysql' 'postgres' 'redis' 'mongo' 'nginx' 'node'
```

اگر تگ محلی هست و رجیستری قطع است، سرویس را با همان تگ بالا بیاورید و pull تازه نخواهید. این همان تصمیمی است که [کار آفلاین](./offline-operations.md) با آن شروع می‌شود.

digest را از `docker image inspect` و فیلد `RepoDigests` بردارید و در تیکت انتشار بنویسید. digest را از یک صفحهٔ وب دیگر وارد مستند نکنید.

ایمیج dangling را فقط وقتی پاک کنید که بیلد تمام شده و هیچ کانتینری به آن نیاز ندارد.

```bash
docker images -f dangling=true
```

اگر فهرست خالی نیست، شناسه را با `docker ps -a` مقایسه کنید. پاک‌سازی کلی `docker image prune` ایمیج بی‌تگ را حذف می‌کند. در Production بدون نگاه کردن به فهرست اجرا نکنید. `docker system prune` گسترده‌تر است و این صفحه آن را فرمان روتین نمی‌داند.

### وقتی خراب می‌شود

`docker images` خالی، بعد از آنکه دیروز پر بوده، سه علت معمول دارد. کلاینت به Engine دیگری وصل است، مثلاً متغیر `DOCKER_HOST`. یا کسی prune کرده. یا پیکربندی فروشگاه ایمیج عوض شده و ایمیج‌های درایور قبلی پنهان شده‌اند. در حالت سوم داده هنوز زیر `/var/lib/docker` یا `/var/lib/containerd` است. پیکربندی را برگردانید. دوباره pull کردن در این وضعیت دیسک را دو برابر پر می‌کند.

`Error response from daemon: conflict` موقع `docker rmi` یعنی کانتینر هنوز ارجاع دارد. `docker ps -a` را ببینید.

اگر `TAG` برابر `latest` است، آن تصویر را مبنای سرویس نکنید حتی اگر همین حالا کار می‌کند. تگ را در Compose به نسخهٔ صریح عوض کنید و دلیل را در [Dockerfile](./dockerfile.md) بخوانید.

## docker build

### توضیح

`docker build` ایمیج را از Dockerfile و یک زمینه (context) می‌سازد. زمینه دایرکتوری است که به دیمون فرستاده می‌شود. هر چه داخل زمینه باشد و `.dockerignore` نگرفته باشد، قابل `COPY` است و زمان بیلد را زیاد می‌کند. زمینه را `/` ندهید.

روی این نصب، `docker build` از پلاگین Buildx و BuildKit استفاده می‌کند. پرچم `--mount=type=secret` برای همین مسیر است و در [Dockerfile](./dockerfile.md) آمده. نیازی به روشن کردن متغیر قدیمی BuildKit نیست.

| پرچم | اثر |
| --- | --- |
| `-t` | تگ ایمیج حاصل. بدون آن، ایمیج dangling می‌شود |
| `-f` | مسیر Dockerfile اگر اسم یا جایش پیش‌فرض نیست |
| `--pull` | پایه را قبل از بیلد تازه می‌کشد |
| `--no-cache` | کش لایه‌ها را نادیده می‌گیرد. کند است. فقط وقتی لازم است |

تگ پیشنهادی برنامهٔ نمونه `shop-api:1.0.0` است، نه `latest`.

### مثال واقعی

```bash
cd /opt/apps/shop-api
docker build --pull -t shop-api:1.0.0 .
docker image inspect shop-api:1.0.0 --format '{{.Os}}/{{.Architecture}} {{.Size}}'
```

اگر Dockerfile جای دیگری است:

```bash
docker build -f /opt/apps/shop-api/Dockerfile -t shop-api:1.0.0 /opt/apps/shop-api
```

آرگومان آخر همیشه زمینه است. `-f` فقط فایل دستور را عوض می‌کند.

### کاربرد Production

بیلد را روی ماشینی بزنید که به رجیستری پایه و به آینهٔ NPM دسترسی دارد، بعد ایمیج را با `docker save` به `10.10.1.30` ببرید اگر خود `docker-1` شبکه ندارد. بیلد وسط قطعی شبکه را با `--no-cache` تکرار نکنید. کش سالم را دور نریزید.

نسخهٔ تگ را از نسخهٔ انتشار برنامه بگیرید و همان را در `compose.yaml` بنویسید. بیلد مجدد با همان تگ، شناسهٔ قبلی آن تگ را بی‌نام می‌کند. کانتینر در حال اجرا تا وقتی بازسازی نشود هنوز ایمیج قبلی را دارد. `docker build` به تنهایی سرویس زنده را عوض نمی‌کند. بعد از بیلد باید `docker compose up -d` در پوشهٔ سرویس اجرا شود تا کانتینر با ایمیج جدید ساخته شود.

`--pull` در شبکه‌ای که پایه را عمداً از کش محلی می‌خواهید ضرر دارد، چون سعی می‌کند به رجیستری برسد و شکست شبکه کل بیلد را متوقف می‌کند. وقتی آفلاین‌اید این پرچم را برندارید.

### وقتی خراب می‌شود

`failed to read dockerfile` یعنی مسیر زمینه غلط است یا فایل اسم دیگری دارد. `ls` همان دایرکتوری را نشان بدهید.

`COPY failed: file not found` یعنی فایل روی میزبان نیست، یا `.dockerignore` حذفش کرده، یا مسیر نسبت به زمینه اشتباه است. مسیر Dockerfile نسبت به زمینه است نه نسبت به شل شما، مگر اینکه مطلق باشد.

`npm ci` که داخل بیلد به رجیستری نمی‌رسد مسئلهٔ Docker نیست. آینهٔ NPM در [آینهٔ بسته](./package-mirrors.md) و حالت آفلاین در صفحهٔ خودش است. لاگ بیلد مرحلهٔ `RUN` را نشان می‌دهد. همان مرحله را بخوانید.

اگر خطا می‌گوید `--mount` ناشناخته است، این میزبان BuildKit این نصب را اجرا نمی‌کند. `docker buildx version` را ببینید. پلاگین `docker-buildx-plugin` باید نصب باشد.

پر شدن دیسک وسط بیلد پیام عجیب می‌دهد. `df -h /var/lib/docker /var/lib/containerd` را همان موقع بگیرید.

## docker run

### توضیح

`docker run` از یک ایمیج کانتینر می‌سازد و شروعش می‌کند. برای سرویس دائمی این فصل ترجیح با Compose است، چون شبکه و ولوم و healthcheck یک‌جا می‌مانند. `docker run` برای آزمون کوتاه و برای فهم فلگ‌ها مانده است.

| پرچم | اثر |
| --- | --- |
| `--rm` | با خروج، کانتینر را حذف می‌کند. برای آزمون |
| `-d` | پس‌زمینه. بدون آن، شل به لاگ کانتینر می‌چسبد |
| `--name` | اسم ثابت به‌جای اسم تصادفی |
| `--restart unless-stopped` | بعد از خرابی و بعد از ریبوت برمی‌گردد، مگر اینکه خودتان متوقف کرده باشید |
| `-p` | انتشار پورت. شکل `آدرس:میزبان:کانتینر` |
| `-v` | سوار کردن ولوم یا مسیر میزبان |
| `-e` | یک متغیر محیطی |
| `--network` | وصل شدن به شبکه‌ای که از قبل ساخته شده |
| `--read-only` | فایل‌سیستم ریشه فقط-خواندنی |

`unless-stopped` با `always` فرق دارد. `always` حتی کانتینری را که اپراتور با `docker stop` خاموش کرده، بعد از ریستارت دیمون دوباره بالا می‌آورد. برای سرویس Production این فصل `unless-stopped` است.

سیاست restart داده را نگه نمی‌دارد. بدون `-v` هر چه فرایند نوشته در لایهٔ قابل نوشتن است.

### مثال واقعی

آزمون یک‌باره:

```bash
docker run --rm nginx:1.28-alpine nginx -v
```

سرویس پس‌زمینه، فقط برای فهم فلگ. نمونهٔ قابل نگهداری در [Nginx](./compose-nginx.md) است.

```bash
docker volume create lab-run-data
docker network create lab-run
docker run -d --name lab-run-nginx --restart unless-stopped \
  --network lab-run \
  -p 127.0.0.1:8080:80 \
  -v lab-run-data:/usr/share/nginx/html:ro \
  nginx:1.28-alpine
docker ps --filter name=lab-run-nginx
```

جمع کردن آزمون:

```bash
docker stop lab-run-nginx
docker rm lab-run-nginx
docker volume rm lab-run-data
docker network rm lab-run
```

### کاربرد Production

انتشار پورت را به یک آدرس محدود کنید. `127.0.0.1:8080:80` فقط از خود میزبان دیده می‌شود. `10.10.1.30:8080:80` از شبکهٔ آزمایشگاه روی همان کارت دیده می‌شود و پورت `80` میزبان را اشغال نمی‌کند. `-p 80:80` هم با Nginx میزبان تصادم می‌کند هم روی همهٔ رابط‌ها گوش می‌دهد.

برای دیتابیس از `docker run` پراکنده استفاده نکنید. یک ولوم بی‌نام می‌ماند و نفر بعدی رمز را در تاریخچهٔ شل پیدا می‌کند، چون `-e MYSQL_ROOT_PASSWORD=...` در تاریخچهٔ دستورات کاربر ذخیره می‌شود. رمز در فایل env با مجوز `0600` است و Compose آن را می‌خواند.

کانتینر تعاملی دیباگ:

```bash
docker run --rm -it --network shop-mysql mysql:8.4 mysql --version
```

`-it` برای انسان است. در اسکریپت و در systemd نگذارید، چون TTY نیست و دستور گیر می‌کند.

### وقتی خراب می‌شود

`port is already allocated` یعنی همان پورت میزبان را کانتینر دیگری یا یک سرویس میزبان گرفته. `ss -ltnp` و `docker ps` را با هم ببینید. راه این فصل برای وب، پورت `8080` است نه `80`.

`Conflict. The container name is already in use` یعنی اسم مانده، حتی اگر کانتینر خارج شده باشد. `docker ps -a --filter name=lab-run-nginx` و بعد تصمیم: لاگ را ببینید یا واقعاً حذف کنید.

اگر کانتینر همان لحظه می‌میرد، `docker ps` خالی به نظر می‌رسد. `docker ps -a` و `docker logs` همان اسم را بزنید. `--restart unless-stopped` ممکن است در حلقهٔ شروع دوباره باشد. در `docker ps` وضعیت `Restarting` را جدی بگیرید و لاگ را بخوانید، نه اینکه پیاپی `run` جدید بزنید.

مسیر سمت چپ `-v` اگر با `/` شروع شود bind از میزبان است. اگر فقط اسم باشد ولوم نام‌دار است. اشتباه گرفتن این دو، داده را یک‌جا و کانفیگ را جای دیگر می‌گذارد.

## docker exec

### توضیح

`docker exec` فرمان تازه‌ای را داخل کانتینر در حال اجرا شروع می‌کند. شل لاگین دائمی نیست. برای دیدن فایل، آزمون کانفیگ، و کلاینت دیتابیس است. جایگزین لاگ نیست.

| پرچم | اثر |
| --- | --- |
| `-i` | stdin باز می‌ماند. برای لوله کردن ورودی |
| `-t` | TTY می‌سازد. همراه `-i` برای شل تعاملی |
| `-u` | کاربر داخل کانتینر |
| `-e` | متغیر فقط برای همین فرمان |
| `-w` | دایرکتوری کاری همین فرمان |

بدون `-it` مناسب اسکریپت است. با `-it` مناسب انسان. ایمیج خیلی کوچک ممکن است `bash` نداشته باشد. `sh` را امتحان کنید. اگر هیچ شلی در ایمیج نیست، exec شل شکست می‌خورد و این نقص ایمیج است نه نقص Engine.

کد خروج، کد همان فرمان داخلی است. `127` یعنی دستور پیدا نشد. `126` یعنی اجرا مجاز نبود.

### مثال واقعی

```bash
docker exec edge-web nginx -t
docker exec edge-web wget -q -O - http://127.0.0.1/health
docker exec -it edge-web sh
```

کلاینت MySQL داخل همان کانتینر، بدون باز کردن پورت به شبکه:

```bash
docker exec -it shop-mysql mysql -uroot -p -e 'SHOW VARIABLES LIKE "character_set_server";'
```

رمز را در خط فرمان نگذارید تا در `ps` و در تاریخچهٔ شل نماند. `-p` بدون مقدار، سؤال می‌کند.

### کاربرد Production

عیب‌یابی را از فرمان غیرتعاملی شروع کنید تا خروجی در تیکت قابل چسباندن باشد.

```bash
docker exec shop-postgres pg_isready -U shop -d shop
docker exec shop-redis redis-cli ping
```

فرمان دوم بدون رمز باید شکست بخورد اگر `requirepass` روشن است. آزمون درست Redis در [نمونهٔ Redis](./compose-redis.md) است و از متغیر env استفاده می‌کند، نه از رمز داخل مستند.

`docker exec` را برای اصلاح دادهٔ زنده عادت نکنید. یک `UPDATE` دستی بدون بکاپ، حادثهٔ بعدی است. برای دیدن وضعیت قبول است.

داخل کانتینر `apt update` و نصب ابزار دائمی نکنید. با مرگ کانتینر می‌رود و ایمیج را از تعریف Dockerfile جدا می‌کند. اگر ابزار لازم است، در ایمیج باشد.

### وقتی خراب می‌شود

`is not running` یعنی کانتینر توقف است. exec آن را زنده نمی‌کند. `docker ps -a` و `docker logs`.

`executable file not found` یعنی آن باینری در ایمیج نیست. `nginx:1.28-alpine` به‌جای `bash` معمولاً `sh` دارد. `mysql:8.4` کلاینت `mysql` را دارد. ایمیج پایهٔ برنامهٔ شما شاید هیچ‌کدام را نداشته باشد.

اگر `nginx -t` خطا داد، کانفیگ سوارشده از میزبان غلط است. فایل روی میزبان را اصلاح کنید و فرایند را با `docker compose restart` یا با سیگنال خود Nginx از نو بخوانید. ویرایش فایل داخل لایهٔ قابل نوشتن با ویرایش فایل mount‌شده یکی نیست. دومی می‌ماند، اولی با بازسازی کانتینر می‌رود.

`-u root` برای دور زدن مجوز فایل، علامت طراحی غلط ولوم است. در دیتابیس مالک دایرکتوری داده باید همان کاربر ایمیج بماند.

## docker logs

### توضیح

`docker logs` خروجی stdout و stderr فرایند اصلی را از درایور لاگ می‌خواند. با `daemon.json` این میزبان، درایور `json-file` است و سقف `10m` در پنج فایل است. قدیمی‌تر از این در خروجی نیست.

| پرچم | اثر |
| --- | --- |
| `-f` | دنبال کردن، مثل `tail -f`. با Ctrl+C قطع می‌شود و کانتینر را نمی‌کشد |
| `--tail` | فقط آخر خطوط |
| `--since` | از یک مدت یا زمان. مثال `15m` یا `2026-09-23T00:00:00` |
| `--until` | تا همان شکل زمان |
| `--timestamps` | مهر زمان روی هر خط |

لاگ سلامت و لاگ اپلیکیشن یکی نیستند. healthcheck شکست‌خورده را گاهی فقط در `docker inspect` در بخش سلامت می‌بینید، نه در stdout برنامه.

### مثال واقعی

```bash
docker logs --tail 100 edge-web
docker logs -f --since 15m --timestamps edge-web
docker logs --tail 50 shop-mysql
```

شکل یک خط Nginx:

```text
2026-09-23T08:15:01Z 10.10.1.5 - - "GET /health HTTP/1.1" 200 3
```

### کاربرد Production

وقتی `docker ps` وضعیت `Restarting` یا `unhealthy` نشان می‌دهد، اول این را بزنید:

```bash
docker logs --tail 200 --timestamps --since 30m shop-api
```

اگر خروجی خالی است، یا برنامه چیزی ننوشته، یا درایور لاگ خواندن را پشتیبانی نمی‌کند، یا سقف فایل لاگ زودتر از حادثه چرخیده. نوع درایور را این‌طور بخوانید.

```bash
docker inspect --format '{{.HostConfig.LogConfig.Type}}' shop-api
```

باید `json-file` باشد. اگر `none` یا `local` یا چیز دیگری است، کسی `daemon.json` یا پرچم کانتینر را عوض کرده. با درایور `json-file` فرمان `docker logs` کار می‌کند. درایور دیگر ممکن است بگوید خواندن پشتیبانی نمی‌شود و لاگ را باید جای دیگری ببینید.

`-f` را در نشست SSH رها نکنید و فکر کنید پایش است. با قطع SSH دنبال کردن قطع می‌شود. برای نگه داشتن طولانی، ابزار پایش میزبان است نه یک شل باز.

رمز و توکن اگر در لاگ برنامه چاپ شود، در فایل json زیر `/var/lib/docker/containers/` می‌ماند تا چرخش پاکش کند. برنامه نباید رمز را لاگ کند. چرخش، کنترل امنیتی کافی نیست.

### وقتی خراب می‌شود

`Error: No such container` یعنی اسم غلط است. از `docker ps -a` کپی کنید، از حافظه ننویسید.

اگر لاگ فقط خطای شروع دیتابیس است و مدام تکرار می‌شود، `restart` دارد کانتینر را دوباره اجرا می‌کند. پیام اول را بخوانید. اغلب مسیر ولوم مجوز ندارد، یا متغیر رمز خالی است، یا پورت داخل کانتینر اشغال است.

`docker logs` تاریخچهٔ `docker build` نیست. لاگ بیلد همان موقع در ترمینال بیلد است. بعد از تمام شدن بیلد، برای دیدن علت لایه به تاریخچهٔ ایمیج نیاز دارید:

```bash
docker history shop-api:1.0.0
```

اگر اینجا مقدار یک `ARG` یا یک رمز دیده می‌شود، ایمیج را منتشر نکنید.

## docker volume

### توضیح

`docker volume` ولوم نام‌دار را مدیریت می‌کند. ولوم از لایهٔ قابل نوشتن جداست. زیر‌دستورهای لازم همین‌ها هستند.

| زیر‌دستور | کار |
| --- | --- |
| `ls` | فهرست |
| `create` | ساختن. اگر اسم وجود داشته باشد، ولوم موجود را برمی‌گرداند |
| `inspect` | مسیر میزبان، زمان ساخت، و برچسب |
| `rm` | حذف. اگر کانتینری هنوز وصل باشد شکست می‌خورد |

`create` را Compose هم انجام می‌دهد. ساختن دستی وقتی مفید است که بخواهید قبل از اولین `up` اسم و وجود ولوم را ثابت کنید. اسم صریح را در نمونه‌های دیتابیس گذاشته‌ایم، مثلاً `shop-mysql-data`.

### مثال واقعی

```bash
docker volume ls
docker volume create shop-mysql-data
docker volume inspect shop-mysql-data
docker volume rm shop-mysql-data
```

اگر حذف به‌خاطر استفاده شکست خورد:

```bash
docker ps -a --filter volume=shop-mysql-data
```

شکل بخشی از `inspect`:

```text
[
    {
        "Name": "shop-mysql-data",
        "Driver": "local",
        "Mountpoint": "/var/lib/docker/volumes/shop-mysql-data/_data",
        "Scope": "local"
    }
]
```

مسیر `Mountpoint` را با ویرایشگر باز نکنید و `chown` نزنید.

### کاربرد Production

قبل از هر حذف، این سه را کنار هم بگذارید.

```bash
docker volume ls
docker volume inspect shop-mysql-data
docker ps -a --filter volume=shop-mysql-data
```

بکاپ دیتابیس از داخل ابزار خود دیتابیس است، نه کپی خام این دایرکتوری در حالی که فرایند در حال نوشتن است. کپی خام وسط نوشتن InnoDB یا Postgres ناسازگار است. تا وقتی صفحهٔ بکاپ دیتابیس را جداگانه اجرا نکرده‌اید، حداقل ولوم را با `rm` «تمیز» نکنید.

`docker compose down` ولوم نام‌دار پروژه را پاک نمی‌کند. `docker compose down -v` پاک می‌کند. پرچم `-v` را از روی عادت به اسکریپت استقرار اضافه نکنید.

ولوم بی‌نام را `docker volume ls` با یک شناسهٔ طولانی نشان می‌دهد. مال ایمیجی است که `VOLUME` داشته و شما مسیری سوار نکرده‌اید. سرویس دیتابیس نباید چنین ولومی داشته باشد. اگر داشت، داده جایی است که در Compose نیست و با یک prune از بین می‌رود.

### وقتی خراب می‌شود

`volume is in use` یعنی هنوز حداقل یک کانتینر، حتی `Exited`، به آن وصل است. اول همان کانتینر را تعیین تکلیف کنید.

`rm` موفق و بعد پشیمانی یعنی داده رفته، مگر بکاپ داشته باشید. Engine سطل زباله ندارد.

اگر دیتابیس بالا می‌آید و پایگاه خالی است، ولوم نو به مسیر درست وصل شده، یا مسیر سوار نقطهٔ دادهٔ ایمیج نیست. برای MySQL 8.4 مسیر داخل کانتینر `/var/lib/mysql` است. برای PostgreSQL 18 مسیر سوار `/var/lib/postgresql` است، نه مسیری که راهنماهای قدیمی `data` را به آخرش چسبانده‌اند. این فرق در صفحهٔ همان سرویس است.

اگر `inspect` مسیر را نشان می‌دهد ولی `df` همان فایل‌سیستم را پر نشان می‌دهد، ولوم جا ندارد. حذف لاگ کانتینر جای داده را آزاد نمی‌کند. داده و لاگ مسیر جدا دارند.

## docker network

### توضیح

`docker network` شبکه‌های Engine را مدیریت می‌کند. سه شبکهٔ `bridge` و `host` و `none` پیش‌فرض‌اند و حذف نمی‌شوند.

| زیر‌دستور | کار |
| --- | --- |
| `ls` | فهرست |
| `create` | ساختن. پیش‌فرض درایور `bridge` است |
| `inspect` | زیرشبکه، دروازه، و کانتینرهای وصل |
| `rm` | حذف، فقط اگر کانتینری روی آن نمانده باشد |
| `connect` | وصل کردن کانتینر در حال اجرا به شبکه |
| `disconnect` | جدا کردن |

روی شبکهٔ کاربری، اسم کانتینر بین اعضای همان شبکه حل می‌شود. روی `bridge` پیش‌فرض این DNS وجود ندارد. Compose برای هر فایل یک شبکهٔ کاربری می‌سازد. اسم آن در نمونه‌ها صریح است.

### مثال واقعی

```bash
docker network ls
docker network create --driver bridge lab-net
docker network inspect lab-net
docker network rm lab-net
```

وصل کردن یک کانتینر موجود:

```bash
docker network connect lab-net edge-web
docker network inspect lab-net
docker network disconnect lab-net edge-web
```

`inspect` باید کانتینر را در فهرست خودش نشان بدهد و یک IPv4 از زیرشبکهٔ `172.30` بدهد، اگر `default-address-pools` صفحهٔ نصب اعمال شده باشد. زیرشبکهٔ واقعی را از خروجی بخوانید، حدس نزنید.

### کاربرد Production

سرویس را به شبکهٔ پیش‌فرض رها نکنید. در Compose شبکه را همنام سرویس تعریف کنید تا در `docker network ls` معلوم باشد. از داخل کانتینر وب، اسم سرویس دیتابیس باید حل شود و آدرس عمومی میزبان دیتابیس نباید لازم باشد.

برای دیدن اینکه دو سرویس واقعاً هم‌شبکه‌اند:

```bash
docker network inspect shop
```

اگر `web` هست و `mysql` نیست، `depends_on` هم نجاتتان نمی‌دهد. وابستگی ترتیب شروع است، اتصال شبکه نیست. هر دو سرویس باید در یک شبکهٔ مشترک لیست شده باشند. جایی که نباید به هم برسند، عمداً دو شبکه بسازید. نمونهٔ این فصل دیتابیس را روی شبکهٔ خودش نگه می‌دارد و پورت را فقط به loopback میزبان می‌دهد.

`connect` دستی بعد از Compose را فراموش می‌کنید و ریستارت بعدی آن را ندارد. اتصال دائمی باید در `compose.yaml` باشد.

### وقتی خراب می‌شود

`network has active endpoints` هنگام `rm` یعنی کانتینر هنوز وصل است. `inspect` همان شبکه فهرستشان را دارد.

`could not find an available, non-overlapping IPv4 address pool` یعنی استخر `default-address-pools` تمام شده یا با شبکهٔ موجود تداخل دارد. شبکهٔ آزمایشی مانده را حذف کنید. استخر را طوری بزرگ نکنید که `10.10.0.0/16` را بپوشاند. تداخل با شبکهٔ آزمایشگاه یعنی مسیر میزبان به `10.10.1.20` یا بقیهٔ نقش‌ها خراب می‌شود.

اگر از داخل کانتینر `ping api` شکست می‌خورد ولی هر دو در `docker ps` بالا هستند، `inspect` هر دو شبکه را مقایسه کنید. اسم سرویس فقط داخل همان شبکه حل می‌شود. همچنین `ping` ممکن است در ایمیج نباشد. آزمون بهتر یک درخواست با ابزاری است که در ایمیج هست، یا `getent hosts api` اگر libc آن را دارد.

خطای `host not found` از برنامهٔ وب به اسم `mysql` اغلب یعنی شبکه جداست، یا اسم سرویس در Compose چیز دیگری است. اسم DNS همان کلید زیر `services` است، نه `container_name`، مگر اینکه کلاینت را با اسم کانتینر صدا زده باشید. در نمونه‌های این فصل به اسم سرویس تکیه می‌کنیم.

## Best Practices

- حادثه را با `docker ps -a` و `docker logs --tail 200 --timestamps` شروع کنید، نه با حذف کانتینر.
- `docker images` را قبل از pull دوباره ببینید. ایمیج محلی هنگام قطع رجیستری کافی است.
- زمینهٔ `docker build` را کوچک نگه دارید و تگ `latest` ندهید.
- `docker run` تعاملی را به سرویس دائمی تبدیل نکنید. سرویس در Compose است.
- `-it` را داخل اسکریپت نگذارید.
- رمز را در آرگومان `docker run` و در آرگومان `exec` ننویسید.
- `docker logs -f` پایش نیست. سقف لاگ ده مگابایت در پنج فایل است.
- `docker volume rm` و `docker compose down -v` را بدون تطبیق اسم ولوم اجرا نکنید.
- شبکهٔ پیش‌فرض را برای سرویس چندبخشی استفاده نکنید. `inspect` را ملاک اتصال بدانید.
- خروجی دستور را در تیکت بچسبانید. شرح «خطا داد» برای نفر بعدی قابل جستجو نیست.
- هر فرمانی که این صفحه نیاورده، از جمله `docker system prune`، فرمان روتین Production نیست.
