# نقشهٔ Docker

## مقدمه

این فصل روش استاندارد تیم برای اجرای سرویس روی میزبان Docker آزمایشگاه است: `docker-1.example.internal` با آدرس `10.10.1.30`. موتور از مخزن رسمی `download.docker.com` نصب می‌شود، فایل چندسرویسی با `docker compose` بالا می‌آید، و وقتی اینترنت آزاد در کار نیست مسیر جایگزین آینهٔ `mirror.example.internal` روی `10.10.1.60` است.

صفحه را از اول تا آخر مثل یک آموزش خطی نخوانید. اگر موتور هنوز نصب نیست از [نصب](./installation.md) شروع کنید. اگر نصب هست و فقط دستور یادتان رفته، [مرجع دستورها](./commands.md) کافی است. اگر `docker pull` خطا می‌دهد، مستقیم به [کار آفلاین](./offline-operations.md) بروید و قبل از آن [آینهٔ رجیستری](./registry-mirror.md) را چک کنید.

## مفهوم اصلی

Docker در این دانشنامه یعنی Docker Engine روی لینوکس، به‌علاوهٔ پلاگین Compose نسخهٔ ۲ و پلاگین Buildx. کانتینر (container) فرایند ایزوله‌شده است، ایمیج (image) قالب فقط-خواندنی آن است، و رجیستری (registry) جایی است که ایمیج از آن کشیده یا به آن پوش می‌شود. ولوم (volume) داده را بعد از حذف کانتینر نگه می‌دارد و شبکهٔ (network) تعریف‌شده توسط کاربر اسم سرویس‌ها را به هم وصل می‌کند.

دستور روزمره `docker` است و دستور فایل چندسرویسی `docker compose` با فاصله است. باینری قدیمی `docker-compose` آموزش داده نمی‌شود؛ اگر روی سرور قدیمی هنوز وجود دارد، خروجی‌اش مبنای کار این فصل نیست. بستهٔ توزیعی `docker.io` هم مسیر نصب این دانشنامه نیست. فرق اسم آن بسته با بسته‌های `docker-ce` در [نصب](./installation.md) آمده است.

فصل به سه کار تقسیم می‌شود: فهم مدل، بالا آوردن سرویس، و زنده ماندن وقتی `registry-1.docker.io` در دسترس نیست. دیتابیس داخل کانتینر در همین فصل نمونهٔ Compose دارد. عملیات کاربر و بکاپ و بازیابی دیتابیس کار همان نمونه را تکرار نمی‌کند؛ اینجا فقط سرویس بالا می‌آید و سلامت آن تست می‌شود.

## چرا استفاده می‌شود؟

یک سرویس را می‌شود مستقیم با systemd روی Ubuntu 26.04 اجرا کرد. کانتینر وقتی انتخاب می‌شود که نسخهٔ زبان یا دیتابیس با بستهٔ توزیع یکی نیست، یا باید همان ایمیج روی `docker-1` و در pipeline یکی باشد. Node.js 24، MySQL 8.4، PostgreSQL 18، MongoDB 8 و Redis 8 در نمونهٔ این فصل از ایمیج رسمی می‌آیند تا میزبان مجبور نباشد چند نسخهٔ متضاد را از APT کنار هم نگه دارد.

کانتینر جایگزین بکاپ، فایروال، و مدیریت کاربر نیست. دیسک پر، رمز پیش‌فرض، و پورت منتشرشده روی `0.0.0.0` با Docker هم حادثه می‌سازند. صفحه‌های نمونه این‌ها را داخل همان سرویسی که کپی می‌کنید اصلاح کرده‌اند، نه در یک پیوست جدا.

این فصل برای توسعه‌دهنده‌ای که فقط `docker run` روی لپ‌تاپ زده هم قابل استفاده است، ولی مثال‌ها را برای سرور آزمایشگاه نوشته‌ایم. پورت دیتابیس روی `127.0.0.1` می‌نشیند. پورت وب نمونهٔ Nginx روی `8080` می‌نشیند تا با Nginx میزبان که پورت `80` را گرفته تصادم نکند.

## Architecture

میزبان، آینه، و مصرف‌کننده در آزمایشگاه ثابت‌اند.

```text
app-1  10.10.1.10          proxy  10.10.1.5
   │                            │
   │  SSH tunnel به دیتابیس     │  HTTP به :8080
   ▼                            ▼
docker-1.example.internal   10.10.1.30
   Engine + containerd
   /var/lib/docker          ولوم و متادیتا
   /var/lib/containerd      لایهٔ ایمیج روی نصب تازه
   │
   │  pull از Docker Hub فقط از راه آینه
   ▼
mirror.example.internal     10.10.1.60
   رجیستری کش، آینهٔ APT، NPM، pip، Composer
```

ترتیب خواندن:

| جایگاه | صفحه | کی بازش کنید |
| --- | --- | --- |
| 1 | همین صفحه | قبل از انتخاب مسیر |
| 2 | [مفهوم‌ها](./concepts.md) | وقتی فرق ایمیج و کانتینر در تصمیم اثر دارد |
| 3 | [نصب](./installation.md) | میزبان تازه یا موتور توزیعی که باید عوض شود |
| 4 | [دستورها](./commands.md) | شیفت و عیب‌یابی روزمره |
| 5 | [Dockerfile](./dockerfile.md) | ساخت ایمیج برنامه |
| 6 | [مدل Compose](./compose.md) | شکل فایل، شبکه، ولوم، سلامت |
| 7 تا 12 | نمونه‌های Nginx، Node، MySQL، Redis، MongoDB، PostgreSQL | کپی سرویس |
| 13 | [آینهٔ رجیستری](./registry-mirror.md) | pull از Hub کند یا بسته است |
| 14 | [آینهٔ بسته](./package-mirrors.md) | APT و NPM و pip و Composer |
| 15 | [کار آفلاین](./offline-operations.md) | اینترنت قطع است یا pull خطا داده |

نمودار وابستگی صفحه‌ها خطی نیست. نمونهٔ MySQL مدل Compose را فرض می‌کند. آینهٔ بسته و آینهٔ رجیستری هر دو به میزبان `10.10.1.60` اشاره می‌کنند ولی مکانیزم‌شان یکی نیست. قاطی کردن `registry-mirrors` با آینهٔ APT باعث می‌شود ساعت‌ها جای اشتباه را لاگ بگیرید.

پورت‌هایی که این فصل روی `docker-1` باز می‌کند از قبل معلوم‌اند تا با هم و با سرویس میزبان تصادم نکنند.

| سرویس | انتشار روی میزبان | از کجا قابل دیدن است |
| --- | --- | --- |
| Nginx نمونه | `10.10.1.30:8080` | پروکسی `10.10.1.5` و شبکهٔ آزمایشگاه |
| Node نمونه | `127.0.0.1:3000` | فقط خود `docker-1`، معمولاً پشت Nginx |
| MySQL 8.4 | `127.0.0.1:3306` | خود میزبان، یا تونل SSH |
| Redis 8 | `127.0.0.1:6379` | خود میزبان، یا تونل SSH |
| MongoDB 8 | `127.0.0.1:27017` | خود میزبان، یا تونل SSH |
| PostgreSQL 18 | `127.0.0.1:5432` | خود میزبان، یا تونل SSH |
| آینهٔ رجیستری | `10.10.1.60:443` | میزبان‌های Docker، نه پورت دیتابیس |

پورت `80` میزبان در این جدول نیست. آن پورت مال Nginx خود سیستم است. اگر نمونه‌ای را با `80:80` بالا بیاورید، با همان سرویس تصادم می‌کند و این فصل را نقض کرده‌اید.

## Installation

نصب قدم‌به‌قدم در [نصب](./installation.md) است. خلاصهٔ تصمیمی که نباید وسط کار عوض شود:

- Ubuntu 26.04 با نام رمز `resolute`، یا Debian 13 با نام رمز `trixie`.
- منبع APT به شکل deb822 و کلید `/etc/apt/keyrings/docker.asc`.
- بسته‌ها: `docker-ce` و `docker-ce-cli` و `containerd.io` و `docker-buildx-plugin` و `docker-compose-plugin`.
- کاربر `ops` در گروه `docker`. این عضویت معادل root است.
- سرویس با `systemctl enable --now docker.service` بالا می‌آید.

بعد از نصب، این سه فرمان باید بدون خطا برگردند. نسخهٔ دقیق را از خروجی خودشان بردارید و در تیکت تغییر ثبت کنید. این صفحه شمارهٔ patch اختراع نمی‌کند.

```bash
docker version
docker compose version
docker info
```

اگر `docker version` بخش Server را خالی نشان داد، یا سوکت `/var/run/docker.sock` در دسترس کاربر فعلی نیست یا daemon بالا نیست. قبل از ساخت Compose سراغ [نصب](./installation.md) برگردید.

## Configuration

پیکربندی میزبان در `/etc/docker/daemon.json` است. دو تنظیم از همین اول لازم‌اند: چرخش لاگ `json-file` تا دیسک پر نشود، و استخر آدرس شبکه تا با `10.10.0.0/16` آزمایشگاه قاطی نشود. متن فایل و معنی هر کلید در [نصب](./installation.md) است.

آینهٔ رجیستری کلید `registry-mirrors` است و فقط وقتی اضافه می‌شود که سرویس آینه روی `mirror.example.internal` واقعاً جواب بدهد. اضافه کردن یک نام که هنوز DNS یا گواهی ندارد، pull را کند و مبهم می‌کند. ترتیب درست: اول آینه را از [صفحهٔ رجیستری](./registry-mirror.md) بالا بیاورید، بعد daemon را عوض کنید، بعد `systemctl restart docker`، بعد `docker info`.

فایل هر سرویس زیر `/opt/apps/` و نام همان سرویس می‌نشیند. در نمونه‌ها پوشه‌ها مشخص‌اند: `edge`، `shop-api`، `shop-mysql`، `shop-redis`، `shop-mongo`، `shop-postgres`. رمز نمونه همیشه `change-me` داخل فایل env با مجوز `0600` است. منطقهٔ زمانی آزمایشگاه `Asia/Tehran` است و در نمونه‌ها با متغیر `TZ` به کانتینر داده می‌شود.

بعد از پیاده کردن نمونه‌ها، این مسیرها باید وجود داشته باشند و مالکشان `ops` باشد. نبود یکی از آن‌ها یعنی آن صفحه هنوز روی میزبان اجرا نشده، نه اینکه Docker خراب است.

```text
/etc/apt/sources.list.d/docker.sources
/etc/apt/keyrings/docker.asc
/etc/docker/daemon.json
/opt/apps/edge/compose.yaml
/opt/apps/shop-api/compose.yaml
/opt/apps/shop-mysql/compose.yaml
/opt/apps/shop-mysql/.env
/opt/apps/shop-redis/compose.yaml
/opt/apps/shop-redis/.env
/opt/apps/shop-mongo/compose.yaml
/opt/apps/shop-mongo/.env
/opt/apps/shop-postgres/compose.yaml
/opt/apps/shop-postgres/.env
```

فایل‌های `.env` را با `ls -l` ببینید. خط مجوز باید با `-rw-------` شروع شود. آینه روی `10.10.1.60` است و فایلش زیر `/opt/apps/registry-mirror` می‌نشیند، نه زیر پوشهٔ سرویس‌های `docker-1`.

## Production Example

شکل سرویسی که به Production می‌رود، نه یک `docker run` تعاملی:

```text
/opt/apps/shop-api/
  compose.yaml      بدون کلید version
  .env              مجوز 0600، رمز غیر از change-me
  Dockerfile        تگ پایه node:24-bookworm-slim، کاربر غیر root
```

بالا آوردن و تست، الگوی همهٔ نمونه‌های بعدی است.

```bash
cd /opt/apps/shop-api
docker compose config
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:3000/health
```

`docker compose config` را قبل از `up` بزنید. اگر متغیر اجباری در `.env` نباشد، همین فرمان باید شکست بخورد، نه اینکه دیتابیس بدون رمز بالا بیاید. `docker compose ps` باید وضعیت `running` و در صورت تعریف healthcheck وضعیت `healthy` را نشان بدهد.

این فصل را برای هر فرایند میزبان انتخاب نکنید. اگر سرویس همان بسته‌ای است که Ubuntu 26.04 یا Debian 13 خودش پشتیبانی می‌کند، واحد systemd و کاربر `deploy` ساده‌تر است و سوکت Docker را وارد مسیر اعتماد نمی‌کند. Docker را وقتی بردارید که نسخهٔ رسمی ایمیج با بستهٔ توزیع یکی نیست، یا باید همان بایت روی runner و روی `docker-1` اجرا شود. Nginx میزبان برای گواهی و پورت `80` و `443` سر جایش می‌ماند. کانتینر وب این فصل روی `8080` می‌نشیند تا آن نقش را تصاحب نکند.

شیفت اول روی میزبان تازه این چهار سؤال را جواب می‌دهد و جواب را در تیکت نصب می‌گذارد.

```bash
docker version
docker compose version
docker info
getent group docker
```

سؤال‌ها: بخش Server پر است یا نه، فرمان Compose فاصله دارد یا کسی باینری خط‌تیره‌دار را نشان می‌دهد، درایور لاگ `json-file` است یا نه، و آیا فقط `ops` در گروه `docker` است. اگر گروه شلوغ است، قبل از بالا آوردن MySQL اعضا را کم کنید. دلیلش در یادداشت امنیتی همین صفحه است.

پورت‌های دیتابیس در نمونه‌ها `127.0.0.1` هستند. از `app-1` مستقیم به آن‌ها وصل نمی‌شوید. مسیر تست از راه تونل SSH در صفحهٔ همان دیتابیس است. پورت `8080` نمونهٔ Nginx برای این است که پروکسی `10.10.1.5` به وب برسد، بدون اینکه پورت `80` خود میزبان را بگیرد.

## Security Notes

گروه `docker` را به کاربر `deploy` یا به حساب شخصی توسعه‌دهنده روی سرور مشترک ندهید. کسی که به سوکت Docker دسترسی دارد می‌تواند ریشهٔ میزبان را داخل کانتینر سوار کند و هر فایلی را با اختیار root بنویسد. فقط `ops` روی `docker-1` این عضویت را دارد.

ایمیج `latest` در Production ممنوع است. دلیل و جایگزین در [Dockerfile](./dockerfile.md) است. تگ‌های این فصل این‌ها هستند: `nginx:1.28-alpine`، `node:24-bookworm-slim`، `mysql:8.4`، `redis:8`، `mongo:8`، `postgres:18`، `registry:2`.

راز را داخل ایمیج نگذارید. `ARG` که در لایه بماند، و `ENV` که رمز را در متادیتای ایمیج بنویسد، هر دو خطا هستند. رمز دیتابیس هنگام اجرا از فایل env می‌آید.

پورت منتشرشدهٔ Docker می‌تواند قانون UFW را دور بزند، چون Engine قاعدهٔ iptables خودش را وارد می‌کند. محدود کردن آدرس bind به `127.0.0.1` یا به `10.10.1.30` این دور زدن را روی بقیهٔ کارت‌های شبکه بی‌اثر می‌کند. جزئیات در یادداشت امنیتی هر نمونه است.

## Troubleshooting

| نشانه | اول این را ببینید |
| --- | --- |
| `permission denied` روی سوکت | عضویت گروه و ورود مجدد، صفحهٔ نصب |
| `docker compose` پیدا نمی‌شود ولی `docker-compose` هست | پلاگین نصب نشده؛ باینری قدیمی را استفاده نکنید |
| pull زمان تمام می‌کند | آینه و بعد کار آفلاین |
| کانتینر بالا است و برنامه داخلش نیست | `docker logs` و healthcheck در مرجع دستورها |
| رمز env را عوض کردید و دیتابیس قبول نمی‌کند | مقدار اولیه فقط روی ولوم خالی اعمال می‌شود |
| دیسک پر شده وسط pull | هم `/var/lib/docker` هم `/var/lib/containerd` |

اگر خطا مال یک دستور مشخص است، همان دستور را در [مرجع](./commands.md) بخش «وقتی خراب می‌شود» ببینید. اگر اینترنت در کار است و pull نیست، ترتیب تصمیم را از [کار آفلاین](./offline-operations.md) طی کنید و از وسط فهرست آینهٔ عمومی ناشناس انتخاب نکنید.

## Best Practices

- هر سرویس یک پوشه زیر `/opt/apps`، یک `compose.yaml`، و در صورت وجود رمز یک `.env` با `0600`.
- قبل از `up` همیشه `docker compose config`.
- تگ قابل فهم و ثابت. `latest` را در فایل سرویس ننویسید.
- ولوم نام‌دار برای هر داده‌ای که با حذف کانتینر نباید برود.
- شبکهٔ تعریف‌شده در همان فایل Compose، نه شبکهٔ پیش‌فرض `bridge`، تا اسم سرویس حل شود.
- `restart: unless-stopped` برای سرویسی که باید بعد از ریبوت برگردد ولی توقف عمدی اپراتور را نباید نادیده بگیرد.
- لاگ را با سقف اندازه نگه دارید. `docker logs` آرشیو بلندمدت نیست.
- آینه فقط آینه‌ای است که سازمان روی `10.10.1.60` اداره می‌کند.
- تغییر daemon را در پنجرهٔ مشخص انجام دهید و بلافاصله با `docker info` تأیید کنید.
- شمارهٔ نسخه‌ای که این صفحه ننوشته را از فرمان همان ابزار بخوانید و در گزارش تغییر بیاورید.
